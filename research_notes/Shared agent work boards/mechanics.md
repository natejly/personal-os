# Shared agent work mechanics

As of 2026-10-02. Mechanics only: how a claim, a completion record, a review gate, and an event log stay honest when more than one actor can touch the same task. Numbers below are only from pages opened for this note. Known local constraints, used as the target for the smallest version and not re-investigated here: the agent loop dies with the HTTP connection, approvals are in memory, the user edits the kanban by hand, and background work is supposed to stay proposal-only for external side effects.

## How do production systems stop two runs from taking the same task?

### Takeaway
The working pattern is a time-bounded claim, not a permanent assignee flag. A queue hides or locks the task for one worker, the worker must renew that claim if the work runs long, and a dead worker’s task becomes available again when the lease expires. The claim is not exactly-once: the worker’s code has to tolerate a second attempt. A name that only one running execution may hold is a second, stricter mutex, and it still needs a lease plus a fencing token if the work can touch anything outside the lock.

### Cited Findings
- Amazon SQS: receiving a message leaves it in the queue but makes it invisible to other consumers for the visibility timeout. The timer starts on delivery. If the consumer does not delete the message before the timeout, the message becomes visible again and another consumer can retrieve it. Default timeout is 30 seconds. `ChangeMessageVisibility` extends or shortens it, including setting it to 0 to hand the message back immediately. The timeout cannot be extended past 12 hours from the first receive; extending it does not reset that cap. Standard queues use this to keep two consumers from processing the same message at the same time, but the at-least-once model means there is still no absolute guarantee against a duplicate delivery during the timeout. A dead-letter queue is the documented place for messages that fail repeated attempts. The same page’s best practice for unknown duration is a short initial timeout plus a heartbeat that keeps extending it. — [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- PostgreSQL documents the queue form of the same idea. `SELECT … FOR UPDATE SKIP LOCKED` skips rows another transaction already locked, instead of waiting. The manual says this view is inconsistent and is not for general reads; it is for avoiding lock contention when multiple consumers read a queue-like table. With `LIMIT`, locking stops once enough rows have been returned. `SKIP LOCKED` is a PostgreSQL extension, not in the SQL standard. — [PostgreSQL SELECT, The Locking Clause](https://www.postgresql.org/docs/current/sql-select.html)
- Temporal’s lock guide uses the workflow id itself as the mutex: with the default conflict policy `FAIL`, two running workflows cannot share an id, so starting a child workflow whose id is `permit:{resource}:{slot}` either acquires the slot or fails with `WorkflowAlreadyStartedError`. Recovery is a lease timer on that child, plus `execution_timeout` if no worker ever picks it up. A late release is pinned to the specific run handle so an expired holder cannot release the next holder’s permit. The guide states the limit directly: lease expiry is recovery, not proof the old holder stopped using the external resource. For anything overlap can corrupt, pass the permit run id as a fencing token and reject stale holders. Heartbeats are the fast path: miss `heartbeat_timeout` and the activity fails, the holder leaves the critical section, and the slot is released; the lease timer is the coarse backstop. — [Coordinate Access to Shared Resources with a Distributed Lock](https://docs.temporal.io/guides/lock-shared-resources)
- River’s worker docs, opened for the completion side of a database queue rather than its fetch SQL: once inserted, a job is worked at least once. A success that fails to be marked complete is rescued and run again. External calls made during the job do not roll back with the database transaction. `JobCompleteTx` writes the completion in the same transaction as the other database changes; a commit means that job will not be rerun, a failed commit discards the changes so the next attempt starts clean. The default client job timeout is 1 minute. — [River: Writing reliable workers](https://riverqueue.com/docs/reliable-workers)
- Inngest separates “this step’s result was saved” from “the outside world changed once.” A stable step id is how a resumed run finds the saved result and skips the callback. If a provider accepted the request but the response was lost, the step can retry the action. Writes, payments, and messages that must not happen twice need their own idempotency key. Step results must be JSON and are capped at 4 MiB; large results are supposed to be stored elsewhere and returned as a reference. — [Inngest: Primitives and steps](https://www.inngest.com/docs/durable-execution/primitives)
- Stripe’s idempotency key is the external-effect half. The server saves the status code and body of the first request for a key, including `500` responses, and later retries with that key return the saved result. Keys may be removed after at least 24 hours; reuse after pruning starts a new request. A retry whose parameters differ from the original is an error. Results are saved only after endpoint execution begins; a validation failure or a conflict with a request already executing does not save an idempotent result, and those can be retried. Keys are up to 255 characters. `POST` accepts them; `GET` and `DELETE` do not need them. — [Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

### Inferences
- Three mechanisms show up, and they are not substitutes. A lease (SQS visibility timeout, Temporal permit timer) answers “who holds this now, and when do we take it back if they vanish.” A compare-and-swap claim (`SKIP LOCKED`, or a single `UPDATE … WHERE status = ready AND lease expired`) answers “two pollers must not both win.” A fencing token (Temporal’s permit run id, Stripe’s idempotency key) answers “the old holder might still be alive and must not apply a second effect.”
- Agent products do not need a separate story. A background run is a worker. If the process dies with the HTTP connection, the claim has to live in the database with an expiry, and the absence of a heartbeat is what returns the card. An in-memory “this run owns the card” flag does not survive that death, and it cannot be seen by a second run.
- For one person, one SQLite file, and a handful of agents, the smallest claim that still works: one conditional update that sets `claimed_by`, `claim_token`, and `lease_expires_at` only when the card is free or the previous lease has expired, and that update changes zero rows for everyone else. Renew the lease on a timer shorter than the expiry. Clear it on finish, failure, or explicit release. SQLite already allows only one writer at a time (below), so `SKIP LOCKED` is unnecessary on a single machine; the conditional update is the mutex. Pass `claim_token` into any local write. Because external side effects stay proposals, the token’s job locally is to stop a stale run from attaching a second proposal or editing the card after the user took it back.
- Idempotency for that scale is a unique key on the proposal (card id + action kind + stable intent id), not a 24-hour public-API cache. A retry of the same run returns the existing proposal row. Stripe’s lesson that still applies: same key with different parameters is an error, and a crash before the row is committed must be retryable.

### Gaps
- River’s own docs page that was opened describes at-least-once execution and transactional completion. It does not show the fetch query. Third-party summaries say River claims jobs with `FOR UPDATE SKIP LOCKED`. That SQL was not opened in the repository (the fetched source file was empty), so it is not treated as verified here.
- No agent-product document opened for this note specified a claim token on a shared task board. The queue and workflow documents above are the concrete implementations.
- SQS’s own page says a duplicate delivery during the visibility timeout is still possible and does not describe a fencing token. The fencing requirement is from Temporal’s lock guide, for resources outside the lock.

## Where is the source of truth for “done”?

### Takeaway
“Done” is an environment check, not the model’s closing sentence and not a status field the model writes. On customer-service and personal-app benchmarks, a large share of failures are cases where the agent asserts success and the database does not match. An LLM reading the transcript is a poor detector of that mismatch. The durable record is the state diff, the test result, or the artifact, written down as an event by the program that checked it.

### Cited Findings
- AppWorld (Trivedi et al., 2024) scores tasks by state, not by comparing the agent’s steps to a reference. A task passes when the database diff from the start state contains every expected change and no other changes except an allow-list (collateral damage fails the task). Those checks are programmatic assertions. Task Goal Completion is the percentage of tasks that pass every evaluation test. The abstract reports that GPT-4o solves only about 49% of the normal tasks and about 30% of the challenge tasks. The agent is instructed to call `complete_task`, and one published evaluator sets `task_completed` from `supervisor.Task.status == "success"` and then separately asserts the database diff (in the example, that only the music player changed and that it is playing). The status write is one assertion input. It is not the score. — [AppWorld (arXiv:2407.18901)](https://arxiv.org/pdf/2407.18901)
- Advani (arXiv:2606.09863), “From Confident Closing to Silent Failure,” defines false success as the agent asserting completion when the environment state says otherwise. Corpus: 9,876 tau2-bench trajectories from 8 model families (8,146 reward = 1, 1,730 reward = 0). Tau2-bench’s reward, as this paper describes it, is 1 only if the final environment state matches the task specification. Among failures, the paper’s three-way split (false success / honest failure / ambiguous) is airline 45/38/17, retail 47/28/24, telecom 3/79/18, and overall 36/44/20 (Table 1). The abstract’s summary is 45–48% of failures in the single-control domains, 3% in dual-control telecom, and 75.8% among the AppWorld trajectories that make an explicit status claim. The introduction’s “44–52%” for single-control domains is the same paper’s wider phrasing; Table 1 is the per-domain split. Overall false-success count is 616 of 1,730 failures (35.6%), which is lower than the single-control rates because telecom and the ambiguous class are in the denominator. — [Advani, arXiv:2606.09863](https://arxiv.org/html/2606.09863)
- AppWorld labeling in that same paper is independent of the agent’s prose. Agents write `status=success` or `status=fail` on a supervisor task. False success means status success and programmatic evaluation failure. The 75.8% figure is not “all AppWorld runs.” React and plan-execute always write success, so they were dropped as a self-assessment signal. Trajectories with no status (3,120) were dropped. The remaining 1,879 explicit claims are 1,425 false success and 454 honest failure: full-code-reflection 74.9% (874/295), interprocedural function-call 77.3% (551/159). — [Advani, arXiv:2606.09863](https://arxiv.org/html/2606.09863)
- The same paper: a human check of 200 tau2 failure trajectories agreed with the regex labels on 91.5% (κ = 0.86). No LLM-judge configuration across 5 judges, 5 prompt strategies, and a condition that included the full task specification exceeded AUROC 0.65 on tau2-bench. The same judges reached AUROC 0.54 on AppWorld API-call traces. Closing messages that contain assertion vocabulary scored 0.27–0.36 points more “completed” whether or not the task had succeeded. Telecom, where a second party can see the state, is the setting where false success falls to 3% of failures. The paper treats that as suggestive of independent verification, and says more dual-control environments would be needed to isolate cause. — [Advani, arXiv:2606.09863](https://arxiv.org/html/2606.09863)
- Temporal’s event history is the production version of “the log says what happened, the worker’s return value is just what got recorded.” `WorkflowExecutionCompleted` and `ActivityTaskCompleted` are service-written events that carry the result. `ActivityTaskFailed` and `ActivityTaskTimedOut` are the failure records. `ActivityTaskStarted` is not written until a terminal event (completed or failed) is written, so a history reader cannot treat “started is in the log” as a live claim. While an activity is still retrying, `ActivityTaskScheduled` may be the only activity event present. — [Temporal Events reference](https://docs.temporal.io/references/events)
- Inngest: the saved step result is what later steps see. Code outside a step can run again. A step id does not make the external call exactly once. — [Inngest: Primitives and steps](https://www.inngest.com/docs/durable-execution/primitives)
- River: returning nil from `Work` only means the job is presumed successful and will be marked complete asynchronously. If that mark fails, the job runs again. Completion is the row transition, and it is reliable in the exactly-once-for-this-database sense only when it commits in the same transaction as the effect (`JobCompleteTx`). — [River: Writing reliable workers](https://riverqueue.com/docs/reliable-workers)

### Inferences
- Three candidates for “done,” and only the third matches these systems. The model’s message is the thing Advani shows is wrong on 45% and 47% of airline and retail failures, and on 75.8% of the filtered AppWorld failures. A journal that copies that message into `status=done` preserves the lie. The source of truth is an external check: database diff (AppWorld), environment match (tau2-bench as Advani describes it), file or test result, or a user acceptance. The journal’s job is to record that check, who ran it, and what it saw.
- AppWorld is the sharp case for a personal app. The agent’s `complete_task(status="success")` is visible in the supervisor row, and the evaluator still refuses the task unless the state diff matches. A local board should treat “the assistant said it finished” as a comment. The card moves to done only when the app records a check: the user marked it, the artifact path exists and matches the hash that was attached, or a stored command result says the tests passed.
- Dual control is the structural version of the same rule. Telecom’s 3% versus 45–47% is the empirical hint: a second party that can see the state suppresses silent success. On a personal board the second party is the user, or a deterministic check, not another model reading the transcript. Advani’s judge results (AUROC at or below 0.65 and 0.54) are why a second model is a weak oracle for this failure.
- Because the local loop dies with the connection, a run that was mid-task must not be completed by the last assistant message that happened to be flushed. Expiry writes a release, not a completion. A later run may resume; it must not inherit “done.”

### Gaps
- Sierra’s tau2-bench `docs/evaluation.md` was not opened. A search snippet said scoring is the final database hash plus required communicated strings, and that action order is not the reward. That communicate clause is not used above. Advani’s description, which was opened, says the reward is whether the final environment state matches the specification.
- Advani’s related work says Cao et al. found that 27–78% of reward = 1 tau-bench trajectories contain procedural violations (“corrupt success”: the outcome matches and the procedure does not). Cao’s paper was not opened. The range is not used as a finding.
- Exact TGC table cells (for example 48.8 and 30.2) appeared in search snippets of the AppWorld PDF. The abstract’s “about 49%” and “about 30%,” which were read in the PDF text, are the figures used here.
- No opened source measured how often a coding agent’s “I opened a PR” was false in production. The evidence is benchmark trajectories with a programmatic oracle.

## What did human studies actually measure about plan-level versus step-level approval?

### Takeaway
The live oversight study measured exposure, intervention, and subjective workload. It did not measure rubber-stamping. Plan-level engagement cut how often the bad action appeared. It did not reliably help people stop that action once it was on screen. Step-by-step confirmation was not the high-workload condition in the short session. A separate paper that talks about approval fatigue is a simulation with persona reviewers, and it says so. The human evidence that repeated approval is tiring is qualitative, from the same oversight study, plus a small trace-verification study that found faster review and higher confidence without better accuracy.

### Cited Findings
- Chen et al. (arXiv:2604.04918) ran a within-subjects study with 48 participants, each supervising a live web agent under four strategies, about 45 minutes, paid $18. The four strategies were Risk-Gated (agent runs, approval only on a flagged step), Action Confirmation (approve every action), Supervisory Co-Execution (plan review, then the agent proceeds with a trace), and Structurally Enriched (plan plus optional step detail and risk labels). Workload was an adapted 5-item NASA-TLX on a 7-point scale (mental demand, time pressure, effort, frustration, and reverse-scored performance). They also measured perceived control, a trust composite, usability, and perceived risk. Behavioral outcomes were whether the embedded bad action occurred, whether the participant blocked it once it occurred, and whether the attack ultimately succeeded. Intervention means rejecting a step, editing the input, or aborting. Looking without changing the outcome does not count. — [Chen et al., arXiv:2604.04918](https://arxiv.org/html/2604.04918)
- Attack occurrence differed by strategy (χ²(3) = 16.93, p < .001). Intervention success did not (χ²(3) = 2.90, p = .407). Final attack success did not (χ²(3) = 5.14, p = .162). Rates: Action Confirmation occurrence 88.5%, intervention 23.9%, attack success 67.3%. Risk-Gated 90.1%, 26.4%, 66.3%. Supervisory Co-Execution 60.4%, 9.2%, 54.8%. Structurally Enriched 74.5%, 14.6%, 63.6%. Collapsing families, the two plan-based strategies had lower occurrence than the two non-plan strategies (OR = 0.25, 95% CI [0.13, 0.49], p < .001), without a comparable gain on intervention or final prevention. The authors note that some of the occurrence drop may be plan revision before execution, which their intervention metric does not count. — [Chen et al., arXiv:2604.04918](https://arxiv.org/html/2604.04918)
- Workload means (lower is better), lower-consequence tasks: Action Confirmation 2.317 (the contrast versus Structurally Enriched was marked p < .05), Risk-Gated 2.683, Supervisory Co-Execution 2.842, Structurally Enriched 3.200. Higher-consequence tasks: Action Confirmation 2.992, Risk-Gated 2.325, Supervisory Co-Execution 2.517, Structurally Enriched 2.325. The omnibus interaction of strategy and context was not significant for workload, control, or usability. It was significant for trust (interaction b = −0.62, p = .006): Action Confirmation had higher trust than Structurally Enriched on lower-consequence tasks (b = 0.32, p = .033), and that contrast reversed on higher-consequence tasks. Higher-consequence tasks had more attack occurrence (91.2% vs 65.8%), less intervention (12.8% vs 29.4%), and higher final attack success (79.5% vs 46.5%). Participants’ own perceived-risk ratings did not differ (2.375 vs 2.281, t(47) = 0.76, p = .451). The authors say the high/low split is confounded with risk type: high-consequence tasks were mostly privacy leakage. — [Chen et al., arXiv:2604.04918](https://arxiv.org/html/2604.04918)
- Interviews with 10 of the 48. The fatigue evidence is quoted speech, not a click-rate. One participant: “I didn’t like having to click approve, approve, approve.” Another said that for routine fields it would be faster to do the step by hand. The authors’ interpretation is that missed interventions were often rationalization (the action looked like autofill, or like the site’s own form), not only inattention. “Approve similar” was a boundary problem: people did not know whether the system’s grouping matched theirs (“If I hit approve similar, I wouldn’t expect it to jump to the billing”). The study is one session, not everyday use. The authors say longitudinal work is still needed. — [Chen et al., arXiv:2604.04918](https://arxiv.org/html/2604.04918)
- Grunde-McLaughlin et al. (arXiv:2602.16844) is three studies, n = 12 each, on how traces help people find errors in a computer-use agent, not on approval clicks. The current step-summary trace was verbose and people missed small errors. In the final comparison, a specification-style interface made error-finding faster (Hedges’ g = −0.65), did not meaningfully change accuracy (g = 0.18), and when people missed an error they were more confident the agent was right (g = 0.85). Process-heavy summaries were the ones that justified overreliance. The PDF’s conference boilerplate date is not a publication date; the identifier used here is the arXiv id. — [Grunde-McLaughlin et al., arXiv:2602.16844](https://arxiv.org/pdf/2602.16844)
- Turan (arXiv:2606.08919, 9 June 2026) is explicit that it is not a human fatigue study. On 125 hand-labeled agent actions, three persona reviewers (called a proxy for annotators) reach Fleiss’ κ = 0.52. Pairwise Cohen’s κ is 0.42, 0.47, and 0.71. The cautious persona marks 45 actions safe; the pragmatic persona marks 87. Gold labels are one author’s judgments; the persona majority matches that gold 74% of the time. The inverted-U (more escalation can reduce safety) is “a modeling result about a plausible model, not an empirical finding about real people,” and the abstract says those results “motivate a human study.” Under the model, at reviewer capacity 25 the safety-optimal escalation rate is 64% with danger-through 42%, versus 57% danger-through if everything is escalated. A simulated flooding attack at an 88% false-alarm policy reaches 40% attack success at 50 filler actions; a 26% escalation policy holds attack success at 0 until filler is on the order of 100 actions. Those percentages are outputs of the fatigue function, not observed humans. — [Turan, arXiv:2606.08919](https://arxiv.org/pdf/2606.08919v1.pdf)

### Inferences
- What to copy is narrower than “prefer plan approval because of fatigue.” In the only live comparison opened here, plan-level structure reduced how often the bad action was attempted (OR 0.25) and did not improve the chance a person stopped it (intervention p = .407). Step-level confirmation, in a 45-minute study, had the lowest workload on the low-stakes tasks. The cost people actually described was repeated clicks on routine steps, and the failure mode was treating a risky step as ordinary.
- For a personal app that already has plan approval and in-memory step cards: persist the approval decision, because the process dies with the connection. Do not put a human gate on every tool call. Gate the plan, and gate the irreversible or external step. Chen’s “approve similar” quotes are a warning against a vague session grant: the grant has to name the class of action (this calendar, these files), or people cannot tell what they handed over. External side effects staying proposal-only is already the stronger gate: the human accepts an artifact, which is one decision, not a step stream.
- Do not cite Turan’s inverted-U or the 40%-at-50-fillers figure as evidence that people rubber-stamp. The paper forbids that reading. The human-adjacent findings that are safe to repeat are Chen’s workload table, the non-effect on intervention, the approve-approve quote, and Grunde-McLaughlin’s faster-but-not-more-accurate trace review with higher confidence on misses.

### Gaps
- No opened human study counted approval latency, edit rate, or override rate as fatigue develops over hours or days. Chen et al. say that longitudinal use was out of scope.
- No opened study randomized “approve the plan once” against “approve every shell call” on a coding agent with a measured rate of mistaken approvals. The computer-use study is the closest, and its tasks were web forms with planted risks.
- Vendor documents for background-agent approval were not opened in this pass. The measurements above are from the papers, not from product docs.

## What does a minimal board event log need, and which fields are cargo-cult?

### Takeaway
The log needs seven event types that change who owns the card or what “done” means: created, claimed, moved, comment, artifact attached, released, failed. Completion is a separate event, written only by the checker. Each event needs an id, a monotonic order, the card id, the actor, and a payload specific to the type. Most of the columns on a workflow-engine history or a team tracker are for multi-tenant search, replay, or sprint planning. They do not earn a place on a one-person board.

### Cited Findings
- Temporal’s history is the existence proof that these distinctions are real events, not columns on one row. `WorkflowExecutionStarted` records who requested the run and the input. `ActivityTaskScheduled` means the work was queued. `ActivityTaskStarted` records worker identity, request id, and attempt, but it is withheld until completion or failure, so it is not a live lease. `ActivityTaskCompleted` carries the result. `ActivityTaskFailed` carries the failure and a `retry_state`. `ActivityTaskTimedOut` carries `timeout_type` (the field list includes Start-to-Close, Schedule-to-Close, and Schedule-to-Start). `WorkflowExecutionSignaled` is an external input with a name and a payload, the closest analogue to a comment that must not be lost. `MarkerRecorded` is an opaque side record the server stores and does not interpret. `WorkflowExecutionCancelRequested` is distinct from `WorkflowExecutionCanceled`. Started, completed, failed, timed out, and signaled are different events because the transitions are different facts. — [Temporal Events reference](https://docs.temporal.io/references/events)
- SQS splits the same facts without an event log: receive is the claim, delete is the successful finish, visibility timeout expiry or `ChangeMessageVisibility` of 0 is the release, and a dead-letter queue is the “failed enough times” bucket. The receipt is what later calls must present. There is no comment type and no artifact type; those are application concerns. — [Amazon SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)
- Inngest’s trace is step-scoped: each step id, whether it completed, waited, or retried, and a JSON result. The documented limit is 4 MiB per step result and 32 MiB of run state, which is why a large artifact is a reference, not an inline blob. A changed step id is new work; the old id will not replay onto new code. — [Inngest: Primitives and steps](https://www.inngest.com/docs/durable-execution/primitives)
- River: the completion row is written with the effect, or the effect can commit and the completion can still be lost. A log that only stores the worker’s intended status, written later and elsewhere, is the failure mode `JobCompleteTx` exists to close. — [River: Writing reliable workers](https://riverqueue.com/docs/reliable-workers)
- AppWorld’s evaluator stores the check next to the claim: status on the supervisor task, plus assertions on the diff (expected changes present, no unexpected changes). The example evaluation names the models that are allowed to have changed. — [AppWorld (arXiv:2407.18901)](https://arxiv.org/pdf/2407.18901)

### Inferences
- Minimal event, all types: `seq` (integer, append order), `card_id`, `type`, `actor` (`user` or an agent id), `at`. Nothing else is universal.
- Type-specific payload that is load-bearing:
  - `created`: title or goal text, and the actor. Not a template id, not a priority enum.
  - `claimed`: `claim_token`, `lease_expires_at`, `attempt`. Without the expiry, a dead HTTP run owns the card forever.
  - `moved`: `from`, `to`, and the `claim_token` or a `version` the writer had seen. A move with no expected version cannot be rejected when the user already moved the card.
  - `comment`: body. Insert only. This is the signal. It is not a status change.
  - `artifact`: a path or hash and a short kind (`file`, `proposal`, `test-result`). Not the file contents. Inngest’s 4 MiB cap is the same constraint at a different scale.
  - `released`: reason `finished`, `expired`, `preempted`, or `cancelled`, plus the `claim_token` being dropped.
  - `failed`: error text, `attempt`, and whether it may be retried. Distinct from released, because “nobody holds it” and “this attempt broke” are both true and easy to conflate.
  - `completed`: only from the checker. Payload is the check (`user_accepted`, `path_exists`, `tests_passed`) and a pointer at the artifact or the command result. The model does not emit this type.
- Write the event and the card’s status column in one SQLite transaction. River’s split between “work committed” and “completion saved later” is the bug a single local transaction avoids. The status column is a cache of the log. The log is what undo replays.
- Cargo-cult, safe to leave out at this scale:
  - Search attributes, memos, headers, cron, parent-workflow namespace, and worker-binary identity on every event (Temporal carries these because it is a multi-tenant history).
  - Writing “started” only when the task ends. That is a history-compaction choice. A board the user is looking at needs the claim to be visible while the run is alive, and needs it to disappear on expiry.
  - Replay determinism, continue-as-new, and reset-to-event-id. Those exist so a workflow can re-execute without repeating side effects. A personal kanban is not replayed. Resume is “read the log, claim again, don’t redo a proposal that already exists.”
  - Story points, sprint, epic, SLA, WIP limits, reaction counts, assignee avatars. Nothing opened here uses them to keep two workers from double-claiming or to decide that work finished.
  - A second bus, a webhook, or a full audit export. One append-only table is the log.
  - LLM-judge columns (“confidence the task is done”). Advani’s AUROC numbers are why that column would be theater.

### Gaps
- No opened board product published a schema limited to these seven types. The list is the intersection of Temporal’s transition set, SQS’s claim/delete/expire/dead-letter set, and AppWorld’s status-versus-diff split, cut down to a single user. It is an inference, not a vendor spec.
- GitHub and issue-tracker timeline APIs were not opened, so this note does not claim their event lists as evidence.

## Conflict and undo: what can one person and a local database get away with?

### Takeaway
One SQLite file already serializes writers, so last-write-wins is acceptable only inside a claim the writer still holds. Comments never update in place. The user, who edits the board by hand, preempts an agent: that move clears the lease. Undo is a new event, not a delete, and a body snapshot is enough when an agent rewrites text. CRDTs and multi-version merge are for concurrent editors on more than one machine. They are not the safety mechanism for a handful of local agents.

### Cited Findings
- SQLite WAL: readers do not block the writer and the writer does not block readers, but “since there is only one WAL file, there can only be one writer at a time.” All processes must be on the same computer; WAL does not work over a network filesystem because readers share memory for the wal-index. A commit appends a commit record to the WAL. Checkpointing copies that back into the database file. A long read can stall the checkpointer. `PRAGMA journal_mode=WAL` is the switch. — [SQLite WAL](https://www.sqlite.org/wal.html)
- PostgreSQL’s `SKIP LOCKED` is the multi-consumer tool, and the manual warns that skipping locked rows is an inconsistent read, appropriate for a queue and not for ordinary queries. A board the user is looking at should be an ordinary consistent read. The claim path is the only place a lock-skipping update belongs, and on SQLite the single writer already provides the serialization. — [PostgreSQL SELECT, The Locking Clause](https://www.postgresql.org/docs/current/sql-select.html)
- Temporal: two running executions cannot share a workflow id under the default conflict policy. Lease expiry does not prove the previous holder stopped. A fencing token (the permit run id) is what a downstream system checks. A release signal is pinned to the run that acquired the lock so a late release cannot free the next holder’s slot. Reset is how Temporal undoes: it terminates the execution and copies history through a reset point into a new execution. Valid reset points are workflow-task boundaries, not arbitrary edits. — [Temporal lock guide](https://docs.temporal.io/guides/lock-shared-resources); [Temporal Events reference](https://docs.temporal.io/references/events)
- Stripe: the idempotency record stores the first result, and a retry with different parameters is rejected. That is last-intent-wins only for an identical retry, not a silent overwrite of a different request. — [Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)
- Chen et al.: people set local boundaries (“approve similar” must not jump from contact fields to billing) and sometimes ignore the side panel if the page looks right. A conflict the user cannot see is a conflict they will not resolve. — [Chen et al., arXiv:2604.04918](https://arxiv.org/html/2604.04918)

### Inferences
- What last-write-wins can cover: fields a single holder writes during a valid lease (progress note, draft body). The write includes `WHERE claim_token = ? AND lease_expires_at > now`. Zero rows means the user preempted or the lease died; the agent discards its write. That is compare-and-swap, not a merge.
- What last-write-wins must not cover: comments, artifact rows, and the completion event. Those are inserts. Two agents commenting on one card do not conflict. Two agents moving one card do, and the claim (or the user’s preempt) is the resolution. There is no need for a CRDT if the writers are serialized by SQLite and only one of them holds the token.
- User edits are the preempt. The smallest rule that matches “the user moves cards by hand”: a user move commits, clears `claim_token` and `lease_expires_at`, and appends `moved` plus `released` with reason `preempted`. The agent’s next heartbeat fails the compare-and-swap and stops. Do not queue the agent’s move to apply later. The user’s board is the board.
- Undo: append `moved` back, or append a `comment` that the previous body is restored, and store the previous body on the edit event (one snapshot per agent write, not a snapshot of the whole board). Deleting history removes the only explanation of why the card jumped. Temporal’s reset-copies-history is the same idea at workflow scale; locally the new event is enough because nothing will replay the old side effects if those side effects were only proposals.
- External effects stay proposals, so the dangerous undo is “the proposal was accepted twice,” not “the text merge lost a sentence.” Accepting a proposal is a `completed` or `artifact` event keyed by the proposal id. A second accept hits the same idempotency key and returns the first result. A stale agent whose lease was cleared cannot create that proposal, because the insert is conditional on the claim token.
- What this scale can skip: operational transform, CRDTs, vector clocks, and a background merge worker. SQLite’s own manual gives the boundary. One writer, same machine. The moment the database is on a network filesystem, or two devices write the file, that permission expires. That is outside this note’s target.

### Gaps
- No opened personal-kanban or local-first note app was compared for undo. The recommendation is from SQLite’s single-writer rule plus the claim/fence/idempotency sources above, aimed at one user and a few local agents.
- Temporal’s reset semantics were read from the events reference and the lock guide’s description of run identity. The full reset documentation page was not opened, so the list of valid reset points is cited only as the events page states it (`WorkflowTaskStarted`, `WorkflowTaskCompleted`, `WorkflowTaskTimedOut`, `WorkflowTaskFailed` appeared in a search snippet of a different Temporal page and are not all repeated here as verified).
