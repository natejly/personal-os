## How does a cowork desk run (plan approval, modes, folder, chained turns, file promotion, parked cards)? What cannot happen?

### Takeaway
A desk is one conversation, one relative folder `cowork/<id>`, and one status row. It runs as a chain of ordinary chat turns under a supervisor. Plan mode withholds consequential tools until the user approves a plan; ask mode cards every change; propose mode refuses external calls outright. The agent nominates files; only the user promotes them, and promotion is verified by read-back. A card with no viewer parks after 180 seconds by default; answering it can wake the desk. Nothing auto-resumes after a restart.

### Cited Findings
- **Shipped — row model.** `Desks` owns `desks`, `desk_events` (timeline and the needs-you queue), and `desk_outputs`. `set_status` is the only status writer and commits the column plus the event in one transaction. `claim_run` and `claim_output` are single-UPDATE locks, so a double Start or a double Accept cannot produce two runs or two promotions. `workspace` stores relative `cowork/<id>`, never an absolute path. Statuses: `draft`, `planning`, `awaiting_plan`, `working`, `needs_approval`, `blocked`, `paused`, `interrupted`, `review`, `done`, `failed`, `stopped`. Live means `planning`, `working`, `needs_approval`. Needs-you means `awaiting_plan`, `needs_approval`, `blocked`, `interrupted`, `review`. — [cowork.py](backend/personal_os/cowork.py)
- **Shipped — folder.** `Workspace.ensure` creates `<data_dir>/cowork/<desk_id>/` with `outputs/` (deliverables), `work/` (scratch), `.baseline/` (first-write snapshots for diffs), and `.trash/` (nothing is unlinked). `resolve_in` is the containment chokepoint (resolve, then contain, including symlinks). Quotas: 500 files, 200_000_000 bytes total, 400_000 characters per text file. Executable suffixes (`.command`, `.app`, `.scpt`, and similar) are blocked. Writes inside the folder are danger `writes`, not `external`. — [workspace.py](backend/personal_os/workspace.py)
- **Shipped — how a turn starts.** `POST /cowork/desks` creates a hidden conversation (`settings.deskId`) and a desk. `start=true` calls `_launch_desk`, which refuses if a run is already live on that conversation or if `deskMaxLive` is already full, then `claim_run` from `draft` only. The claim moves a desk with no `plan_id` to `planning` and one with a plan to `working`. A supervisor task (`_desk_supervisor`) owns the chain; the next turn is not started from inside the previous run. — [app.py `_launch_desk`, `create_desk`](backend/personal_os/app.py)
- **Shipped — three autonomy modes, enforced in the reply loop.** `AUTONOMY = plan | ask | propose`, default `plan`. `planning` is true only when autonomy is `plan` and there is no active plan. While planning, schemas keep only `propose_plan` and tools whose danger is `safe`, `network`, or `plan`; `desk_done` is popped even though it is `safe`; MCP schemas are withheld. A call whose danger is outside that set is denied with the plan-blocked reason, not offered and then refused. `ask` forces every mutating call to a card and sets `forced`, so a standing grant cannot turn the card off. `propose` sets external calls (including MCP, which is external by construction) to off with the propose-only reason — it does not record an inbox proposal. A desk never offers `desk_start`. Conversation `planMode` is stored as `off` for ask desks and `always` otherwise, but the loop reads the desk row’s `autonomy`, so a later mode change applies on the next turn. — [cowork.py `DESK_PLAN_HINT`](backend/personal_os/cowork.py); [plans.py `PLAN_SAFE_DANGER`](backend/personal_os/plans.py); [app.py `_schemas`, autonomy branch](backend/personal_os/app.py)
- **Shipped — plan approval.** `propose_plan` always asks. `Plans.claim` matches an approved step by argument digest, once, inside the run (and for a desk even when the call would have run without a card). A rejected matching call is denied. Unexpected taint voids a pre-approval and forces a card before any claim. A chat that runs out of budget while holding an approved plan may still execute those steps; a desk may not — remaining steps go to the next chained turn. — [plans.py](backend/personal_os/plans.py); [app.py around the budget exception and `plans.claim`](backend/personal_os/app.py)
- **Shipped — chained turns.** Defaults: `deskMaxTurns` 12, `deskMaxCost` 2.0, `deskMaxLive` 4. A desk budget may only tighten those, never loosen them. `_chain_kind` returns `continue` when the reply hit a per-reply budget stop (`rounds`, `tokens`, `time`, or `cost`) and the turn made progress (`steps_consumed > 0` or `tool_ok > 0`). It returns `nudge` once when the reply simply ended (no `desk_done` / `desk_ask` / stop), and never two nudges in a row. It returns nothing on error, user stop, a non-live status, or when the desk turn or cost cap is already spent. Ask and propose desks count as live while status is still `planning`, because only plan autonomy is actually held in plan mode. The next user message is `continue_message`: instruction plus the tail of `work/PROGRESS.md` (3_000 characters), fenced as the desk’s own notes. `DESK_HINT` tells the model a new turn sees earlier replies, not their tool results. — [llm.py defaults](backend/personal_os/llm.py); [app.py `_chain_kind`, `_desk_supervisor`](backend/personal_os/app.py); [cowork.py `DESK_HINT`, `continue_message`](backend/personal_os/cowork.py)
- **Shipped — settle.** `Desks.settle`: user stop → `stopped`; error → `failed`; if the desk already left the live set (ask, done, park, pause), that decision stands unless stop or crash outranks it; `chain=True` leaves it `working`; `partial == blocked` → `blocked`; other partial (`rounds|tokens|time|cost|loop`) → `review`; a reply that ended with undecided outputs → `review`, otherwise → `blocked`. `done` is only written when the desk decides it (`desk_done`), never inferred. — [cowork.py `settle`](backend/personal_os/cowork.py)
- **Shipped — parked cards.** Default `parkAfterSeconds` is 180. Only desk cards park, and only when `run.watchers == 0`. Park does not deny: the approval row stays pending, the desk becomes `blocked` with reason `approval` or `plan`, and the run lets go. A chat never parks (`parkAfterSeconds` is ignored when there is no desk). Answering a parked card wakes the desk via `_wake_desk` / `_missed_wake` if the run was still closing when the decision landed. `parked_report` is injected as a system note on the next turn: an approved ordinary call must be repeated with the same arguments to spend `claim_parked` (any argument change asks again); a rejected call must not be retried; an approved `desk_ask` includes the user’s note; a dismissed question tells the model to use judgement. Parked approvals cannot take edits (`400`: approve as proposed or deny). — [llm.py `parkAfterSeconds`](backend/personal_os/llm.py); [app.py park loop, approval edit refusal, `parked_report` injection](backend/personal_os/app.py); [cowork.py `parked_report`](backend/personal_os/cowork.py)
- **Shipped — file promotion.** `desk_deliver` nominates a path under `outputs/` and records sha256; it does not promote. Rewriting the file resets the row to `proposed`. `POST /cowork/desks/{id}/accept` is the only promotion path: `claim_output`, then `call_once`, then `_promote`, then read-back. Destinations: `doc` (new doc, content compared), `doc_append` (a pending doc revision; the user’s doc is not overwritten), `document` (upload, hash of the stored file), `download` (file stays in the workspace; verified if the bytes still match the declared hash). Unverified → `promote_failed`, which is claimable again. Reject is a separate writer. — [tools.py `desk_deliver`](backend/personal_os/tools.py); [app.py `_promote`, `accept_outputs`](backend/personal_os/app.py); [cowork.py `declare_output`, `claim_output`, `finish_output`](backend/personal_os/cowork.py)
- **Shipped — restart.** `recover()` moves every desk in `planning`, `working`, `needs_approval`, or `awaiting_plan` to `interrupted` with a needs-you event. Paused and blocked desks are left alone. Nothing is auto-resumed. Resume claims from `awaiting_plan`, `blocked`, `paused`, `interrupted`, `review`. A message can also wake `done`, `failed`, `stopped`. A background shell note can wake a desk that has no live run. — [cowork.py `recover`, `RECOVER_FROM`](backend/personal_os/cowork.py); [app.py `RESUME_FROM`, `_shell_wake`](backend/personal_os/app.py)
- **Shipped — agent-started desks, narrower than the REST route.** `desk_start` is danger `plan` (always a card). Allowed modes are only `plan` and `propose`, never `ask`. It calls the same `create_desk` with `start=True` and counts against `deskMaxLive`. The tool’s success note always says the desk is planning and will wait for plan approval, including when `mode` is `propose`. — [subagents.py `desk_start`, `DESK_MODES`](backend/personal_os/subagents.py); [app.py `_desk_start_tool`](backend/personal_os/app.py)
- **What cannot happen (enforced).** A desk cannot promote its own files, start another desk, auto-resume after restart, or run two turns from one claim. Plan mode cannot run writes, shell, or external tools before approval. Propose mode cannot perform external actions (they are denied, not proposed). Ask mode cannot skip the card via a standing grant. A chained turn cannot see prior tool results, only assistant text plus `PROGRESS.md`. A parked card cannot be edited. A second Start or Accept loses the row lock. The live cap (`deskMaxLive`, default 4; 0 means unlimited) blocks another launch. `done` is not inferred from a quiet ending.

### Inferences
- The README’s chain rule (“only while the approved plan still has steps left and the last turn consumed one”) is stricter than `_chain_kind`. The code also continues after any successful tool, and it issues one nudge with no plan-step check. See the disagreement section.
- Desk gating is a narrowing layered on the normal tool mode: it can force ask or deny, and the shell auto-ok inside the desk workspace can turn a default `ask` into `on` only when nothing else already forced a card. Skip-permissions does not apply to jobs; whether it applies to desks depends on the chat/global switch and `permrules.lift_permission_ask`, which still keeps `propose_plan` and `desk_ask` as cards. That interaction belongs with the permissions note; the desk-specific rules above are the ones this loop actually applies.

## How do scheduled tasks and the agent inbox work (cron, catch-up, proposals, no nested scheduling)?

### Takeaway
A job is a cron expression or a single instant, stored with the slot it is waiting for. The scheduler sleeps until that slot (capped at 60 seconds), fires at most one run per job per wake, and collapses a gap into one late run for the most recent missed slot. The run is a fresh conversation with `kind=job`: outward and scheduling calls become inbox proposals and never execute. A job cannot nest another schedule by itself; accepting the proposal is what creates the next job. Overlap skip, retry, failure-streak pause, per-job allowlists, dry run, and per-job history are in this tree.

### Cited Findings
- **Shipped — schedule kinds.** `kind` is `cron` (exactly five fields; a sixth, seconds, is refused) or `once` (`run_at`). Timezone is an IANA name (`$TZ`, then `/etc/localtime`, else UTC), so DST follows the wall clock. Fall-back duplicate wall times are skipped so one slot fires once. `parse_when` accepts ISO-8601 with a time and rejects a bare date. Natural language is not parsed. A new one-off more than 120 seconds in the past is a 400; an already-stored past slot is catch-up, not a write error. — [jobs.py `valid_cron`, `next_fire`, `parse_when`](backend/personal_os/jobs.py); [app.py `_check_schedule`, `BACKDATE_GRACE_S`](backend/personal_os/app.py)
- **Shipped — clock.** `Scheduler.loop` sleeps until the earliest `next_due_at`, capped at `MAX_SLEEP_S` 60, because the asyncio clock does not advance during suspend. An idle wake is a SELECT and no model call. `tick` arms enabled jobs that have no slot (a job armed this way has nothing to catch up), then launches each due job at most once. `mark_fired` commits clock bookkeeping before launch, so a crashing launch cannot re-fire the same slot. A one-off sets `enabled=0` after it fires (`disable=True`) and is not re-armed. Re-enabling a spent one-off without a new `run_at` is a 400. Disabling, or changing kind/cron/run_at/timezone, re-arms from now, so a job that was off across a slot has no missed slot. — [jobs.py `Scheduler`, `Jobs.arm`, `Jobs.update`](backend/personal_os/jobs.py)
- **Shipped — catch-up.** `plan()` sets `due_at` to the most recent slot at or before now, never before the slot the job was waiting on. `missed_slots` is `slots_between` minus one, capped at 500. `late` is true when lateness exceeds `LATE_GRACE_S` (90 seconds) or more than one slot was collapsed. `_job_prompt` prepends `LATE_NOTICE` telling the model to say it is late and re-check time-sensitive facts. A missed one-off still runs, once, late. — [jobs.py `plan`, `slots_between`](backend/personal_os/jobs.py); [app.py `LATE_NOTICE`](backend/personal_os/app.py)
- **Shipped — the run.** `_launch_job` creates a new conversation each fire (`autoLearn` off, `settings.job_id` set so it stays out of the sidebar) and starts `kind=job`. `PROPOSAL_ONLY_KINDS = ("job",)`. Caps, applied only downward: 8 tool rounds, 60_000 tokens, 240 seconds, $0.20. A hard ceiling `JOB_HARD_SECONDS` is 1800. `JOB_HINT` is injected. Three seed jobs (morning brief, unread drafts, weekly review) are created disabled, each with an `allowed_tools` list. — [app.py `JOB_BUDGET`, `_launch_job`](backend/personal_os/app.py); [jobs.py `SEED_JOBS`](backend/personal_os/jobs.py)
- **Shipped — proposals, including no nested scheduling.** Danger `external` and `schedules` are proposal-only. `_call_tool` turns those calls into a `proposals` row and does not call the tool. `Toolbox.call` repeats the refusal if a caller forgets the first gate. `schedules` is included specifically so a background run cannot book more background runs. The model is told the call was recorded, not executed. `POST /proposals/{id}/accept` claims `pending` → `accepted` once (optional edited args), then runs the tool with `proposal_only` false, through `call_once`, so a second accept does not run it again. MCP tools on accept go through `_mcp_call`, not `toolbox.call`. Reject is the other terminal status. A job that hits an ordinary `ask` (not an outward proposal) is denied immediately: “nobody is watching”; it does not park. — [tools.py `PROPOSAL_ONLY_DANGER`, `PROPOSAL_ONLY_REFUSED_SCHEDULE`](backend/personal_os/tools.py); [app.py `_propose`, `_call_tool`, `accept_proposal`](backend/personal_os/app.py); [jobs.py `Proposals.claim`](backend/personal_os/jobs.py)
- **Shipped — chat scheduling still asks.** `schedule_task` is danger `schedules` (default mode `ask`). It creates an enabled cron or once job in the current project. One of `cron`, `when`, or `in_minutes`, not several. `scheduled_tasks` lists; `cancel_scheduled_task` disables. — [tools.py `_register_schedule`](backend/personal_os/tools.py)
- **Shipped — overlap, retry, pause.** `JobPolicy.admit` refuses a fire while another non-dry run of the same job has no `ended_at` and status `running` or `awaiting_approval` (lookback 24 hours). The skip is stored (`last_skip_reason`) and the slot is already consumed by `mark_fired`. Manual `POST /jobs/{id}/run` returns 409 with the same reason. A watcher follows non-manual, non-dry runs: `error` or `interrupted` retries the same slot up to `max_retries` (default 1, max 5) with backoff `jobRetryBackoffS` (default 120, cap 1800). Attempt number lives in `agent_runs.input`, not in memory. After `jobFailureStreakLimit` (default 3) failed fires, `Jobs.pause` sets `enabled=0`, clears `next_due_at`, and sets `paused_reason`. Enabling the job clears the reason and the streak. User-stopped runs, manual runs, dry runs, and runs left interrupted by a process restart are not retried (the watcher dies with the process; nothing re-attaches on boot). `_launch_job` also bails if `last_run_id` is still in `bus.live_ids()` and the fire is not manual, returning that run id instead of stacking a conversation. — [jobs_policy.py](backend/personal_os/jobs_policy.py); [app.py `_launch_job`, `run_job_now`](backend/personal_os/app.py)
- **Shipped — Agent Inbox.** `GET /inbox` (default last 72 hours, limit 20) is built from rows. Needs you: pending approvals, pending proposals, and paused jobs (`enabled=0` and `paused_reason` set). While you were away: one entry per `kind=job` run, with late flag, missed-slot count, attempt, `retry_of`, tool-call count, proposal counts, and the first 1400 characters of the transcript. Dry runs are omitted unless `include_dry=1`. `GET /inbox/notify?since=` returns at most 20 events (names and counts, not reply text). The renderer reads `settings.notifyJobs` (default on unless explicitly false). Desk needs-you is a different queue: `Desks.inbox()` over unseen `desk_events`, not this route. — [app.py `agent_inbox`, `inbox_notify`](backend/personal_os/app.py); [cowork.py `Desks.inbox`](backend/personal_os/cowork.py); [App.tsx](src/renderer/src/App.tsx)

### Inferences
- “No nested scheduling” means the job process cannot create a job. The user can still accept a `schedule_task` proposal, and that accept does create one, because accept clears `proposal_only`.
- Catch-up is coalesce-to-one, not replay-every-missed-slot, and not drop-the-slot.

### Gaps
- Event triggers (webhook, file change, calendar) were not found. Kinds are only `cron` and `once`.
- No deterministic jitter and no automatic expiry of recurring jobs were found in `jobs.py`.
- A cloud worker that fires while the Mac is asleep is described in the README as planned and was not found in this scope.
- Whether the inbox History drawer renders every field `job_history.summarize_run` returns was not opened in the UI. The route and the client (`api.jobs.runs`, `dryRun`, CSV) exist.

## How are skills authored, linted, approved, and injected? Is there progressive disclosure?

### Takeaway
Yes, progressive disclosure is shipped, and it is conditional. Approved skills are inlined in full until the fenced block exceeds `skillsInlineBudget` (default 6_000 characters) or the chat sets `skillsDisclosure` to `manifest`. Past that, the prompt gets an index of up to 50 skills and the model reads a body with `skill_view`. A model can only create or fork candidates. Approval is a human status change, and authority-grabbing sentences block it.

### Cited Findings
- **Shipped — table.** `skills`: name, description, procedure, status `candidate|approved|rejected`, source `induced|proposed|user`, optional `project_id`. Caps: name 80, description 300, procedure 4_000. `propose()` always inserts `candidate`. No caller can insert `approved`. Zero-width and bidi controls are stripped; fence closers `<<` / `>>` are stripped so a procedure cannot break out of its block. — [learn.py `Skills`, `propose`, `_fence_safe`](backend/personal_os/learn.py)
- **Shipped — authoring.** Model tools `skill_draft` and `skill_revise` only produce candidates. Revising an approved skill forks a new candidate and leaves the live text unchanged. `POST /skills/import` parses SKILL.md via `skillmd.import_text` and also stores a candidate (422 on parse errors). `GET /skills/{id}/export` returns SKILL.md text. `skillmd` validates name/description/compatibility, warns that `allowed-tools` is ignored and that `scripts/` or `references/` are not imported, and rejects a body over 4_000 characters. — [tools.py `skill_revise`](backend/personal_os/tools.py); [app.py `/skills/import`, `/skills/{id}/export`](backend/personal_os/app.py); [skillmd.py](backend/personal_os/skillmd.py)
- **Shipped — lint and approval.** `skillbuild.lint_skill` is the shared checker for the review surface and for `skill_draft`. Errors block approval; warnings do not. The blocking class is authority language (a procedure that claims to change permissions or skip confirmation). Empty name and empty procedure are also errors. Unknown tool names and shape issues (unnumbered steps, generic name, missing trigger) are warnings. `approval_blockers` guards the human PATCH to `approved`. Candidates and rejected rows never enter `approved_block`. — [skillbuild.py `lint_skill`, `_authority`](backend/personal_os/skillbuild.py); [learn.py `approved_block`](backend/personal_os/learn.py); [README Library paragraph](README.md)
- **Shipped — injection and progressive disclosure.** `context.build_context` injects only approved, non-empty procedures when `useSkills` is true. `skill_block` fences at most `MAX_INJECTED_SKILLS` (12) full bodies under `<<<APPROVED SKILL>>>`, with a header that they are reference, not instructions, and cannot grant permissions. If `skillsDisclosure` is `manifest`, or mode is `auto` (the default) and `len(skill_block) > skillsInlineBudget` (default 6_000), the prompt gets `skill_manifest` instead: `<<<APPROVED SKILL INDEX>>>` lines of `{id} | {name}: {description}`, up to 50, and `used.skills` is marked `disclosure: manifest`. `mode == full` (anything other than `manifest` that does not trip the budget) keeps full bodies, and skills past the 12th are omitted from that block. `skill_view` returns only an approved, in-scope row, wrapped in the same fence; otherwise it returns an error and the approved names. — [context.py skill injection](backend/personal_os/context.py); [learn.py `skill_block`, `skill_manifest`](backend/personal_os/learn.py); [tools.py `skill_view`](backend/personal_os/tools.py); [llm.py `skillsInlineBudget`](backend/personal_os/llm.py)

### Inferences
- Disclosure is size-triggered, not “always an index.” A small library still pays the full procedure text, and in that mode the 13th approved skill is still dropped.
- Bundled skill files are explicitly not imported. A skill remains prose plus the three text fields.

### Gaps
- No usage counter on the `skills` table was seen.
- Did not open `SkillsPanel` to confirm the import/export buttons are on the Library screen. The routes exist.

## How do MCP connectors join the tool box, and is tool search deferred?

### Takeaway
Connectors do not become built-in specs. Each ready, granted, non-quarantined tool is appended as a schema named `mcp__<server>__<tool>`, danger external, description prefixed with the server name. Deferred search is shipped: when more than `mcpDeferAbove` (default 12) of those schemas are ready, the model is offered `mcp_tool_search` instead, and only slugs it loads are callable. At or under the threshold, every schema is sent every round. The loaded set is per reply.

### Cited Findings
- **Shipped — join path.** `_mcp_tooling` lists tools whose server is in `mcp.ready_slugs()`, skips mode `off`, and skips anything `mcp_drift.offerable` withholds. `effective_mode` decays an `on` grant to `ask` when `schema_hash` no longer matches the grant. Schemas are concatenated after built-in schemas in `_schemas`. A job allowlist that set a slug `off` in conversation `settings.tools` removes it from both the mode map and the schemas, because MCP modes come from `mcp_grants`, not that map. Unloaded slugs are absent from `modes`, so a hallucinated call is denied (“not loaded; call mcp_tool_search first”) and is not executed. After `mcp_tool_search`, schemas are refreshed. Taint and ask still key off `mcp_is` (the `mcp__` prefix). — [app.py `_mcp_tooling`, `_schemas`, defer block](backend/personal_os/app.py); [mcp_search.py `should_defer`, `select_schemas`](backend/personal_os/mcp_search.py)
- **Shipped — search.** `mcp_tool_search` is a built-in, group `mcp`, danger `safe`. BM25 is pure Python over slug tokens (weighted), description, argument names, and argument descriptions. Query truncated at 500 characters; limit clamped to 1..10, default 5. `should_defer` is true only when `threshold > 0` and `n_tools > threshold` (12 tools with threshold 12 does not defer). Catalog hint lists server names and counts. `mcpDeferAbove: 0` disables deferral. — [mcp_search.py](backend/personal_os/mcp_search.py); [tools.py `mcp_tool_search`](backend/personal_os/tools.py); [llm.py `mcpDeferAbove`](backend/personal_os/llm.py)
- **Shipped — drift quarantine (beyond “join”).** `mcp_drift.offerable` hides a tool whose new shape added a fail-level finding until `POST /mcp/tools/{slug}/accept`. Accept clears quarantine and does not raise the grant; hash decay to `ask` remains. Sync writes version history and calls `apply_review`. — [app.py `_mcp_tooling` comment and accept route](backend/personal_os/app.py); [mcp_drift.py](backend/personal_os/mcp_drift.py); [mcp_client.py review hook](backend/personal_os/mcp_client.py)
- **Partial — transports.** Stdio is supported. Transport `http` uses the streamable HTTP client and optional OAuth (`mcp_oauth.py`: refresh without a browser sign-in raises needs-auth). Any other transport raises “not supported yet.” — [mcp_client.py `_open`](backend/personal_os/mcp_client.py)
- **Gating on a job.** An MCP call in a `kind=job` run is recorded as a proposal (`proposes()` cannot see MCP specs, so the loop special-cases `mcp_is`). Accept is what calls it. — [app.py proposing branch, `accept_proposal`](backend/personal_os/app.py)

### Inferences
- Tool search is deferred only past the threshold, and discoveries do not stick across turns: `tool_ctx["mcp_loaded"]` is a new set at the start of each `_chat_stream`, which includes each chained desk turn.
- Children are not given `mcp_tool_search` (`CHILD_BLOCK`), so a subagent cannot load connector schemas on its own.

### Gaps
- Resources, prompts, sampling, elicitation, and `list_changed` were not re-audited in `mcp_client.py`. The research note says only `tools/list` and `tools/call` are used; that sentence was not re-verified line by line.
- SSE as a distinct transport is absent (`transport != "http"` fails).
- Registry browse and bundle install were not found in this pass.

## Subagents, workflows, per-job allowlists, run history: shipped, partial, or absent?

### Takeaway
All four are shipped in the backend, with stated limits. Subagents and workflows are registered on the toolbox. Per-job allowlists narrow a run and cannot widen it. Run history is `GET /jobs/{id}/runs` (and stats and CSV), separate from the inbox’s 72-hour feed. Commands are a lighter sibling of workflows: a saved prompt, optionally run as a child.

### Cited Findings
- **Subagents — shipped.** `tools.py` calls `subagents.register`. Tools: `agent_spawn`, `agent_wait`, `agent_stop`, plus `desk_start`. A child is a durable run `kind=subagent` with `parent_run_id`, its own loop, no parent history, no auto-learn, no plan mode, no steering. Context is the role prompt, the task, project instructions, and pinned memories. Built-in roles: `researcher` and `reviewer` (read tools only), `worker` (also file writes, shell, `run_python`, desk file tools, and spawn). `tools` on the call can only narrow the role. Modes are intersected with the parent: off stays off; ask stays ask unless this chat is skipping permissions. Defaults: concurrent 4 (clamp 1..20), depth 2 (clamp 0..3), rounds 12, cost $0.25. Children may use at most 0.6 of the parent’s token/cost/time budget. Foreground spawn waits; read-only spawns in one round are prestarted together, except in plan mode or ask autonomy. `background=true` returns an id. `resume_id` continues a finished child. The report is capped at 6_000 characters, wrapped as untrusted data; the transcript stays behind a handle. Worker writes are confined to the desk workspace and `workspaceRoots`, and overlapping writable roots take a lock. At the step cap the child is forced into a tool-less summary rather than killed; the cost cap is a hard stop. Approval cards publish on the parent run, labelled with the child. — [subagents.py module docstring, `CHILD_BLOCK`, `child_modes`, `BUILTIN_ROLES`](backend/personal_os/subagents.py); [llm.py subagent defaults](backend/personal_os/llm.py); [app.py `prestart` call](backend/personal_os/app.py)
- **Subagents — cannot.** `CHILD_BLOCK` always drops memory writers, todos, `propose_plan`, desk ask/done/deliver/start, `schedule_task`, `cancel_scheduled_task`, workflow tools, `skill_draft`, `skill_revise`, `mcp_tool_search`, shortcuts, `open_page`, and Gmail send/draft/modify. Danger `plan`, `schedules`, and `external` are dropped except file and shell tools, which stay confined to a root. Spawn tools are not offered at max depth. A child cannot ask the user. — [subagents.py `CHILD_BLOCK`](backend/personal_os/subagents.py)
- **Subagents — partial.** User-authored role markdown is parsed and stored by `AgentDefs` (`save`, `approve`, `delete`). Built-ins do not need approval. The Library screen for those definitions was not opened. Boot recovery of in-flight children was not traced; `stop_tree` and `halt` exist. — [subagents.py `AgentDefs`, `parse_def`](backend/personal_os/subagents.py)
- **Workflows — shipped.** `workflows.register` adds `workflow_list`, `workflow_run`, `workflow_resume`. A definition is JSON, or YAML if PyYAML imports: name, params, steps (`tool`, `agent`, or `fan_out`), `needs`, optional `approval: required`, `when`. Templates are `{{param}}`, `{{step_id.result}}`, and inside a fan-out `{{item}}` / `{{index}}`. Nothing is evaluated. `validate` checks ids, dependencies, and that tools exist. A run starts only after the user approves `plan_digest` (sha256 of canonical definition plus params). Editing the definition invalidates a run still waiting. Each step is a `workflow_steps` row. Tool steps go through the toolbox (modes, taint, idempotency). A done step is not run again; resume starts at the first step that is not done. Agent steps spawn subagents. A failed step stops dependents; independent steps still finish. `workflow_run` from chat or from a job only records `awaiting_approval` (job runs are tagged `source=job`). `workflow_resume` is refused when `proposal_only`. Steps may not call `workflow_run`, spawn, desk tools, `schedule_task`, or `todo_write` (`TOOL_BLOCK`). Max 40 steps. — [workflows.py module docstring, `TOOL_BLOCK`, `workflow_run`](backend/personal_os/workflows.py)
- **Commands — shipped, light tier.** `commands.register`. A command is markdown frontmatter (`name`, `description`, `subtask`, `role`) plus a template. Only `$ARGUMENTS` and `$1`..`$n` expand. No shell or file reads at template time. `subtask: true` runs the filled prompt as a child (default role researcher) and returns its report; otherwise the text is instructions for the current reply. — [commands.py](backend/personal_os/commands.py)
- **Per-job allowlists — shipped.** `jobs.allowed_tools`: NULL means inherit every tool; a JSON list narrows. `_launch_job` writes `off` into the job conversation’s `settings.tools` for every tool not on the list (and, for a dry run, for every non-read-only tool). Tools omitted from that map keep the user’s modes, so the list cannot turn a globally off tool on. Unknown names are 400. Tools that book future unattended work are rejected even if listed. Seeded jobs set lists at create time; the seeder skips names that already exist, so older rows stay NULL. `POST /jobs/{id}/dry_run` sets `input.dry_run`, prefixes `DRY_RUN_HINT`, stays proposal-only, is hidden from the away list, and is not counted as a failure. — [jobs.py `FIELDS`, `SEED_JOBS`](backend/personal_os/jobs.py); [app.py `_launch_job`, `_check_allowed_tools`, `dry_run_job`](backend/personal_os/app.py)
- **Run history — shipped.** `GET /jobs/{id}/runs` (default 50, comments say 200 max) returns status including a derived timed-out, duration, cost, tool counts, and proposal counts via `job_history.summarize_run` and `RunStore.of_job`. `GET /jobs/{id}/stats?days=30` and `GET /jobs/{id}/runs.csv` exist. The client exposes `runs`, `dryRun`, and CSV download. The cross-job inbox feed is still the last 72 hours, not this history. — [app.py `job_runs`, `job_stats`, `job_runs_csv`](backend/personal_os/app.py); [api.ts](src/renderer/src/lib/api.ts); [types.ts `JobRunRecord`](src/shared/types.ts)
