# Tool permissions and human approval

As of 2026-10-02. Primary docs only. Products named because the comparison needs them. Where two official pages disagree, both are cited.

## What permission modes do leaders ship?

### Takeaway
Leaders ship a small set of session modes (ask, auto-accept edits, plan, classifier auto-approve, deny-unless-allowlisted, skip prompts) and, separately, durable allow / ask / deny rules. “Always” is usually a saved rule, not a sixth mode. Plan-only and skip-all are real modes, and skip-all is fenced.

### Cited Findings
- Claude Code modes, config value in parentheses: Manual (`default`, alias `manual` from v2.1.200), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions`. Manual auto-runs reads only. `acceptEdits` also auto-runs in-workspace file edits and common filesystem commands (`mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed`, and the PowerShell equivalents `Set-Content`, `Add-Content`, `Clear-Content`, `Remove-Item`). Plan reads and explores and does not edit source until the plan is approved. Auto runs actions after a classifier check. `dontAsk` runs only pre-approved tools and auto-denies the rest. `bypassPermissions` skips prompts. Shift+Tab cycles `default` → `acceptEdits` → `plan`; `dontAsk` is never in the cycle; `bypassPermissions` appears only after it was enabled at launch. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes), [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude Code rule buckets are `permissions.allow`, `permissions.ask`, and `permissions.deny`. Allow skips the prompt, ask forces a prompt, deny blocks. The same “Yes, don’t ask again” choice is not one persistence scope: a Bash approval is saved permanently per repository and command; a file-modification approval lasts until the session ends and is not written to the settings file. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude Code Desktop scheduled tasks each have their own permission mode, chosen in the task’s instructions picker. Cloud routines have no permission prompts and run autonomously. `/loop` inherits the open session’s mode. If a Desktop task is in Manual and lacks permission, the run stalls and the session stays open for a later answer. MCP tools marked `requiresUserInteraction` prompt on every call and do not offer always-allow. — [Schedule recurring tasks in Claude Code Desktop](https://code.claude.com/docs/en/desktop-scheduled-tasks)
- Claude Code on the web cloud sessions offer Accept edits, Plan, and Auto. Accept edits there corresponds to `default`, because cloud sessions pre-approve file edits. Bypass is not available. Remote Control sessions offer Manual, Accept edits, and Plan, not Auto or Bypass. The Cowork tab does not use these modes and has its own, documented elsewhere. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Approving a Claude Code plan exits plan mode. The choices are: switch to auto (or, if auto is unavailable, auto-accept edits; if the session was started with bypass available, switch to bypass for the session); approve and review each edit; or stay in plan mode. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Codex separates sandbox mode from approval policy. Sandbox values in current docs: `read-only`, `workspace-write`, `danger-full-access`. Approval values still described on the developers site: `on-request`, `never`, `untrusted`, and a granular object (`sandbox_approval`, `rules`, `mcp_elicitations`, `request_permissions`, `skill_approval`). Who reviews an eligible prompt is `approvals_reviewer`: `user` (default) or `auto_review`. Presets: Auto is `workspace-write` + `on-request`; read-only browsing is `read-only` + `on-request`; CI read-only is `read-only` + `never`; `--yolo` / `--dangerously-bypass-approvals-and-sandbox` is no sandbox and no approvals. `/permissions` switches to read-only for chat or plan without edits. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security), [Codex rules](https://developers.openai.com/codex/rules)
- ChatGPT Learn, fetched the same day, says Codex and ChatGPT Work no longer support `approval_policy = "untrusted"` and that the retired value can prevent the client from starting. Replacement for interactive read-only is `sandbox_mode = "read-only"` plus `approval_policy = "on-request"`. A stricter per-project substitute is `trust_level = "untrusted"` under `[projects."<path>"]` with no explicit approval policy: commands then require approval unless an execution-policy rule allows them, and project-local configuration is disabled. — [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security); contradicted on the `untrusted` value still being valid by [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security). The CLI change is the merged 2026-08-20 change that removes `untrusted` from the CLI, config schema, and MCP tool interface and fails startup if the setting remains. — [Retire the untrusted approval policy](https://github.com/openai/codex/pull/39630)
- ChatGPT desktop permission modes, as far as the non-tabbed page text goes: Ask for approval (always available; work inside the workspace, pause before leaving it), Approve for me (settings label Auto-review; must be turned on before it appears; same sandbox, boundary crossings go to automatic review), and Full access (also opt-in in Settings > General). Enabling a mode does not select it. — [Permissions](https://learn.chatgpt.com/docs/permission-modes)
- ChatGPT Computer Use asks before it can use an app. The user can choose Always allow for later tasks, or answer for the current ask. ChatGPT may also ask before sensitive or disruptive actions. App approval is separate from macOS Screen Recording and Accessibility, and separate from file and shell sandbox settings. Admins can restrict which apps are usable and whether approvals can be saved. — [Computer Use](https://learn.chatgpt.com/docs/computer-use)
- Cursor Run Modes, Settings > Agents > Approvals & Execution: Auto-review (allowlisted calls run immediately; other shell commands run in the sandbox when they can; calls that cannot use the sandbox go to a classifier), Allowlist (allowlisted actions run; sandbox optional; no classifier), Run Everything (every tool call, no sandbox, no classifier). Ask Every Time was deprecated in Cursor 3.5 on 2026-05-22; an empty allowlist is the replacement. Run in Sandbox was folded into Allowlist with sandboxing. Auto-review shipped as the recommended default in 3.6 on 2026-05-29. Browser Protection, File-Deletion Protection, and External-File Protection can still require approval when a mode would otherwise run automatically. — [Run Modes](https://cursor.com/docs/agent/security/run-modes)
- OpenAI Agents SDK (Python) is not a product mode switch. A tool opts into approval with `needs_approval=True` or an async predicate. Local `ShellTool` and `ApplyPatchTool` are opt-in: `needs_approval` defaults to `False`, and an `on_approval` callback alone does not enable approval. Decisions are approve or reject, with `always_approve` / `always_reject` sticky for that tool identity for the rest of the run. Hosted MCP uses `require_approval: "always"` or `"never"`. Local MCP servers take `require_approval`. There is no plan mode in this flow. — [Human-in-the-loop (Python)](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- The JS Agents SDK uses the same pause: `needsApproval` true or a function, `result.state.approve` / `reject`, and `{ alwaysApprove: true }` or `{ alwaysReject: true }` for the rest of the run. — [Human-in-the-loop (JS)](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)
- MCP does not define allow/ask/deny modes. Tools are model-controlled. The spec says there SHOULD always be a human in the loop who can deny a tool invocation, and clients SHOULD present confirmation prompts. Annotations are optional hints, not modes. — [MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### Inferences
- The comparable vocabulary is: ask-by-default, allow-by-rule, deny-by-rule, session-scoped grant, durable always-allow, plan-only, classifier-instead-of-human, and skip-prompts. Claude Code is the only one of these products that ships all of those as first-class controls. Codex and Cursor split “what the process can touch” (sandbox) from “when to ask” (approval policy or run mode). The Agents SDK ships only the pause/resume primitive and leaves modes to the app.
- “Skip” is never quite total. Claude `bypassPermissions` still prompts for explicit ask rules, org-forced connector asks, `requiresUserInteraction` tools, and critical-path `rm`/`rmdir`. Codex `never` still obeys the sandbox unless the sandbox is also `danger-full-access`.

### Gaps
- The ChatGPT permissions page is tabbed. The fetch returned the framing (Ask for approval, Approve for me, Full access) and not the per-mode tables, so exact auto-run sets for those three labels are not fully quoted here.
- Claude Code’s permission-modes page says Cowork has separate permission modes and shows no mode selector until an extra mode is enabled. Those Cowork modes were not fetched.
- Gemini CLI and GitHub Copilot’s coding agent were not fetched.

## How are rules evaluated?

### Takeaway
Claude evaluates deny, then ask, then allow, and specificity does not reorder that. Codex execution rules take the strictest match (`forbidden` over `prompt` over `allow`) and only govern commands outside the sandbox. MCP annotations are untrusted hints with pessimistic defaults. Cursor’s natural-language Auto-review instructions steer a classifier; its sandbox network deny list is the hard rule.

### Cited Findings
- Claude Code: “Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn’t change the order.” A broad deny such as `Bash(aws *)` blocks a narrower allow such as `Bash(aws s3 ls)`. A matching ask prompts even when a more specific allow also matches. A deny at any settings level cannot be allowed by another level, including `--allowedTools`. Managed settings are highest; user deny beats project allow and the reverse is also true. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- A bare Claude deny such as `Bash` or `Bash(*)` removes the tool from the model’s context. A scoped deny such as `Bash(rm *)` leaves the tool visible and blocks matching calls. `EndConversation` cannot be removed while any other tool remains, and an ask rule never prompts for it. Deny and ask accept tool-name globs (`*`, `mcp__*`). Allow globs are only valid after a literal `mcp__<server>__` prefix; `"*"`, `"B*"`, and `"mcp__*"` as allow rules are skipped with a warning. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude Bash patterns: `*` matches any character sequence, including spaces. A trailing ` *` (space before the star), as in `Bash(ls *)`, requires a word boundary, so it matches `ls -la` and not `lsof`. `Bash(ls*)` matches both. Compound commands split on `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines; every subcommand must match. Approving a compound command saves up to five separate rules, one per subcommand that needed approval, not one rule for the whole string. Wrappers stripped before matching: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, zsh `noglob`, and bare `xargs` with no flags. `direnv exec`, `npx`, and `docker exec` are not stripped. `watch`, `setsid`, `ionice`, `flock`, and `find -exec` / `find -delete` cannot be auto-approved by a prefix rule. Deny and ask match past any leading environment assignment; allow matches only past a built-in set of known-safe assignments. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude Read and Edit rules use four anchors: `//` filesystem absolute, `~/` home, `/` relative to the settings source (not the filesystem root), and `./` or a bare path relative to the current directory. `*` is one path segment; `**` crosses directories. Allow `Edit(src/**)` matches only the top-level `src`; the same pattern as deny or ask matches a `secrets`-style directory at any depth. A `Read` deny also blocks Edit and Write on that path (edits since v2.1.208, writes since v2.1.228). Those path rules also apply to recognized Bash file commands such as `cat` and `sed`, not to a Python or Node script that opens files itself. Symlinks: an allow matches only if both the link and the target match; a deny matches if either matches. `WebFetch(domain:…)` matches the hostname, case-insensitive; `*.example.com` matches subdomains but not the apex; a wildcard elsewhere matches only one label, so `example.*` does not match `example.evil.com`. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude parameter rules `Tool(param:value)` exist for deny and ask on a top-level scalar only. They cannot target `command`, `file_path`, `url`, and the other primary content fields; `Bash(command:rm *)` is ignored. Allow rules do not use this parameter form. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude hooks do not override deny or ask. A PreToolUse `"allow"` still loses to a matching deny or ask, to org connector tools set to `ask`, and to MCP tools marked `requiresUserInteraction`. A hook that exits 2 blocks before permission rules run, so it can stop a call an allow rule would have permitted. With the Bash sandbox and `autoAllowBashIfSandboxed` left at its default `true`, a bare `Bash` ask rule does not prompt for sandboxed commands, except in plan mode. Content-scoped ask rules such as `Bash(git push *)` still prompt. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude auto mode decision order, first match wins: (1) allow, ask, and deny rules, except protected-path writes and critical-path `rm`/`rmdir` still go to the classifier, and org-ask connectors plus `requiresUserInteraction` MCP tools prompt anyway; (2) read-only actions and working-directory edits are auto-approved, except protected paths; (3) everything else goes to the classifier; (4) a block is returned to Claude, usually as the fixed text `Blocked by classifier` from v2.1.208. On entering auto mode, broad allows are dropped for that mode only: `Bash(*)`, `PowerShell(*)`, wildcarded interpreters, package-manager run commands, `Agent` allows, and `Monitor` allows (the Monitor drop is v2.1.236+). Narrow rules such as `Bash(npm test)` stay. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude built-in read-only Bash commands run without a prompt in every mode unless an ask or deny names them. The set includes `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, and read-only `git`, and it is not configurable. Unparsed commands and commands longer than 10,000 characters prompt. A `cd` plus `git` in another directory prompts because hooks in that directory could run. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude project `permissions.allow` and `additionalDirectories` in `.claude/settings.json` apply only after the workspace trust dialog. Deny and ask apply without that trust. In `-p`, no dialog appears and those allow rules stay ignored. — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Codex `prefix_rule` patterns are ordered argv tokens, not shell globs. A list element is an alternative at that position. `decision` defaults to `allow`. If several rules match, the strictest wins: `forbidden` > `prompt` > `allow`. `match` and `not_match` are checked when the file loads. Rules apply to commands run outside the sandbox. Linear `bash -lc` / `bash -c` scripts of plain words joined by `&&`, `||`, `;`, or `|` are split with tree-sitter and each command is judged; the strictest result wins, so an allow for `git add` does not allow `git add . && rm -rf /`. Redirection, substitution, assignments, wildcards, and control flow are not split; the whole `bash -lc` invocation is matched as one command. Project `.codex/rules/` loads only when that project layer is trusted. Admins can put restrictive prefix rules in `requirements.toml`. — [Codex rules](https://developers.openai.com/codex/rules)
- Codex network domain policy, when the network proxy is on: exact host, `*.example.com` for subdomains but not the apex, `**.example.com` for apex plus subdomains, `deny` wins over `allow`. `allow_local_binding` defaults false. A hostname that resolves to a private address stays blocked even if the name is allowlisted. Failed DNS lookups are blocked. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security)
- Codex: “Destructive app/MCP tool calls always require approval when the tool advertises a destructive annotation, even if it also advertises other hints (for example, read-only hints).” — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security). The ChatGPT Learn copy of that page says the opposite parenthetical: a destructive annotation always requires approval “unless the tool advertises a read annotation, which takes priority.” — [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security)
- Codex Auto-review evaluates only actions that already need approval (sandbox escalations, blocked network, `request_permissions`, side-effecting app and MCP calls). In-sandbox actions are not sent to the reviewer. The reviewer can proceed on low and medium risk when policy allows, denies critical risk, and requires enough user authorization plus no matching deny for high risk. Prompt-build, review-session, and parse failures fail closed. A timeout is reported separately and the action does not run. Managed `guardian_policy_config` outranks a local `[auto_review].policy`. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security)
- Cursor Auto-review reads plain-English `allow_instructions` and `block_instructions` from `~/.cursor/permissions.json` and `<project>/.cursor/permissions.json`. Both files apply if both exist. A team dashboard configuration, when defined, takes priority and the local files are ignored. The reference page says those sentences are steering: an allow instruction still goes through the safety check, and a block instruction can still be approved when Cursor insists. `terminalAllowlist` and `mcpAllowlist` in that file override the in-app allowlists; defining one does not freeze the other. `permissions.json` takes effect only when a Run Mode is on. `autoRun` is consulted only in Auto-review. — [Run Modes](https://cursor.com/docs/agent/security/run-modes), [permissions.json reference](https://cursor.com/docs/reference/permissions)
- Cursor `sandbox.json` network policy: `deny` is highest priority and blocks even if the same pattern is also in `allow`. `networkPolicy.default` `"deny"` wins over `"allow"` when files are merged. Private IPv4, IPv6, and the cloud metadata address are blocked by default. Team-admin policy and hardcoded rules cannot be weakened by either file. — [sandbox.json reference](https://cursor.com/docs/reference/sandbox)
- MCP `ToolAnnotations`, as stated by the protocol blog on 2026-03-16 for the interface shipped in spec revision 2025-03-26: `readOnlyHint` default false, `destructiveHint` default true, `idempotentHint` default false, `openWorldHint` default true, plus optional `title`. A tool with no annotations is treated as non-read-only, potentially destructive, non-idempotent, and open-world. Every property is a hint. Clients must treat annotations as untrusted unless the server is trusted. The 2025-11-25 tools page repeats that clients MUST consider tool annotations untrusted unless they come from trusted servers, and that clients SHOULD prompt before sensitive operations and show tool inputs before the call. The blog’s example client uses, which it presents as examples rather than required behavior: skip confirmation when `readOnlyHint` is true, warn when `destructiveHint` is true, retry when `idempotentHint` is true, scrutinize output when `openWorldHint` is true. — [Tool annotations blog, 2026-03-16](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/), [MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- Agents SDK callable `needs_approval` fails closed: missing, empty, whitespace, malformed JSON, non-object JSON, or `NaN` / `Infinity` skips the callable and requires manual approval. A per-call decision already stored for that call ID skips a new prompt. Sticky always-approve for hosted MCP is keyed by `server_label` plus tool name, and only when both are non-empty. — [Human-in-the-loop (Python)](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- Claude’s own non-MCP flag for “must interact” is `_meta["anthropic/requiresUserInteraction"]`. In `dontAsk` those tools are denied even if an allow rule matches, because the approval card would have nobody to answer it (v2.1.199+). — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)

### Inferences
- Three different “deny wins” mechanisms are in production: Claude’s ordered deny-then-ask-then-allow scan; Codex’s severity sort across all matching prefix rules; Cursor’s sandbox network deny list. They are not interchangeable. Claude will not let a specific allow punch a hole in a broad deny. Codex will let a `forbidden` rule beat an `allow` rule, which is the same outcome with a different algorithm. Cursor’s classifier instructions explicitly do not have that guarantee.
- Annotation precedence is not settled even inside OpenAI’s own docs. One page says a destructive hint forces approval even beside a read-only hint. The other says a read annotation outranks destructive. A comparison should not treat “destructiveHint forces a prompt” as a single cross-product rule.

### Gaps
- The numbered steps under “Cursor checks each call in this order” did not survive the Run Modes fetch, so the exact Auto-review step list is not quoted. The mode table on that page is the source for what runs without asking.
- `permissions.json` and `sandbox.json` field behavior above is from the official reference pages as returned in search extracts, not from a second full-page fetch of those two references. The Run Modes page, which was fetched in full, independently confirms the file locations, the merge, team priority, and that `allow_instructions` / `block_instructions` are plain-English classifier guidance.
- No fetched MCP schema file newer than the 2025-11-25 tools page was opened. The March 2026 blog is the source for the four booleans and their defaults. A generated Rust schema page mentioned protocol date 2026-07-28 and the same fields; that page was not treated as the spec.
- The five open annotation proposals listed on the March 2026 blog (`unsafeOutputHint`, `secretHint`, `trustedHint`, and two broader drafts) were still drafts or proposals as of that post. Their later status was not re-checked.

## How does approval survive restart, and how is “always allow” persisted?

### Takeaway
Durable always-allow is a file the client writes: Claude’s `.claude/settings.local.json` for shell prefixes, Codex’s `~/.codex/rules/default.rules`, Cursor’s `permissions.json`, and ChatGPT’s Computer Use app list. Session-only grants and in-run sticky approvals die with the session unless the app serializes them. MCP itself stores nothing.

### Cited Findings
- Claude Code writes a permanent Bash “Yes, don’t ask again” rule to `.claude/settings.local.json` at the git repository root, resolving worktrees to the main checkout (v2.1.211+). It then applies to later sessions anywhere in that repository, including subdirectories and worktrees. A file-edit approval is not saved; it lasts until the session ends. Outside a git repo, or when the repo root is the home directory, the rule is saved in the directory where Claude Code was started. Before v2.1.211 the rule was always saved in the starting directory. Generated path rules escape gitignore metacharacters so the saved rule is literal (v2.1.202+). — [Configure permissions](https://code.claude.com/docs/en/permissions)
- Claude settings that survive restart: user `~/.claude/settings.json`, project `.claude/settings.json` (allow rules wait for workspace trust), local `.claude/settings.local.json`, and managed settings. Workspace trust is saved per git root. Trust started in the home directory is held for the current session only and is not written to disk. A Desktop mode picked in the mode selector is remembered per folder and outranks `defaultMode` for that folder. Plan is the exception: it applies to the current session only. The one-time bypass-permissions responsibility dialog is saved to user settings so it is not shown again. Declining exits. Non-interactive mode shows no dialog, and `--bg` is refused until an interactive session has accepted it. — [Configure permissions](https://code.claude.com/docs/en/permissions), [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude Code Desktop scheduled tasks: “always allow” on a Run now prompt is reused by later runs of that same task. The task detail page has an Always allowed panel that can revoke them. Allow rules from `~/.claude/settings.json` also apply. The on-disk prompt file is `~/.claude/scheduled-tasks/<name>/SKILL.md` (or under `CLAUDE_CONFIG_DIR`). That file’s frontmatter holds `name` and `description` only. The docs say schedule, folder, model, and enabled state are not in the file. They do not say where the permission mode or the Always allowed set is stored. Tasks themselves persist across app restarts, but a run only starts while the app is open and the computer is awake. On wake, at most one catch-up run is started for the most recent miss inside seven days. — [Schedule recurring tasks in Claude Code Desktop](https://code.claude.com/docs/en/desktop-scheduled-tasks)
- Claude auto-mode “don’t push” style boundaries are re-read from the transcript. They are not saved as rules, and compaction can drop them. A deny rule is the durable form. Classifier network verdicts are cached for a host and port and are dropped when the permission mode or the rules change. In non-interactive and Agent SDK sessions a classifier deny is reused for the rest of the run. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- `permissions.defaultMode: "auto"` does not take effect from project or local settings as of v2.1.142; it has to be in `~/.claude/settings.json` or managed settings. Other mode values can be set in any settings file, with managed winning. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Codex: adding a command to the TUI allow list writes a `prefix_rule` into the user layer `~/.codex/rules/default.rules`, so later runs skip the prompt. The rules page says to restart Codex after creating a rules file. Codex reads `rules/` under every active config layer at startup. Smart approvals, on by default, may propose a prefix during an escalation; the user is told to review the prefix before accepting. Sandbox and approval defaults live in `config.toml` (`approval_policy`, `sandbox_mode`, `approvals_reviewer`) and in named profiles. — [Codex rules](https://developers.openai.com/codex/rules), [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security)
- ChatGPT Computer Use Always allow is removed from Settings > Computer Use. On Windows the persistent list is `[computer_use.windows] always_allowed_app_ids` in `$CODEX_HOME/config.toml`. Apps not in the list prompt. Older `$CODEX_HOME/computer-use/config.toml` allow-list entries are migrated; that older file’s `denied` list is not part of the current schema. Admins can disable Computer Use with `[features].computer_use = false` in `requirements.toml`, which is separate from the local allow list. The docs say administrators can restrict whether approvals can be saved, and point at a managed-controls page that was not fetched. — [Computer Use](https://learn.chatgpt.com/docs/computer-use)
- Cursor allowlists and Auto-review instructions persist in `~/.cursor/permissions.json` and `<project>/.cursor/permissions.json`. Sandbox reach persists in `sandbox.json` at the same two scopes. Team dashboard settings outrank both. — [Run Modes](https://cursor.com/docs/agent/security/run-modes)
- Agents SDK sticky `always_approve` / `always_reject` live in `RunState`. They survive `to_json` / `from_json` and `to_string` / `from_string` for that same paused run. They are not described as a user-level allow file. `RunState.from_json` does not authenticate the snapshot or the person submitting it. The docs tell apps to keep the snapshot in server storage, show the reviewer only tool details plus opaque ids, and apply approve/reject only to the server-owned pending items. A schema check or tool-call fingerprint does not authenticate a snapshot. Per-call approvals are scoped to the call ID and do not stick. — [Human-in-the-loop (Python)](https://openai.github.io/openai-agents-python/human_in_the_loop/)
- MCP has no approval store. Persistence is entirely a client choice. — [MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### Inferences
- “Always allow” that survives restart is a prefix or tool rule in a config file the product owns, keyed either to a repo (Claude Bash rules, Cursor project file) or to the user (Codex default.rules, Claude user settings, Computer Use app ids). Session-scoped always is a different product decision: Claude uses it for file edits, and the Agents SDK uses it only inside one run’s serialized state.
- A paused Agents SDK run can survive process restart only if the application stored `RunState` and resumes the same agent. The SDK does not do that by itself, and it warns that the blob is capability-bearing and must not be accepted from the client.

### Gaps
- Official Desktop scheduled-task docs do not say the on-disk path of the per-task permission mode or the Always allowed set. `SKILL.md` is explicitly not the store for schedule, folder, model, or enabled state. Permission mode is absent from both the “stored in frontmatter” list and the “not in this file” list.
- No Codex sentence was found that offers a session-only allow which does not write `default.rules`. The documented TUI allow-list action writes the user rules file.
- Cursor’s in-app allowlist editor, as opposed to `permissions.json`, was not fetched as its own page. The reference extract says that once the file defines an allowlist, the in-app editor for that type becomes read-only.

## What review exists before external side effects?

### Takeaway
Shell, out-of-workspace files, and network are the reviewed boundaries. Mail and calendar are not special-cased in the pages fetched; they show up as MCP, connector, or Computer Use actions, and those still ask when the tool is marked interactive, destructive, or outside an allow rule. Read-only local inspection is the thing most products let through.

### Cited Findings
- Claude Code Manual mode asks before most file edits, shell commands, and network. Reads inside the working directory and `additionalDirectories` do not ask. Bash still asks except the built-in read-only set. WebFetch is a separate tool with domain allow rules; a WebFetch allow does not stop Bash from using `curl` or `wget` if Bash is allowed. The docs say argument-shaped Bash allows such as `Bash(curl http://github.com/ *)` are fragile because of flag order, `https`, redirects, and variables, and they recommend denying `curl`/`wget` and using WebFetch domain rules instead. — [Configure permissions](https://code.claude.com/docs/en/permissions), [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude protected paths are never auto-approved except in `bypassPermissions` and in plan sessions where bypass is available. The set includes `.git`, `.claude` (except `.claude/worktrees`), `.vscode`, `.idea`, shell rc files, `.npmrc`, `.mcp.json`, `.claude.json`, and others listed on the permission-modes page. An allow rule does not pre-approve those writes. In modes that prompt, a `.claude/` write can be approved for the rest of the session via “allow Claude to edit its own settings for this session.” Critical-path `rm`/`rmdir` (filesystem root, top-level directories, home, the working directory and its parents, and globs under a possibly empty variable) cannot be approved by an allow rule or by a PreToolUse `"allow"`. In `bypassPermissions` those removals still ask. PowerShell `Remove-Item` against system paths or a bare `*` is denied in every mode without asking. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude auto mode’s classifier blocks, among other defaults: `curl | bash`, sending sensitive data to external endpoints, production deploys and migrations, mass cloud deletion, IAM or repo permission grants, force push, destroying files that existed before the session, `terraform destroy` and similar, writing to a secret manager, changing DNS or TLS, merging a PR no human has approved, posting a comment that is itself an automation command, printing a live credential, and opening a tunnel or reverse shell. It allows local file operations in the working directory, dependency installs from lockfiles, read-only HTTP, and reading `.env` to send credentials to the matching API. Pushing the current repository is allowed unless the content or the target trips another rule. Conversation boundaries (“don’t push”) are also blocks, until lifted or compacted. Subagent `permissionMode` frontmatter is ignored; each subagent action is classified, the task description is classified before spawn (v2.1.178+), and the action history is classified when the subagent returns. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude org policy can set a claude.ai connector tool to `ask`. Allow rules then do not apply. The prompt still appears in `auto` and `bypassPermissions`. In `dontAsk` the call is denied. Connector tools are named `mcp__claude_ai_<server>__<tool>`. Scheduled-task runs that hit `requiresUserInteraction` stall on every call. — [Configure permissions](https://code.claude.com/docs/en/permissions), [Schedule recurring tasks in Claude Code Desktop](https://code.claude.com/docs/en/desktop-scheduled-tasks)
- Codex default local sandbox: network off, writes limited to the active workspace. `workspace-write` keeps network off unless `sandbox_workspace_write.network_access = true`. Auto (`on-request`) asks to edit outside the workspace or to run commands that need network. Writable roots still keep `.git` (and a gitdir pointer target), `.agents`, and `.codex` read-only, recursively. Web search defaults to a cached index, not live fetch; `--yolo` or full-access switches web search to live unless configured otherwise. App and connector tools that advertise side effects can require approval even when the action is not a shell command or a file change. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security), [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security)
- Codex cloud (legacy, on the developers page): setup may use the network, then the agent phase is offline unless internet is enabled for that environment. Secrets exist only during setup and are removed before the agent phase. The Learn page points current Codex Cloud credential handling at a different page and keeps the two-phase description for legacy cloud. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security), [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security)
- ChatGPT Computer Use can act only in apps the user allows, and it asks before using an app. Sensitive or disruptive actions may ask again. It cannot automate terminal apps or ChatGPT itself, cannot approve OS security prompts, and cannot authenticate as an administrator. File edits and shell commands still follow the task’s sandbox and approval settings. GUI changes may not show up in the review pane until they are saved and tracked. macOS locked use can continue after the screen locks only if the user enabled it; the unlock is scoped to an active Computer Use turn, covers the displays, and relocks if local input is detected. Windows Computer Use stays in the foreground and cannot run in the background on the same session. — [Computer Use](https://learn.chatgpt.com/docs/computer-use)
- Auto-review does not replace Computer Use app-level prompts. The Learn Auto-review description, from the search extract of that page, says the reviewer does see shell escalations, blocked network, edits outside writable roots, MCP or app calls that require approval because of annotations or approval mode, and Computer Use access to a new website or domain. App approvals still go to the user. With `approval_policy = "never"`, `:danger-full-access`, or `--yolo`, an action can avoid creating the boundary-crossing request that review needs. — [Auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review), [Computer Use](https://learn.chatgpt.com/docs/computer-use)
- GPT-6 Astra safety monitoring, on the Learn approvals page, can pause a task after the triggering activity. It does not replace sandboxing or per-action review. An action that automatic review approved can still sit inside a task that monitoring later pauses. CLI and mobile do not get the findings-and-resume flow; the task ends. — [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security)
- Cursor: sandboxed shell can read and write the workspace, cannot freely read protected paths (`.git/config`, `.git/hooks`, `.vscode`, `.cursorignore`, and sensitive Cursor config), and has network blocked until a network mode opens it. Commands that need full network, writes outside the workspace, or privileged operations skip the sandbox and go to the classifier in Auto-review, or to the user. If a sandboxed command fails because of the sandbox, the agent may rerun it outside, and that rerun is classified. File-Deletion Protection blocks automatic deletes, including `rm`. External-File Protection blocks automatic create, modify, or delete outside the workspace. Browser Protection blocks automatic Browser tools. The classifier can make read-only `ReadFile`, `Grep`, `Glob`, and `ListDir` calls while judging a command. If the agent disagrees with a block, Cursor shows an approval prompt. The page says the classifier is not a security boundary. — [Run Modes](https://cursor.com/docs/agent/security/run-modes)
- The older Cursor agent-security page, seen as a search extract and not re-fetched, says reads and code search do not require approval, workspace edits do not require approval except configuration files, terminal commands need approval by default, every MCP connection needs approval, and after the connection each tool call still needs approval unless it is on an MCP allowlist. `.cursorignore` blocks agent access to listed files. — [Agent Security](https://cursor.com/docs/agent/security)
- Agents SDK examples put approval on `send_email` (predicate: subject contains “refund” in the documented sample) and on `cancel_order` (always). The API guide’s table says to pause before side effects such as cancellations, edits, shell commands, or sensitive MCP actions. Shell and apply-patch approval is still opt-in. Hosted shell environments do not support `needs_approval` or `on_approval`. — [Human-in-the-loop (Python)](https://openai.github.io/openai-agents-python/human_in_the_loop/), [Guardrails and human review](https://developers.openai.com/api/docs/guides/agents/guardrails-approvals)
- MCP’s security section says clients SHOULD prompt on sensitive operations and SHOULD show inputs before calling the server, to avoid exfiltration. Servers MUST validate inputs, enforce access control, rate-limit, and sanitize outputs. The March 2026 blog says a `readOnlyHint` from an untrusted server is not a reason to skip confirmation, and that exfiltration prevention belongs in network controls or a sandbox. It also describes a demonstrated chain that used a malicious calendar event description plus an MCP calendar server plus local code execution. That is an attack write-up, not a product approval rule for calendar writes. — [MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [Tool annotations blog, 2026-03-16](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

### Inferences
- External side effects are reviewed by class of mechanism, not by app name. Shell and network are first-class. Mail send and calendar write are reviewed only when they arrive as an MCP or connector tool, a Computer Use app, or an SDK tool the developer marked `needs_approval`. Nothing fetched defines a built-in “sending mail” or “creating an event” mode that is stricter than a generic side-effecting tool.
- Two review layers show up repeatedly: a deterministic boundary (sandbox, deny rule, protected path) and a model reviewer that runs only after that boundary says the action is not already allowed. Claude auto mode, Cursor Auto-review, and Codex `approvals_reviewer = "auto_review"` all work that way. Skipping the boundary also skips the reviewer.

### Gaps
- No official help page fetched here names Gmail, Google Calendar, or a similar connector and specifies the confirmation copy, the always-allow scope, or whether a send can be undone. Claude’s connector “ask” policy is the closest product control, and it is described generally.
- The Cursor agent-security statements about config-file edits and per-MCP-call approval are from a search extract of a page that may predate Run Modes. They are included because they are specific, and they are not restated as if the Run Modes page had repeated them.
- The Auto-review page’s list of what the reviewer sees (including a new Computer Use website) is from a search extract. The fetched Computer Use page independently says app approvals are not replaced by Auto-review.

## What do official docs treat as the safe default for unattended runs?

### Takeaway
Unattended does not mean skip every check. The documented safe patterns are: a sandbox that stays on, an allowlist that denies everything else, or a classifier inside a workspace boundary. Full prompt bypass is documented only for an isolated container or an explicit danger flag, and cloud agents that cannot ask simply run with no human checkpoint.

### Cited Findings
- Claude Code’s built-in starting mode depends on how it is launched. `claude -p` and the Agent SDK start in `default` (Manual). Pro, Max, and Team interactive terminal and VS Code sessions start in `auto` from v2.1.228 (macOS, Linux, WSL) and v2.1.233 (native Windows), unless feature flags could not be fetched, this is the first session after install or upgrade, or `disableAutoMode` is set. Enterprise plans and Claude Console API keys start in Manual. Amazon Bedrock, Google Cloud’s Agent Platform, Microsoft Foundry, and signed-in Claude apps gateway sessions start in Manual even though auto can be selected. If auto is selected but unavailable, the session starts in Manual. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude’s own “common setups” table: review every action with Manual; explore with `plan`; hands-off with a classifier with `auto`, called the built-in starting mode on Pro, Max, and Team, and described as not a safety guarantee; CI with an exact allowlist using `claude -p … --permission-mode dontAsk --allowedTools …`; fully unattended with `claude -p … --dangerously-skip-permissions` inside a container or VM, on Linux and macOS as a non-root user. In that `-p` bypass run, calls that would still have prompted are denied instead. Claude Code on the web ignores `dontAsk` and `bypassPermissions` from settings files. Bypass as root or under sudo is refused outside a recognized sandbox. The page says to use auto mode, not bypass, when the goal is fewer prompts with background checks. Admins can set `disableBypassPermissionsMode` or `disableAutoMode` to `"disable"`. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- `dontAsk` auto-denies anything that is not an allow rule, a built-in read-only Bash command, or a PreToolUse hook approval. It denies explicit ask rules, `AskUserQuestion`, org-ask connectors, `requiresUserInteraction` MCP tools, and critical-path removals. The session does not wait. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- A non-interactive Claude `-p` run with no `--permission-prompt-tool` has nothing to fall back to when auto mode’s classifier blocks. After 3 consecutive blocks or 20 total, the action does not run and Claude keeps working, including in subagents. The run is not stopped. Those thresholds are not configurable. — [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)
- Claude cloud routines: permission prompts are “No (runs autonomously).” Desktop scheduled tasks are “Configurable per task.” The Desktop page’s stall-avoidance instruction is to Run now once and choose always allow, not to turn on bypass. Manual mode stalls until a person answers. — [Schedule recurring tasks in Claude Code Desktop](https://code.claude.com/docs/en/desktop-scheduled-tasks)
- Codex launch recommendation: version-controlled folders get Auto (`workspace-write` + `on-request`); non-version-controlled folders get `read-only`. Depending on setup, Codex may also stay read-only until the directory is trusted. The documented non-interactive read-only combination is `--sandbox read-only --ask-for-approval never`. `codex exec --sandbox workspace-write` is the non-interactive edit path; `codex exec --full-auto` is a deprecated compatibility path that prints a warning. `never` disables prompts and still leaves the sandbox in force. Full access without prompts is `danger-full-access` or `--yolo`, labeled not recommended. Inside a container that cannot run the inner Linux sandbox, the docs allow `danger-full-access` and warn that a malicious project can then exfiltrate anything in the container, including Codex credentials. — [Agent approvals & security (developers)](https://developers.openai.com/codex/agent-approvals-security)
- ChatGPT desktop: “For most work, start with Ask for approval.” Approve for me and Full access are off until enabled in settings. Approve for me does not widen the sandbox. — [Permissions](https://learn.chatgpt.com/docs/permission-modes)
- The configuration reference, as extracted in search, says `on-failure` is deprecated and to use `on-request` for interactive runs or `never` for non-interactive runs. That page’s enum still listed `untrusted` on the developers host. The Learn approvals page says `untrusted` is retired and can prevent startup. — [Configuration reference](https://developers.openai.com/codex/config-reference), [Agent approvals & security (ChatGPT Learn)](https://learn.chatgpt.com/docs/agent-approvals-security)
- Cursor: “The safest useful setup for most people is Auto-review.” Run Everything is “you accept the risk and want zero prompts.” Cloud Agents do not use Run Modes. They run on their own machine and never ask for approval. If the Linux sandbox cannot be created, Cursor falls back to asking before commands. — [Run Modes](https://cursor.com/docs/agent/security/run-modes)
- MCP’s unattended stance is the opposite of a skip default: there SHOULD always be a human who can deny the call, and clients SHOULD confirm sensitive operations. The March 2026 blog tells client authors to keep safety guarantees in deterministic controls and to treat untrusted annotations as informational. — [MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools), [Tool annotations blog, 2026-03-16](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)
- The Agents SDK does not name an unattended default. Leaving `needs_approval` at its default means local shell and apply-patch run without a pause. Setting hosted MCP `require_approval` to `"never"` is documented for trusted servers. The pause-and-serialize path is the documented way to keep a human in a long-running side-effecting run. — [Human-in-the-loop (Python)](https://openai.github.io/openai-agents-python/human_in_the_loop/)

### Inferences
- “Safe unattended” in these docs means one of three things: (1) Claude `dontAsk` or Codex `read-only` + `never`, where anything not already allowed does not run and nobody is waiting; (2) Claude `auto` or Cursor Auto-review or Codex `auto_review`, where a second model reviews boundary crossings and a human is not in the loop for ordinary workspace work; (3) a container plus skip-prompts, which the docs treat as an isolation requirement rather than a safe mode. A Desktop scheduled task left in Manual is explicitly the unsafe unattended choice, because it stalls.
- Products that cannot show a prompt do not queue one forever. Claude `-p` denies the would-be prompt in bypass and, in auto, drops the blocked action and continues. Cursor cloud agents never ask. Claude cloud routines never prompt. Codex `never` does not ask and does not escalate. The Agents SDK pauses only if the application is there to resume it.

### Gaps
- GitHub issues claim that around Claude Code v2.1.206 Desktop scheduled tasks stopped inheriting `permissions.defaultMode`, fell back to Manual, and could not set the mode through the create-task tool. Those are issue reports, not docs, and they were not used as product behavior. The official page does say each task has its own mode and that Manual stalls.
- No fetched page states Cursor’s default Run Mode for an existing user who never opened Approvals & Execution, as opposed to the recommendation and the 2026-05-29 changelog line that Auto-review shipped as the recommended default.
- Whether Codex `approval_policy = "never"` combined with a `prefix_rule` of `prompt` or `forbidden` still prompts or still blocks was not spelled out beyond the granular policy, which can keep selected prompt categories interactive while auto-rejecting others.
