## What does the Today screen show, and what is the one-click brief?

### Takeaway
Today (`HomeView`) is a greeting, a quick-ask box, and a set of toggleable cards. The one-click brief is not a generated artifact: **Brief me** opens a new chat and sends a fixed prompt. A separate **Daily recap** is an LLM markdown note cached per calendar day.

### Cited Findings
- The page header is “Today” plus the local long date. Cards are gated by `homeModuleOn` and toggled from a “Show on Today” popover (or Settings). A missing `homeWidgets` key means on. Defaults turn off only the cowork and meetings cards; library, cowork, meetings, and activity views start hidden. — [HomeView.tsx](src/renderer/src/components/HomeView.tsx); [modules.ts](src/renderer/src/modules.ts); [llm.py](backend/personal_os/llm.py)
- Card list, in order: Agent inbox, Cowork desks, Daily recap, Calendar (next 48h), Todos, Health, Inbox (unread, 14 days, first 8), Google Tasks (first 8), Drive (recently modified, first 8), Upcoming meetings, Projects, Recently learned (first memories from the dashboard payload), Recent chats. Google cards show a Connect prompt when `google.connected` is false; Drive also offers Reconnect when `missing_scopes` contains `drive`. — [HomeView.tsx](src/renderer/src/components/HomeView.tsx); [modules.ts](src/renderer/src/modules.ts)
- `GET /dashboard` returns Google status, each module’s `today()`, projects with stats, `recent_memories` (6), `recent_conversations` (6), then, if connected, `calendar_events(2)`, `gmail_search("is:unread in:inbox newer_than:14d", 10)`, `tasks_list("@default")`, and `drive_files` only when the token has `drive.readonly`. Per-source failures land in `errors`, not a failed response. Module `today()` must not call Google. — [app.py `dashboard`](backend/personal_os/app.py); [modules/__init__.py](backend/personal_os/modules/__init__.py)
- Native todos on Today come from `TodosModule.today()`: open todos across all projects, sliced to 12, plus `todo_stats`. The card renders the first 8 of those with compact `TodoItem`s and an open/overdue count. Sort is the store default (`done`, null dues last, due, priority, `created_at DESC`), not urgency. — [modules/todos.py `today`](backend/personal_os/modules/todos.py); [todos.py `list`](backend/personal_os/todos.py); [TodosCard.tsx](src/renderer/src/features/todos/TodosCard.tsx)
- The Google Tasks card is a separate live read of the default task list, not the native todo table. Tasks sync defaults to enabled, so the two cards can show the same work when both widgets are on. — [HomeView.tsx](src/renderer/src/components/HomeView.tsx); [gtasks.py `DEFAULT_CONFIG`](backend/personal_os/gtasks.py)
- **Brief me** calls `newChat(null)` then `send` with: check calendar today and tomorrow, scan unread mail for replies, list open todos and flag overdue ones, end with the 3 things to do first, concise, with headers. The assistant then uses whatever tools that chat has. A seeded job, “Morning brief”, uses nearly the same prompt on cron `30 7 * * *` with a read-only allowlist (`current_time`, `calendar_events`, `calendar_get`, `gmail_search`, `gmail_read`, `todo_list`, `google_tasks_list`) and is created **disabled**. — [HomeView.tsx `brief`](src/renderer/src/components/HomeView.tsx); [jobs.py `SEED_JOBS`](backend/personal_os/jobs.py)
- Daily recap is `GET /recap`. Unless `force`, it returns the row saved for `YYYY-MM-DD`. Facts are chats and memories from the last 36 hours, up to 20 open todos, todo stats, project stats, calendar for the next 3 days, and up to 10 unread subjects. `generate_recap` asks for sections “Since yesterday”, “Today”, and “Suggested focus”, under 180 words, and forbids invented facts. Empty content if there is no API key. The card can regenerate (`force`) or hide for the session. — [app.py `recap`](backend/personal_os/app.py); [dashboards.py `RECAP_SYSTEM`](backend/personal_os/dashboards.py); [HomeView.tsx](src/renderer/src/components/HomeView.tsx)
- The quick-ask field sends Enter as a new chat and ⌘/Ctrl-Enter as `addTodo({ title })`. Page context handed to the assistant is today’s events, later events (10), open todos (ids and dues), and the first 1500 characters of the recap. Hints include “Block time for my todos”. — [HomeView.tsx](src/renderer/src/components/HomeView.tsx)
- Mail-watch counts are merged into the dashboard payload by `MailWatchModule.today()` from the local `thread_status` table, with no Google call. `HomeView` does not render that key. Planner `today()` returns `{}`. — [modules/mailwatch.py `today`](backend/personal_os/modules/mailwatch.py); [modules/planner.py `today`](backend/personal_os/modules/planner.py)

### Inferences
- “One-click brief” in the product is an attended chat turn. The unattended morning brief is the same idea only after the user enables the seed job, and that job cannot send mail or write calendar events (see the proposal section).
- Today’s todo list is a date/priority slice, even though urgency sort exists on the Todos page.

### Gaps
- Whether the Meetings card’s “take notes” flow is in scope was left alone beyond the fact that the card exists and defaults off.
- No measurement of how often the recap cache hits, or of how large the 48-hour calendar payload is.

## What can native todos, the week calendar, kanban boards, and mail do in the UI and via tools?

### Takeaway
All four surfaces are real in the UI and in the toolbox. Todos, boards, and the calendar grid are local or Google-backed CRUD. Mail is Gmail search plus compose, with reply tracking as a separate on-demand panel. External Google tools default to ask; in-app todo and board writes default to on.

### Cited Findings

#### Native todos
- Schema fields in use: id, project, title, notes, due (`YYYY-MM-DD` or null), priority 1–3, done, source, Google Tasks link (`external_id`, `remote_updated`, `synced_at`), calendar mirror link (`calendar_event_id`, `calendar_link`, `calendar_id`, `calendar_sig`), `repeat` JSON, `estimate_min`, trash columns. `Todos.update` accepts title, notes, due, priority, done, project_id, calendar link fields, repeat, and estimate_min. Completing an open todo that still has `repeat` spawns the next instance and clears `repeat` on the completed row. — [todos.py](backend/personal_os/todos.py)
- UI (`TodosView`): add with due, priority, project scope, and a repeat select (none / daily / weekly / monthly / yearly, `every: 1`, `mode: from_due`). Sort toggle Due vs Urgency. Each row can complete, edit, delete (trash), show a repeat badge and urgency number, set an estimate in minutes, and schedule onto Google Calendar. `PlannerPanel` (“Plan my day”) sits on this page. — [TodosView.tsx](src/renderer/src/components/TodosView.tsx); [TodoItem.tsx](src/renderer/src/components/TodoItem.tsx); [PlannerPanel.tsx](src/renderer/src/components/PlannerPanel.tsx)
- Tools, group `todos`, danger `writes` except the list: `todo_list` (open by default, project scope plus personal, `sort` `due|urgency`, rows include urgency, repeat, estimate), `todo_add`, `todo_update`, `todo_delete` (trash, 30-day restore note). Repeat args are `repeat_every`, `repeat_unit` (`day|week|month|year`), `repeat_mode` (`from_due|from_completion`). `estimate_min` is on add and update. `todo_write` is a separate plan artifact in `tools.py`, not a row in the todo table. — [modules/todos.py](backend/personal_os/modules/todos.py); [tools.py `todo_write`](backend/personal_os/tools.py)
- Default tool mode: `writes` is `on`, `external` is `ask`. — [tools.py `DEFAULT_MODE`](backend/personal_os/tools.py)
- Two-way Google Tasks sync (`TasksSync`) runs about every `intervalMinutes` (default 5, floor 60s) and on a debounced poke after local edits. `tasks_all` is a full uncached list (`showCompleted`, `showHidden`). Tombstones go first; then per-link local `updated_at > synced_at` vs remote `updated`. Recurrence is not a Google Tasks field, so the next spawned todo syncs as a new local task. — [gtasks.py](backend/personal_os/gtasks.py); [google.py `tasks_all`](backend/personal_os/google.py)
- `TodoCalendarMirror` puts each due, still-relevant todo on a configured calendar (default interval 15 minutes). The event body is title, notes, start = due date or due plus a clock time, and `transparency: transparent` so the marker does not look busy. Dragging the event’s time is adopted back (`_adopt` / `_sig` stores title, notes, due, time). A hand-deleted event is recreated. Deleting the todo removes the event via tombstones. — [todocal.py](backend/personal_os/todocal.py)
- Absent on the todo model: subtasks, dependencies, tags, and a start/scheduled field separate from `due`. Those names in the repo belong to commands, activity insights, or board cards, not todos. — [todos.py schema and `update`](backend/personal_os/todos.py); [sota-pim.md gap 7](docs/research/sota-pim.md) still matches this part

#### Week calendar
- `CalendarView` is a 7-day grid (`CalendarWeek`) from Sunday-week start, previous/next week, Today, refresh, and New event. With Google disconnected, a bar says it is showing todos only. Connected: a rail of calendars to show or hide. Events load via `api.google.calendarRange` for the week; a saved view paints before the request returns. `calendar_events` fans out one `events.list` per id, `singleEvents=True`, and when ids are `["all"]` it keeps the first 15 non-hidden calendars. - Double-click an hour to open a one-hour create (`CalendarWeek` `onDoubleClick`). Drag moves start/end only; if the event has attendees, a `window.confirm` asks whether to email them (`send_updates` `all` or `none`). A recurring instance is toasted as “this occurrence”. Dropping a todo sets `due` to that day and, if Google is connected, `scheduleTodo` creates an event (all-day if the drop has no hour, otherwise `HH:00`). `scheduleTodo` prefers the mirror calendar when that mirror is enabled, and stores the event id on the todo so the next mirror pass adopts it. — [CalendarView.tsx](src/renderer/src/components/CalendarView.tsx); [CalendarWeek.tsx](src/renderer/src/components/CalendarWeek.tsx); [TodoItem.tsx `scheduleTodo`](src/renderer/src/components/TodoItem.tsx)
- `EventEditor` covers all-day vs timed, RRULE presets plus custom RRULE/EXDATE/RDATE, series vs this occurrence (`recurring_event_id`), guests and their RSVP, guest permissions, Meet add/remove, reminders, color, location, description. — [EventEditor.tsx](src/renderer/src/components/EventEditor.tsx)
- Header **Plan my week** starts a chat: look at the next 7 days and open todos, then propose a schedule. That is a prompt, not `schedule_suggest`. — [CalendarView.tsx](src/renderer/src/components/CalendarView.tsx)
- Tools, group `google`, danger `external` for writes: `calendar_events`, `calendar_get`, `calendar_create`, `calendar_update`, `calendar_delete`, `calendar_respond` (`accepted|declined|tentative`), `calendar_free_busy`, `calendar_find_time` (work hours default 9–18 local, weekdays; declined and transparent events do not block), `calendar_propose` (batch `create|update|delete` reviewed on a calendar overlay; nothing is written until approval; each change is then read back). Create/update descriptions include recurrence, reminders, guests, Meet, color, busy/free, and `send_updates` `none|all|externalOnly`. For a series, the instance id edits one occurrence and `recurring_event_id` edits the series. — [tools.py](backend/personal_os/tools.py); [google.py](backend/personal_os/google.py)

#### Mail
- `MailView` searches Gmail (`api.google.gmail`, 30 results) with folder (inbox, all mail, user labels), read filter, starred, attachments, `newer_than` range, and a 400ms-debounced query. ## How does Google sign-in work, which scopes, and which writes are verified by read-back?

### Takeaway
Sign-in is a desktop-loopback OAuth flow. The requested scope set is broader than the README’s four names: Calendar, Gmail modify, Tasks, plus OpenID email, Drive read-only, Drive file, Docs, and Sheets. Every external write in `google.py` attaches a `verification` object from a read-back; anything but verified is a failure.

### Cited Findings
- Client resolution: a client pasted in Settings (`googleClientId` / `googleClientSecret`) wins; else `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`. Flow type in the client config is `installed` (Desktop). `start_auth` builds an authorization URL with `access_type=offline`, `prompt=consent`, a random `state`, and no `include_granted_scopes`. PKCE verifier and redirect are stored under `googleAuthPending` for 15 minutes so a backend restart can still finish. `finish_auth` exchanges the code, requires the pending state, reads email from the userinfo endpoint, and stores the token in settings `googleToken` (access token, refresh token, client id/secret, scopes, expiry, email, `connected_at`). — [google.py](backend/personal_os/google.py)
- `status()` is connected when a refresh token exists. It lists granted scopes, `missing_scopes` against the full `SCOPES` list, and `needs_reauth` when the token says so, scopes are missing, or the token’s client id no longer matches the configured client. `OAUTHLIB_RELAX_TOKEN_SCOPE` is set so a non-identical scope string does not fail sign-in; the app compares scopes itself. — [google.py `SCOPES`, `status`](backend/personal_os/google.py)
- Requested scopes: `openid`, `userinfo.email`, `calendar`, `gmail.modify`, `tasks`, `drive.readonly`, `drive.file`, `documents`, `spreadsheets`. — [google.py `SCOPES`](backend/personal_os/google.py)
- README setup still says enable Calendar, Gmail, and Tasks only, and lists scopes as `calendar`, `gmail.modify`, `tasks`, `email`. — [README.md](README.md)
- Read cache TTLs include calendar events 60s, Gmail list 60s, Gmail threads 120s, tasks 30s. Own writes invalidate namespaces. Calendar and Gmail list also keep a disk snapshot (`ReadStore`) and refresh with `updatedMin` or Gmail `historyId` / `history.list`. Tasks sync does not use `updatedMin`. No `syncToken` string exists in `google.py`. — [google.py `TTL`, `_list_events`, `gmail_search`, `tasks_all`](backend/personal_os/google.py)
- Read-back helper is `verify.check`: it retries while the object is not yet visible, then diffs fields. Verdicts are verified, unverified, or mismatch. `verify.attach` puts that on the result. `tools.py` turns a non-ok verification into a tool error that starts with `UNVERIFIED` and tells the model not to claim success and not to retry. — [verify.py](backend/personal_os/verify.py); [google.py module docstring](backend/personal_os/google.py); [tools.py](backend/personal_os/tools.py)
- Calendar create/update: `_verify_event` refetches by id and diffs the fields that were written (times compared as instants) plus status confirmed. Delete: `_verify_event_gone` requires 404 or `status=cancelled`. RSVP: `_verify_rsvp` compares the self attendee’s `responseStatus`. — [google.py](backend/personal_os/google.py)
- Gmail send: `_verify_sent` refetches metadata, requires the `SENT` label, and compares `thread_id`, subject, and To addresses, with `verify.MAIL_RETRY_DELAYS`. Draft: `_verify_draft` refetches the draft and compares subject. Modify: `_verify_labels` checks added labels present and removed labels gone. Sends from the product path are not this function’s caller until the outbox hold ends (or the hold is disabled). — [google.py `gmail_send`, `_verify_sent`](backend/personal_os/google.py); [outbox.py `queue`](backend/personal_os/outbox.py)
- Tasks insert/patch/delete: `_verify_task` refetches title, notes, due, and status, or requires the task to be gone. — [google.py `tasks_insert` / `tasks_update` / `tasks_delete`](backend/personal_os/google.py)
- Docs and Sheets have `_verify_doc` and `_verify_cells` in the same file. They are outside this note’s surfaces but they are in the same verified-write set the README table describes. — [google.py](backend/personal_os/google.py); [README.md verified-writes table](README.md)
- Planner apply uses the same `calendar_create` and treats `verified` false as a failed block, not a success. — [modules/planner.py `apply_sync`](backend/personal_os/modules/planner.py)
- Mail compose treats `status === 'sent' && verified === false` as an error toast. Calendar create toasts success only if `createEvent` resolves, and toasts the error message if it throws. — [MailView.tsx `doSend`](src/renderer/src/components/MailView.tsx); [CalendarView.tsx `create`](src/renderer/src/components/CalendarView.tsx)

### Inferences
- A token minted before Drive/Docs/Sheets were added stays “connected” and is flagged `needs_reauth` until the user consents again. Today’s Drive card is the UI for that case.
- The README’s “45% of the time” completion-claim figure is an argument in the README, not a measurement in this repo.

### Gaps
- The loopback port bind (who listens, which redirect URI is registered) was not re-read beyond `start_auth(redirect_uri)` and the README’s Desktop-client explanation.
- Exact retry delays inside `verify.MAIL_RETRY_DELAYS` were not opened.

## What is the outbox or proposal path for mail and calendar when nobody is watching?

### Takeaway
Two different queues. Interactive mail, including the assistant, is held in `pending_sends` for 60–120 seconds (default 90) and then sent. A scheduled job (`run.kind == "job"`) never performs an external tool: mail and calendar writes become `proposals` rows in the Agent inbox, and accepting one is what runs it, once. Accepting a `gmail_send` proposal then enters the outbox.

### Cited Findings
- Outbox hold: `gmailSendHold.seconds` clamped to 60–120, default 90, default enabled. `queue` inserts `pending_sends` with `send_after = now + seconds`. If the hold is disabled, `queue` calls `google.gmail_send` immediately and returns `status: sent` with the verification. — [outbox.py](backend/personal_os/outbox.py)
- `gmail_send` the tool calls `outbox.queue` when an outbox is wired, origin `"assistant"`. It tells the model the mail is not sent yet. `as_draft` routes to `gmail_draft` instead. `gmail_outbox` can list or cancel this conversation’s holding rows and cannot send early. “Send now” is `Outbox.send_now`, claimed from `holding` or `expired`, and is not a tool. — [tools.py `gmail_send`, `gmail_outbox`](backend/personal_os/tools.py); [outbox.py `send_now`](backend/personal_os/outbox.py); [README.md](README.md)
- Claim is one atomic `UPDATE ... WHERE status='holding'`. Statuses: holding, sending, sent, cancelled, failed, expired. A send that raises is marked failed and not retried. On startup, `resume()` leaves a still-running hold alone; a hold that came due less than `STALE_AFTER` (15 minutes) ago is left for the loop to send; older overdue holds are marked expired and not sent, and stay listable. The worker applies the same 15-minute cutoff before claiming. The verdict is stored on the row when delivery runs. — [outbox.py](backend/personal_os/outbox.py)
- Job runs are proposal-only: `PROPOSAL_ONLY_KINDS = ("job",)`. `_call_tool` records the call via `Proposals.create` and returns `{proposed: true, ...}` without `toolbox.call` when `toolbox.proposes(name)` (danger `external` or `schedules`). The model is told not to call it again. `Toolbox.call` also refuses those dangers if `proposal_only` is set, as a second gate. Accept (`POST /proposals/{id}/accept`) flips pending to accepted once, then `toolbox.call` with `proposal_only: false`. A second accept gets 409. Reject only works while pending. — [app.py `proposal_only`, `_propose`, `accept_proposal`](backend/personal_os/app.py); [jobs.py `Proposals`](backend/personal_os/jobs.py); [tools.py `proposes`](backend/personal_os/tools.py)
- So an unattended `gmail_send`, `gmail_draft`, `gmail_modify`, `calendar_create`, `calendar_update`, `calendar_delete`, `calendar_respond`, or `calendar_propose` is a proposal, not an outbox row and not a Google write. After accept, `gmail_send` hits the outbox hold; calendar tools hit `google.py` and the read-back. `schedule_suggest` and `mail_followups` are not `external`, so a job that is allowed to call them can run them. The morning-brief seed allowlist does not include them or any external tool. The “Scan unread and draft replies” seed includes `gmail_draft`, which a job can only propose. — [jobs.py `SEED_JOBS`](backend/personal_os/jobs.py); [tools.py danger flags](backend/personal_os/tools.py)
- Jobs do not inherit “skip permissions”. `UNATTENDED_KINDS` is `("job", "scheduled")`. If a non-proposing tool still needs an approval and `unattendedApprovals` is `deny`, the call is refused and an approval row is recorded as denied by `unattended`. If it would ask and nobody is watching, and it was not turned into a proposal, it is denied with “nobody is watching”. No writer of `kind="scheduled"` was found. — [app.py](backend/personal_os/app.py)
- Catch-up: one run for the most recent missed slot, marked late. A one-off still runs late, then turns itself off. A job cannot schedule further jobs (`schedules` is proposal-only). — [jobs.py module docstring](backend/personal_os/jobs.py); [tools.py `PROPOSAL_ONLY_DANGER`](backend/personal_os/tools.py)
- `calendar_propose` while someone is in a chat is a different review: the user edits the batch on a calendar overlay and one approval applies each change with a per-change outcome. It is still danger `external`, so a job records the whole batch as one proposal instead of opening that overlay. — [tools.py `calendar_propose`](backend/personal_os/tools.py)

### Inferences
- “Nobody watching” does not mean the 90-second undo window. That window assumes a person can press Undo. A job never enters it until a person accepts.
- A laptop asleep for more than 15 minutes after a compose-window send will not emit that mail by itself. A missed morning brief still runs once, late, and can only propose outward actions.

### Gaps
- What `run.kind == "scheduled"` is for was not found. The deny-if-nobody-is-watching branch applies to it, but no constructor showed up in this pass.
- The Agent Inbox UI (accept/edit/reject controls) was not read; the HTTP contract was.

## Recurring todos, reply tracking, time-blocking: shipped, partial, or absent?

### Takeaway
Recurring todos are shipped. Reply tracking is shipped as an on-demand classifier with a Mail-page panel, not as automatic triage. Time-blocking is partial: a deterministic planner proposes blocks and the user applies them; nothing silently places or moves blocks.

### Cited Findings
- **Recurring todos: shipped.** `repeat` JSON is `{every, unit, mode}` with units day/week/month/year and modes `from_due` / `from_completion`, parsed by `todo_rules.parse_repeat`. Completing via `Todos.update` (including Tasks sync, which uses that update) calls `_spawn_next` with `source='local'` and the same estimate. Repeat is cleared on the completed row so a second completion does not spawn again. UI presets are every-1 from due only; tools can set every-N and `from_completion`. Google Tasks is not given a recurrence. The mirror will create an event for the new due date on its next pass. — [todos.py](backend/personal_os/todos.py); [modules/todos.py](backend/personal_os/modules/todos.py); [TodosView.tsx](src/renderer/src/components/TodosView.tsx); [TodoItem.tsx](src/renderer/src/components/TodoItem.tsx)
- **Urgency: shipped beside recurrence**, though `sota-pim.md` still lists it as a gap. `todo_list(sort=urgency)` and the Todos page sort use `todo_rules.urgency`. Today’s card does not. — [modules/todos.py](backend/personal_os/modules/todos.py); [TodosView.tsx](src/renderer/src/components/TodosView.tsx)
- **Reply tracking: shipped, with the automation left off.** Statuses are `to_reply`, `awaiting_reply`, `fyi`, `actioned`, stored in `thread_status`. `classify` uses headers and snippets (who sent last, request phrases, age).
