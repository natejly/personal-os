## What are the tool modes, and how do global, project, and chat scopes combine?

### Takeaway
Built-in tools resolve `on | ask | off` as chat override, then project override, then the global map, then a danger-tier default. MCP tools use the same three scopes in a separate grant table, default `ask`, and an `on` grant decays to `ask` when the tool’s schema hash changes. A chat-level Tools switch can hide the whole set.

### Cited Findings
- Modes are exactly `on`, `ask`, and `off`. `ToolOverride` adds `inherit`. Booleans still normalize: `true` → `on`, `false` → `off`. — [types.ts](src/shared/types.ts) (`ToolMode`, `ToolOverride`); [tools.py](backend/personal_os/tools.py) `Toolbox._norm`
- Danger defaults: `safe`, `writes`, `network`, and `executes` → `on`; `external`, `plan`, and `schedules` → `ask`. A spec may override that default. `shell_run` is `executes` but its spec default is `ask`. — [tools.py](backend/personal_os/tools.py) `DEFAULT_MODE`, `ToolSpec.default_mode`; [shell.py](backend/personal_os/shell.py) `spec.default = "ask"`
- Built-in resolution, most specific last: start from the global map or `spec.default_mode`, replace with the project map if that key normalizes, then replace with the chat map. A missing or invalid value does not override. `inherit` does not normalize, so it falls through. — [tools.py](backend/personal_os/tools.py) `Toolbox.effective`
- The chat loop loads that map only when the conversation’s `useTools` is true (default true). Otherwise `modes` is empty and a call’s raw mode is `off`. — [app.py](backend/personal_os/app.py) `_chat_stream` (`use_tools`, `raw_mode = modes.get(c["name"], "off")`)
- MCP grants persist in `mcp_grants`, unique on `(tool_slug, scope, scope_id)`, bound to `schema_hash`. Scopes are `global`, `project`, `chat`. `effective_mode` walks global, then project, then chat; a later grant replaces an earlier one. No grant means `ask` (`DEFAULT_MODE`). If the grant’s hash differs from the live tool, `stale` is true and `on` becomes `ask`. — [mcp_servers.py](backend/personal_os/mcp_servers.py) `set_grant`, `effective_mode`
- A quarantined (drifted) MCP tool is not offered. A slug whose server is not ready is left out. A chat tool map entry of `off` removes that slug from the MCP mode map even if a grant says otherwise. — [app.py](backend/personal_os/app.py) `_mcp_tooling`, chat-off filter
- Chat per-tool UI is “per-tool overrides” in the context drawer, against a project base. Global toggles and the rules editor live on Settings → Tools. — [ContextDrawer.tsx](src/renderer/src/components/ContextDrawer.tsx); [ToolPermissions.tsx](src/renderer/src/components/ToolPermissions.tsx); [SettingsModal.tsx](src/renderer/src/components/SettingsModal.tsx)
- `llm.py` still comments that `tools` is `{tool_name: bool}` and “missing = on”. `Toolbox.effective` does not do that: a missing key uses the danger default, so `external` stays `ask`. — [llm.py](backend/personal_os/llm.py) `DEFAULT_SETTINGS["tools"]`; [tools.py](backend/personal_os/tools.py) `effective`

### Inferences
- Project and chat maps are whole-tool switches. They do not carry argument patterns. Argument patterns are the separate global `permissionRules` object (next section).
- Chat `off` is the only chat-scope control that can silence an MCP tool whose grant is `on`. Chat `on` for an MCP slug is not how MCP grants are stored; `always_chat` writes `mcp_grants` instead of `settings.tools`.

### Gaps
- This pass did not enumerate every built-in’s `danger` and `default`. The rule above is the resolver; individual tools can set `spec.default` or `force_ask` (confirmed for `shell_run` / `unsandboxed` only).

## How do permission rules, skip-permissions, and approval cards work?

### Takeaway
Rules are a global allow/ask/deny list of `Tool` or `Tool(pattern)` strings. Deny refuses before the tool runs, and nothing in the rule engine or skip-permissions lifts a deny or the hardline shell list. Skip-permissions (chat value if stored, else global, default off) turns remaining `ask` cards into runs, except `propose_plan` and `desk_ask`, and never for job or scheduled runs. Approval cards can allow once, allow for this chat session, save an allow rule, or set the whole tool to `on` for the chat or globally. Forced cards are one-shot for those grants.

### Cited Findings
- Rule shape and load: `parse_rule` / `load_rules`. Malformed entries are skipped. Stored at `settings.permissionRules`, default `{allow: [], ask: [], deny: []}`. Not per project or per chat. — [permrules.py](backend/personal_os/permrules.py) `Rule`, `load_rules`; [llm.py](backend/personal_os/llm.py) `DEFAULT_SETTINGS`
- Subjects: `Bash(<command>)` for `shell_run`; `Read(<path>)` for `read_local_file`, `fs_glob`, `fs_grep`; `Edit(<path>)` for `write_local_file`, `fs_edit`, `fs_copy`, `fs_mkdir`, `move_local_file`, `trash_local_file` (copy and move also see source/dest); `Agent(<type>)` for `agent_spawn`; otherwise the bare tool name with no argument. — [permrules.py](backend/personal_os/permrules.py) `subject_for`, `READ_TOOLS`, `EDIT_TOOLS`
- Shell evaluation order inside `_evaluate_bash`: hardline deny, then any deny rule, then ask if any subcommand hits an ask rule or the line is opaque or a path is outside the workspace roots, then allow only if every subcommand is read-only or allow-listed, else no opinion. Deny/ask see nested `$(...)` and `sh -c`. One denied or asked part decides the line. — [permrules.py](backend/personal_os/permrules.py) module docstring, `_evaluate_bash`, `hardline`
- Hardline (no rule and no card lifts it): fork bomb, recursive `rm` of `/`, home, or system dirs, `mkfs`/`newfs`, `dd` or writes to disk devices, `kill -1`, `shutdown`/`reboot`/`halt`/`poweroff`/`killall5`, `diskutil erase`. — [permrules.py](backend/personal_os/permrules.py) `hardline`, `_hardline_tokens`
- Fixed read-only shell set includes `ls`, `cat`, `head`, `tail`, `wc`, `pwd`, `echo`, `which`, `file`, `stat`, `grep`, `rg`, `find` (find writers such as `-exec`/`-delete` are excluded), and `git status|diff|log|show|branch` with a small flag set. — [permrules.py](backend/personal_os/permrules.py) `READONLY`, `GIT_READONLY`, `_readonly`
- `resolve`: if the incoming mode is `off`, return it and do not apply rules. A deny sets `refusal` and does not change mode; the loop turns that into `tools.denied` before the tool runs. A doom-loop forces `ask` and `forced` even after an allow. An ask rule sets `ask` unless a session grant covers the pending keys and the card is not forced. An allow rule, or a session grant with no rule opinion, turns `ask` into `on` only when not forced. — [permrules.py](backend/personal_os/permrules.py) `resolve`; [app.py](backend/personal_os/app.py) call site (`perm.refusal` → `pre`)
- The loop does not call `resolve` for MCP slugs. Comment: MCP keeps schema-bound grants. — [app.py](backend/personal_os/app.py) `if c["name"] != PLAN_TOOL and mode != "off" and not mcp_is`
- Session grants: in-memory `SESSION`, per conversation id, exact set of pending keys, cleared on process restart. `always_session` adds them only when the card was not forced, then runs as `allow`. — [permrules.py](backend/personal_os/permrules.py) `SessionGrants`; [app.py](backend/personal_os/app.py) decision `always_session`
- Doom loop: the third identical executed call in a row (`StuckDetector.repeat_count >= 2`) becomes a forced `doom_loop` card. Rules do not lift it. Skip-permissions does: the docstring says a doom-loop card is an ask and this mode lifts it. — [stuck.py](backend/personal_os/stuck.py) `repeat_count`; [permrules.py](backend/personal_os/permrules.py) `DOOM_LIMIT`, `lift_permission_ask`
- Three consecutive refusals (rule deny, unattended deny, or a denied card) make `DenialStreak` attach a stop-varying note on a later result. The loop calls `note()` before `record()`, so the note appears once the counter is already at 3, on the following result. — [permrules.py](backend/personal_os/permrules.py) `DENIAL_LIMIT`, `HARD_STOP`; [app.py](backend/personal_os/app.py) `denials.note` / `denials.record`
- Skip-permissions flag: `skip_permissions_on` — if the conversation settings dict contains `skipPermissions`, that boolean wins, including false; otherwise the global setting, default false. The chat loop clears the flag when `run.kind` is `job` or `scheduled`. — [permrules.py](backend/personal_os/permrules.py) `skip_permissions_on`; [llm.py](backend/personal_os/llm.py); [app.py](backend/personal_os/app.py) `UNATTENDED_KINDS`
- `lift_permission_ask`: if skip and mode is `ask` and the name is not in `STILL_ASK` (`propose_plan`, `desk_ask`), return `on`. `off` stays `off`. A refusal already in `pre` is not replaced. The lift runs after plan mode, desk autonomy, taint, and `resolve`, and it does not check `forced`. — [permrules.py](backend/personal_os/permrules.py) `STILL_ASK`, `lift_permission_ask`; [app.py](backend/personal_os/app.py) skip block
- UI: composer button writes the chat setting when a conversation id exists, otherwise the global setting. Displayed state is chat value if present, else global. Settings → Tools checkbox is the global default; its copy says deny rules still refuse, plans and desk questions still wait, and jobs keep their own setting. Context drawer Tools hint says cards are off and deny rules still refuse when the effective flag is on. — [SkipPermissionsToggle.tsx](src/renderer/src/components/SkipPermissionsToggle.tsx); [Composer.tsx](src/renderer/src/components/Composer.tsx); [SettingsModal.tsx](src/renderer/src/components/SettingsModal.tsx); [ContextDrawer.tsx](src/renderer/src/components/ContextDrawer.tsx)
- A `run_python` tool-bridge call returns approved immediately when skip is on, without a card. — [app.py](backend/personal_os/app.py) `_bridge_approve`
- Card decisions accepted by `POST /approvals/{call_id}`: `allow`, `deny`, `always_chat`, `always_global`, `always_session`, `always_rule`. First decision wins on the SQLite row. There is no auto-deny timer in the wait loop. — [app.py](backend/personal_os/app.py) `ApprovalIn`, `approve_tool_call`, wait loop comment
- `always_rule` appends validated rules to global `permissionRules.allow` before the decision, and only if the row is pending, not forced, and not a plan. Saved rules must match a subject of this call, must have a pattern, and must not be a blanket `*` (max 5). — [app.py](backend/personal_os/app.py) `_save_allow_rules`; [permrules.py](backend/personal_os/permrules.py) `validate_saved_rules`
- `always_chat` / `always_global` set that tool’s mode to `on` (MCP: a grant at that scope). If the card was forced, or the tool is `propose_plan`, the standing grant is dropped and the decision is a one-shot `allow`. The loop re-reads settings before writing so a change during the wait is not overwritten blindly. — [app.py](backend/personal_os/app.py) standing-grant block
- Card extras (`permission` on the tool event) come from `Resolution.card` when the call is still asking: kind, subject, rule, suggestions, and whether a session grant is offered. Forced cards omit session and saved-rule buttons. Kinds the UI explains: `doom_loop`, `opaque`, `external_directory`, `rule`. — [permrules.py](backend/personal_os/permrules.py) `Resolution.card`; [ApprovalRules.tsx](src/renderer/src/components/ApprovalRules.tsx); [ToolEvents.tsx](src/renderer/src/components/ToolEvents.tsx)
- Optional edited arguments on a non-plan card are schema-checked and become the call that runs. Parked cards reject edits. A deny can carry a note back to the model (500 chars on the live path). — [app.py](backend/personal_os/app.py) `approve_tool_call`
- `POST /permissions/evaluate` previews a rule or a call against saved rules and roots. It does not run the tool. — [app.py](backend/personal_os/app.py) `evaluate_permission`
- Unattended jobs: if the call would still ask and `unattendedApprovals` is `deny` (default is `ask`), the loop records a denied approval and refuses. A background proposal-only run that still needs a card is refused rather than parked. — [llm.py](backend/personal_os/llm.py) `unattendedApprovals`; [app.py](backend/personal_os/app.py) unattended and proposal-only blocks
- Writes outside granted folders, or inside a granted folder (not a desk workspace) after untrusted content, set `fs_needs_ask`, which upgrades `on` to `ask` and marks the card forced, so an allow rule cannot turn it back off. Desk-workspace paths do not ask for this reason. — [fsx.py](backend/personal_os/fsx.py) `needs_approval`, `needs_ask`; [app.py](backend/personal_os/app.py) `fs_ask` / `forced`
- Taint (sticky on the conversation, plus this turn’s meetings, activity, document excerpts, page detail, or a sandbox import) forces `external`, `network`, `schedules`, prompt-write tools, and a networked sandbox from `on` to `ask` via `Toolbox.gate` / `_gate`. That upgrade is forced, so rules do not downgrade it. Skip-permissions still lifts it, because the lift ignores `forced`. — [app.py](backend/personal_os/app.py) `tool_ctx["tainted"]`, `_gate`; [tools.py](backend/personal_os/tools.py) `gate`, `PROMPT_WRITES`
- `shell_run` with `unsandboxed: true` is `force_ask`. A sandboxed shell whose cwd is inside the desk workspace can skip its default `ask` when `deskShellAuto` is on (default true) and the user has not set a shell mode; later gates still apply. — [shell.py](backend/personal_os/shell.py) `auto_ok`, `force_ask`; [app.py](backend/personal_os/app.py) auto_ok block

### Inferences
- Deny beats allow, ask, session grants, whole-tool `on`, and skip-permissions. The hardline list is a deny. Skip-permissions beats ordinary asks, doom-loop cards, taint-forced asks, desk “ask as it goes” cards, and outside-folder file cards. It does not beat `off`, a refusal, plan drafting blocks, propose-only external blocks, `propose_plan`, or `desk_ask`.
- `always_chat` / `always_global` are coarser than `always_rule`: they flip the tool, they do not store an argument pattern. Gmail and calendar calls have no argument subject, so a saved rule for them cannot name a recipient or calendar.
- A chat that died while a card was open records the decision and tells the user the call did not run. A desk card can still wake the desk (next section).

### Gaps
- No per-project or per-chat rule lists, no grant audit (who, when, how many fires), and no batch card for several asks in one round. Those are absent, not partial.
- Did not re-read every wrapper stripped by `strip_wrappers` or the full glob grammar in `_path_match`. The evaluation order above is what `evaluate` / `_evaluate_bash` implement.

## What is verified on external writes, and what is not?

### Takeaway
Google Calendar, Gmail, Tasks, Docs, and Sheets writes that go through `google.py` are re-read and labeled `verified`, `unverified`, or `mismatch`. Anything but `verified` becomes a tool error so the model is told not to retry. Local files, the host shell, the browser, MCP calls, and creating a secondary calendar are not proved that way.

### Cited Findings
- `verify.check` re-fetches the object. `verified` means it was found and compared fields match (or, for a delete, it is gone or a cancelled tombstone). `unverified` means not visible or the read failed. `mismatch` means it was found but fields differ, or a delete left it present. Retries are two delays (0.5s, 1.5s); mail adds a third (3.0s). The function does not raise. — [verify.py](backend/personal_os/verify.py) `check`, `RETRY_DELAYS`, `MAIL_RETRY_DELAYS`
- `tools.checked` turns a non-verified Google result into `unverified()`, which sets `error` and tells the model not to repeat the write. — [tools.py](backend/personal_os/tools.py) `checked`, `unverified`
- Shipped read-backs, all via `verify.attach` in [google.py](backend/personal_os/google.py):
  - `calendar_create` / `calendar_update`: fields actually written, plus status (`_verify_event`)
  - `calendar_delete`: absent or cancelled tombstone (`_verify_event_gone`)
  - `calendar_respond`: the self attendee’s `responseStatus` (`_verify_rsvp`)
  - `gmail_send`: message id exists, `SENT` label, thread id, subject, and To addresses. Body is not in `compare`. Delays use the mail ladder (`_verify_sent`)
  - `gmail_draft`: draft exists and subject matches. Recipients and body are not compared (`_verify_draft`)
  - `gmail_modify`: labels (`_verify_labels`)
  - `tasks_add`, `tasks_complete`, `tasks_insert`, `tasks_update`, `tasks_delete`: task read-back (`_verify_task` and the delete call beside it)
  - `docs_create` / `docs_append`: title when set, and the written text as a whitespace-collapsed tail of at most 200 characters (`_verify_doc`)
  - `sheets_write`: row shape and filled-cell count (`_verify_cells`)
  - `sheets_create`: spreadsheet title only. Initial cell values are written and not part of that compare
- Held sends go out through `gmail_send`, so the same SENT read-back applies when the hold ends. — [outbox.py](backend/personal_os/outbox.py) calls `gmail_send`
- `calendar_ensure` inserts a secondary calendar for the todo mirror and returns `{id, summary, created}` with no `verify.attach`. — [google.py](backend/personal_os/google.py) `calendar_ensure`; callers in [modules/planner.py](backend/personal_os/modules/planner.py) and [todocal.py](backend/personal_os/todocal.py)
- Local writes: `post_write` records the file as read and, for `.py` / `.json` / `.toml` / `.yaml`, reports `syntax_error` if the text does not parse. It does not compare bytes to what was requested. `pre_write` can require a full read before overwrite (`requireReadBeforeWrite`, default true). `filesnap` stores a pre-image for undo when wired; that is not a read-back proof. — [fsx.py](backend/personal_os/fsx.py) `post_write`, `pre_write`; [tools.py](backend/personal_os/tools.py) filesnap capture around the local write path; [llm.py](backend/personal_os/llm.py) `fileSnapshots`, `requireReadBeforeWrite`
- Sensitive local paths are refused (`.env`, keys, credential directories, `/dev`, `/proc`), which is a gate, not a verification. — [fsx.py](backend/personal_os/fsx.py) `sensitive_reason`; [mac.py](backend/personal_os/mac.py) is what `allowed_path` enforces for reads (referenced from `pre_read` / `resolve_path`)
- Cowork output promotion (`_promote` path in app.py) re-reads the destination and returns `verified`. That is a separate read-back for accepted desk outputs, not for every tool write. — [app.py](backend/personal_os/app.py) promote helpers around the “read it back” comment
- No `verify.check` / `verify.attach` call sites outside `google.py` (and the `checked()` wrapper in `tools.py`). Shell, browser, and MCP results are not passed through it. — repo search for `verify.check(` and `verify.attach`

### Inferences
- “Verified” in this tree means a second Google API read of selected fields, with a short retry. It does not mean the full payload matches, and it does not cover non-Google side effects.
- An unverified Google write may still have landed. The tool error says so. Local writes that return success are trusted without that second read.
- `sheets_create` with seed values and `gmail_send` body content can be `verified` while the part the user cares about was not compared.

### Gaps
- Did not trace every in-app SQLite write (memories, todos, boards, local docs) for a read-back. They are not on the `verify.py` path. Whether each handler re-reads its own row was left to other notes.
- Did not re-audit `mac.allowed_path`’s full deny list in this pass; `fsx.sensitive_reason` is the file-tool list that was read.

## How do cowork modes and parked approval cards fit?

### Takeaway
Desk autonomy is `plan` (plan first), `ask` (ask as it goes), or `propose` (work locally, refuse external actions). It is stored on the desk and applied inside the same gate as chat plan mode, after tool modes and before permission rules. Parked cards are a desk-only way to drop a waiting run and still honor an exact later yes.

### Cited Findings
- Allowed values: `plan`, `ask`, `propose`. New desks default to `plan`. UI labels: “Plan first”, “Ask as it goes”, “Work and propose”. Hints: plan waits before it touches anything; ask shows a card for every consequential tool; propose works in its folder and brings the result back. — [cowork.py](backend/personal_os/cowork.py) `AUTONOMY`, schema default; [DeskRail.tsx](src/renderer/src/components/DeskRail.tsx) `AUTONOMY`
- The loop reads `autonomy` from the desk row each turn, not from chat settings. Ordinary chats do not use it. Chat plan mode is forced empty when a desk is set. — [app.py](backend/personal_os/app.py) desk block (~1558–1573)
- Chat plan mode is separate: `off | auto | always`, chat setting over global, default `off`. Composer cycles it. `always` starts drafting immediately. `auto` flips planning on at the first mutating call whose group is not exempt, refuses that call, and offers a reduced schema next round. — [llm.py](backend/personal_os/llm.py) `planMode`; [PlanModeToggle.tsx](src/renderer/src/components/PlanModeToggle.tsx); [app.py](backend/personal_os/app.py) `chat_plan_mode` gate
- While `planning` is true, any tool whose danger is not `safe`, `network`, or `plan` is set `off` with reason `PLAN_BLOCKED` (not a card). Desk `plan` starts in that state until an approved plan exists. — [plans.py](backend/personal_os/plans.py) `PLAN_SAFE_DANGER`, `PLAN_BLOCKED`; [app.py](backend/personal_os/app.py) planning branch
- `propose`: if danger is `external`, mode `off` and reason “this desk may only propose external actions”. It does not turn the call into a proposal row. `writes` and `executes` are not in that branch. — [plans.py](backend/personal_os/plans.py) `PROPOSE_ONLY`; [app.py](backend/personal_os/app.py)
- `ask` autonomy: danger in `writes | executes | external` becomes a forced `ask`, so a standing grant cannot clear it. Skip-permissions can still lift that ask (previous section). — [plans.py](backend/personal_os/plans.py) `MUTATING`; [app.py](backend/personal_os/app.py)
- `propose_plan` is always a card (`mode` forced to `ask`, not `forced` for grant purposes). An approved step whose argument digest matches is claimed once and stands in for the card, except when the approval was forced (taint). A chat consults the plan when it would have asked; a desk also claims steps that were going to run, so the plan stays the progress record. A previously rejected step is denied. — [app.py](backend/personal_os/app.py) `PLAN_TOOL` and `plans.claim` block
- These cowork/plan branches only narrow: they set `off` or forced `ask`. They do not clear a card by themselves. Shell `auto_ok` can clear a default ask earlier, and then these branches can put it back. — [app.py](backend/personal_os/app.py) comment above the plan-mode block; [shell.py](backend/personal_os/shell.py) `auto_ok` docstring
- Parking: only if `desk_id` is set and `parkAfterSeconds` > 0 (default 180). Chats pass 0 and wait with no timeout. A desk parks only when the run has zero watchers and the wait has reached the threshold. `RunStore.park` leaves status `pending`, sets `decided_by='park'`. The reply ends, the card stays on the message, desk status becomes `blocked`. — [llm.py](backend/personal_os/llm.py) `parkAfterSeconds`; [runs.py](backend/personal_os/runs.py) `park`; [app.py](backend/personal_os/app.py) park loop
- Answering a parked desk card does not resume the dead run. `POST /approvals` records the decision, patches the transcript, and `_wake_desk` starts a later turn. `parked_report` injects what was decided. An approved ordinary call must be repeated with the same argument digest; `claim_parked` spends that once. A different digest asks again. Plan approval is described as the plan to carry out; a desk question’s note is the answer. — [cowork.py](backend/personal_os/cowork.py) `parked_report`; [runs.py](backend/personal_os/runs.py) `unreported`, `claim_parked`; [app.py](backend/personal_os/app.py) `approve_tool_call` wake path and `claim_parked` in the loop
- Parked cards cannot take edited arguments. — [app.py](backend/personal_os/app.py) `decided_by == "park"` check

### Inferences
- “Plan first”, “ask as it goes”, and “propose only” are desk autonomy, not tool modes. Chat “plan mode” is the same drafting block (`planning`) with `off | auto | always`, and it is disabled for desks so the two do not stack.
- “Work and propose” does not mean every action is a proposal. External danger is refused with a message. Local writes follow the normal mode, rules, and folder grants. Background jobs are the path that records proposals instead of calling external tools (`proposal_only`).
- A parked yes is not a session grant and not a saved rule. It is one digest, one desk, one use.

### Gaps
- Did not read `_wake_desk` or `_should_chain` line by line. The approval route’s comment says a non-live parked answer wakes the desk; the exact resume prompt is only confirmed through `parked_report`.
- Did not confirm `PLAN_AUTO_EXEMPT_GROUPS` membership.

## Where do README and the research notes disagree with the code?

### Takeaway
`docs/research/sota-cowork.md` “Where we are” (2026-10-01) and `docs/research/track-d-safety.md` “current design” (2026-09-29) describe a permissions system the working tree has replaced. README’s opening feature list is still roughly the mode model; its roadmap still describes the pre-fix defects and a future MCP client. Later README shell text matches the host shell that the cowork note says does not exist.

### Cited Findings
- README features: each tool is on / ask / off; in-app defaults on; outside-the-app defaults ask; overrides are global, project, or chat; ask pauses with an approve/deny card. That matches `DEFAULT_MODE` and `Toolbox.effective`, and it omits rules, session scope, skip-permissions, shell’s ask default, and cowork autonomy. It is incomplete rather than inverted. — [README.md](README.md) “Tools with permissions”; [tools.py](backend/personal_os/tools.py) `DEFAULT_MODE`
- README roadmap: “four live security defects”; stock modes let an injected page or email read the Fireworks key and the database and exfiltrate them with no card; MCP client is “later”. — [README.md](README.md) Roadmap, “Read Track 5 first”
