# TencentDB-Agent-Memory versus Grain memory: feature-by-feature comparison

Research note, 2026-10-13. This folder is the one place in the repo that names other products.

**Sources.**
- TencentDB-Agent-Memory ("TDAM"): a read-only clone at `/Users/natejly/.claude/jobs/30924ed5/tmp/tdam/src` (no commit id was checked). Nothing in it was run or installed. Paths are relative to `MemoryCore/src/` unless they start with `MemoryProxy/`, `MemoryPanel/`, `MemoryKnowledge/`, or `README.md`.
- Grain: worktree `memory-merge-tdam`, branch `worktree-memory-merge-tdam`, at 77b7ac10 (the write-time merge judge is committed there). Paths are relative to `backend/personal_os/` unless they start with `scripts/`, `src/` or `docs/`.
- Already covered, not redone here: `docs/research/parity-memory.md` (product parity with chat assistants) and `docs/research/hindsight-memory.md` (event time, evidence-backed observations, standing questions).

**Conventions.** Every cell cites a file and line that was read. "(inferred)" means the claim follows from code that was read but no single line states it. The clone contains zero `*.test.ts` files, so nothing about TDAM quality was checked by tests; all TDAM verdicts come from reading code. README claims count as unverified unless code backs them (section 14).

**What TDAM is.** A TypeScript memory service for agents, with four layers: L0 raw messages, L1 extracted atoms (`persona`, `episodic`, `instruction`, plus four `work_*` types in a team mode), L2 "scene" markdown files edited by an LLM agent, and L3 a single persona document. It runs as an OpenClaw plugin, a gateway, or behind a proxy that injects memory into other agents' requests, with a control panel for teams, ACLs, skills, a wiki and a code graph. Grain is a single-user local app: five memory kinds with supersession history, a bi-temporal knowledge graph, hybrid retrieval with rerank, and approve-only consolidation.

## 0. Bottom line

- Grain is ahead on most of the memory path: retrieval (five weighted rankers, rerank, temporal window, eval harness), write safety (cosine guard, validated judge output, credential scrub, taint handling), history and restore, user control.
- TDAM is ahead in six places worth taking: an extractor that sees background messages, event time on episodic memories, a durable cursor so nothing queued is lost, a synthesized persona document (as a reviewable proposal in Grain), CJK word segmentation, and a few cheap hygiene details (code-block stripping, a recall truncation suffix that names the search tool, JSON repair, a closed set of "empty run" reasons).
- Two of the three TDAM ideas the team already planned need re-scoping. The write-time judge (a) is built and committed; TDAM's version has weaker guards than Grain's. The small-corpus exemption (b) fixes a BM25 threshold problem Grain does not have, because Grain never thresholds lexical hits; Grain's real tiny-corpus gap is the vector-only floor (section 7, row 9).
- Do not take: scene files and heat, the unused priority score, cross-type merge, age-based hard deletion, tenancy and ACLs, the external decision gate, the disabled prompt-injection regex filter.

## 14. Claims checked

**PersonaMem 48% to 76% (README.md:271-277).** Unverified. The string "PersonaMem" appears only in `README.md` and `README_CN.md` (`grep -rIl`). There is no benchmark harness for it, no fixture, no test file. The only benchmark scripts in the clone are Mongo throughput scripts. Treat the figure as a vendor claim with no reproducible method.

**"Results are further capped by item count, character budget, and timeout limits" (README.md:257).** Partly true. Item cap 5 and a 5 s race exist; the character budgets default to 0, which disables them (`config.ts:273-274`).

**Layered recall (README.md:257).** True for L2 and L3: persona and scene navigation are injected every turn, and L1 is searched per turn. L0 is reachable only through the conversation-search tool.

**Code and comment drift inside TDAM** (each shows the code was changed without the docs, so prefer the code):
- L1 idle timeout documented as 30 s, default 600 s (`config.ts:98` versus `:683`); L2 delay documented as 90 s, default 10 s (`config.ts:101` versus `:684`).
- Max scenes documented as 20, default 15 (`config.ts:77` versus `:664`).
- Memories per extraction: extractor fallback 10, config default 20 (`core/record/l1-extractor.ts:152` versus `config.ts:658`).
- Memory type comment says three types and version "starts at 1"; code has seven types and starts at 0 (`core/record/l1-writer.ts:15,76` versus `:31-38,191`).
- Scene "heat" described as recall hits, implemented as an LLM-edited counter (section 5).
- A prompt-injection filter is written and disabled (`utils/sanitize.ts:153`).
