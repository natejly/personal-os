# Chat and agent loop — what to build

Synthesized 2026-10-02 from `chat-agent-app.md` and `chat-agent-market.md` only. No new web research. The market note does not audit Grain, so it cannot contradict the app note’s feature list. One market inference does conflict with the app note; it is marked in section 3.

The app note read the working tree on 2026-10-02, including uncommitted edits in `backend/personal_os/app.py`, `llm.py`, `context.py`, `subagents.py`, `src/renderer/src/components/Composer.tsx`, `ContextDrawer.tsx`, `src/shared/types.ts`, and `SkipPermissionsToggle.tsx`. It did not run the app or the test suite, and it did not split committed code from dirty code. This comparison inherits that limit.

Effort: **S** is a change in one or two existing functions, no new table, offline-testable. **M** crosses a few existing modules and stays inside the current loop. **L** is a new transcript model or a second chat surface.

Do not close any gap below by raising `maxToolRounds` (default 25), auto-enabling skills, adding a heartbeat or poller, or clicking the screen. Writes and external tools stay behind the existing ask. The runner stays on this machine.

## 1. What Grain ships now

A chat turn is a background run. The composer posts `POST /conversations/{id}/chat`. `chat()` starts `_run_chat` → `_chat_stream`. Every window tails that run’s stored event tape with `GET /conversations/{id}/stream`. Closing the window detaches the client and leaves the run going. A later `attachSession` can tail it from `GET /runs` while `answering` is still true. `run_id` pins the tape so a reconnect cannot land on a newer run.

The composer sends on Enter. While a reply is answering, the placeholder is “Steer the reply…” and Send stays available beside Stop. Steer (`POST /conversations/{id}/steer`) persists the user message, cancels the provider read, and continues the same run. If that segment already streamed or ran tools, the loop finishes that assistant row, yields `done` with `segment: true`, and opens a new assistant message. A second send while a conversation is being created waits and joins the same chat. A 409 from chat attaches to the live run and steers into it.

Streaming events include `user_message`, `title`, `assistant_message`, `span`, `delta`, `reasoning`, `tool_call`, `tool_result`, `taint`, `plan`, `plan_card`, `plan_decision`, `artifact`, `parked`, `done`, `error`, `learned`, and `style_learned`. Reasoning is stored on the message and is not sent back on the next turn. Stop sets the run’s stop event; the local abort controller does not stop the run. A cancel closes the provider socket, drops partial tool calls, and marks the rest of the round not executed. Regenerate is available when the last message is an assistant and the chat is not streaming. It posts chat with empty content, deletes that trailing assistant row, and replies to the last user message.

The model picker follows the conversation, the draft, or `settings.defaultModel`. `GET /models` lists an OpenAI-compatible `/models` endpoint. Effort is per conversation. Fast mode sends `service_tier: "priority"` only for provider ids `openai`, `litellm`, or `custom`. Before the first byte, retryable HTTP and transport errors retry (`llmRetries`, default 3, cap 10) with jitter, floored at `Retry-After`, capped at 30 seconds. After the first byte, failures are not retried.

Projects store `name`, `description`, `system_prompt`, `color`, and `tools`. `build_context` puts the global system prompt, the project line, the description, and `project.system_prompt` in the stable prefix, with approved skills and the style profile. Page, memories, graph, document excerpts, activity, and meetings are volatile. With `cacheLayout` default true, volatile blocks are a second system message immediately before the newest user message. A 12-hex `stable_hash` is stored on the context span. `_today_hint()` (weekday, date, zone, next 7 days) is joined into the stable prefix. Page detail is clipped at 6000 characters and selection at 2000. `estimate_tokens` is `len//4`.

The tool loop is `while True` in `_chat_stream`: microcompact, drain background-shell notes, move the plan block onto the last message, then one streamed completion. The provider may return several calls. The parent runs them one after another. Read-only `agent_spawn` calls can prestart together when the round is not in plan mode and autonomy is not `"ask"`. A child’s own loop gathers consecutive read-only calls (`danger` in `safe` or `network`, mode `on`, not a writer, not `agent_*`), at most 8 at a time, and runs identical `(tool, args)` once. The parent loop does not gather ordinary read-only tools.

Default caps are `maxToolRounds` 25, `maxRunTokens` 200_000, `maxRunSeconds` 300, `maxRunCost` 0.50. `0` means unlimited. Approval wait is subtracted from the wall clock. At 60% of the tightest axis, one `SOFT_NUDGE` is appended. Crossing 100% answers pending calls with `BUDGET_STOP` and runs one tool-free `_final_round` (90 seconds, exempt from the budget). Scheduled jobs use tighter caps. The same tool and args five times in a row stops the loop. `StuckDetector` (default on) also flags same tool+args+result four times, the same call erroring three times, A/B alternation for six observations, and one tool erroring four times with different args. Three consecutive errors from one tool disable it for the rest of the reply. Side-effecting tools (`writes` or `external`) go through `RunStore.call_once`. An approval in an ordinary chat has no timeout.

The durable record is `agent_runs`, `run_events`, approval rows, and `executed_calls`. Startup marks a dead run `interrupted`, leaves pending approvals pending, and rebuilds an empty assistant message from the tape. Event rows older than 14 days are deleted. `call_once` replays a finished write, refuses a write left in `started` (`unknown_outcome`), and runs again on `error`. Resume is user-initiated and only for an interrupted, latest, non-desk chat that nobody has already resumed. It does not delete the salvaged assistant message. It appends a note (partial text, finished tool results, `started` calls told not to repeat, approvals) and inherits the write journal. It does not restore the dead run’s in-memory tool list. Chat resume does not start by itself on startup.

Compaction does not edit the messages table. When auto-compact is on, the chat is long enough, and the estimate crosses `0.7 × 128_000`, older turns become one `conv_summaries` row. Replay is the first user message, a synthetic summary message, then the tail. `POST /conversations/{id}/compact` takes `{focus}`. The context drawer shows a meter and Compact now. Each round, `microcompact` can stub old tool messages past half the window and keep `result_id` on a handle. `DELETE /conversations/{id}/summary` drops the summary.

`history` and `history_rows` select content only. The next turn sees assistant prose, or a summary, not prior `role: tool` messages. Within one run those tool messages exist only in the in-memory list. Large tool JSON is replaced for the model by a handle. Image bytes are shown in the UI and not sent back.

Usage rows store prompt, completion, cached, cache-write, and reasoning tokens, duration, and cost. `Pricing.cost` can discount cache reads and writes. The in-run `Budget.add` call does not pass those counts, so the dollar cap uses the full input price. An unpriced model adds `0.0` and does not trip the cost axis. There is no per-round or per-tool usage row. `UsageView` shows cache hit rate and reasoning tokens. Traces have parent ids. Kinds on a chat reply include `context`, `compact`, `llm`, `tool`, and `style`. OTLP export exists and defaults off. A `done` event is yielded before the style span is written onto the trace.

`_call_tool` calls `snaps.before` when `snaps.wants(...)`. The snapshot policy itself is outside the app note. The loop also calls the permission gate, filesystem ask, plan mode, desk autonomy, `permrules`, proposal-only jobs, and `skip_permissions`. That policy is another note. Auto-learn runs after `done` when it is enabled, the reply is non-empty, the run is not proposal-only, and the turn is not tainted. `replied` flips on `done`, so a new turn can start while the style pass is still calling the model.

The first user message in a chat titled “New chat” renames it from the first 48 characters. There is no conversation branch. Regenerate does not keep the discarded assistant message.

## 2. What leading apps ship that Grain does not

Names below are the comparison set in the market note. Model names that appear only as examples on a vendor page are what that page says, not a verified catalog.

**Fork and sibling answers.** LibreChat: hover a message, fork, and choose “Visible messages only,” “Include related branches,” or “Include all to/from here” (the default). “Start fork here” forks forward. The original chat is unchanged. Edit can Save in place or Update & rerun as a new sibling, keeping files, manually selected skills, and quoted context. Shareable links keep branches. Sources: [LibreChat forking](https://www.librechat.ai/docs/features/fork), [message actions](https://www.librechat.ai/docs/features/message_actions), [shareable links](https://www.librechat.ai/docs/features/shareable_links). Msty: “Edit as Branch” saves an alternative path; Branch Explorer is documented for label, navigate, and compare, including a side-by-side diff. The explorer page was indexed, not fully fetched. Source: [Msty responses](https://docs.msty.ai/studio/conversations/responses), [Branch Explorer](https://docs.msty.ai/studio/conversations/branch-explorer). Claude Code: `/branch` copies the transcript into a new session and leaves in-flight background work writing into the copy; two terminals on one session without a fork interleave one transcript. Source: [Manage sessions](https://code.claude.com/docs/en/sessions). Claude’s unified desktop/web chat lists “Branching a conversation from an earlier point isn’t available” as a current limitation. Source: [Claude Help Center](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude). ChatGPT is contested, not a spec: an OpenAI staff reply (year not on the page) says “Try again” replaces the previous response and there is no setting to restore multi-version regenerate; later community reports describe a “Message Versions” menu whose continue path is “Branch to a new chat,” and one report says desktop regenerate erases other messages while web arrows remained. Sources: [staff reply](https://community.openai.com/t/where-are-options-for-choosing-better-answers-in-chatgpt/1375312), [See versions follow-up](https://community.openai.com/t/chatgpt-web-update-removed-message-version-arrows-cannot-access-edited-message-history/1374666/220), [r/ChatGPT](https://www.reddit.com/r/ChatGPT/comments/1w19at5/new_message_selector/), [r/OpenAI](https://www.reddit.com/r/OpenAI/comments/1sp6acy/psa_regenerating_a_response_or_editing_your/). Grain regenerates by deleting the last assistant row. The app note states there is no branch and no time-travel fork.

**One prompt, several models.** Open WebUI’s live docs (fetched 2026-10-02): a Compare button sends the same prompt to two or more models, columns on a wide screen and stacked on a small one. Admins can disable it. Merge (“Merge Responses”) runs only on the last exchange, only after every model has finished, on the model whose response is being viewed, and is marked experimental. The docs repo’s `main` MDX still described a “+” control; prefer the live page. Client source, not a help article: regenerating one column resends the parent prompt with that column’s model id. Sources: [Open WebUI docs](https://docs.openwebui.com/features/chat-conversations/chat-features/multi-model-chats/), [Chat.svelte](https://github.com/open-webui/open-webui/blob/53764fe6/src/lib/components/chat/Chat.svelte), [MultiResponseMessages.svelte](https://github.com/open-webui/open-webui/blob/ecd48e2f/src/lib/components/chat/Messages/MultiResponseMessages.svelte). Msty: “Add Split Chat” syncs the composer across panes; layouts save as presets; “Use as Prompt in New Split” opens an unsynced pane for one message without copying the path. Source: [Msty Split Chat](https://docs.msty.ai/studio/conversations/split-chat). Neither Claude’s unified article nor ChatGPT’s Work and projects docs describe sending one prompt to several models at once. Grain keeps one model on the conversation. Switching it does not clear the thread, which the market note treats as ordinary, not as compare mode.

**Read-only tools in parallel inside the parent turn.** Claude Code’s published loop runs `Read`, `Glob`, `Grep`, and MCP tools marked read-only concurrently in one model message. `Edit`, `Write`, and `Bash` run one at a time. Custom tools are serial unless `readOnlyHint` is set. A denial comes back as a tool result and the model continues the same run. Source: [Claude Code agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop). Grain’s parent loop awaits each call. The child loop and read-only `agent_spawn` prestart already follow a parallel-read rule. That parent gap is the one to close. Do not parallelize writes. The market note’s inference is that a loop which parallelizes writes is outside the published Claude contract and needs its own locking story.

**Tool calls and results still in context on the next turn and after resume.** Claude Code accumulates tool inputs and outputs for the session. Resume restores conversation history including tool calls and results, plus the model when it is still allowed. It does not restore background Bash, monitor tasks, or several launch flags (`--mcp-config`, `--settings`, `--plugin-dir`, `--fallback-model`, `--add-dir`). If a Pro or Max session has been idle for more than about an hour and is over 100,000 tokens, the product asks before the next request because the prompt cache is cold either way: compact now, resume the full history, or don’t ask again. Those two thresholds are Claude’s, not numbers to copy. Sources: [agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop), [Manage sessions](https://code.claude.com/docs/en/sessions). Grain’s next turn is content-only. Resume starts a new run with a note and the write journal. A finished write is not executed again. A write left `started` is refused. A read is not journaled, so a resumed run can read it again. The model cannot page the old in-run tool handles unless the note or a later call names them.

**A meter that separates the window from the spend.** LibreChat’s gauge is fed by streaming usage. It can show prompt against the window, a breakdown for dialogue, retained tool results, agent instructions, cached input, completions, branch totals, and conversation totals, plus a runway estimate when consecutive snapshots match. After summarization, the gauge counts the summary plus later turns, while usage and cost totals still include the full branch, including labeled subagent totals. Dollar cost is hidden unless an admin enables it. Reopened chats keep the totals. Source: [LibreChat token usage](https://www.librechat.ai/docs/configuration/token_usage). Claude Code’s `/cost` is session tokens and dollars for API-key billing; `/context` shows what is consuming the window; enterprise seats can see a limit message and no token meter until the limit hits. Source: [Claude Help Center](https://support.claude.com/en/articles/14552983-models-usage-and-limits-in-claude-code). Grain’s context meter returns window, estimate, threshold, and summary. Cache hit rate and reasoning tokens are on a separate usage view. The in-chat meter does not document a post-summary numerator beside a pre-summary spend total, and usage rows are not tagged by round or tool.

**Queue a follow-up instead of interrupting.** LibreChat documents three composer outcomes while a run is in progress: inject at the next tool or agent step, queue for after the response, or interrupt at a provider-safe boundary, keep the partial, and continue the same assistant response. One run accepts up to 10 pending steers. If the server cannot interrupt the provider stream, it falls back to inject-at-boundary. Quoted excerpts (up to 10, 1,500 characters each) stay attached across reconnects; if a replica cannot accept them, they return to the composer. The rendered agents page fetched the same day did not include the steer section; the docs source on `main` and the message-actions page did. Treat the queue and the same-response continue as specified in that source, and confirm on a running build before copying every cap. Sources: [agents.mdx](https://github.com/LibreChat-AI/librechat.ai/blob/main/content/docs/features/agents.mdx), [message actions](https://www.librechat.ai/docs/features/message_actions). Grain already interrupts: steer cancels the provider read and can split a new assistant segment. The described path has no queue-until-done outcome and no quoted-excerpt attachment.

**A pinned goal with pause that is not stop.** ChatGPT desktop `/goal` uses the goal text as the first prompt and the completion criteria. A progress row can pause, resume, edit, or clear it. Follow-ups can be sent while it runs. A side chat can ask for a status recap without injecting into the run. Starting a goal does not widen the sandbox or the approval policy. Pause before losing connectivity. Parallel goals are parallel chats, and the doc says not to let two chats change the same files. Source: [long-running work](https://learn.chatgpt.com/docs/long-running-work). Grain reinjects a plan block every round, and Stop ends the provider read. The app note does not describe a completion criterion pinned above the composer.

**Manual context edits that are not a summary.** Msty: Context Shield drops prior conversation from later turns, with an option to summarize one response at a time. Isolate Context excludes one response and is reversible. Hide removes a message from view and still includes it in context. Delete of the current message tries to reconnect the path; “Delete Message and Descendants” removes the rest of that branch. Continue generation extends a reply that was cut off. Response Metrics can show estimated input and output tokens, latency, and tool name, input, and output. Sources: [Msty responses](https://docs.msty.ai/studio/conversations/responses). Grain’s compaction leaves the messages table alone and stubs old tool messages inside a run. The app note does not describe exclude-one-message, hide-but-keep-in-context, or continue-from-the-cutoff. Grain’s trace view indents spans and shows cached and reasoning counts on the LLM row. The app note does not say whether that view already shows tool arguments and outputs, so a second tool inspector is not justified from these notes.

**On-demand tool schemas, as a related idea.** LibreChat keeps deferred MCP tools out of the initial context and loads them with `ToolSearch` for the rest of the conversation (`deferred_tools` default on). Claude Code defers MCP tool schemas via tool search, except on Vertex or a non-first-party base URL. Sources: [LibreChat agents](https://www.librechat.ai/docs/features/agents), [Claude Code agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop). The app note does not describe on-demand schema loading. It does say `tools_hint` is baked into the system message once, while plan mode and MCP search can change `tool_schemas` later in the same reply without rewriting the hint.

**Specified, and poor near-term copies.** LibreChat’s programmatic tool calling is opt-in: selected MCP tools run from inside a code-interpreter sandbox, and unregistered calls are rejected. It needs a code-interpreter deployment. Source: [LibreChat agents](https://www.librechat.ai/docs/features/agents). Msty Turnstiles are user-authored queues (prompt, regenerate, shield, conditional, loop, checkpoint, fallback model), not a model-driven loop, and they require an Aurum license in the docs. Source: [Msty Turnstiles](https://docs.msty.ai/studio/add-ons/turnstiles). Neither belongs inside `_chat_stream`. Hosted schedule contracts were not fetched. Claude Code’s on-disk JSONL is explicitly unstable; do not parse it. Checkpoint/rewind was named and the page was not fetched.

**Cloud continuation is real and out of scope here.** Claude’s unified experience keeps cloud tasks running if the laptop is closed; tasks that use local files, the browser, or the computer need the desktop open. Source: [Claude Help Center](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude). ChatGPT Work on the desktop can run in a managed cloud environment, or locally when enabled. If the computer is unavailable when a new turn starts, an eligible task can continue in a cloud container that cannot see that computer’s files. Work cannot switch from local to cloud during a turn. Source: [get started with Work](https://learn.chatgpt.com/docs/get-started-with-work). A Codex cloud help page returned 403; a search excerpt said saved VM state is recoverable for up to 7 days. Do not treat 7 days as re-verified. Computer use (clicks, types, opens apps) is a Claude desktop beta and is not a target. An indexed sentence that new Cowork tasks on Pro and Max run in the cloud on 6 October 2026, and that “Only on your computer” will be removed, was not re-read from a full page. Today is 2026-10-02. Do not treat that sentence as current.

## 3. Where Grain is already ahead, or different on purpose

**The window is not the run.** The market note infers that a local Electron app looks thin next to Claude and ChatGPT “if a run dies when the window closes.” The app note says the opposite for the window: abort detaches the viewer, the run keeps publishing to `run_events`, and a later attach tails it. That inference assumed a fact the market note did not check. Process death is a different case, and Grain does not claim laptop-closed continuity. Startup marks the run interrupted, salvages text and tool cards onto the assistant message when it was empty, and waits for the user to press Resume. Pending approvals stay pending.

**Writes have a journal the fetched docs do not describe.** `call_once` keys `run_id`, round, tool name, and args digest. `done` is returned and not called again. `started` returns `unknown_outcome` and is not called again, including across resume via `prior_call`. `error` may run again. Only `writes` and `external` use the journal. Claude Code documents restoring the transcript and not restoring background Bash. It does not document this refuse-to-repeat rule. Keep it. A resumed read can still run again, because reads are not journaled.

**Stop conditions are already stricter than “add more rounds.”** The loop has rounds, tokens, wall clock, and dollars, a nudge at 60%, and a tool-free closing call. Approval time does not count as work time. Stuck detection (four patterns, default on) sits on top of the five-identical-call stop. Job runs use tighter caps and a 1800-second wait around the whole job. Claude Code’s published contract caps tool-use turns and USD. LibreChat’s default max agent steps is 25, with a tool round often counted as three steps (request, tool batch, follow-up). Grain’s default of 25 rounds stays. Matching LibreChat’s three-step arithmetic would change how many model calls fit, which this comparison does not recommend.

**Compaction keeps the raw messages and puts standing instructions back every turn.** The summary is one row. The user can delete it. Manual compact accepts a focus string. Microcompact stubs old tool messages inside the run and can keep a `result_id`. Project name, description, and `system_prompt` are in the stable prefix on every request. Claude Code tells users to keep durable rules in a file that is re-injected, because a summary can drop early instructions, and it emits a compact-boundary event. Grain already re-injects the project prompt and emits a `compact` span. Two user-reported Claude Code bugs (a resumed compacted session that restarted a multi-agent workflow because the session id changed, and a later auto-compact that did not fire) are bug reports, not a contract. Grain should not switch to a compaction that deletes message rows.

**Cache layout and token columns exist.** Stable text is the first system message. Volatile blocks sit just before the newest user message. Usage rows store cached, cache-write, and reasoning tokens, and the usage view shows cache hit rate and reasoning tokens. `stream_chat` does not send `cache_control`. Caching is prefix order plus whatever the provider does automatically. The remaining defect is that the dollar cap ignores the discount the usage row already records, and the date line sits in the stable prefix, so the prefix changes every day. An older context note wanted that date line in the volatile block. That part is still open. It is not “no cache accounting.”

**Traces exist.** Spans have `parent_id`. Tool spans parent to the round. Compact and style spans exist. OTLP export is implemented and off by default. Open WebUI’s fetched docs do not document a built-in tool trace; a third-party filter and a maintainer thread are not the product. LibreChat’s first-party trace mention in this pass is an admin Langfuse link. Msty documents per-message tool name, input, and output. Grain’s gap against LibreChat is the window-versus-spend meter, not an empty trace.

**One composer, local files, asks left in place.** Claude’s unified product and Grain both use one thread for a short question and a longer tool-using task. Grain’s ask path waits on an approval row with no timeout in an ordinary chat. `SkipPermissionsToggle.tsx` is already in the working tree the app note read. Leave external side effects behind an ask. Do not default the skip control on. ChatGPT’s own rule is the local-first rule to keep: do not move a turn that used this machine’s files onto a runner that cannot see them. Grain has one runner, on this machine. That is the design, not a missing cloud VM.

**Subagent isolation is not established either way.** Claude Code and LibreChat document a child with its own window whose final text returns to the parent. The app note describes the child loop, the gather cap, and read-only prestart. It does not say whether the parent ingests the child transcript. Do not build or skip an isolation change from these two notes.

**Parity, so leave it alone.** Streaming with stop, regenerate-in-place, a model picker that does not clear the thread, project instructions in the prompt, a tool loop that pauses for approval, and a usage readout are what the market note treats as ordinary controls. Grain ships them. The README under-describes steer, durable runs, resume, compaction, stuck detection, cache layout, and cache columns. That is a docs miss. It is not a product gap.

## 5. The top three builds

Order follows the loop. A fork of a transcript that still drops tool results copies the hole. Parallel reads need the serial write journal to stay put. The dollar cap should match the price the usage row already records before any new meter is trusted.

### 1. Put tool results on the next turn and on resume

**Work.** `repos.history` and `history_rows` gain the tool events already stored on the message. `compaction.prepare_history` attaches them only on the unsummarized tail, using the handle text `tool_results.for_model` already builds, not raw image bytes. Turns folded into `conv_summaries` stay folded. Resume still goes through `resume.build_resume_note` and `runs.call_once(inherit=...)`. The new run’s model messages include the salvaged tool results because they are on the message row, not because the dead Python list was restored.

**Offline check.** A fixture conversation with an assistant row that has `tool_events`. Building the next turn’s messages includes those results for a chat under the compact threshold. For a chat over the threshold, tool results older than the summary boundary appear only as part of the summary placeholder, and tool results on the kept tail are still present. Resume fixture: a journaled `done` write returns `replayed: true` and the tool function is not called; a `started` write returns `unknown_outcome` and is not called; the messages handed to a stubbed `stream_chat` contain the salvaged tool result text. No network.

### 2. Run read-only parent tools together

**Work.** In `_chat_stream`, batch a round with the predicate `subagents._parallel_ok` already uses, capped at 8. Identical `(tool, args)` in that batch run once and share the result. Anything in `writes` or `external`, anything whose mode would ask, plan mode, and `agent_*` remain a barrier and run one at a time. Side effects keep `call_once` and the approval row. Stop fills the unfinished calls with the existing “not executed” tool message.

**Offline check.** Two `safe` or `network` tools in one parent round both start before either finishes. The same `(tool, args)` twice invokes the function once. A `writes` tool placed between two reads does not start until the reads have finished, and it is the only call that hits the journal. An `external` tool is not in the gather. A stop set after the first call starts leaves the later call unexecuted. No network.

### 3. Charge the cap what the log charges, and split the meter

**Work.** At `Budget.add` in `_chat_stream`, pass cached and cache-write tokens into `Pricing.cost`, the same arguments `_record_usage` already passes. Move `_today_hint()` from the stable prefix into `volatile_blocks`. Extend `GET /conversations/{id}/context-meter` with a window figure (summary plus tail, once a summary exists) and a spend figure summed from `usage_log` for that conversation, including rows from before the summary. Stamp the loop’s round index on the usage row. Show the two figures in `ContextDrawer`. Leave `maxToolRounds` at 25. Leave unpriced models at cost `0`.

**Offline check.** A usage sample with cached tokens produces a `Pricing.cost` below the full input price, and `Budget.add` for that sample equals the discounted figure. A fixture whose discounted cost is under `maxRunCost` and whose undiscounted input cost is over it does not set `partial` to `cost`.
