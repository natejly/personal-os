## Scheduled tasks, agent jobs, agent inbox and Cowork desks

### Where we are

**Scheduler (`backend/personal_os/jobs.py`, 495 lines).** A `jobs` table (db.py SCHEMA ~L205; `kind` and `run_at` added through `_migrate`) holds `kind` (`cron`|`once`), `cron`, `run_at`, `timezone`, `enabled`, `prompt`, `project_id`, plus bookkeeping `next_due_at`, `last_due_at`, `last_fired_at`, `last_run_id`, `last_error`. `Scheduler.loop` sleeps to the earliest `next_due_at` (capped at `MAX_SLEEP_S`=60 because asyncio's clock stops during suspend), then `tick()` calls `Jobs.arm()` and `Jobs.due()`. For each due job it runs `plan()` and then `mark_fired()` (clock bookkeeping is committed BEFORE launch, so a crashing launch cannot re-fire). Catch-up is exactly one run for the most recent missed slot (`prev_fire`), with `slots_between` capped at 500 and `LATE_GRACE_S`=90. `app._job_prompt` prepends a late notice. Once-jobs retire themselves (`mark_fired(disable=True)`). `SEED_JOBS` (morning brief, reply drafts, weekly review) ship disabled. croniter and ZoneInfo are used; the DST behaviour was already considered.

**Job run (`app._launch_job`, ~L2051).** Each fire creates a fresh conversation with `settings.job_id` (hidden from the sidebar) and starts `bus.start(..., kind="job")` over `_run_chat`. `PROPOSAL_ONLY_KINDS=("job",)` turns outward tool calls into rows in `proposals` (pending/accepted/rejected, `args_digest`, atomic `claim`, edit-on-accept; `POST /proposals/{id}/accept` executes through `run_store.call_once`). `JOB_BUDGET` caps jobs at 8 rounds, 60k tokens, 240 s and $0.20. `JOB_HINT` is injected into the prompt. `POST /jobs/{id}/run` fires a job by hand.

**Agent Inbox (`app.agent_inbox`, `GET /inbox`; `AgentInbox.tsx`, 285 lines).** It is built purely from rows. "Needs you" holds pending approvals and pending proposals. "While you were away" holds one entry per `kind='job'` run in the last N hours, with late/missed counts, tool-call count, proposal counts and the first 1400 chars of the reply.

**Cowork desks (`cowork.py` 657, `workspace.py` 378, `plans.py` 409; `CoworkView/DeskRail/DeskDetail/DeskPlan/DeskReview/DeskFiles/HomeCowork.tsx`; `/cowork/desks*` routes at app.py ~L4773-5120).** Tables `desks`, `desk_events` (timeline plus the needs_you queue) and `desk_outputs`. `Desks.set_status` is the only status writer (status and event commit in one tx). `claim_run` and `claim_output` are single-UPDATE locks. `settle()` decides terminal state from (partial, stopped, error). `recover()` marks live desks `interrupted` on boot and never auto-resumes. Budgets live in `desks.budget` / `deskMaxTurns/Cost/Live`. A desk can be started, resumed, paused, stopped, steered, and have its outputs accepted or rejected (promote and read-back verify). The renderer raises a `new Notification('Cowork', ...)` at App.tsx:72 for desk events only.

**Weak spots (verified in code).**
1. A failed or errored job run is never retried; `Scheduler.tick` has no completion hook (it does not wait on the run), so `jobs.last_error` only records a *launch* exception, not a run that ended `error`/`interrupted`.
2. There is no overlap guard. `_launch_job` never checks whether the previous run of the same job is still live; a slow run plus a short cron stacks runs. `bus.start` is keyed per conversation, and each fire makes a new conversation, so nothing prevents it.
3. There is no failure streak, auto-pause or backoff. A job whose model key is broken fails every slot forever, silently, and only shows up as a "failed" count in the inbox.
4. There is no per-job run history surface. History is derived from `agent_runs where kind='job'` limited to the last 72 h, with no per-job view, no duration, no success rate and no cost.
5. Jobs get no OS notification on completion or failure (desks do); a job that "needs you" only appears if the app is open and the inbox is looked at.
6. There is no per-job tool allowlist; every job gets the global tool set (minus outward calls). AnythingLLM scopes tools per job.
7. There are no event triggers (webhook or file or calendar change); cron and once only.
8. Jobs have no manual dry run that shows what would happen without creating proposals, and no deterministic jitter or expiry for forgotten recurring jobs.
9. `docs/research/roadmap.md` A8 ("tasks with inbox, run history, OS notifications") is only partly shipped: the inbox exists; history and notifications do not.

### What the best open-source systems do

- **AnythingLLM Scheduled Jobs** ([overview](https://docs.anythingllm.com/scheduled-jobs/overview), [viewing runs](https://docs.anythingllm.com/scheduled-jobs/viewing-runs), [configuration](https://docs.anythingllm.com/scheduled-jobs/configuration)). A Job is (name, prompt, schedule, allowed tools). A Run is a row with status `queued|running|completed|failed|timed out`, start, duration, error, and the full result with thoughts and tool calls. The UI shows the last 50 runs per job. `SCHEDULED_JOB_MAX_CONCURRENT` defaults to 1 and `SCHEDULED_JOB_TIMEOUT_MS` to 300000; a timed-out run is killed and its partial output is kept. A single job cannot overlap itself. Completion notifications use browser push. It has no catch-up: scheduled times are missed while the host is down (we are ahead there).
- **APScheduler** ([user guide](https://apscheduler.readthedocs.io/en/3.x/userguide.html)). The three knobs every serious scheduler converges on are `misfire_grace_time` (how late a fire may still run), `coalesce` (collapse N missed runs into one; we do this) and `max_instances` (default 1: do not start a job whose previous run is still going; we do not do this).
- **OpenHands Automations** ([RFC #13275](https://github.com/OpenHands/OpenHands/issues/13275), [repo](https://github.com/OpenHands/automation), [managing](https://docs.openhands.dev/openhands/usage/automations/managing-automations)). Automation, AutomationTrigger (cron or webhook with secret and event filter) and AutomationRun (PENDING to RUNNING to COMPLETED/FAILED, linked to a real conversation). Webhook events pass an auth check and a filter, then go onto a queue, then execute in a fresh sandbox. The Activity Log supports JSON/CSV export of run history.
- **Khoj Automations** ([docs](https://docs.khoj.dev/features/automations/)). Cron in the user's tz, one dedicated conversation per automation, manual "run now", results delivered by email, and the query is rewritten before execution. The docs say nothing about retries or failure handling; that is a known gap, not a model to copy.
- **n8n** ([error handling](https://mintlify.com/n8n-io/n8n/workflows/error-handling)). Per-node `retryOnFail`, `maxTries` (cap 5), `waitBetweenTries` (cap 5 s); a separate Error Workflow fires on a failed execution for alerting. Caveat from [#37779](https://github.com/n8n-io/n8n/issues/37779): a retry budget that resets every cycle can loop forever, so the retry count has to be persisted across attempts. Activepieces follows the same pattern (runs list with statuses, retry a failed run, failure alerts; [docs](https://www.activepieces.com/docs/flows/debugging-runs), page not retrievable in full).
- **Huginn** ([scheduler](https://github.com/huginn/huginn/blob/master/lib/huginn_scheduler.rb), [event.rb](https://github.com/huginn/huginn/blob/master/app/models/event.rb)). Agents emit Events with `expires_at` from `keep_events_for`, a "Dry Run" button executes an agent without side effects, and propagation to downstream agents runs on a 1-minute tick. Retention is per event, with a cleanup tick every 6 h.
- **Claude Code scheduled tasks** ([docs](https://code.claude.com/docs/en/scheduled-tasks)). Deterministic per-task jitter derived from the task id (up to 30 min or half the interval for recurring, up to 90 s early for one-shots); recurring tasks auto-expire after 7 days (fire once more, then delete) to bound forgotten loops; at most 50 tasks; no catch-up (one fire when idle). Durable scheduling is a separate product (Routines / Desktop scheduled tasks), with per-task permission modes.

Not found: a mature open-source "Devin-style" async UX beyond OpenHands (run = real conversation, activity log, resolver on events). Our desk model (plan approval, outputs gate, needs_you queue) is already ahead of most of it.

### Gaps

| # | gap | who does it | impact | effort |
|---|---|---|---|---|
| 1 | No overlap guard (`max_instances=1`): a still-running job is launched again | APScheduler, AnythingLLM | High (cost and duplicate proposals) | S |
| 2 | No retry with persisted attempt count for runs that END in error | n8n, Activepieces | High | M |
| 3 | No failure streak, auto-pause or alert; silent permanent failure | n8n error workflow, Activepieces alerts | High | S |
| 4 | No per-job run history (duration, status incl. timed out, cost, success rate) and no >72 h view | AnythingLLM, OpenHands | Med-High | M |
| 5 | No OS notification for job completion/failure/proposals | AnythingLLM push | Med-High | S |
| 6 | No per-job tool allowlist | AnythingLLM | Medium (safety and cost) | M |
| 7 | No dry run / preview of a job without creating proposals | Huginn | Medium | S |
| 8 | No event triggers (webhook, file change, calendar) | OpenHands, n8n, Activepieces | Medium; external surface, needs ask-first design | L |
| 9 | No deterministic jitter or expiry for recurring jobs | Claude Code | Low (local single user) | S |
| 10 | Run retention is implicit; no export | OpenHands, Huginn | Low | S |

### Build next

**jobs-1 (job run policy: overlap guard, retry with backoff, failure streak auto-pause).** A new `jobs_policy.py` adds a `RunWatcher` that awaits each launched run and applies three rules: skip a fire while the previous run of the same job is still live (recorded as a skipped fire, not silent); re-launch a run that ended in `error` or `interrupted` up to `max_retries` times with exponential backoff, the attempt count persisted in the run's `input` so it cannot reset; and after N consecutive failed fires set `enabled=0` with a `paused_reason` the inbox shows as needs-you. Everything is offline testable with the injected clock and sleep already in `Scheduler`.

**jobs-2 (per-job run history, plus job notifications).** `GET /jobs/{id}/runs` returns the last 50 runs with status, duration, cost, tool-call count and proposal counts (rows only), the inbox gains a per-job History drawer, and the existing renderer `Notification` path is extended to job failures, auto-pauses and new pending proposals so unattended work is visible without the inbox open. Nothing leaves the machine.

**jobs-3 (per-job tool allowlist plus a safe dry run).** Each job gets an optional `allowed_tools` list, enforced by writing `off` into the job conversation's `settings.tools` for every other tool (a narrowing only, never widening, and it cannot undo the proposal-only rule). `POST /jobs/{id}/dry_run` runs the same prompt with every non-read tool turned off, so the user can preview a job's report before enabling it.

Specs below carry the file lists and tests. I did not spec event triggers (gap 8): they add an inbound network surface, which needs an owner decision on ask-first design.

### Specs

#### jobs-1: Job run policy: overlap guard, retry with backoff, failure-streak auto-pause (M)

**Why.** Highest-leverage reliability gaps, verified in code: Scheduler.tick launches without checking whether the previous run is live (APScheduler max_instances=1, AnythingLLM 'a job cannot overlap itself'), nothing retries a run that ends in error (n8n retryOnFail/maxTries, with the n8n #37779 lesson that the attempt count must be persisted), and a permanently failing job fails silently forever (n8n error workflow, Activepieces alerts). jobs.last_error today only records launch exceptions.

**Files.** `backend/personal_os/jobs_policy.py (new)`, `backend/personal_os/db.py (additive _migrate entries for jobs)`, `backend/personal_os/jobs.py (Scheduler: optional policy hook, skip recording)`, `backend/personal_os/llm.py (DEFAULT_SETTINGS keys)`, `backend/personal_os/app.py (small: construct policy, wire into scheduler and _launch_job, JobIn/JobPatch fields, inbox needs_you)`, `src/renderer/src/lib/types.ts, api.ts, components/AgentInbox.tsx (show paused/skipped/retry badges, resume button)`, `backend/tests/test_job_policy.py (new)`

**Design.** Schema: add via db._migrate `wanted['jobs']` (ALTER, not SCHEMA): `max_retries INTEGER NOT NULL DEFAULT 1`, `consecutive_failures INTEGER NOT NULL DEFAULT 0`, `paused_reason TEXT`, `last_skip_at REAL`, `last_skip_reason TEXT`. Add `Jobs.FIELDS` entries for `max_retries` only (user-editable); the rest are written by policy methods on Jobs (`record_outcome(id, ok)`, `record_skip(id, reason, at)`, `pause(id, reason)`), each a single UPDATE. Settings (add to llm.DEFAULT_SETTINGS or PUT /settings drops them): `jobRetryBackoffS: 120` (base; delay = base * 2**(attempt-1), capped 1800), `jobFailureStreakLimit: 3`. jobs_policy.py: `class JobPolicy(jobs: Jobs, run_store, clock, sleep, launch)`. (a) `async def admit(job, fire) -> tuple[bool, str|None]`: look up `run_store.of_kind('job', since=now-86400)`; if any run whose `input.job_id == job.id` has status 'running' (use the store's live status; a run row with ended_at NULL), return (False, 'previous run still running'), call `jobs.record_skip`. Manual /jobs/{id}/run also goes through admit but returns 409 with the reason. (b) `async def watch(job, fire, run_id)`: spawned with asyncio.create_task by the wrapped launch; polls `run_store.get(run_id)` via the injected sleep (1 s, cap) until ended; status 'done' -> `record_outcome(ok=True)` resets streak; status 'error' or 'interrupted' -> `record_outcome(ok=False)`; if `fire.get('attempt',1) <= job.max_retries` and streak < limit, sleep backoff then `launch(job, {**fire, 'attempt': attempt+1, 'retry_of': run_id, 'late': False})` (attempt rides in agent_runs.input, so it survives; the retry is the same slot, never a new one); a stop by the user (status 'stopped' or 'cancelled') is NOT a failure. When `consecutive_failures >= jobFailureStreakLimit` call `jobs.pause(id, 'paused after N failed runs: <last error>')` which sets enabled=0 and next_due_at=NULL (use Jobs.update re-arm path). (c) `JobPolicy.recover_on_boot()`: runs left 'interrupted' by a restart are NOT retried (outcome unknown; a restart is not a model failure) but do count nothing; document this. Scheduler: add optional `policy` param; in tick, before `launch`, `ok, why = await policy.admit(job, fire)`; if not ok, skip launch but still call mark_fired so the slot is consumed (no thundering catch-up after the long run ends) and append the skip to `fired` with `skipped: why`. After a successful launch, `asyncio.create_task(policy.watch(...))` and keep the task in a set so shutdown cancels it. Inbox: `agent_inbox()` adds paused jobs (enabled=0 and paused_reason not null) to `needs_you.paused_jobs` and counts; fire records in away entries expose `attempt` and `retry_of`. UI: AgentInbox shows 'Paused: <reason>' with a Resume button (PATCH /jobs/{id} {enabled:true} which also clears paused_reason and consecutive_failures in Jobs.update when enabled flips true), a 'retry 2/2' chip, and a 'skipped: still running' note. Anti-goals respected: no heartbeat (watch only exists while a run is live), retries reuse the same proposal-only run kind, nothing outward is executed.

**Tests.** backend/tests/test_job_policy.py, plain script style like test_agent_jobs.py, injected fake clock/sleep, stub `launch` that returns synthetic run ids and a stub run_store whose rows the test flips to done/error. Cases: (1) overlap: job whose last run is still running is skipped, last_skip_reason set, slot consumed (next_due_at advanced, no second launch after the run finishes); (2) retry: run ends error, retried once after base backoff delay (assert the fake sleep received 120), attempt=2 and retry_of in the fire record, a second failure does not retry past max_retries=1; (3) attempt count persisted: a fresh JobPolicy built from the stored input does not reset attempts; (4) streak: 3 consecutive failed fires pauses the job (enabled False, paused_reason set, next_due_at None, Scheduler.due() excludes it); a success in between resets the streak; (5) user-stopped run is not counted as a failure; (6) resuming via Jobs.update(enabled=True) clears paused_reason and streak and re-arms from now with no catch-up; (7) migration idempotent on an existing DB: open a db created with the old jobs schema, new columns appear, existing rows keep enabled state; (8) /inbox exposes paused_jobs (TestClient with the token header); (9) manual POST /jobs/{id}/run on a job with a live run returns 409.

**Done when.** With the stub launcher: a still-running job is never launched twice; an errored run is retried up to max_retries with exponential backoff and the attempt count survives a policy rebuild; three consecutive failures auto-pause the job and the Agent Inbox shows it under Needs you with a working Resume; user stops never count as failures; existing test_agent_jobs.py, test_runs.py and test_scheduled_tasks-style tests still pass; no network and no real model calls.

#### jobs-2: Per-job run history API/UI and OS notifications for job events (M)

**Why.** AnythingLLM and OpenHands both centre the feature on a per-job run history (status incl. timed out, duration, error, last 50 runs, export); ours has only a 72 h cross-job feed with no durations, cost or per-job view, so the user cannot tell whether a job is healthy. docs/research/roadmap.md A8 listed 'run history and OS notifications' and only the inbox shipped. Desks already raise a Notification (App.tsx:72); jobs never do, so unattended failures and new proposals are invisible while the app is in the background.

**Files.** `backend/personal_os/job_history.py (new: pure functions over run_store/proposals rows)`, `backend/personal_os/app.py (small: GET /jobs/{id}/runs, GET /jobs/{id}/stats, GET /jobs/{id}/runs.csv; add `since_id`-style cursor to /inbox)`, `backend/personal_os/runs.py (add RunStore.of_job(job_id, limit) using json_extract on agent_runs.input, and an index-free scan fallback)`, `src/renderer/src/lib/api.ts, types.ts`, `src/renderer/src/components/AgentInbox.tsx (History drawer per job)`, `src/renderer/src/App.tsx (extend the existing Notification effect to job events)`, `backend/tests/test_job_history.py (new)`

**Design.** job_history.py: `summarize_run(run_row, event_counts, proposal_counts, tx_cost) -> dict` with fields {run_id, conversation_id, status ('done'|'error'|'interrupted'|'stopped'|'running'; add derived 'timed_out' when run budget.partial in ('time','seconds') or error text matches the JOB_BUDGET maxRunSeconds stop), started_at, ended_at, duration_s, due_at, late, missed_slots, attempt, manual, tool_calls, proposals {pending,accepted,rejected}, cost (from run budget snapshot if present else null), error, summary (first 400 chars)}; `stats(rows) -> {runs, ok, failed, success_rate, median_duration_s, last_ok_at, total_cost}`. RunStore.of_job: `SELECT * FROM agent_runs WHERE kind='job' AND json_extract(input,'$.job_id')=? ORDER BY started_at DESC LIMIT ?` (limit clamp 1..200, default 50), no new table, no retention change. Routes: `GET /jobs/{id}/runs?limit=50` and `GET /jobs/{id}/stats?days=30` (404 for unknown job), `GET /jobs/{id}/runs.csv` returns text/csv for export (local download only). Inbox: add `GET /inbox/notify?since=<ts>` returning compact events `[{id:'run:<run_id>:done|error', kind:'job_failed'|'job_done_with_proposals'|'job_paused'|'proposal_pending', title, body, at}]` computed from rows with created/ended time > since, capped at 20; no polling loop on the backend. Renderer: the App already receives /events app-wide SSE topic (LearnWorker, see async-learn); on a job run `done` event or on window focus, call `/inbox/notify?since=<last seen, localStorage>` and fire `new Notification(title, {body})` only when document is hidden and permission is not denied (same guard as App.tsx:72); add a Settings key `notifyJobs: true` (add to llm.DEFAULT_SETTINGS) that gates it. Notification bodies include only job name and counts, never reply text (privacy: reply can contain mail content). AgentInbox: a 'History' button per job row opens a drawer with the stats strip and a list of runs, each linking to its conversation, plus 'Export CSV'.

**Tests.** backend/tests/test_job_history.py: build a temp DB via the existing test harness pattern, insert agent_runs rows with kind='job' and varying input.job_id / status / timestamps through RunStore (no model calls); assert of_job filters by job_id, orders newest-first, honours limit; summarize_run computes duration, derives timed_out from a budget snapshot, attaches proposal counts from Proposals.counts; stats gives correct success_rate and median on a hand-made set including 0 runs (no ZeroDivision); CSV export has header row and escapes commas/newlines in error text; /jobs/{unknown}/runs is 404; /inbox/notify with since filters older events, redacts reply text (assert body contains no substring of the stubbed reply), and caps at 20; settings round-trip: PUT /settings {notifyJobs:false} persists (proves the DEFAULT_SETTINGS key was added).

**Done when.** Each job has a History view showing its last 50 runs with duration, status (including timed out), proposals and a link to the transcript, plus a success-rate strip; CSV export downloads; a failing, paused or proposal-producing job raises one OS notification when the app is hidden and notifyJobs is on, and none when off; notification text contains no model output; all tests pass offline.

#### jobs-3: Per-job tool allowlist and side-effect-free dry run (M)

**Why.** AnythingLLM scopes each scheduled job to an explicit set of tools/skills/MCP servers; our jobs inherit the whole toolbox, which makes unattended runs costlier, noisier and a larger prompt-injection surface (a morning brief has no business calling run_python or MCP tools). Huginn's Dry Run lets users see what an agent would do before trusting it; our seeded jobs ship disabled precisely because the user cannot preview them cheaply. Both fit the existing mechanism: conversation settings.tools already overrides toolbox.effective (app.py ~L1069).

**Files.** `backend/personal_os/job_tools.py (new: allowlist -> tools-mode map, read-only classifier)`, `backend/personal_os/db.py (additive _migrate: jobs.allowed_tools TEXT)`, `backend/personal_os/jobs.py (FIELDS gains allowed_tools; JSON encode/decode in _row and writers)`, `backend/personal_os/app.py (small: _launch_job applies the map; JobIn/JobPatch field; POST /jobs/{id}/dry_run)`, `src/renderer/src/components/AgentInbox.tsx (or the job editor sheet: tool multi-select and Preview button)`, `src/renderer/src/lib/api.ts, types.ts`, `backend/tests/test_job_tools.py (new)`

**Design.** Schema: `jobs.allowed_tools TEXT` (NULL = inherit global behaviour, so every existing job is unchanged; JSON array of tool names otherwise), added through db._migrate. Jobs._row decodes it to list|None; create/update accept `allowed_tools: list[str]|None`, validated against `toolbox.list()` names in the route (400 on unknown names, listing them). job_tools.py: `def tool_modes(allowed: list[str]|None, all_tools: list[dict]) -> dict[str,str]`: for every tool NOT in allowed set mode 'off'; tools in allowed are left out of the map (so the user's global/project mode stays; this can only NARROW, never turn something on or bypass ask-first). Always-forced rule: tools whose danger tier is 'schedules' stay off for job runs regardless (already proposal-only; keep consistent) and the allowlist can never include them; `READ_ONLY_TOOLS` derived from the existing tool metadata (the danger tier field `safe`; verify field names in tools.py when building) is used by dry run. `_launch_job`: after `convos.create`, `convos.update(conv.id, {'settings': {..., 'tools': tool_modes(job['allowed_tools'], toolbox.list())}})` only when allowed_tools is not None; MCP tools are matched by their effective name and an allowlisted MCP tool still honours its grant and schema_hash pinning (unchanged code path). Dry run: `POST /jobs/{id}/dry_run` builds the same conversation but with `tool_modes` forcing every non-read-only tool off (read-only = the safe tier: search, read, list, memory read, todos read) and prefixes the prompt with a one-line DRY_RUN_HINT ('This is a preview. Do not propose or perform any change; describe what you WOULD do and report what you found.'); it runs as kind='job' with `input.dry_run=true` so it is proposal-only anyway, is excluded from `consecutive_failures` accounting and from the inbox 'while you were away' list unless `?include_dry=1`, and returns {run_id, conversation_id}. Budget stays JOB_BUDGET (no maxToolRounds increase). UI: in the job editor add 'Tools' (default 'All tools' = NULL; choosing 'Only these' shows checkboxes grouped as in Settings), and a Preview button next to Run now that opens the resulting conversation. Seeded jobs get sensible allowlists when created: Morning brief = calendar/gmail/todos read tools; Weekly review = todos/calendar/search_chats; Scan unread = gmail read + draft tool (draft stays a proposal). Seeding only affects rows created after upgrade; existing rows keep NULL.

**Tests.** backend/tests/test_job_tools.py, offline, stub llm: (1) tool_modes(None, tools)=={} and a job without allowed_tools launches exactly as before (assert conversation settings has no 'tools' key); (2) tool_modes(['calendar_events'], tools) marks every other tool 'off' and never includes the 'schedules' tier tool as allowed even if listed (route returns 400 for it); (3) unknown tool name in POST /jobs returns 400 naming it; (4) _launch_job with allowed_tools set: use a stub llm that requests a tool outside the list and assert the toolbox returns the disabled/unknown-tool error result and the proposal count is zero; use one inside the list and assert it executes (read tool, fake); (5) the allowlist cannot widen: a globally 'off' tool listed in allowed_tools stays off; (6) dry_run: stub llm that tries a write tool is refused, no `proposals` rows created, run input has dry_run=true, run excluded from /inbox by default and present with include_dry=1, and a failed dry run does not increment consecutive_failures (guard with hasattr if jobs-1 has not merged: test only the exclusion from inbox); (7) migration idempotent and existing rows decode allowed_tools to None; (8) PATCH allowed_tools: null resets to inherit.

**Done when.** A job can be restricted to a named tool list and, when it is, a run provably cannot call anything else (verified with a stub model that tries); the restriction only narrows existing tool modes; Preview runs the job read-only, creates no proposals and no external effects, and does not pollute the inbox or failure counts; existing jobs behave identically; no new settings keys are required (if one is added it is in llm.DEFAULT_SETTINGS); all tests pass offline.
