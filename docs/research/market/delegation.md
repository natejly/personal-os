# Delegation features in personal AI apps (as of 2026-10-02)

Scope is product behavior a later comparison can turn into gaps: Claude desktop cowork, scheduled tasks, and skills; ChatGPT scheduled tasks and projects; the MCP spec and official client guidance around the 2026-07-28 revision; Open WebUI and AnythingLLM skills and tool scoping. Grain’s codebase was not reviewed. Claims below come from pages fetched on 2026-10-02 unless a finding says the page was only seen as a search extract.

## What did Claude desktop ship by late 2026 for cowork, scheduled tasks, and skills? How do runs get permission when nobody is watching?

### Takeaway
By 2 October 2026 Claude Cowork is a paid, multi-surface agent that already defaults to cloud sessions, with scheduled tasks that keep running when the computer is off, three permission modes (and a narrower Auto/Manual pair in the new combined chat experience), and account-level skills that require code execution. Unattended runs are expected to use Auto or Skip; deletion still stops for an explicit Allow, and Anthropic’s own safety article tells people not to schedule consequential actions because nobody is watching.

### Cited Findings
- Cowork is on paid plans only (Pro, Max, Team, Enterprise). Desktop (macOS and Windows) is available on all of those plans. Web is on Pro, Max, and Team, and on Enterprise only if an admin enables it. Mobile matches web. The Chrome side panel is on Max and Team, rolling out to Pro, and Enterprise only if an admin enables it. Chat and Cowork share one home on desktop, web, and mobile; the Chrome side panel opens straight into a Cowork session. — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork) (help article, updated 2026-10-01)
- A new experience is rolling out gradually to Pro and Max, with more plans later: the message box no longer offers separate Chat and Cowork choices, and Claude decides whether a message is a quick answer or a task. The same note appears on the scheduled-tasks and safety articles. — [Get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Schedule recurring tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork) (updated the week of 2026-10-02); [Use Claude Cowork safely](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely) (updated more than two weeks before 2026-10-02)

Tasks already started on the computer stay there. — [Get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Schedule recurring tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)
- As of the 1 October help article, Cowork sessions already run remotely in the cloud (called beta). Work runs in an isolated environment on Anthropic’s servers; sessions and files follow the account across desktop, web, and mobile; work continues if the laptop is closed. Local files, the browser, and computer use still need the Claude Desktop app open and connected. Code and shell commands run in that isolated server environment. Claude can break work into subtasks and coordinate parallel workstreams. — [Get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Use safely](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely)

Isolation limits where code runs, not what Claude can read or do through granted connectors, folders, or the browser. If the desktop app is offline, a cloud session cannot reach the computer. Files opened through the desktop app are processed on Anthropic’s servers. — [Use safely](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely)

Live artifacts created before 19 August 2026, and plugins that include local MCP servers, are desktop-only. — [Get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)

### Inferences
- The product already treats “cowork” as the agent path inside Claude, not a separate app, and is mid-migration from optional local sessions to cloud-by-default for new Pro/Max tasks on 6 October 2026.
- Unattended permission is a saved mode plus classifiers, not a human queue. Auto is the designed unattended mode (a model checks each action). Skip is unattended with no check. Manual cannot finish a blocked action until someone answers, so it is a poor fit for a run with nobody present. The scheduled-task form’s “approval mode” field is the likely place that choice is stored, but the help article never says so.
- File deletion is the one action the docs say always waits for a person, in every mode. A scheduled cleanup that needs a permanent delete will stall or fail closed unless someone is there to press Allow.
- Skills are account-scoped instruction packages with progressive use (description decides when they load; full instructions are in the skill), shared across chat, Cowork, Office add-ins, and Claude Code. They are not a per-run tool allowlist.

### Gaps
- The scheduled-task article names “approval mode” and does not define the options, the default, or what happens when a cloud run in Manual (or a blocked Auto action) needs a person who is offline. No fetched page says whether the run queues, skips the action, fails, or waits until the next time the app is open.
- No fetched page gives numeric caps for Claude scheduled tasks (how many active tasks, minimum interval beyond the hourly/daily/weekly/weekday/manual set, or a usage quota specific to schedules).
- The dedicated Cowork projects article was not fetched. Projects are confirmed only as workspaces with their own files, context, instructions, and memory.
- Dispatch was not fully fetched. Finer limits (which Pro/Max accounts, how pairing works) are unverified.
- The plugins blog’s date was not on the extract, so “older” is inferred from it contradicting the current help center, not from a dateline.
- No 2026 Anthropic engineering post on cowork permissions was fetched. The sources here are help center, Academy, the plugins blog, the plugin GitHub README, and the enterprise skills docs.

## How do ChatGPT scheduled tasks and projects compare (caps, inbox, permissions)?

### Takeaway
ChatGPT’s fetched product docs separate two products. Scheduled tasks are unattended runs with an inbox called Scheduled, cloud-or-desktop placement, sandbox modes, and `approval_policy = "never"` when the org allows it. Projects are persistent workspaces (files, instructions, memory), not a scheduler. Numeric active-task caps are widely repeated in search snippets of the help article, but that article timed out on every fetch and the snippets disagree, so the caps are not treated as verified.

### Cited Findings
- Scheduled tasks run in the background. On web and mobile, eligible plans can also run tasks from supported app events. The Scheduled view lists active, paused, and completed tasks and recent runs. Tasks can be combined with skills. Workspace admins are pointed at a separate Team Tasks feature: recurring or event-triggered work shared by a team, run in the cloud through the team’s service account and configured app connections. — [Scheduled tasks (ChatGPT Learn)](https://learn.chatgpt.com/docs/automations) (full fetch, 2026-10-02)
- The same page says GPT-5.5 retires from ChatGPT, ChatGPT Work, and Codex on all plans on 14 October 2026, and tells people to retarget scheduled tasks off GPT-5.5. For Codex with ChatGPT sign-in it names `gpt-6-sol` where the plan and workspace allow it. The API is unaffected. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Web vs desktop placement: web tasks (Chat or ChatGPT Work) can use uploaded context, connected tools, skills, and plugins available to that chat, and cannot work directly in a folder on the computer. They do not keep a local folder or worktree between runs; durable instructions go in the prompt or an attached skill, and source material goes in a project, upload, or connected service. Desktop scheduled tasks can work with local projects in the project directory or an isolated worktree, and the computer must stay on with the app running when the task needs local files. Codex CLI and the IDE extension do not host the Scheduled UI; creation and management are on web or desktop. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Two shapes: a standalone task starts a new chat per run and reports in Scheduled; a task scheduled inside a chat returns to that chat’s existing context. In-chat tasks can use minute-based intervals for follow-up loops, or daily and weekly times. Standalone tasks support custom schedule controls and direct edit of an RFC 5545 RRULE (the page’s example is monthly on day 1 at 09:00). One standalone task can run across more than one project. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- The Scheduled view in the desktop sidebar is described as the inbox. Runs with findings appear there, and an unread indicator shows when a run needs attention. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Git repos: each task runs in the local project or on a dedicated background worktree. Worktrees isolate changes from unfinished local work; local mode can modify files still being edited. Non-git projects run directly in the project directory. Frequent worktree schedules can accumulate worktrees; the page says to archive runs you no longer need and avoid pinning runs unless the worktree should be kept. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Event triggers, eligible plans, web and mobile only (not desktop, Codex CLI, or the IDE extension): Gmail new messages, optional sender or subject filter; Slack new messages in selected channels, optional author filter and whether thread replies count (reactions, edits, deletes, and DMs are not supported; `@ChatGPT` must be in each watched channel); GitHub pull request activity, filterable by PR, author, title, or label, and by whether reviews, comments, commit updates, or only merges fire. The app must be connected first; the GitHub app must have access to the repo. One task can have multiple event triggers but cannot mix events with a time schedule. Nearby events may be combined into one run. Managed workspaces have an admin permission, “Allow event-triggered scheduled tasks.” — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Unattended permissions: scheduled tasks use the user’s default sandbox settings. Read-only: calls fail if they need to modify files, use the network, or use apps on the computer. Workspace-write: calls fail outside the workspace, on the network, or for local apps; rules can allowlist commands to run outside the sandbox. Full access: background tasks may change files, run commands, and use the network without asking; the page recommends workspace-write plus rules instead. Admins can disallow `approval_policy = "never"` or constrain sandbox modes via admin-enforced requirements (`requirements.toml`). Scheduled tasks use `approval_policy = "never"` when org policy allows it; if that value is disallowed, they fall back to the approval behavior of the selected permission mode. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- Skills: desktop can invoke a skill in a scheduled prompt with `$skill-name`. Tasks created with ChatGPT Work on the web, or ChatGPT Work or Codex on desktop, can use plugins. The page says to put the action in a skill and to name the skill in the prompt when the workflow should not rely on automatic tool selection. Skills can themselves create or update scheduled tasks. — [Scheduled tasks](https://learn.chatgpt.com/docs/automations)
- A separate use-case page says connected email checks can run in the browser so they continue when the laptop is off, or on desktop if the computer stays on and the app is running. It describes ChatGPT proposing cleanup and drafting replies, then waiting for approval before taking the action. Voice chats do not support scheduled tasks. — [Get your email to inbox zero](https://learn.chatgpt.com/use-cases/manage-your-inbox) (search extract, not a full fetch). That “waits for approval” line is about the inbox-zero workflow on that page; the automations page says scheduled tasks use `approval_policy = "never"` when allowed. Both are OpenAI pages; they are not the same control.
- Projects are available on all free and paid plans globally. Business, Enterprise, and Edu can share with teammates. A project groups chats, uploaded files, and custom instructions. Project instructions apply only inside that project and override global custom instructions. Users can create an unlimited number of projects. Projects do not cost extra; model and tool usage is charged as in regular chats. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521) (full page captured 2026-10-02)
- File caps: only 10 files can be uploaded at once. Per project: Free 5; Go and Plus 25; Edu, Pro, Business, and Enterprise 40. Collaborator caps on personal sharing: Pro 40 files and 100 collaborators; Plus and Go 25 files and 10 collaborators; Free 5 files and 5 collaborators. Business, Enterprise, and Edu projects support 40 files and currently 100 people total, regardless of invite type. Sharing update dated 22 October 2025 in the article: sharing is on for Free, Plus, Pro, and Go globally on web, iOS, and Android, not only workspace plans. — [Projects](https://help.openai.com/en/articles/10169521)
- Share roles: edit can change instructions, add or remove files, and invite others but not remove existing members; chat can see and use chats, files, and instructions but not invite. Only the owner sets “Anyone with a link” versus invite-only. A link open to anyone lets any logged-in ChatGPT user join. Workspace link invitees join with chat access. Enterprise owners and admins can disable the permission to view workspace members and groups, which blocks sharing GPTs, projects, or chats. — [Projects](https://help.openai.com/en/articles/10169521)
- Memory: at creation, project-only or default. Existing projects stay on default; project-only cannot be switched on later. Sharing forces project-only and that cannot be reverted, including after all collaborators are removed. Project-only does not use saved memories or chats outside the project; it can use other chats in the project. Shared projects do not see a member’s context, custom instructions, or memories from outside the project. Default memory on Enterprise and Edu still cannot reference chats outside the project. Default memory on non-Enterprise, including Business, can reference non-project chats unless the other project is project-only. There is no list of “project memories”; ignoring one chat means deleting or moving it. Temporary chats cannot be added to a project. Chats created with a GPT cannot be moved into a project. — [Projects](https://help.openai.com/en/articles/10169521)
- Workspace controls: if deep research, voice, memory, or another feature is off at workspace level, it is off inside every project. Retention, residency, encryption, access control, and audit logging match standard chats. Deleted projects and their chats, files, and instructions are removed within 30 days unless legal or security retention applies. Business, Enterprise, and Edu do not train on project data by default. Free, Plus, and Pro may, if “Improve the model for everyone” is on. Shared-project training happens only if every contributor and the owner have that toggle on. Apps in projects are supported for Free, Go, Plus, Pro, Business, Teachers, Enterprise, and Edu. Google Drive added inside a project can be searched but is not synced in advance. — [Projects](https://help.openai.com/en/articles/10169521)
- Desktop projects, from ChatGPT Learn (full page not re-fetched; search extract of [Projects and chats](https://learn.chatgpt.com/docs/projects)): the Projects view includes ChatGPT projects and local projects bound to folders. A ChatGPT project does not give direct access to a computer folder; sources are uploads and connections. A local project gives chats access to one or more folders. Project instructions apply across its chats. The extract also says chats can install plugins, configure MCP servers when the org or developer setup exposes them, and use memories where available.
- Help-center article `10291617` did not load (three fetch timeouts). Search snippets of [Scheduled tasks in ChatGPT](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt) and [the shorter slug](https://help.openai.com/en/articles/10291617) disagree with each other. One snippet says active-task limits are 3 for Free and Go, 5 for Plus, 10 for Business and Edu, and 15 for Pro and Enterprise; Free is at most daily with flexible windows; paid plans can be hourly with exact times; event-triggered tasks up to 30 per hour and 720 per day. Another snippet of the same article number omits Free, says tasks cannot run more than once per hour, gives Go 3 / Plus 5 / Business and Edu 10 / Pro and Enterprise 15, and then in the same card says Pro, Business, and Enterprise can have 15. Those numbers are not used below as facts.

### Inferences
- Projects and scheduled tasks solve different problems. A project is the durable desk (files, instructions, scoped memory, optional sharing). A scheduled task is the unattended runner. On desktop they compose: a schedule can target a local project or a worktree. On the web, a schedule can use a project’s uploads but not the laptop’s folders.
- ChatGPT’s unattended permission story is sandbox plus “never ask,” not Claude’s Auto classifier. If the org forbids `approval_policy = "never"`, the run falls back to whatever interactive approval the user selected, which will stall when nobody is there. Full-access sandbox is the dangerous unattended setting the docs explicitly warn about.
- The inbox is a first-class review surface (unread runs), closer to a results queue than to “reopen the chat and scroll.”

### Gaps
- Verified numeric caps for active ChatGPT tasks, minimum cadence by plan, and event-trigger rate limits. The help article that search associates with those numbers could not be fetched, and the snippets conflict.
- Whether a web scheduled task inherits a project’s instructions and memory, or only its uploads, is not stated on the fetched automations page.
- No fetched ChatGPT page describes a per-task tool allowlist. The controls that were fetched are sandbox mode, command rules, connector authorization, admin `requirements.toml`, and naming a skill so selection is not automatic.
- The inbox-zero page’s “wait for approval before acting” was not reconciled with `approval_policy = "never"` beyond noting they are different pages.
- ChatGPT Learn’s projects page was not fully fetched, so the local-project and MCP sentences are from a search extract.

## What does the MCP spec and the official client guidance say about tool annotations, registries, and deferred tool loading in 2026?

### Takeaway
The 2026-07-28 spec does not add a deferred-tool protocol or change the tool-annotation vocabulary. It tells clients that tool annotations are untrusted unless the server is trusted, adds cache hints and `server/discover`, and makes the core protocol stateless. Official client guidance recommends progressive discovery (a `search_tools` meta-tool, schemas loaded on demand) once definitions consume on the order of 1–5% of the context window. The MCP Registry is still a preview metadata catalog that hosts are told not to call directly.

### Cited Findings
- Revision 2026-07-28 is the spec relative to 2025-11-25. Major changes include: no protocol-level sessions and no `Mcp-Session-Id` on Streamable HTTP; list endpoints no longer vary per connection; cross-call state uses server-minted handles passed as ordinary tool arguments (SEP-2567). No `initialize` / `notifications/initialized` handshake; every request carries protocol version and client capabilities in `_meta`; mismatches return `UnsupportedProtocolVersionError` (SEP-2575). Servers MUST implement `server/discover` to advertise supported versions, capabilities, and identity (SEP-2575). — [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Subscriptions move to `subscriptions/listen`, one long-lived POST stream; clients opt into `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, and `resourceSubscriptions`. `ping`, `logging/setLevel`, and `notifications/roots/list_changed` are removed. Experimental tasks leave the core and become extension `io.modelcontextprotocol/tasks`, with poll via `tasks/get` and `tasks/update` instead of a blocking `tasks/result` (SEP-2663). — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Multi Round-Trip Requests (SEP-2322) replace server-initiated requests such as `roots/list`, `sampling/createMessage`, and `elicitation/create`. The server returns `resultType: "input_required"` with `inputRequests`; the client retries the original request with `inputResponses`. Results require `resultType` (`complete` or `input_required`); older servers that omit it are treated as `complete`. SSE resumability (`Last-Event-ID`) is removed; a broken response stream means the client re-issues the request. — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [spec blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/) (search extract: the blog also describes `Mcp-Method` and `Mcp-Name` headers, cache hints, and Tasks moving to the extension)
- List results for tools, prompts, resources, resource reads, and resource templates require `ttlMs` and `cacheScope` (`public` or `private`) via `CacheableResult` (SEP-2549). Servers SHOULD return `tools/list` in a deterministic order for client and prompt caches. Streamable HTTP POSTs require `Mcp-Method` and `Mcp-Name`; tool parameters may surface as headers via `x-mcp-header` (SEP-2243). — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- The changelog does not mention `ToolAnnotations`, `readOnlyHint`, or deferred tool loading. A deprecated-features registry is a process artifact (SEP-2596): feature states Active, Deprecated, and Removed, with at least a twelve-month deprecation window. Roots, Sampling, and Logging are deprecated (SEP-2577). HTTP+SSE, already deprecated since 2025-03-26, is reclassified under that policy. Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents. This registry is not the server marketplace. — [Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- On the tools page of that same revision: `annotations` are optional properties describing tool behavior. “For trust & safety and security, clients MUST consider tool annotations to be untrusted unless they come from trusted servers.” Content annotations (audience, priority, timestamps) are a different mechanism, shared with resources and prompts. `x-mcp-header` must not be used on passwords, API keys, tokens, or PII. — [Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- The 16 March 2026 MCP blog says tool annotations shipped in the 2025-03-26 revision so servers could say whether a tool is read-only, destructive, idempotent, or reaches outside its local environment. It says the interface stayed small on purpose: `title` is a display name with no trust implications; a proposed `taskHint` landed as `Tool.execution` instead, because execution metadata is not a behavioral hint. As of that post, five SEPs were open or proposed: #1913 trust and sensitivity, #1984 governance/UX annotations, #1561 `unsafeOutputHint`, #1560 `secretHint`, #1487 `trustedHint`. — [Tool Annotations as Risk Vocabulary](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/) (search extract of the official blog; the TypeScript block itself was not in the extract)
- A secondary August 2026 write-up names the four hints `readOnlyHint`, `destructiveHint`, `idempotentHint`, and `openWorldHint`, says they are unchanged in 2026-07-28, and says three of the five March SEPs later closed and #1913 moved off the core-spec track. That status was not checked against the SEP tracker. The “unchanged in the 2026-07-28 changelog” part matches the changelog fetched above. — [ChatForest](https://chatforest.com/guides/mcp-tool-annotations-explained/) (secondary)
- Official client guidance calls the scaling pattern progressive discovery, not a spec feature. The host still calls `tools/list`, but defers putting definitions in the model context, exposes a lightweight `search_tools` meta-tool, and loads full definitions only when needed. Switch when definitions take a significant share of the window; the suggested threshold is about 1–5%. Search can be keyword, embedding, a small subagent, or a hybrid. If the model provider already has tool search (the page names OpenAI and Anthropic), prefer that. The illustrated three layers are catalog (`search_tools` returns names and one-line descriptions), inspect (`get_tool_details`), and execute. — [Client best practices, 2026-07-28 docs](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)
- The same page extends this to servers: keep a registry of servers and descriptions, connect only when needed (`server/discover`, then `tools/list`), disconnect when done. It says a skill file can declare which MCP servers it needs so the host connects them only when that skill is invoked. Cache definitions host-side; re-index on `notifications/tools/list_changed`; treat a cached list as stale when that notification arrives even if `ttlMs` has not expired. To protect prompt caches, append newly discovered definitions after the cache breakpoint or route every call through one stable `call_tool({name, args})` meta-tool; treat disconnect as a conversation boundary. — [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)
- The same page documents programmatic tool calling (“code mode”) as a second pattern: the model writes code against typed stubs generated from MCP schemas, the code runs in a sandbox with no direct network, and only the final output returns to the model. Approving the script does not blanket-approve every call; the host broker still applies the human-in-the-loop policy, though it may grant a category for the script run (the example is allowing one tool for that run rather than prompting per loop iteration). Credentials stay on the host. — [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices)
- An open RFC (issue #2376), written against the 2025-11-05 handshake, proposed `lazyRegistration` / `supportsLazyRegistration` so a client could defer `tools/list`. It is not in the 2026-07-28 changelog. The issue itself describes Claude Code `defer loading: true` (MCP Tool Search in v2.1.9) as a client-side, non-standard mitigation. — [Issue #2376](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/2376) (search extract)
- The official MCP Registry is in preview; the about page warns that breaking changes or data resets may happen before general availability. It is a centralized metadata repository for publicly accessible servers, backed by contributors including Anthropic, GitHub, PulseMCP, and Microsoft. It stores `server.json` (name, where to get the server, execution instructions, description, capabilities), not the server artifacts. Names are reverse-DNS and tied to a verified GitHub account or domain. The page says the registry is not intended to be consumed directly by host applications; hosts should use downstream registries or marketplaces that conform to the registry OpenAPI. — [About the MCP Registry](https://modelcontextprotocol.io/registry/about) (search extract)
- Aggregators scrape a read-only unauthenticated API at `https://registry.modelcontextprotocol.io`: `GET /v0.1/servers`, `GET /v0.1/servers/{serverName}/versions`, and `GET /v0.1/servers/{serverName}/versions/{version}` with `latest` as a version. Path parameters must be URL-encoded. The registry does not promise uptime or durability; aggregators are expected to scrape infrequently (the example is about hourly) and store their own copy. A subregistry can add ratings, download counts, or scan results in `_meta`. Publishing uses `mcp-publisher`; the registry only holds metadata, so the package is published to npm (or similar) first, with an `mcpName` field. — [Registry aggregators](https://modelcontextprotocol.io/registry/registry-aggregators); [Quickstart](https://modelcontextprotocol.io/registry/quickstart) (search extracts). The production UI is [registry.modelcontextprotocol.io](https://registry.modelcontextprotocol.io/).

### Inferences
- “Deferred tool loading” in 2026 is a client pattern (progressive discovery, or a vendor’s private tool-search flag), not an MCP method. The spec’s contribution is cacheable, deterministic `tools/list` results plus `server/discover`, which make that pattern cheaper.
- Annotations are hints for UX and policy, and the spec forbids treating them as proof. A client that auto-approves because a server set `readOnlyHint` is ignoring a MUST in the 2026-07-28 tools page.
- There are two different “registries”: the preview server catalog (install metadata, not a runtime tool index) and the deprecated-features list (spec process). Neither is a per-user connector allowlist.
- MRTR is the spec’s answer to “the server needs a human mid-call” after the removal of server-initiated elicitation. It still needs a client that can collect the answer. It does not define what an unattended scheduled run should do.

### Gaps
- The exact `ToolAnnotations` JSON Schema in revision 2026-07-28 was not opened. The tools prose says annotations are untrusted optional behavior properties and does not list the hint fields on the fetched page. Field names beyond the March 2026 blog’s prose (read-only, destructive, idempotent, open-world, plus `title`) rely on the secondary ChatForest page.
- SEP status after March 2026 was not verified on GitHub.
- The registry about, aggregators, and quickstart pages were search extracts, not full fetches. Preview status and the “do not consume directly” rule were in that extract; current server counts were not.
- No official page fetched here requires clients to implement progressive discovery. It is guidance (“should”), with a suggested 1–5% threshold, not a conformance rule.

## How do Open WebUI or AnythingLLM-class apps do skills and per-job tool allowlists?

### Takeaway
Open WebUI’s current docs lazy-load skills with a `view_skill` tool, restrict built-in tools per model (and again by global flags and user permissions), and can ask before each tool call. Scheduled automations skip that ask. AnythingLLM exposes an agent-skill toggle list and a chat Tools button, plus a relevance filter it calls Intelligent Tool Selection. Neither product’s fetched docs show a per-job tool allowlist.

### Cited Findings
- Open WebUI docs (docs repo `main`, page retrieved 2026-10-02): skills attach on the model via Workspace or Settings > Admin > Models → Edit → Skills. The model gets a summary of each attached skill (name and description) in `<available_skills>` tags and a `view_skill` tool to load the full instructions. `view_skill` is not a Builtin Tools checkbox; it appears only when at least one skill is attached, and resolving a skill still checks ownership and access grants. A per-chat skill pick from the input bar injects that skill’s full content into the system prompt instead of using `view_skill`. If no skills are attached, `view_skill` is absent. — [Open WebUI tools docs](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- Builtin tool categories (memory, notes, knowledge, web search, image generation, code interpreter, channels, tasks, automations, calendar, and others on that page) are on by default. Turning a category off stops those tools from being injected. The toggles only further restrict what global feature flags and the user’s `features.*` permissions already allow; they cannot turn a globally disabled feature back on. Admins pass the RBAC checks. Examples on the page: a privacy model disables Memory and Chat History; a read-only assistant disables Notes. — [Open WebUI tools docs](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- Tool approval is experimental and off by default (`ENABLE_TOOL_PERMISSIONS` under Settings > Admin > Interface). Full access runs calls immediately. Ask for approval stops at the first tool call and shows Allow and Deny; parallel calls are approved one at a time. The choice is saved on the user and applies to later chats. A denial is returned to the model as an error. Two cases always run with full access: automations, because they run on a schedule with nobody watching, and channel replies. Approval needs a saved chat; temporary chats have nowhere to store the pending call. — [Open WebUI tools docs](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- The same page lists automation tools the model can call: `create_automation`, `update_automation`, `list_automations`, `toggle_automation`, `delete_automation`. It does not describe a tool allowlist stored on the automation. — [Open WebUI tools docs](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- Workspace Tools access is called out as dangerous: untrusted users who can upload tools can run arbitrary Python on the server. — [Open WebUI tools docs](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- External / MCP tools are not given a hard per-model allowlist in the docs page above. A 2025-era discussion reports that a model’s external-tool selection pre-enables tools but a user who has permission can still turn other tools on, unlike built-in features such as web search, which the model config can fully block. — [Discussion #17980](https://github.com/open-webui/open-webui/discussions/17980) (discussion, not docs)
- A later discussion proposes `allowed_models` / `allowed_base_models` on a tool-server connection because `toolIds` on a model is a default, not a limit, and a direct `/api/chat/completions` call can name any tool id. That is a requested design, not a documented shipped feature. — [Discussion #18445](https://github.com/open-webui/open-webui/discussions/18445)
- A comment on issue #25862 says a global filter inlet can strip ids from `body["tool_ids"]` before tools are resolved, including MCP ids of the form `server:mcp:<server_id>`, and that this covers UI and API callers. That is a userland filter, not a per-job allowlist in the product UI. — [Issue #25862](https://github.com/open-webui/open-webui/issues/25862) (search extract of the comment)
- AnythingLLM: Settings > Agent Skills is a per-skill enable list. Some skills are on by default; some need extra configuration. The chat input has a Tools button that toggles skills for the prompt. Web-Browsing defaults to DuckDuckGo and can be pointed at another search provider. The workspace can use a different model for agent sessions than the system LLM. — [AnythingLLM agent setup](https://docs.anythingllm.com/agent/setup)
- On that same page, Intelligent Tool Selection is AnythingLLM’s name for adding only the tools and MCPs it judges useful for the chat, instead of every tool on every turn. The page claims this saves up to 80% on every chat, and says Open WebUI, Claude, and others put every tool and MCP into the prompt every chat. The toggle is a settings icon on the Agent Skills page. The 80% figure and the comparison are the vendor’s claims on its own docs; no method or measurement is on the page. — [AnythingLLM agent setup](https://docs.anythingllm.com/agent/setup)
- The AnythingLLM setup page does not describe scheduled jobs, an approval mode, or a per-job allowlist. The Open WebUI tools page does not describe one either, aside from model-level category toggles, user-level Ask vs Full access, and the automation bypass.

### Inferences
- In this class of app, “skills” means a markdown procedure with a short description always visible and a body loaded on demand (Open WebUI) or a toggleable agent capability (AnythingLLM). That is the same shape as Claude skills, implemented locally.
- The practical allowlist is per model or per user, not per scheduled job. Open WebUI’s explicit choice for unattended work is to skip approval and run with full access. AnythingLLM’s Intelligent Tool Selection is retrieval of relevant tools, which can hide a tool the job should have been forbidden to call, and can still surface a tool the job should not call, because relevance is not permission.
- A real per-job allowlist, in the sense of “this Monday job may use these tools and no others, even if the user could use them in chat,” is not what these docs describe. The closest shipped Open WebUI mechanism is a filter function an admin writes.

### Gaps
- Open WebUI docs were read from the GitHub docs source, not from a rendered docs.openwebui.com URL, so the published site could lag or lead `main`. The page content refers to 2026 model names, so it is not an old snapshot, but it has no dateline.
- No AnythingLLM page on schedules or MCP allowlists was fetched beyond agent setup. If a later docs page adds per-agent tool grants, it is not in these notes.
- Whether Open WebUI automations can be bound to a model’s builtin-tool toggles (so the model restriction still applies when approval is skipped) is not stated.
- Discussion #17980’s date and whether later releases closed the external-tool hole were not verified. The proposal in #18445 should not be read as shipped.

## What is table stakes versus still rare?

### Takeaway
By October 2026 the expected set is a cloud schedule that survives a closed laptop, a place to review runs, reusable skills that load on demand, MCP connectors, and at least two permission postures (ask, or proceed without asking). Still uneven: a safe unattended write path that neither stalls nor rubber-stamps, event triggers, per-job tool allowlists, and treating the MCP registry or deferred loading as something the protocol itself provides.

### Cited Findings
- Cloud schedules that do not need the device: Claude help says scheduled tasks run remotely with the computer asleep or the app closed, with the local-files exception noted above. ChatGPT web tasks cannot touch a local folder and do not need the desktop app; desktop tasks that need local files require the computer on and the app running. — [Claude scheduled tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork); [ChatGPT scheduled tasks](https://learn.chatgpt.com/docs/automations)
- A review surface for past and upcoming runs: Claude’s Scheduled page; ChatGPT’s Scheduled view, which the docs call an inbox with an unread indicator. — [Claude](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork); [ChatGPT](https://learn.chatgpt.com/docs/automations)
- Skills as reusable, selectively loaded instructions, usable from a scheduled run: Claude account skills and plugins; ChatGPT skills including `$skill-name` and skills that can create tasks; Open WebUI `view_skill`; AnythingLLM agent-skill toggles. — [Claude skills](https://support.claude.com/en/articles/12512180-use-skills-in-claude); [ChatGPT automations](https://learn.chatgpt.com/docs/automations); [Open WebUI](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx); [AnythingLLM](https://docs.anythingllm.com/agent/setup)
- MCP as the connector plug, plus a public metadata registry that is still preview and explicitly not the host’s runtime catalog. — [Registry about](https://modelcontextprotocol.io/registry/about); [Claude plugins help](https://support.claude.com/en/articles/13837440-use-plugins-in-claude)
- Ask-versus-proceed permission modes in the mainstream products: Claude Manual / Auto / Skip; ChatGPT sandbox modes and `approval_policy`; Open WebUI Full access / Ask for approval, off by default. — [Claude get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [ChatGPT automations](https://learn.chatgpt.com/docs/automations); [Open WebUI](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- Persistent desks with their own files and instructions: Claude Cowork projects; ChatGPT projects on every plan, with file caps and optional project-only memory. — [Claude get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [ChatGPT projects](https://help.openai.com/en/articles/10169521)
- Documented on one vendor and not matched in the other fetched docs: ChatGPT event triggers for Gmail, Slack, and GitHub, web and mobile only, not combinable with a clock schedule. Claude’s fetched schedule article only lists clock cadences and manual run. — [ChatGPT automations](https://learn.chatgpt.com/docs/automations); [Claude scheduled tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)
- Documented on ChatGPT desktop and not in the Claude help pages fetched here: scheduled runs in a git worktree so the agent’s edits stay off the working tree. — [ChatGPT automations](https://learn.chatgpt.com/docs/automations)
- Documented for Claude Enterprise and not in the ChatGPT or open-app pages fetched here: skill and plugin security scanning before a third-party skill can run, with publish-to-org review. — [Use skills](https://support.claude.com/en/articles/12512180-use-skills-in-claude)
- Unattended write policy differs and none of the fetched docs show a per-run allowlist that is both enforced and reviewed: Claude Auto screens then blocks or asks; Skip screens nothing; deletion always asks. ChatGPT scheduled tasks prefer `approval_policy = "never"` inside a sandbox, and full access is called out as elevated risk. Open WebUI automations always use full access and do not ask. — [Claude get started](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Claude safety](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely); [ChatGPT automations](https://learn.chatgpt.com/docs/automations); [Open WebUI](https://github.com/open-webui/docs/blob/main/docs/features/extensibility/plugin/tools/index.mdx)
- Deferred tool loading and annotation-based auto-approval are guidance and hints, not table-stakes protocol behavior. The spec says annotations are untrusted. Progressive discovery is a client best practice. The server registry is preview metadata for aggregators. — [Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [Client best practices](https://modelcontextprotocol.io/docs/2026-07-28/develop/clients/client-best-practices); [Registry about](https://modelcontextprotocol.io/registry/about)

### Inferences
- Table stakes for a personal agent in late 2026: schedule a prompt, run it when the laptop is shut (at least for connector and account-file work), show the run afterward, attach skills and MCP connectors, and let the user pick ask versus don’t-ask.
- Still rare as a complete pattern: unattended execution that can take real write actions without either stalling for a human or disabling the check; a per-job tool allowlist distinct from the user’s global connectors; event triggers; org review of skills; worktree isolation. Open-source desks have the skill shape and a coarse tool toggle, and they send scheduled work through with approval off.
- A gap analysis that scores “has MCP” or “has skills” as parity will miss the permission and scheduling differences above. Those are where the products actually diverge.

### Gaps
- No independent survey or usage data was fetched, so “table stakes” and “rare” are inferred from what the primary docs of these four products describe, not from market share.
- Products outside this set (other desktop agents, other self-hosted UIs) were not reviewed. A feature that is rare here may be common elsewhere.
- Claude event triggers, if they exist under another name, were not found in the scheduled-task article.
- ChatGPT numeric task caps remain unverified, so they are not part of the table-stakes claim.
