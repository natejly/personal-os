# Memory, graph, and voice: what to build next

Date: 2026-10-02. Sources are only [memory-app.md](memory-app.md) (working tree that day) and [memory-market.md](memory-market.md) (product and paper notes fetched the same day). No new research. Vendor and author benchmarks are labeled and are not treated as independent.

The two notes do not disagree about Grain. The market note did not read Grain’s code. Inside the market note, conflicting figures are kept side by side below. The app note’s code inventory wins over README and over `docs/research/sota-memory.md`, which still describe the older keyword-only, overwrite-and-delete memory path.

Effort: **S** is one module and an offline test. **M** crosses prompt, persistence, and UI, still inside the existing SQLite file. **L** would be another database, a graph server, or an extra model call on every turn. Nothing below is an L, and none of the closes add one.

## 1. What Grain ships now

From the app note only.

**Memories.** After a successful, non-tainted, non-proposal-only reply, and only when global `autoLearn` and the chat’s `autoLearn` are both on, `LearnWorker` runs one extraction (`backend/personal_os/learn.py`, queue depth 32, one job at a time, full queue drops the job). The model returns JSON memories, updates, forgets, entities, and relations. New rows go to `memories` with an FTS5 mirror (`porter unicode61`), `source="auto"`, and conversation/message provenance. Kinds are `fact|preference|goal|note`. Exact duplicate text in the same scope returns the existing live row. The user can add, edit, pin, and move scope from Memory. Personal rows have `project_id` NULL. A project chat’s scope includes that project plus personal. A personal chat sees personal rows only.

Injection is a capped bullet list under `## What you remember about the user`, each line clipped to 500 characters, marked as notes rather than instructions. With a query vector, that list is the hybrid top 40. Without one, it is pinned-then-recent (limit 40) unioned with up to 15 BM25 hits. `search_memory` uses the same hybrid path when a vector exists.

**Graph.** The same extraction upserts `kg_nodes` and edges. Identity is exact label inside a scope (case-insensitive). Self labels are dropped. Injection, when `useGraph` is on, loads the in-scope graph, seeds labels that appear in the user message, keeps one hop, and caps nodes at 30. The Memory screen has a force layout with hand edit and hard delete. Tools: `graph_search`, `graph_traverse`, `graph_add`.

**Voice.** Separate tables: verbatim samples and one profile per scope (personal, or one project, not merged). Chat turns that pass `looks_like_prose` are banked when `learnStyle` and chat `autoLearn` are on. Doc saves are banked the same way, except meeting recordings, and a doc save does not relearn. The profile is re-derived from the newest samples unless the user has edited it. When the chat’s Writing style toggle is on and the profile is enabled and non-empty, the profile markdown is appended to the stable system prefix, including on ordinary replies.

**Controls.** Per-chat toggles for memory, graph, writing style, and auto-learn. Context drawer: Last reply, Preview, Trace. Memory panel: list, graph, split, Voice, Show history, Tidy up. Defaults turn memory, graph, style, and auto-learn on.

**Partials the rest of this file uses.** Pin is not forced into the hybrid top 40. User Forget is 30-day trash; extractor forget invalidates and keeps a history row; Show history shows the second store. Extractor updates skip pinned rows. Hand edits overwrite content and do not append history. `save_memory` and hand create store no conversation provenance. Edge column `fact` is unused by extraction. Edges can be invalidated; the graph UI never shows that history. `valid_from` / edge `valid_at` are set to insert time; nothing checks that the model turned relative dates into absolute ones. `useMemory` does not gate extraction. A tainted chat still receives an existing voice profile. Settings has no field for `embeddingModel`, `hybridRetrieval`, `retrievalMode`, or `consolidateEvery`. Drawer copy still describes pinned, recent, and matching memories.

## 2. What leading apps ship that Grain does not

Named only where the market note has a source. Benchmarks in this section are the authors’ or the vendor’s.

### ChatGPT

- A background synthesis OpenAI calls dreaming, announced as Dreaming V3 on 2026-06-04. It rewrites time-sensitive memories (their example: “You’re going to Singapore in July” becomes “You went to Singapore in July 2026”) and shows a reviewable summary page where the user can edit highlights and say which topics to bring up and when. Rollout described that day: Plus and Pro in the US, other countries and Free and Go over the following weeks. The help center, fetched with the market note, still documents Improved Memory versus a legacy explicit list. — [OpenAI, Dreaming (2026-06-04)](https://openai.com/index/chatgpt-memory-dreaming/); [OpenAI Help, Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- Grain’s counterpart is per-row extraction plus approve-only proposals, including a relative-date proposal for auto rows older than 30 days. Grain has no applied background rewrite and no summary page of topic instructions. Whether that page is worth copying is in section 3.
- Project-only memory, chosen when a project is created: saved memories are not referenced, and chats do not see conversations outside the project. Sharing a project locks that wall on. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Grain’s stated scope is the opposite for reads: personal rows are included in every project chat (`include_global` defaults true; the Memory panel says so).
- Temporary Chat, documented in the Enterprise/Edu table: ChatGPT Memory is not available, and other chats are not referenced. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Saved-memory controls can include version history, depending on plan and platform. Deleting a chat does not delete the saved memory. OpenAI may keep logs of deleted saved memories for up to 30 days. — [OpenAI Help, Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- An older help article says referenced saved memories are kept until deleted and are always in future responses. The market note says to treat that two-toggle writeup as the pre-Dreaming-V3 surface if it disagrees with the 2026-06-04 post and the current Memory article. — [OpenAI Help, Reference saved memories](https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work)
- OpenAI does not document the ranker behind reference-chat-history or dreaming. Past-chat search as a separate memory input is described there. The app note does not inventory search over raw chats (document RAG is out of its scope), so this file does not score Grain on it and does not propose a chat-search build.

### Claude

- Current memory, help article updated about 2026-10-01: short per-topic files written during the chat, listed under Settings, each readable, editable, and deletable. “Remember this,” and chat instructions to change or forget, apply to the next conversation. The 24-hour cross-chat summary is the legacy mode on that same page. Citing it as current Claude behavior is stale. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context); [Claude blog](https://claude.com/blog/claudes-memory-works-everywhere-and-you-decide-whats-in-it)
- Grain already writes discrete editable rows during and after the chat. The Claude behaviors Grain’s inventory does not include: sensitive topics excluded unless the user opts in; Pause, which keeps memory but neither reads nor writes it; Reset of all memories including project memories; each project’s memory isolated from other projects and from non-project chats.
- Search past chats (paid plans) as retrieval-augmented tool calls with citations back to the source chat. Incognito chats are not saved to history or memory. A separate control, Memory off in the “+” menu before the first message, keeps the chat in history, locks after the first message, and neither uses nor adds memory. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context); [Claude Help, incognito chats](https://support.claude.com/en/articles/12260368-use-incognito-chats)
- The app note’s toggle list has auto-learn and a memory injection switch. Extraction checks `autoLearn` and taint, not `useMemory`. Turning memory injection off still allows new rows. The drawer’s taint copy says the writing voice stays off; `build_context` does not read the taint flag.
- Experimental import/export is documented. The same help article says legacy export remains until 2026-09-09, while the note’s fetch was about 2026-10-01, so that sentence was already past its own date. This file does not resolve which is true. — [Claude Help, import and export memory](https://support.claude.com/en/articles/12123587-import-and-export-your-memory-from-claude). No import/export route is in the app note’s route list. A build is not recommended from that alone.
- Claude does not document how topic files are chosen into the prompt or how large they can get.

### Letta

- Labeled text blocks, always prepended, with a character limit. Examples on the docs use 4000 and 5000 characters. The agent rewrites them with tools; a developer can patch `value`; read-only blocks cannot be updated by the agent. Starter labels are `human` and `persona`. — [Letta docs, memory blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks); [Letta blog, Memory blocks](https://www.letta.com/blog/memory-blocks/)
- That is the “cannot fall out of a top-k” property. Grain’s pin tooltip and Memory panel say pinned rows are always in context. Hybrid search replaces the candidate list with the top 40, and the recency weight is 0.5, so a pinned row with no lexical, vector, or graph support can miss the cut.
- Letta in 2026 is a separate local runtime (`~/.letta/lc-local-backend`, per-agent git memory repos), not a library inside another app’s SQLite file. The PostgreSQL server line is the retired one; the current self-host page is the source to prefer. — [Letta docs, self-hosting](https://docs.letta.com/self-hosting/); [Docker Hub, letta/letta](https://hub.docker.com/r/letta/letta). Do not embed that server.
- `persona` is the agent’s own block. The market note does not describe it as a profile learned from the user’s prose. None of the products in the market note document Grain’s sample-and-profile voice store.

### Mem0 and Mem0g

- Paper pipeline (author-run, arXiv:2504.19413): extract candidate facts from the new pair plus a summary plus the previous m messages (m = 10 in the reported config), embed each candidate, fetch the top s = 10 similar memories, then a tool call ADD, UPDATE, DELETE, or NOOP. Mem0g stores directed triplets, matches nodes above a similarity threshold, and can mark a conflicting relationship invalid. The paper’s graph implementation is Neo4j. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Current OSS docs: graph memory is a platform feature, not in the open-source Python or TypeScript SDKs. OSS vector stores are Qdrant, pgvector, Chroma, FAISS, and others, not the application’s SQLite. — [Mem0 OSS configuration](https://docs.mem0.ai/open-source/configuration); [vector DB overview](https://docs.mem0.ai/components/vectordbs/overview)
- Grain’s missing piece relative to this paper is fuzzy node match at write time, and an explicit NOOP. Grain’s extraction has no NONE event; empty arrays mean nothing durable. Grain already invalidates contradicted edges and superseded memories, which base Mem0 does not (base Mem0 DELETE drops the fact). Do not add Neo4j, Qdrant, or the Mem0 service to get that.

Author-reported LOCOMO judge scores are in the market note’s tables. They are not used here as a build target. Full context still scored higher than Mem0 on that judge (72.90 vs 66.88) while using far more tokens. Their OpenAI-memory baseline stuffed every generated memory into the prompt because they had no selective-retrieval API.

### Zep / Graphiti

- Three layers in the paper: episode nodes (raw messages, text, or JSON), entity/fact edges, and community summaries. Each edge has transaction time and valid time. A contradicted edge is invalidated, not deleted. Entity names are embedded and full-text searched; an LLM decides duplicates. Retrieval in the paper is cosine, BM25, and breadth-first search, then a reranker. Experiments used BGE-m3 embeddings and gpt-4o-mini for construction. — [Zep paper](https://arxiv.org/html/2501.13956v1)
- The live engine wants Neo4j, FalkorDB, Neptune, or deprecated Kuzu. There is no SQLite driver. Default extraction expects an OpenAI key; the README says smaller models fail schemas. — [Graphiti README](https://github.com/getzep/graphiti)
- Grain’s edge table already has `valid_at`, `invalid_at`, `superseded_by`, `source_message_id`, and `fact`. Extraction does not fill `fact`. There is no world-time column the model fills. The graph screen does not show invalidated edges. Community summaries and episode nodes as a second copy of the transcript are not in the app note. The market note’s practical reading: copy the edge columns, skip the graph server, and skip communities for a single user because full rebuilds are costly.
- One operator’s backfill (not a controlled study) found 771 of 1,384 edges with `valid_at` at midnight UTC on the processing day, because the model guessed “today.” The proposed fix is to default `valid_at` to the episode time when the model leaves it empty. — [Graphiti issue 1492](https://github.com/getzep/graphiti/issues/1492)

Three Zep LOCOMO-style figures in the market note are not one result: Mem0’s authors scored a Zep run at judge 65.99; a Zep papers repo README shows 75.14 ± 0.17 with no protocol beside it; a Zep research page (`dateModified` 2026-09-29) reports 94.7%. Do not merge them, and do not treat 94.7% as the January 2025 paper. — [Mem0 paper, Table 2](https://arxiv.org/html/2504.19413); [zep-papers locomo_eval](https://github.com/getzep/zep-papers/tree/main/kg_architecture_agent_memory/locomo_eval); [Zep research benchmarks](https://www.getzep.com/research/)

The January 2025 paper’s LongMemEval comparison is against full context, not against BM25. On gpt-4o, Zep’s 1.6k retrieved tokens scored 71.2% versus 60.2% for 115k-token full context, with the gain on temporal, multi-session, preference, and knowledge-update questions, and a loss on single-session-assistant questions (80.4% vs 94.6%). Latency includes a network hop the local baseline did not have. — [Zep paper, Tables 2–3](https://arxiv.org/html/2501.13956v1)

### What the retrieval evidence supports, and what it does not

Yuan, Su, and Yao (arXiv:2603.02473, March 2026) ran a 3×3 on LoCoMo. Writes (raw chunks, Mem0-style facts, session summaries) moved judge accuracy about 3–8 points inside one retriever. Retrievers moved it about 14–23 points. Column averages: BM25 57.1%, cosine 73.4%, hybrid 77.2%. That hybrid is cosine plus BM25, then GPT-5.2 reranking to k=5, not reciprocal rank fusion. Raw chunks won under cosine and under that hybrid. The authors list the limits: one backbone, one benchmark, fixed k, prompt imitations of Mem0 and MemGPT, LLM judges. — [memory-probe paper](https://arxiv.org/html/2603.02473v1)

No source in the market note ablates RRF(BM25, cosine) against BM25 alone on answer accuracy. Anthropic’s 2024 contextual-retrieval post is document RAG: embeddings plus BM25 versus embeddings, not a chat-memory result, and it does not publish a BM25-only failure rate. — [Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)

Mnemo and Popoto numbers are vendor dashboards. Popoto’s corrected LoCoMo note is a near-tie between lexical and hybrid, not a hybrid win. They are not build targets.

Nobody in the market note publishes a pinned block against a BM25 list. Letta’s claim is architectural: a fact in the block cannot be missed by a ranker. The memory-probe utilization result is the nearby evidence: once a relevant item is in the prompt, failure to use it stays about 4–8%, while BM25 retrieval failure on raw chunks is 35.3%.

## 3. Where Grain is already ahead, or different on purpose

**One SQLite file already holds the practical stack.** FTS5, float32 vectors in `memory_vectors`, and RRF across BM25, cosine, recency, and graph-label seeds (weights 1.0, 1.0, 0.5, 0.7, k=60) run inside this process. The market note’s order for a single file is: a few always-present editable fields, then FTS5 plus embeddings, then validity intervals that invalidate instead of deleting. Grain has the second and third. The first is the pin hole in section 4. Mem0 OSS, Graphiti, and the current Letta server each add another store or another process. Do not take that dependency.

**Contradictions stay as history.** Extractor updates supersede memories. Extractor forgets and `ended` / `replaces` invalidate edges. Base Mem0 deletes the contradicted fact. User-visible Show history and restore exist for the supersession chain. OpenAI’s 30-day retention is a safety log of deleted saved memories; Grain’s 30-day trash is the user’s undo for Forget.

**Tidy-up stays approve-only on purpose.** `propose` never applies. ChatGPT dreaming writes the synthesis itself. The memory-probe study does not support spending the next build on a smarter write: summaries and extracted facts did not beat raw text once the retriever was decent, except a small BM25-only bump for summaries. Keep Apply and Dismiss. Do not auto-apply proposals. Do not add the spec’s cosine ≥ 0.88 cluster inside consolidation; `memory_candidates` is token Jaccard ≥ 0.6, and the market note does not show that clustering buys accuracy.

**Atomic rows, not a dreaming summary.** A single synthesized profile is the ChatGPT and legacy-Claude product. It is also the write strategy that lost to raw chunks under cosine and hybrid in the 2026 study. Grain’s list, edit, pin, and hybrid injection should stay the store. A summary page would be a second artifact on top, not a replacement.

**Personal rows in project chats are the stated product.** The panel copy says personal memories go into every chat, and project memories only into that project. Claude’s per-project wall and ChatGPT’s project-only mode exist for shared work contexts. Grain is a single-user local app, and the current copy promises the leak. An opt-in wall is a small flag on `_scope_clause` (`include_global=false`) plus a matching ban on personal writes from that chat. It is not a bug fix, and it should not become the default.

**Sensitive-topic refusal should not be copied.** Claude does not store health and similar categories unless the user opts in, and some identifiers are never stored. A personal app on one machine is where those facts are supposed to live. Skipping them would fight the extractor rule the app note already records: user-said, durable for about a month, preferences kept faithful.

**Pin already behaves like a read-only block on the write path.** Auto-learn will not supersede or invalidate a pinned row. That matches Letta’s read-only block more than it matches “the model may rewrite your pin.” The broken half is injection, section 4.

**Voice is ahead of every product in the market note, and the injection rule is the hole.** Samples, a prose filter, a per-scope profile, an enable switch, and “Re-read my writing” are shipped. The market note never documents a learned user-voice profile. Letta’s persona block is not that profile. The app note is explicit that “do not imitate this when speaking to the user” is `STYLE_FOOTER`, a paragraph inside the same block that is sent on every styled turn. Section 5 is the code path that omits it.

**Graph communities, a second transcript store, and an LLM reranker are the wrong copies.** Communities are the expensive layer the Zep authors refresh only periodically. Episode nodes would duplicate chat history the app note did not inventory. A GPT-class rerank per query is what produced the 57.1% → 77.2% gap, and the market note says a local app that will not pay for that call should not cite 77% or 81% as the RRF result. Grain’s RRF path is already the fusion that fits this file.

**Exact-label nodes are a known limit, and tidy-up already proposes alias merges.** “Postgres” and “PostgreSQL” stay two nodes until a proposal is applied. That proposal path is shipped. Extract-time fuzzy merge is in the table as a later, optional prompt change, not as a new database.

Out of the table on purpose:

- Past-chat search and incognito history deletion. Leading apps ship them. The app note does not inventory them, and document RAG was out of scope. No build is specified.
- A dreaming-style summary that replaces the memory list. Different on purpose; see section 3.
- Sensitive-topic filtering. Different on purpose.
- Cosine clustering, auto-apply tidy, graph communities, Neo4j, Qdrant, FalkorDB, a Letta sidecar, an LLM reranker on every query.
- Per-register voice (email vs chat vs doc) and few-shot injection of raw samples. The app note records both as absent. The market note does not document them as something leading apps ship. Raw samples would also put topic content into the prompt, which `ANALYSIS_PROMPT` tells the model to leave out of the profile.

## 5. The top three builds

Order is user-visible harm, then how sure the notes are, then fit to one SQLite file. Each check runs with a fixture database and a stubbed model. No network, no embedding server.

### 1. Draft-only voice, enforced in code

Build the voice row from the table.

Offline acceptance:

1. Profile summary text is the fixture string `SHORTSENTENCEVOICE`. `useStyle` is true. The profile is enabled.
2. `build_context` for a non-draft turn does not contain `## How the user writes` and does not contain `SHORTSENTENCEVOICE`. `writing_style` for that turn does not contain the guidelines or the phrases.
3. The same conversation state, next call, draft flag true, chat not tainted: the context contains the header and `SHORTSENTENCEVOICE`. The block is produced on that call, so a following non-draft call can omit it without relying on a cached stable prefix.
4. Draft flag true and the chat tainted: the header is absent.
5. `useStyle` false and draft flag true: the header is absent.

A keyword list inside the model prompt does not satisfy this. The boolean has to be an argument to `build_context` and to the tool.

### 2. Pinned rows survive hybrid injection

Build the pin row from the table.

Offline acceptance:

1. In-memory SQLite, hybrid enabled. Stub `query_vec` with a local vector so `MemoryIndex.search` runs and does not call HTTP.
2. One pinned live memory whose text shares no tokens with the query, plus 40 unpinned live memories that match the query on FTS and, if the cosine ranker runs, sit closer to the stub vector than the pinned row does.
3. The string placed under `## What you remember about the user` includes the pinned content.
4. The pinned row is still absent from `Consolidator` memory candidates, and a stubbed extractor update for that id does not change its content.
5. Repeat with `query_vec` returning None. The pinned content is still present (fallback path).

### 3. Absolute dates on new memories, fact text and message time on edges

Build the time-and-fact row from the table. This is the Graphiti-shaped work that fits the current tables, and the dreaming-shaped work that does not require a background rewriter.

Offline acceptance, with the extractor stubbed to a fixed JSON payload and `Today is Friday, 2026-10-02` supplied the same way `EXTRACT_PROMPT` already receives it:

1. Candidate content `User is traveling next Tuesday` is not stored as that relative phrase. It is either absent or stored with an absolute date derived from 2026-10-02. Content `User went to Singapore in July 2026` is stored.
2. A relation payload that includes `fact` text and omits a time produces an edge whose `fact` column is that text and whose `valid_at` equals the fixture message timestamp passed into `learn_from_exchange`, including when the test sets that timestamp to something other than the wall clock.
3. `build_context`’s graph section contains the fact text. A second payload that ends that edge leaves it out of the default graph section.
4. `Graph.get(include_invalid=true)` returns the ended edge. Default `Graph.get` does not.

Do this before any new graph engine. Live chat is already close on transaction time (`valid_at` defaults to `now()` at insert). The check that is missing is the relative-date guard, the fact string, and a UI that can show the closed edge.

The memory-off write gate (table row, effort S) can ship in the same week as build 2. It does not depend on voice. It is fourth because two switches already exist and the defect is a missing condition in `_chat_stream`, while builds 1 and 2 contradict copy the user can see on every turn.

## 6. Already shipped, so not a gap

These are in the working tree the app note inventoried. A comparison that starts from README step 2 or from `sota-memory.md` “Where we are” will list them again. Do not rebuild them.

- **Hybrid retrieval.** When `embeddingModel` is set, `hybridRetrieval` is not false, and `retrievalMode` is not `bm25`, memory retrieval fuses FTS BM25, brute-force cosine, pinned/recent, and graph-label seeds with `embed.rrf`. Defaults satisfy that (`qwen3-embedding-8b`, hybrid, `hybridRetrieval` true). Embeddings time out after 2 seconds and fall back to `Memories.for_context`. Vectors live in `memory_vectors` in the same SQLite file. The remaining work is the pin union, the silent fallback, and the settings field, not a second retriever stack. This RRF is not the memory-probe LLM reranker, so do not quote 77.2% as Grain’s measured gain.
- **Supersession.** `Memories.supersede` inserts a new live row and sets `invalid_at` and `superseded_by` on the old one. Extractor forget calls `Memories.invalidate`. `history()` walks the chain. Show history and `POST /memories/{id}/restore` are in the UI. Edge `invalidate_edge` is the graph version. The remaining work is user-edit history, the pinned in-place branch, trash versus invalid labeling, and showing ended edges.
- **Approve-only tidy-up.** `memory_proposals` kinds `merge_memories`, `rewrite_memory`, and `merge_entities`. Candidates are capped at 20: token Jaccard ≥ 0.6, stale relative dates on auto rows older than 30 days, and alias-like entity pairs. `propose` never applies. Auto proposals run every `consolidateEvery` new auto memories (default 25; 0 disables). Memory “Tidy up” calls `POST /memories/consolidate`. Apply and Dismiss are `POST /memories/proposals/{id}/apply|dismiss`. Pinned rows are excluded. The remaining work is the write-time relative-date check in build 3, not auto-apply and not cosine clustering.

Also already shipped, and easy to “recommend” from the stale docs: provenance columns on auto-learn rows, `valid_from` / `invalid_at`, the voice sample store and profile, per-chat toggles, context Preview / Last reply / Trace, exact-duplicate suppression, and 1-hop graph injection. The app note’s deviations from the memory-2 spec (HTTP embeddings and numpy in `embed.py`, `rrf` living in `embed.py`, default embedding model non-empty, no settings field) are implementation details. Only the missing settings field and the silent fallback are in the table.
