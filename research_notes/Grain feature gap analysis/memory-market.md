# Long-term memory and knowledge graphs (as of 2026-10-02)

Scope is product behavior and published mechanisms. No Grain code was read for this note. Dates below are source dates, not assumptions. Vendor benchmarks are labeled as such and are not treated as independent.

## How do ChatGPT memory, Claude memory, and project-scoped memory work in product?

### Takeaway

As of early October 2026, both ChatGPT and Claude keep a user-editable memory artifact separate from raw chat history, can search past chats, and offer a mode that neither reads nor writes memory. ChatGPT’s current system is a background synthesis OpenAI calls dreaming (Dreaming V3, announced 2026-06-04), with the 2024 explicit “saved memories” list still available as a legacy mode. Claude’s current system writes short per-topic memory files during the chat; a legacy mode still synthesizes one summary about every 24 hours, and legacy export is offered until 2026-09-09. Projects on both products are a scope wall: Claude gives each project its own memory and summary; ChatGPT lets a new project be project-only, and sharing a project locks that wall on permanently.

### Cited Findings

**ChatGPT: two layers, then a synthesis**

- Memory launched April 2024 as saved memories: written during the conversation, triggered by strong cues such as “remember I’m traveling to Singapore in July.” OpenAI says those notes go stale. In April 2025, “dreaming” was added as a background process that curates memory from chat history without an explicit remember-request. On 2026-06-04 OpenAI announced Dreaming V3 as the memory architecture, framing the lineage as 2024 saved memories, 2025 saved memories plus Dreaming V0, 2026 Dreaming V3. — [OpenAI, Dreaming (2026-06-04)](https://openai.com/index/chatgpt-memory-dreaming/)
- Dreaming rewrites time-sensitive memories. OpenAI’s example is “You’re going to Singapore in July” becoming “You went to Singapore in July 2026” after the trip. The same post says the synthesized memories are reviewable on a memory summary page, where the user can see highlights, add or update information, and give instructions about which topics to bring up and when. Drilling into a topic is done by chatting with the model. — [OpenAI, Dreaming (2026-06-04)](https://openai.com/index/chatgpt-memory-dreaming/)
- The post says Dreaming V3 began rolling out to Plus and Pro in the US on 2026-06-04, with other countries and Free and Go “over the coming weeks.” It also says recent work cut the compute to serve dreaming to Free users by about 5x, and that this allows higher memory capacity for Plus and Pro. The extracted article text describes three eval axes (carry context forward, follow preferences, stay current) and says dreaming “provides a substantial lift” on time-sensitive prompts. It does not print numeric scores for the 2024 / 2025 / 2026 systems; any chart values were not in the fetched text. — [OpenAI, Dreaming (2026-06-04)](https://openai.com/index/chatgpt-memory-dreaming/)
- Help Center, alongside that rollout: when Memory is on, ChatGPT can use past chats, saved memories, custom instructions, files in Library, and content from connected apps such as Gmail. Controls named on that page include Memory, Reference saved memories, Reference chat history, Memory summary, Manage, and Saved memories. Improved Memory “continually updates a broader summary.” Legacy saved memories are “a more explicit list of individual memory items.” Settings path given: Personalization, then saved memories for the legacy experience, or “Try improved memory” to return. — [OpenAI Help, Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- Saved memories are stored separately from chat history. Deleting the chat does not delete the saved memory. Deleting a saved memory stops future personalization but does not scrub mentions already in past chats. OpenAI may keep logs of deleted saved memories for up to 30 days for safety and debugging. Deletion and memory updates “can take time” to propagate. Depending on plan and platform, saved-memory controls include search, sorting, automatic prioritization, and version history. — [OpenAI Help, Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt); same separation and 30-day log also in [Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq)
- An older Help article still describes two toggles: “Reference saved memories” (explicit remembers, kept until deleted, always in future responses) and “Reference chat history” (details can change as ChatGPT updates what is useful; it does not retain every past-chat detail). Turning saved memory off does not delete what was already stored. Temporary Chat is the way to chat without saved memory. — [OpenAI Help, How does “Reference saved memories” work?](https://help.openai.com/en/articles/11146739-how-does-reference-saved-memories-work) (the fetched mirror was help-lb.openai.com; treat this two-toggle writeup as the pre-Dreaming-V3 control surface if it disagrees with the 2026-06-04 post and the current Memory in ChatGPT article)
- Temporary Chat, in the Enterprise/Edu context table: custom instructions available, ChatGPT Memory not available, reference to other chats not available. — [OpenAI Help, Projects in ChatGPT](https://help.openai.com/en/articles/10169521) (page says updated 4 days before fetch, so about 2026-09-28)

**ChatGPT projects**

- A project holds chats, uploaded files, and project instructions. Project instructions apply only inside that project and “will override your global custom instructions.” — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- On create, the user chooses project-only or default memory. Existing projects stay on default. Project-only can only be set when starting a new project. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Project-only: previously saved memories are not referenced; chats may reference other chats in the same project; they cannot reference chats outside it. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Default memory: saved memories are referenced, and chats can draw on other conversations in the same project. Whether chats outside the project are visible depends on plan. Enterprise and Edu: even default-memory project chats cannot reference conversations outside the project, and outside chats cannot reference the project. Non-Enterprise, including Business: chats can reference project and non-project conversations unless the other project is project-only, and those chats can be referenced from outside. Plus and Pro: ChatGPT prioritizes the project’s chats and files. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Enterprise and Edu context table: inside a project, account custom instructions are “Not available (only project instructions)” under both default and project-only. ChatGPT Memory is available in default project chats and not available in project-only. Reference to other chats is “only within a project” in both modes. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Sharing a project sets memory to project-only from that point and it cannot be reverted, including after collaborators are removed. Shared projects do not see a member’s context, custom instructions, or memories outside the project. Project-memory prerequisites: Enterprise needs Reference saved memories plus workspace Memory; other plans need Reference saved memories and Reference chat history. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)
- Sharing has been available to Free, Plus, Pro, and Go since an update dated 2025-10-22 on that page. Collaboration caps on that page: Pro 40 files and 100 collaborators; Plus and Go 25 files and 10 collaborators; Free 5 files and 5 collaborators; Business, Enterprise, and Edu 40 files, and workspace projects capped at 100 people. Unlimited projects. — [OpenAI Help, Projects](https://help.openai.com/en/articles/10169521)

**Claude: topic files now, one summary before**

- Help Center article “updated yesterday” relative to this fetch (so about 2026-10-01): Anthropic has migrated users to an improved memory experience. Legacy export remains under Settings > Memory until 2026-09-09. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Current behavior: Claude saves memory as individual topics during the chat, “rather than summarizing conversations after they end.” The user can also say “remember this.” Everything remembered is a list of files under Topics in Settings > Memory. Each topic can be read, edited, or deleted; a fix in one topic applies to later conversations. The user can also tell Claude in chat to remember, change, or forget, and that applies to the next conversation. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context); same topic-file description in [Claude blog](https://claude.com/blog/claudes-memory-works-everywhere-and-you-decide-whats-in-it)
- Memory is on by default for Free, Pro, and Max on web, desktop, and mobile. On Team and Enterprise, owners control availability and it is off per member until they turn it on. Memory is shared between Chat and Claude Cowork when Cowork runs in the cloud; local Cowork sessions do not use memory. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Sensitive topics (health, race, ethnicity, religious beliefs, politics, gender identity, and similar) are not stored by default. “Include sensitive topics in memory” is opt-in and is not retroactive. Turning it off later removes sensitive items already saved. Some items are never saved even if asked: government ID numbers, criminal history, financial account numbers, immigration status. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Account controls: Pause keeps existing memory but does not use it or add to it, and paused conversations are not added later if memory is unpaused. Reset permanently deletes all memories including project memories. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Search past chats is a separate capability, on by default once rolled out, for paid plans (Pro, Max, Team, Enterprise) on web, desktop, and mobile. The help article says these searches use retrieval-augmented generation and show up as tool calls. Search scope: all chats outside projects, or, inside a project, only that project’s conversations. Citations link back to the source chats. Enterprise orgs on customer-managed encryption keys cannot search past chats because content is encrypted. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Deleting or expiring a conversation does not remove memory entries already generated from it. The user can delete individual memories. All memory is in data exports and follows chat retention. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Legacy experience, still documented on the same page for accounts that see Memory under Settings > Capabilities: Claude summarizes conversations into chat summaries and a cross-chat synthesis, updated every 24 hours, excluding project chats. The user edits that summary in “View and edit memory,” or by telling Claude in chat, and chat edits apply to the next conversation without waiting for the daily job. In the legacy enterprise section, deleted conversations are removed from memory synthesis, and synthesis updates within 24 hours of create, modify, or delete. That deletion behavior disagrees with the current-experience sentence that generated entries are not removed when the source chat is deleted. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Import/export exists and is described as experimental. A separate help article says Claude’s memory is oriented to work context and may drop imported personal details that are not work-related; the user can force an item by editing memory. — [Claude Help, import and export memory](https://support.claude.com/en/articles/12123587-import-and-export-your-memory-from-claude)

**Claude projects and incognito**

- Both the current and legacy sections say each project has its own memory space and a dedicated project summary, separate from other projects and from non-project chats. — [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Incognito chats exist for Free, Pro, Max, Team, and Enterprise. They are not saved to chat history or to memory, are not used as memory input, are not pulled into past-chat search, and are not in the monthly recap. Starting one does not use existing memory. They are still retained: 30 days by default, or longer under an Enterprise custom retention setting, and they are included in org data exports. — [Claude Help, incognito chats](https://support.claude.com/en/articles/12260368-use-incognito-chats); also [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Incognito is only outside projects (no ghost icon inside a project). Inside or outside a project, the user can turn Memory off in the “+” menu before the first message. That chat does not use or add to memory (including project memory). Unlike incognito, the chat stays in history and can still be found when other conversations search past chats. The memory-off chat itself does not search past chats. The setting locks after the first message. — [Claude Help, incognito chats](https://support.claude.com/en/articles/12260368-use-incognito-chats); [Claude Help, chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Team/Enterprise product post (older than the topic-file rollout; do not treat its “memory is opt-in” line as current for Free/Pro/Max): project-scoped memory, view/edit, and incognito that does not appear in history or save to memory. — [Anthropic, Bringing memory to teams](https://claude.com/blog/memory)

**Not the consumer product**

- Anthropic’s Managed Agents API memory stores (public beta, header dates in 2026) are a different surface: up to 8 workspace-scoped text-file stores per session, mounted at `/mnt/memory/...`, read and written with ordinary file tools, attachable only at session create, with read-only as the recommended mode when input is untrusted because a later session will trust what was written. — [Claude Platform, Using agent memory](https://platform.claude.com/docs/en/managed-agents/memory)

### Inferences

- The durable product pattern in 2026 is a small editable artifact (summary or topic files) that is always eligible for the next chat, plus a separate search over raw history, plus an explicit off switch. Neither product describes a user-visible knowledge graph.
- ChatGPT’s project-only mode and Claude’s per-project memory are the same product idea: a scope that does not inherit the global profile. ChatGPT’s non-Enterprise default mode is leakier than Claude’s: a default project can still see saved memories and, off Enterprise/Edu, chats outside the project.
- “Incognito” and “memory off for this chat” are different. Incognito drops history and memory. Memory-off keeps history and remains searchable from other chats.
- The 24-hour Claude synthesis is legacy. Citing it as current Claude behavior is stale after the topic-file migration described in the help article updated about 2026-10-01.

### Gaps

- The Dreaming post’s eval charts were not extracted as numbers. No independent measurement of Dreaming V3 vs saved memories was found.
- OpenAI does not document the retrieval algorithm behind “reference chat history” or dreaming (embeddings, BM25, or a model reading a summary). The help pages describe controls and data boundaries, not the ranker.
- Claude does not document how topic files are selected into the prompt, how large they can get, or how the project summary relates to topic files inside a project.
- Whether ChatGPT Temporary Chat still allows custom instructions on non-Enterprise plans is only pinned down by the Enterprise/Edu table on the Projects page.
- Managed Agents memory stores were not compared to claude.ai consumer memory beyond noting they are a different product.

## What do Mem0, Letta/MemGPT, and Zep/Graphiti actually do?

### Takeaway

Mem0 (paper April 2025) is an LLM extraction pass plus an LLM tool-call update (ADD, UPDATE, DELETE, NOOP) over a vector store; the graph variant stores directed triplets and marks conflicting relationships invalid instead of deleting them. Letta’s current core mechanism is not a retriever: labeled text blocks are pinned in the prompt and the agent rewrites them with tools, under a character limit. Graphiti, the engine behind Zep, builds three layers (episodes, entity/fact edges, communities) and keeps two clocks on each edge, valid time and transaction time, invalidating contradicted edges instead of deleting them. Retrieval in the Zep paper is cosine plus BM25 plus breadth-first search, then a reranker, with no requirement that an LLM sit in the query path.

### Cited Findings

**Mem0 extraction and update (author paper, arXiv:2504.19413)**

- Pipeline runs on each new message pair (typically user message plus assistant reply). Extraction prompt is the pair, plus a conversation summary S, plus the previous m messages. An async summary job refreshes S off the hot path. The LLM returns candidate facts. In the reported config, m = 10 and the LLM is GPT-4o-mini. — [Chhikara et al., Mem0, arXiv:2504.19413](https://arxiv.org/html/2504.19413)
- Update: for each candidate, embed it, fetch the top s similar memories (s = 10), and let the LLM choose via a tool call: ADD if nothing equivalent exists, UPDATE to merge complementary detail, DELETE if the new fact contradicts an old one, NOOP otherwise. The paper uses dense embeddings for that similarity search. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Mem0g stores a directed labeled graph: nodes are typed entities with an embedding and a creation timestamp; edges are triplets. Extraction is two LLM stages (entities, then relationships). On write, source and destination are matched to existing nodes above a similarity threshold t. A conflict detector plus an LLM resolver can mark relationships invalid rather than delete them, which the paper says is what enables temporal reasoning. Retrieval is dual: expand incoming and outgoing edges from query-matched entity nodes, and separately embed the query against triplet text and keep triplets above a threshold. Implementation named in the paper: Neo4j, GPT-4o-mini with function calling. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Current OSS docs (fetched 2026-10-02) say graph memory is not in the open-source Python or TypeScript SDKs; it is a Mem0 Platform feature. OSS vector stores include Qdrant (Python default), pgvector, Chroma, FAISS, and others. A running vector store is required except Python’s default Qdrant and Node’s in-memory store. Optional `historyDbPath` is a file path for a history store; the docs snippet does not name the engine. A separate evaluation page describes three layers (vector store, graph/entity store, SQL history of ADD events plus a rolling message window); that page is about their evaluation stack and should not be read as “OSS includes the graph.” — [Mem0 OSS configuration](https://docs.mem0.ai/open-source/configuration); [vector DB overview](https://docs.mem0.ai/components/vectordbs/overview); [LLM config, historyDbPath](https://docs.mem0.ai/components/llms/config); [memory evaluation storage table](https://docs.mem0.ai/core-concepts/memory-evaluation)

**Mem0 numbers, author-run, not independent**

- LOCOMO: 10 conversations, about 600 dialogues and 26,000 tokens each, about 200 questions each. Adversarial questions excluded. Judge metric J is an LLM judge, mean of 10 runs. — [Mem0 paper](https://arxiv.org/html/2504.19413)
- Table 1 J (LLM-as-a-Judge), Mem0 vs Mem0g vs their OpenAI-memory run vs their Zep run: single-hop 67.13 / 65.71 / 63.79 / 61.70; multi-hop 51.15 / 47.19 / 42.92 / 41.35; open-domain 72.93 / 75.71 / 62.29 / 76.60; temporal 55.51 / 58.13 / 21.71 / 49.31. Mem0 leads single-hop and multi-hop. Mem0g leads temporal. Their Zep run leads open-domain. The graph does not help single-hop or multi-hop in this table. — [Mem0 paper, Table 1](https://arxiv.org/html/2504.19413)
- Table 2 overall J: full-context 72.90 ± 0.19 (26,031 tokens, total p95 17.117 s); Mem0 66.88 ± 0.15 (1,764 tokens, search p95 0.200 s, total p95 1.440 s); Mem0g 68.44 ± 0.17 (3,616 tokens, total p95 2.590 s); Zep 65.99 ± 0.16 (3,911 tokens); their OpenAI memory run 52.90 ± 0.14 (4,437 tokens, total p95 0.889 s); best RAG cell they report is k=2, 256-token chunks, J 60.97. The abstract’s “26% relative improvement over OpenAI” matches (66.88 − 52.90) / 52.90 on this judge, against their own ChatGPT-memory procedure, which stuffed all generated memories into context because they had no selective-retrieval API. The abstract’s “91% lower p95 latency” and “more than 90% token cost” are versus full-context (1.440 vs 17.117 seconds; 1,764 vs 26,031 tokens), not versus a BM25 list. Full-context still wins overall J. — [Mem0 paper, abstract and Table 2](https://arxiv.org/html/2504.19413)
- Their OpenAI baseline was weak on temporal J (21.71) because, they write, most generated memories lacked timestamps despite a prompt asking for them. — [Mem0 paper §4.1](https://arxiv.org/html/2504.19413)

**Letta / MemGPT**

- MemGPT (Packer et al., 2023, arXiv:2310.08560) is the paper Zep treats as the prior system. Zep quotes its DMR score as 93.4% with gpt-4-turbo, against 35.3% for recursive summarization. That paper is three years old relative to 2026-10-02. — cited inside [Rasmussen et al., Zep, arXiv:2501.13956](https://arxiv.org/html/2501.13956v1), reference [3]
- Current Letta docs: a memory block is a labeled section prepended to the prompt in an XML-like wrapper (`label`, `description`, `value`, `limit` in characters, plus `read_only`). Blocks are always in context. The agent reads and updates them with built-in memory tools. The description is what tells the agent how to use the block. Recommended starter blocks are `human` and `persona`. Examples use limits of 5000 and 4000 characters. Setting `value` replaces the whole block; concurrent writers, last write wins. Read-only blocks cannot be updated by the agent. Blocks can be shared across agents. Developers can also patch a block from outside the agent. — [Letta docs, memory blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)
- A Letta skills note describes the older hierarchy: core blocks always in context; archival memory behind `archival_memory_insert` and `archival_memory_search`, off unless base tools are enabled; guidance of roughly 2000–5000 characters per block and 5–15 blocks. That note is an API-client skill, not the 2026 self-host page, so treat the archival tier and the numeric guidance as possibly stale. — [letta-ai/skills, memory-architecture.md](https://github.com/letta-ai/skills/blob/HEAD/letta/letta-api-client/memory-architecture.md)
- Letta’s own blog states the same origin: MemGPT chat used two self-editing blocks, human and persona, each with a character limit, persisted so a developer can edit the context directly. — [Letta blog, Memory blocks](https://www.letta.com/blog/memory-blocks/)
- Self-host as documented now: local CLI, desktop app, or App Server with `--backend local`. Agent state including memory stays on disk under `~/.letta/lc-local-backend`. Per-agent MemFS git repos live at `~/.letta/lc-local-backend/memfs/<agent-id>/memory`. No Letta account required. Inference is whatever provider you connect; local state does not imply local inference. Skip-login in the desktop app stores agents locally. — [Letta docs, self-hosting](https://docs.letta.com/self-hosting/)
- The Docker image `letta/letta:latest` is Letta Code / App Server. The old Python server’s PostgreSQL data directory is explicitly unsupported; image tags `0.16.x` remain only for historical reproducibility. A v1-SDK Docker page still documents `LETTA_PG_URI` plus `pgvector` and optional MemFS. That page conflicts with the current self-host page and the Docker Hub retirement note; prefer the self-host page for “what runs in 2026.” — [Docker Hub, letta/letta](https://hub.docker.com/r/letta/letta); [Letta v1 SDK Docker](https://docs.letta.com/v1-sdk/docker/index.md)

**Zep / Graphiti construction (paper: experiments Dec 2024–Jan 2025)**

- Graph has three tiers. Episode nodes store raw messages, text, or JSON (non-lossy). Semantic nodes are resolved entities; semantic edges are facts between entities, and the paper says the same fact can be a hyper-edge across more than two entities. Community nodes are clusters with map-reduce summaries, built with label propagation rather than Leiden, plus a one-step dynamic update when a new entity arrives, with periodic full refreshes. — [Zep paper §2](https://arxiv.org/html/2501.13956v1)
- Bi-temporal clocks, stored on edges: `t'created` and `t'expired` are when the system learned or invalidated the fact (transaction time); `t_valid` and `t_invalid` are when the fact was true in the world (valid time). Each message has a reference timestamp `t_ref` so relative dates (“two weeks ago”) can be resolved. Entity extraction uses the current message plus the last n = 4 messages, then a reflection pass. Entity names are embedded (1024-d in the paper) and also full-text searched; an LLM decides duplicates and rewrites the name and summary. Database writes are fixed Cypher, not model-written queries. — [Zep paper §2.1–2.2](https://arxiv.org/html/2501.13956v1)
- Invalidation: an LLM compares a new edge to semantically related existing edges between the same entity pair. On a temporally overlapping contradiction, `t_invalid` of the old edge is set to `t_valid` of the new edge. New information wins. Edges are not deleted. — [Zep paper §2.2.3](https://arxiv.org/html/2501.13956v1)
- Retrieval: cosine, Okapi BM25 (Neo4j Lucene in the paper), and breadth-first search out from seed nodes, including recent episodes as seeds. Rerankers: reciprocal rank fusion, maximal marginal relevance, an episode-mention frequency reranker, a node-distance reranker, and an optional cross-encoder. The context string is facts with valid/invalid date ranges, entity name plus summary, and community summaries. The paper’s experiments retrieved the top 20 edges and entity nodes (top 10 in the DMR run). Embeddings and reranking in the experiments were BGE-m3. Graph construction used gpt-4o-mini-2024-07-18. — [Zep paper §3–4](https://arxiv.org/html/2501.13956v1)
- Live Graphiti README (Apache-2.0, about 30,529 stars at fetch): same story in product language. Facts have validity windows and are invalidated rather than deleted. Episodes are provenance. Ontology can be prescribed with Pydantic models or learned. Hybrid retrieval is semantic plus keyword (BM25) plus graph traversal, described as not relying on LLM summarization at query time. Query latency claim on that page is “typically sub-second,” which is a project claim, not a paper table. Default LLM and embedding path is an OpenAI API key; structured output is called out as important, and smaller models are described as prone to bad schemas and ingestion failure. — [getzep/graphiti README](https://github.com/getzep/graphiti)
- Backends required by that README: Neo4j 5.26, FalkorDB 1.1.2, Amazon Neptune plus OpenSearch Serverless, or Kuzu 0.11.2. Kuzu is deprecated because upstream is unmaintained, still installable as `graphiti-core[kuzu]`, emits DeprecationWarning. FalkorDB can be a Docker server or, on Python 3.12+, an embedded extra `graphiti-core[falkordblite]`. There is no SQLite graph driver. Zep the product now says its managed service uses a proprietary Context Graph Engine and does not require the user to run Neo4j; Graphiti remains bring-your-own-graph. — [Graphiti README](https://github.com/getzep/graphiti)
- A Graphiti GitHub issue (not a controlled study) reports that on one backfill of 1,384 edges from 264 historical episodes, 771 edges (56%) had `valid_at` set to midnight UTC on the processing day rather than the episode’s reference time, which the author attributes to the extraction prompt letting the model guess “today.” That is one operator’s count, and it is evidence the bi-temporal fields are only as good as the extractor. — [getzep/graphiti issue 1492](https://github.com/getzep/graphiti/issues/1492)

**Zep paper numbers vs later vendor numbers**

- DMR (500 conversations, 5 sessions, up to 12 messages, so about 60 messages; the paper says this fits in a modern context window). gpt-4-turbo: recursive summarization 35.3% (MemGPT’s reported figure), conversation summaries 78.6%, MemGPT 93.4% (reported, not re-run), full conversation 94.4%, Zep 94.8%. gpt-4o-mini: summaries 88.0%, full conversation 98.0%, Zep 98.2%. Zep could not reproduce MemGPT on gpt-4o-mini. The authors call DMR too easy and a poor enterprise proxy. — [Zep paper Table 1 and §4.2](https://arxiv.org/html/2501.13956v1)
- LongMemEval_s, conversations averaging about 115k tokens, judged by GPT-4o with the benchmark’s prompts. gpt-4o-mini: full-context 55.4% at 31.3 s and 115k context tokens, Zep 63.8% at 3.20 s and 1.6k tokens. gpt-4o: full-context 60.2% at 28.9 s, Zep 71.2% at 2.58 s and 1.6k tokens. The abstract’s “up to 18.5%” is the absolute gap 71.2 − 60.2, and “90%” latency is about (28.9 − 2.58) / 28.9. These baselines are full context, not BM25. Zep was worse on single-session-assistant questions (gpt-4o 80.4% vs 94.6% full-context). Knowledge-update improved only with gpt-4o (83.3% vs 78.2%), not with gpt-4o-mini (74.4% vs 76.9%). Temporal-reasoning: 62.4% vs 45.1% on gpt-4o. They could not get a working MemGPT run on this benchmark. Network path was a laptop in Boston to Zep in AWS us-west-2, so Zep’s latency includes a hop the local full-context baseline did not. — [Zep paper Tables 2–3](https://arxiv.org/html/2501.13956v1)
- Do not merge these with later Zep marketing. A Zep research page, `dateModified` 2026-09-29, reports LoCoMo accuracy 94.7% (1,459 / 1,540), temporal 95.6% (311 / 325), retrieval 87/155 ms, and describes a five-way multi-scope retrieval (facts, entities, episodes, observations, thread summaries) plus a separate “auto search” that reranks across scopes into a character-bounded block. That page is the vendor’s current harness, not the January 2025 paper. — [Zep research benchmarks](https://www.getzep.com/research/)
- A Zep papers repo README reports a different LoCoMo overall of 75.14 ± 0.17%, with single-hop 79.79%, multi-hop 74.11%, open domain 66.04%, temporal 67.71%, and no protocol next to the numbers. — [getzep/zep-papers locomo_eval](https://github.com/getzep/zep-papers/tree/main/kg_architecture_agent_memory/locomo_eval)
- Mem0’s authors, on their judge, scored a Zep platform run at overall J 65.99, below Mem0. Different judge, different retrieval budget, different year. The three Zep LoCoMo-style figures (65.99, 75.14, 94.7) are not one result. — [Mem0 paper Table 2](https://arxiv.org/html/2504.19413); [Zep research](https://www.getzep.com/research/); [zep-papers](https://github.com/getzep/zep-papers/tree/main/kg_architecture_agent_memory/locomo_eval)

### Inferences

- “Update” means three different things. Mem0 overwrites or deletes a fact. Mem0g and Graphiti close an interval and keep the old edge. Letta replaces a whole text block, or the agent edits it in place, with no bi-temporal record unless the app adds one.
- Graph structure is not a free accuracy win. In Mem0’s own table the graph helps temporal questions and hurts or ties single-hop and multi-hop. Zep’s gain versus full context shows up on temporal, multi-session, and preference questions, and reverses on single-session-assistant questions.
- Extraction quality bounds the clocks. Graphiti’s model is only bi-temporal if `valid_at` is actually the episode time. Issue 1492 is a concrete way that fails.
- Letta in 2026 is a local agent runtime with pinned blocks and a git-backed memory directory, not a library you embed in another process’s SQLite. The PostgreSQL+pgvector server is the retired line.

### Gaps

- No primary Mem0 doc fetched here states that `historyDbPath` is SQLite. It is only documented as a file path.
- Letta’s 2026 self-host page does not describe archival vector memory or a sleep-time consolidation agent. Those designs exist in the 2023 paper and in secondary Letta writing; whether the App Server still runs them was not confirmed.
- Graphiti’s README does not publish a BM25-only ablation. The paper’s ablations are against full context and summaries.
- The 2026-09-29 Zep LoCoMo page does not document the judge model, the prompt, or a public rerun script in the snippet that was fetched. Treat 94.7% as a vendor figure until a paper or repo pins the protocol. The 75.14% repo number is similarly under-specified.
- Community summaries and label propagation are in the paper. The live README still lists communities as part of the context graph. Whether every current Graphiti release builds them by default was not re-checked in source.

## What is the evidence that hybrid retrieval, consolidation, or pinned blocks beat a flat BM25 list?

### Takeaway

The cleanest 2026 evidence is a controlled LoCoMo study (arXiv:2603.02473): swapping BM25 for a hybrid of cosine and BM25 plus an LLM reranker moves average accuracy from 57.1% to 77.2%, while changing the write strategy (raw chunks, Mem0-style facts, MemGPT-style summaries) only moves it 3–8 points. Raw chunks, which are a flat list plus a retriever, match or beat the consolidated stores under the same retriever. Nobody in the sources below publishes a head-to-head of a pinned profile block against a BM25 list. Anthropic’s 2024 contextual-retrieval post shows embeddings plus BM25 beating embeddings alone on document RAG; it is not a conversational-memory result and it does not report a BM25-only failure rate in the summary.

### Cited Findings

**Hybrid vs BM25, conversational memory, March 2026**

- Yuan, Su, and Yao, “Diagnosing Retrieval vs. Utilization Bottlenecks in LLM Agent Memory,” arXiv:2603.02473. 3×3 on LoCoMo, 1,540 non-adversarial questions. Writes: raw 3-turn chunks (no LLM at write time), Mem0-style extracted facts with add/update/noop, MemGPT-style one summary per session. Retrievers, k=5: cosine over text-embedding-3-small, BM25, and Hybrid+Rerank (top 2k from each of cosine and BM25, then GPT-5.2 reranks to k). Backbone for answers is GPT-5-mini. This hybrid is not reciprocal rank fusion; the fusion step is an LLM judge. — [memory-probe paper](https://arxiv.org/html/2603.02473v1)
- Accuracy, LLM-as-judge. Basic RAG: cosine 77.9%, BM25 59.2%, hybrid 81.1%. Extracted facts: 72.2 / 49.4 / 77.3. Summarized episodes: 70.1 / 62.7 / 73.3. Column averages: cosine 73.4%, BM25 57.1%, hybrid 77.2%. Spread across retrievers is 14–23 points; spread across writes inside one retriever is 3–8 points. — [memory-probe Table 1](https://arxiv.org/html/2603.02473v1)
- The one place a summary beats raw text is BM25: summarized episodes 62.7% vs raw chunks 59.2%. The authors’ explanation is that compression packs vocabulary BM25 can match. Under cosine and hybrid, raw chunks win. Extracted facts are the worst BM25 cell (49.4%). — [memory-probe §3.1](https://arxiv.org/html/2603.02473v1)
- Retrieval failure, not utilization, is the large term. For raw chunks, retrieval-failure rate goes from 35.3% (BM25) to 11.4% (hybrid). Utilization failure stays about 4–8% and hallucination about 0.4–1.4% across all nine cells. Precision@5 correlates with accuracy at r=0.98. Token F1 barely moves (hybrid average 0.221 vs BM25 0.168) while judge accuracy moves 20 points. — [memory-probe Table 2 and §3.2–3.3](https://arxiv.org/html/2603.02473v1)
- Limitations the authors state: one backbone, one benchmark, fixed k=5, prompt-based imitations of Mem0 and MemGPT rather than the real systems, LLM judges, and the raw-chunk advantage may shrink if the context budget is too small for chunks. — [memory-probe §4](https://arxiv.org/html/2603.02473v1)

**What the vendor papers actually compare against**

- Mem0’s RAG baseline is embedding search over fixed chunks, k in {1, 2}, not BM25. Best reported RAG J is 60.97. Mem0 J is 66.88. Full-context J is 72.90. So in that paper, extraction beats their vector-chunk RAG and loses to putting the whole conversation in context, on the judge score, while winning on tokens and latency. — [Mem0 paper Table 2](https://arxiv.org/html/2504.19413)
- Zep’s LongMemEval comparison is full-context vs the graph retriever, not BM25 vs hybrid. The hybrid (cosine + BM25 + BFS + rerank) is the system, with no ablation that turns BM25 off. — [Zep paper §3 and Table 2](https://arxiv.org/html/2501.13956v1)
- Zep DMR: a pinned-block / self-editing system (MemGPT, 93.4% as reported by its authors) does not beat Zep’s full-conversation reimplementation (94.4%) or Zep (94.8%) on gpt-4-turbo, and all three dwarf recursive summarization (35.3%). The paper says the conversations are short enough to fit in context, so this is weak evidence that pinned blocks beat a retriever. — [Zep paper Table 1](https://arxiv.org/html/2501.13956v1)

**Document RAG, September 2024, not a memory benchmark**

- Anthropic, 2024-09-19: contextual retrieval prepends a 50–100 token Claude 3 Haiku blurb to each chunk before embedding and before BM25. Failure metric is 1 − recall@20, averaged over code, fiction, and papers, top embedding setup Gemini Text 004. Embeddings only: 5.7% failure. Contextual embeddings: 3.7% (35% relative reduction). Contextual embeddings plus contextual BM25: 2.9% (49% relative reduction from 5.7%). Adding a Cohere reranker over the top 150, then keeping 20: 1.9% (67% relative reduction). They also say top-20 beat top-10 and top-5. One-time contextualization cost they quote is $1.02 per million document tokens with prompt caching. They do not publish a BM25-only failure rate in the body of the post. If the corpus is under about 200,000 tokens, they say to skip RAG and put it in the prompt. — [Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- This is evidence that adding BM25 to embeddings reduces retrieval failure on document chunks. It is not evidence about chat memory, consolidation, or pinned profile blocks. The post is from 2024; the failure rates are Anthropic’s own eval.

**Pinned blocks**

- Letta’s claim is architectural: blocks “are always visible — no retrieval needed,” so a fact in the human block cannot be missed by a ranker. No accuracy table versus BM25 is on that page. — [Letta docs, memory blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)
- memory-probe’s utilization result is the nearest indirect evidence: when a relevant memory is actually in the prompt, the model’s failure to use it is the small term (about 4–8%). A pinned block is a way to force that case for a few facts. It does not say the block beats BM25 on the long tail that does not fit in the block. — [memory-probe Table 2](https://arxiv.org/html/2603.02473v1)

**Vendor pipelines that add BM25 and then claim a gain**

- Mnemo’s docs show a LOCOMO stack climbing from “LanceDB vector only 66.7%” to “+ BM25 fusion 82.4%” and then 85.2% after a Voyage embedding upgrade and a larger pool. Each row changes more than one thing, the judge definition is theirs (≥2 on a 0–3 scale), and this is a vendor doc. Useful as a sign that they believe BM25 fusion helped inside their pipeline. Not an independent ablation. — [Mnemo LOCOMO docs](https://docs.m-nemo.ai/guide/benchmark.html)
- Popoto’s hybrid-vs-lexical note is a counterexample, not a win: after a scoring correction, on 250 LoCoMo questions their BM25-style lexical run and their BM25+vector RRF run were within one Recall@10 question, because their router sent name and date queries down the lexical path. Same site, different page, reports LongMemEval-S any-hit Recall@5 of 95.2% for both a BM25+vector reference and their BM25-only baseline. Recall@10 was 98.6% vs 97.8%. That is a retrieval-recall metric on a benchmark where keywords often appear in the question, not an answer-accuracy result. — [Popoto LoCoMo hybrid](https://popoto.io/benchmarks/results/locomo_hybrid/)

### Inferences

- Against a flat BM25 list, the supported upgrade on conversational questions is a second retriever plus a rerank, not a smarter write. memory-probe’s 20-point average gap is judge accuracy on LoCoMo, with GPT-5.2 doing the rerank, so the gain is not free and is not “RRF alone.”
- Consolidation (Mem0-style facts or session summaries) does not beat storing raw turns, on that study, except a small BM25-only bump for summaries. Mem0’s paper is not a counterexample to this, because its RAG baseline is vector search, its full-context baseline still scores higher, and the write and the retriever change together.
- A pinned profile block is justified as a miss-prevention device for a handful of facts that must always be present. The benchmarks do not show it outperforming a decent retriever over the whole store. On short DMR conversations, full context already matches MemGPT.
- Graph retrieval’s published wins (Zep LongMemEval) are against full context on long transcripts, concentrated on temporal and multi-session questions, with a regression on “what did the assistant say in this session.” That is a different claim from “hybrid beats BM25.”

### Gaps

- No source found that ablates RRF(BM25, cosine) against BM25 alone on LoCoMo or LongMemEval answer accuracy. memory-probe’s hybrid includes an LLM reranker. Zep supports RRF but does not publish that ablation.
- No source found that compares a pinned human/persona block plus BM25 over the remainder against BM25 over everything.
- Anthropic does not report BM25-only failure, so “hybrid beats BM25” cannot be read off the 5.7% → 2.9% line. That line is hybrid versus embeddings.
- Popoto and Mnemo figures are vendor or project dashboards. They are cited only as conflict or pipeline anecdote.
- LoCoMo itself is a 2024 benchmark (Maharana et al., ACL 2024). Later papers disagree on whether to drop adversarial items and on which judge to use, so absolute percentages do not transfer across papers.

## Which of these are practical for a local single-user SQLite app?

### Takeaway

The mechanisms that fit a single SQLite file are the product patterns and Letta’s block idea: a few editable text fields always inserted into the prompt, a separate history table, a project id on each row, and a per-conversation flag that skips reads and writes. Hybrid keyword-plus-embedding retrieval also fits, because SQLite already has FTS5 and the app can store vectors itself; the memory-probe gain, though, used a paid reranker. Mem0’s algorithm can be reimplemented on that store, but running Mem0 as shipped wants a vector database and an LLM call on the write path, and its graph is platform-only. Graphiti as a dependency does not fit: it wants Neo4j, FalkorDB, Neptune, or a deprecated embedded graph, plus several LLM calls per episode. The part worth copying is the edge schema (valid time and transaction time, invalidate rather than delete), which is an ordinary table.

### Cited Findings

**Fits in SQLite without a second database**

- ChatGPT and Claude’s user-facing memory is a short editable artifact plus optional history search, with a no-memory mode. Nothing in the help pages requires a graph database. Project scope is a filter: Claude isolates project memory and project chat search; ChatGPT project-only drops saved memories and outside chats. A `project_id` column and a `use_memory` flag implement those walls. — [Claude Help](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context); [OpenAI Projects](https://help.openai.com/en/articles/10169521); [OpenAI Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- Letta blocks are strings with a character limit, prepended every turn. The docs show 4000–5000 character examples. That is a table of text columns, not a retriever. The agent updates them with tools; the app can also overwrite `value`. Last write wins, so a single-user app still needs to serialize writes. — [Letta memory blocks](https://docs.letta.com/guides/core-concepts/memory/memory-blocks)
- Letta’s current local mode already keeps state on one machine’s disk (`~/.letta/lc-local-backend` and a per-agent git memory repo) and can call a local model (Ollama, LM Studio, llama.cpp). It is a separate runtime, not an embedded library, and it is not SQLite. Useful as a design reference; adopting the server means a second process and a Node 22.19+ CLI. — [Letta self-hosting](https://docs.letta.com/self-hosting/)
- memory-probe: raw chunks plus BM25 are the weak cell (59.2%), raw chunks plus cosine are 77.9%, raw chunks plus hybrid rerank are 81.1%. For a local app that can embed queries, storing turns and embedding them beats spending LLM calls to consolidate, on this benchmark, until the prompt cannot hold the chunks. The hybrid’s extra point over cosine (81.1 vs 77.9 on raw chunks; 77.2 vs 73.4 averaged) required a GPT-5.2 rerank call per query. — [memory-probe Table 1](https://arxiv.org/html/2603.02473v1)
- Anthropic’s 2024 note: under about 200,000 tokens, put the corpus in the prompt and skip RAG. A single user’s profile and a modest memory list are far under that, which is the practical case for pinned blocks. The same post is also the warning that BM25 and embeddings fail differently (exact codes vs paraphrase), so a second channel matters once the store is larger than the prompt. — [Anthropic, Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)

**Mem0: algorithm yes, dependency maybe**

- The paper’s hot path is two LLM calls per turn (extract, then update against 10 neighbors), GPT-4o-mini in the paper, plus a vector search. That is practical on a single-user machine if a local or proxied model is acceptable, and expensive if it runs on every assistant message. — [Mem0 paper §2.1](https://arxiv.org/html/2504.19413)
- OSS does not store vectors in the application’s SQLite. Documented vector providers include Qdrant (default), Chroma, FAISS, pgvector, and others. FAISS and embedded Chroma are local processes or files, still a second store. Graph memory, the part that marks edges invalid, is platform-only in the OSS docs. — [Mem0 OSS configuration](https://docs.mem0.ai/open-source/configuration); [vector DB overview](https://docs.mem0.ai/components/vectordbs/overview)
- DELETE in base Mem0 throws the contradicted memory away. A local app that wants history has to deviate from base Mem0 and copy Mem0g or Graphiti’s invalidate-instead. — [Mem0 paper §2.1–2.2](https://arxiv.org/html/2504.19413)

**Graphiti: schema yes, engine no**

- Supported engines are Neo4j, FalkorDB (server or `falkordblite` on Python 3.12+), Neptune, and deprecated Kuzu. No SQLite driver. Default extraction uses an OpenAI key and is described as unreliable on small models that lack structured output. — [Graphiti README](https://github.com/getzep/graphiti)
- Each episode in the paper is several LLM calls: entity extraction with reflection, entity resolution, fact extraction, edge dedup, temporal extraction, and invalidation against neighboring edges, with n=4 messages of context. That cost is the opposite of a local single-user write path unless it is batched off the reply. — [Zep paper §2](https://arxiv.org/html/2501.13956v1)
- The data model that does fit SQLite is small: an edge row with fact text, embedding, source episode ids, `valid_at`, `invalid_at`, `created_at`, `expired_at`. Point-in-time questions are a filter on those columns. BFS over neighbors is a recursive query or a few joins, not a graph server, at single-user scale. The paper’s community layer (label propagation plus LLM summaries) is the part that is hard to justify for one user; the authors themselves refresh communities only periodically because full rebuilds are costly. — [Zep paper §2.2.3 and §2.3](https://arxiv.org/html/2501.13956v1)
- Do not expect the clocks to be correct without a hard fallback. On one reported backfill, 56% of `valid_at` values collapsed to “today midnight” because the model guessed. A local implementation should default `valid_at` to the episode time when the model leaves it empty, which is the fix that issue proposes. — [Graphiti issue 1492](https://github.com/getzep/graphiti/issues/1492)

**Where a graph pays, if the LLM budget exists**

- On LongMemEval_s, Zep’s retrieved 1.6k tokens beat 115k-token full context by 10.8 points (gpt-4o, 71.2 vs 60.2) and cut latency about 90%, with the gain on temporal, multi-session, preference, and knowledge-update, and a loss on single-session-assistant. That is the workload where a validity interval is doing work a flat list does not. It was measured against a hosted Zep service, not against SQLite BM25. — [Zep paper Tables 2–3](https://arxiv.org/html/2501.13956v1)
- Mem0g’s temporal J (58.13) beats Mem0 (55.51) and crushes their timestamp-poor OpenAI memory run (21.71), while losing on single-hop and multi-hop and costing more tokens (3,616 vs 1,764) and higher p95 (2.590 s vs 1.440 s). For a single user, the graph is a temporal index, not a general upgrade. — [Mem0 paper Tables 1–2](https://arxiv.org/html/2504.19413)

### Inferences

- Practical order for one SQLite file: (1) pinned editable profile block and project-scoped notes, always in the prompt, with a no-memory flag; (2) FTS5 over memories and, if an embedding model is already available, fuse it with BM25; (3) only if those miss contradictions, add `valid_at` / `invalid_at` and stop deleting. Skip shipping Neo4j, Qdrant, or Graphiti.
- An LLM reranker is what memory-probe used to get most of the hybrid-versus-BM25 gap. A local app that will not pay for a rerank call should expect a smaller lift than 57% → 77%, closer to the cosine-versus-BM25 gap (73.4 vs 57.1 averaged), and should not cite 81% as the RRF outcome.
- Write-time consolidation is the expensive optional piece. memory-probe says it does not pay for itself on LoCoMo if raw turns are still retrievable. It pays when the goal is a user-editable summary (the actual ChatGPT and Claude product) or when the store must forget contradictions. Those are product requirements, not accuracy requirements.
- Letta is practical as a local app the user runs beside the SQLite app. It is not practical as a library inside that SQLite file. Mem0 OSS is practical as a sidecar with Qdrant, Chroma, or FAISS. Graphiti is practical as a sidecar with FalkorDB or embedded FalkorDBLite, and impractical if the constraint is truly one SQLite file and no extra LLM calls on the write path.

### Gaps

- No measurement was found of FTS5 plus local embeddings plus RRF, on LoCoMo or LongMemEval, inside SQLite. The 20-point hybrid gap uses GPT-5.2 reranking. The Anthropic hybrid gap is document RAG from 2024.
- Mem0’s default Qdrant and FAISS/Chroma options were not install-tested. “Can run on one machine” is from the docs, not from a run here.
- `falkordblite` is documented as an extra. Whether it is stable enough for a daily personal app was not checked beyond the README.
- Letta MemFS layout was not inspected on disk. The self-host page says state is under `~/.letta/lc-local-backend`; it does not say those files are SQLite.
- Single-user scale (how many edges before recursive SQL stops being fine) is not in any of these papers. Zep’s latency numbers include a network hop to AWS and a proprietary engine in the 2026 marketing page.
