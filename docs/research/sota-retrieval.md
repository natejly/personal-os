## Documents, retrieval (RAG) and the Docs/Files editor

### Where we are

Two separate stores, both keyword-only.

**Uploaded files (`documents` + `chunks`).** `POST /documents` (app.py ~L2579) calls `extract_text.extract_text()` and stores the raw bytes under `uploads/`. The extractor is minimal. PDF is `pypdf` `page.extract_text()` joined with blank lines, so there is no layout, no tables, no headings, no page numbers and no OCR; scanned PDFs give empty text. DOCX is `python-docx` paragraphs only, so tables and heading levels are dropped. Everything else is a utf-8 decode. `repos.Documents.create()` chunks with `chunk_text()`: paragraph packing to `CHUNK_SIZE=900` chars, `CHUNK_OVERLAP=120` applied only when a single paragraph exceeds 900. It knows nothing about headings, pages or tokens. Each chunk goes into `chunks(id, document_id, idx, text)` and `chunks_fts` (FTS5, porter unicode61). `Documents.search()` runs `fts_query()` (up to 12 terms OR-ed, no stopword removal, 3+ char terms only) and orders by `bm25()`. There is no score floor, no dedup, no per-document cap, no neighbour expansion, no embeddings and no reranker. `litellm.yaml` routes `qwen3-embedding-8b` (mode: embedding under model_info), but no code calls it: `llm.py` has only `stream_chat` and `complete`. Retrieval reaches the model two ways. `context.build_context()` injects the top 6 chunks as "## Relevant document excerpts" when `useDocuments` is on. The `search_documents`, `read_document` and `list_documents` tools (tools.py ~L536-559) give paged access. Excerpts are labelled "name (chunk N)" with no page or section, so nothing finer than that can be cited. Re-uploading the same file creates a duplicate (no content hash). There is no re-index path: changing the chunker means re-uploading everything.

**Docs editor (`docs`, `doc_revisions`, `doc_folders`, `docs_fts`).** This is the user's own markdown, with revisions, assistant edits as pending diffs, and per-project folder trees (docs.py). `Docs.search()` is FTS over whole-document title+body with one snippet per document. It is reachable only through the `doc_search` and `doc_read` tools. `build_context` never auto-retrieves from Docs, so the user's own notes are invisible to ordinary chat unless the model chooses to call a tool. Docs are not chunked and do not share an index with uploads. `docs/research.md` R1 (hybrid RRF with `qwen3-embedding-8b`) and its chunking advice are unshipped; the code confirms it.

UI: `DocumentsView.tsx` (103 lines) is a list plus upload with a text preview. `DocsView.tsx`, `MarkdownEditor.tsx` and `DocTree.tsx` are the editor and tree. None of them show where an answer came from, and nothing shows index status.

**Weak spots, ranked by user-visible damage.**
- Paraphrase and conversational queries miss (BM25 only, OR of 12 terms).
- Chunks lose their context: no heading path, page, or document title in the indexed text.
- PDF and DOCX extraction loses tables and headings, and scanned PDFs are silently empty.
- The user's own Docs are not in auto-context.
- No relevance floor, so weak hits are injected anyway, and there is no way to see why a chunk was chosen.
- No dedup and no re-index.

### What the best open-source systems do

- **Anthropic contextual retrieval** ([post](https://www.anthropic.com/news/contextual-retrieval)). Prepend an LLM-written 50-100 token blurb ("situate this chunk within the overall document for the purposes of improving search retrieval") to each chunk before both embedding and BM25. Retrieval failure at top-20: 5.7% embeddings only, 3.7% with contextual embeddings, 2.9% adding contextual BM25, 1.9% adding a reranker. Top-20 beat top-5 and top-10. Cost is about $1.02 per million document tokens with prompt caching. Fusion is rank-based.
- **Hybrid search with RRF in SQLite** ([Willison / Garcia](https://simonwillison.net/2024/Oct/4/hybrid-full-text-search-and-vector-search-with-sqlite/)). BM25 and vector scores are incomparable, so rank each list separately and sum `weight / (k + rank)`, with k=60 by convention. [sqlite-vec](https://alexgarcia.xyz/sqlite-vec/) provides `vec0` virtual tables with brute-force KNN. It is MIT/Apache, pure C and still alpha (v0.1.10-alpha). Brute force over a numpy matrix is equivalent at personal scale (under about 100k chunks) with no extension to ship.
- **Docling** ([chunking](https://docling-project.github.io/docling/concepts/chunking/)). `HierarchicalChunker` emits one chunk per document element and attaches heading and caption metadata. `HybridChunker` then splits oversized chunks by token count and merges undersized neighbours that share the same headings. `contextualize()` serialises heading path plus text, and that string is what gets embedded.
- **PyMuPDF4LLM** ([repo](https://github.com/pymupdf/pymupdf4llm)). Outputs markdown with headings inferred from font size or the TOC, pipe tables, and `page_chunks=True` giving per-page dicts with metadata. Hybrid OCR runs only on pages that need it. Licence is AGPL, which is awkward for us.
- **MarkItDown** ([repo](https://github.com/microsoft/markitdown)). MIT. Converts PDF, DOCX, PPTX, XLSX, HTML and EPUB to markdown, with per-format optional extras (`markitdown[pdf,docx]`).
- **RAGFlow** ([repo](https://github.com/infiniflow/ragflow)). DeepDoc layout recognition, template-based explainable chunking, human-editable chunk visualisation, multi-recall with fused re-ranking, grounded citations. The system is heavy (16GB RAM minimum); the useful ideas are inspectable chunks and templates.
- **Kotaemon** ([repo](https://github.com/cinnamon/kotaemon)). Hybrid full-text plus vector retrieval, reranking, in-browser PDF viewer with the cited passage highlighted, and a low-confidence warning. Also question decomposition and GraphRAG variants.
- **Khoj** ([repo](https://github.com/khoj-ai/khoj)). Bi-encoder embeddings plus cross-encoder rerank. Indexes markdown by heading and syncs incrementally by file hash.
- **AnythingLLM** ([repo](https://github.com/Mintplex-Labs/anything-llm)). Per-workspace similarity threshold and top-N, and pin-document-into-context.
- **Open WebUI**. Its RAG docs page returned 404 on fetch, so this is from memory of its documented settings and not verified: hybrid BM25+vector ensemble, a relevance threshold, optional reranker, markdown-header text splitter.

### Gaps

| # | Gap | Who does it | Impact | Effort |

### Build next

**docs-1 (hybrid retrieval).** Add an embedding client through the existing LiteLLM base URL, a `chunk_embeddings` table of float32 blobs, and numpy brute-force KNN. Fuse it with the existing BM25 list using RRF (k=60), apply a floor and a per-document cap, and widen to top-20 candidates before trimming. Everything degrades to today's BM25 behaviour when no embedding model is available. This is the single highest-leverage fix, and the model is already routed in `litellm.yaml`.

**docs-2 (structure-aware chunking).** Extraction emits markdown-ish structure with page markers (DOCX headings and tables via python-docx; PDF page tags via pypdf). A new `chunker.py` splits by heading, carries the heading path and page into new `chunks.heading` and `chunks.page` columns, and builds a contextualised string (title, heading path, text) that is what gets indexed in FTS and embedded. Existing documents are re-chunked from stored `documents.text` through a `POST /documents/reindex` route. Excerpts in context and tool results then cite "name, section, p.N".

**docs-3 (Docs in retrieval).** Chunk the user's own Docs into the same retrieval pipeline, kept in sync from `Docs._reindex`. `build_context` and `search_documents` then retrieve across uploads and notes, with the `source` ("file" or "doc") marked on each hit. This closes the gap where notes are only reachable if the model calls `doc_search`. It builds on docs-1 and docs-2 for the fusion and the chunker, so build it last.

Deliberately not specced this round: contextual retrieval (gap 5, needs an LLM call per chunk, so it should follow docs-1 behind an off-by-default setting), reranking, OCR and PDF viewer highlighting.

### Specs

#### docs-1: Hybrid retrieval: embeddings + BM25 fused with RRF, with graceful BM25 fallback (M)

**Why.** Retrieval is BM25-only (repos.Documents.search, fts_query). Every leader (Open WebUI, Khoj, Kotaemon, RAGFlow) does vector+keyword hybrid; Anthropic measured failure 5.7% embeddings-only vs 2.9% fused, and top-20 beating top-5/10. qwen3-embedding-8b is already routed in litellm.yaml but nothing calls it. Brute-force numpy KNN avoids shipping sqlite-vec (alpha) and numpy is already installed.

**Files.** `backend/personal_os/embed.py (new)`, `backend/personal_os/retrieval.py (new)`, `backend/personal_os/db.py (new table in SCHEMA)`, `backend/personal_os/repos.py (Documents.create/delete/search hooks, small)`, `backend/personal_os/llm.py (DEFAULT_SETTINGS keys only)`, `backend/personal_os/app.py (small: construct Embedder, POST /documents/embed-backfill, GET /documents/index-status)`, `backend/personal_os/tools.py (search_documents passes through; localized)`, `backend/tests/test_retrieval.py (new)`

**Design.** Schema (add to db.SCHEMA, CREATE IF NOT EXISTS): chunk_embeddings(chunk_id TEXT PRIMARY KEY REFERENCES chunks(id) ON DELETE CASCADE, document_id TEXT NOT NULL, model TEXT NOT NULL, dim INTEGER NOT NULL, vec BLOB NOT NULL) + index on document_id. vec = float32 little-endian, L2-normalised before storage (qwen3 vectors are not normalised), so cosine = dot.

embed.py: `async def embed_texts(settings, texts, model=None) -> list[list[float]]` POSTs to {baseUrl}/v1/embeddings (OpenAI shape, same headers as llm._headers), batches of 32, raises EmbedError on failure/timeout (10s per batch). Also `pack(vec)->bytes`, `unpack(blob)->np.ndarray`, `normalize`. `class Embedder` holds an injectable `fn` (default = embed_texts) so tests stub it.

retrieval.py: `rrf(lists: list[list[str]], weights, k=60) -> list[(id, score)]`; `class Retriever(db, documents, embedder)` with `async search(project_id, query, settings, limit=6) -> list[hit]`: (1) bm25 = documents.search(project_id, query, limit=candidates*2); (2) if settings['retrievalMode']=='hybrid' and embedding model configured: embed query (try/except EmbedError -> log + bm25 only), load vectors for chunks in scope (JOIN documents with the same _scope_clause; chunks lacking vectors are simply absent from the vector list), numpy matrix @ q, top candidates; (3) RRF with weights (1.0 bm25, 1.0 vector); (4) drop hits whose vector cosine < settings['retrievalMinSimilarity'] ONLY when they have no bm25 rank (so exact keyword hits survive); (5) cap at retrievalPerDocCap chunks per document; (6) return top `limit` dicts with the existing keys (chunk_id, document_id, name, idx, text) plus `score`, `sources` ['bm25','vector'].

Indexing: Documents.create() after inserting chunks calls an optional `self.on_chunks(did, [(cid, text)])` callback; app wires it to schedule an async embed task (asyncio.create_task, never blocks the upload, failures leave rows unembedded). `POST /documents/embed-backfill` embeds all chunks lacking a row for the current embedding model (batched, returns {embedded, remaining}); `GET /documents/index-status` returns {chunks, embedded, model, mode}. Changing embeddingModel makes old rows stale: query only uses rows whose model == current model.

Wiring: context.build_context is sync and calls documents.search; add optional `retriever` param and make the call site in app.py pass pre-computed hits, OR (smaller edit) run `await retriever.search(...)` in app.py just before build_context and pass `doc_hits=` into it; build_context uses doc_hits when given else falls back to documents.search. The search_documents tool awaits retriever.search the same way. Documents.delete already deletes chunks; the CASCADE removes embeddings (foreign_keys=ON is set).

Settings (add to llm.DEFAULT_SETTINGS): retrievalMode 'hybrid' ('bm25' to force old behaviour), embeddingModel 'qwen3-embedding-8b', retrievalMinSimilarity 0.25, retrievalPerDocCap 3, retrievalCandidates 20. No UI beyond an optional read-only index-status line in the Settings Knowledge Base tab.

**Tests.** backend/tests/test_retrieval.py, plain script in the test_docs.py style (temp PERSONAL_OS_DATA_DIR, check() counter). Stub embedder with a deterministic fake: map text to a bag-of-words hashed 64-d vector plus a hand-built synonym table so 'automobile' and 'car' embed near each other. Cases: (a) rrf() unit test with known ranks gives expected order and k=60 arithmetic; (b) paraphrase query ('automobile repair') finds the chunk containing 'car maintenance' in hybrid mode but NOT in retrievalMode='bm25'; (c) exact-keyword chunk with low cosine survives the floor; (d) a stub that raises EmbedError makes search return the BM25 result, no exception; (e) per-document cap limits to 3 chunks from one document; (f) chunks missing vectors still appear via bm25; (g) deleting a document removes chunk_embeddings rows; (h) pack/unpack roundtrip and normalisation; (i) index-status and embed-backfill routes via TestClient with the stub injected; (j) project scoping: a chunk in another project never appears. No network: monkeypatch Embedder.fn.

**Done when.** With the stub embedder, a paraphrase query retrieves the right chunk in hybrid mode and does not in bm25 mode; with the embedder raising, behaviour equals current BM25 exactly; uploads never block or fail on embedding errors; embed-backfill is idempotent; settings keys survive PUT /settings; all existing tests (test_docs.py, test_doc_scopes.py, test_working_memory.py) still pass; no new required dependency (numpy is already installed).

#### docs-2: Structure-aware chunking with heading path, page and contextualised index text, plus re-chunk route (M)

**Why.** chunk_text packs paragraphs to 900 chars and discards headings, pages and title, so retrieval and citations lack context. Docling HybridChunker/contextualize() and Khoj's heading splitting show that carrying the heading path into the indexed text materially improves recall. DOCX tables/headings and PDF page numbers are cheaply recoverable with deps already installed (python-docx, pypdf). Anthropic's contextual-retrieval gain comes from the same idea (situating context in the indexed text).

**Files.** `backend/personal_os/chunker.py (new)`, `backend/personal_os/extract_text.py (add extract_structured, keep extract_text unchanged in signature)`, `backend/personal_os/db.py (migration: chunks.heading, chunks.page, documents.content_hash)`, `backend/personal_os/repos.py (Documents.create uses chunker; add reindex(); search returns heading/page)`, `backend/personal_os/context.py (excerpt header shows section/page)`, `backend/personal_os/tools.py (search_documents result adds heading/page, localized)`, `backend/personal_os/app.py (small: POST /documents/reindex, dedup on content_hash in upload)`, `backend/tests/test_chunker.py (new)`

**Design.** Migration (db._migrate `wanted` dict, same style as existing): chunks: {heading: "TEXT NOT NULL DEFAULT ''", page: 'INTEGER'}; documents: {content_hash: "TEXT NOT NULL DEFAULT ''"}. chunks_fts is rebuilt per document on reindex; to make the heading path searchable add the contextualised string to the FTS text column (chunks.text stays the clean excerpt; FTS row text = contextualised string).

extract_text.py: add `extract_structured(name, data, mime) -> list[Block]` where Block = {kind: 'heading'|'para'|'table'|'page', level, text, page}. DOCX: iterate document.element.body children in order (paragraphs with style name 'Heading N' -> heading level N; tables -> pipe-table markdown rows of cell.text). PDF: per page, text from pypdf, emit {kind:'page', page:n} then paragraphs; guess headings only for short all-caps/Title lines followed by a blank line (conservative). Markdown/text: parse ATX '#' headings, fenced code kept intact. Other types: single para blocks. `extract_text` keeps returning plain text (join of blocks) so nothing else changes; also store plain text in documents.text as today.

chunker.py: `chunk_blocks(blocks, title, max_chars=1200, min_chars=300, overlap=120) -> list[Chunk{text, heading, page, ctx}]`. Walk blocks keeping a heading stack; accumulate paragraphs under the current heading until max_chars; never merge across a heading boundary unless the pending chunk is < min_chars AND the next heading is deeper or equal level sharing the same parent (Docling merge_peers analogue); an oversized para/table is split on line then sentence boundaries with `overlap` carry; tables are split by rows and the header row repeated. `ctx = f"{title} > {' > '.join(heading_path)}\n{text}"` is the string to index/embed; `text` is what is shown. Keep CHUNK_SIZE/CHUNK_OVERLAP constants in repos.py and keep `chunk_text` as the fallback for plain text so existing tests keep passing.

repos.Documents.create(): compute sha256 of bytes-or-text into content_hash; build chunks via chunker (fall back to chunk_text on any exception); insert chunks with heading/page; insert chunks_fts with ctx. New `Documents.reindex(id=None) -> int`: re-chunk from stored documents.text (re-run extract_structured on the file at documents.path when it exists, else treat text as markdown), delete+reinsert chunks and FTS rows, update chunk_count, return count; also delete that document's chunk_embeddings rows if the table exists (docs-1) so they re-embed. Route: POST /documents/reindex (body optional {id}). Upload route: if a document with the same content_hash and project scope exists, return it with `duplicate: true` instead of inserting.

context.build_context: excerpt header becomes `### {name} — {heading} (p.{page})` omitting absent parts, falling back to `(chunk N)`; used['chunks'] entries gain heading and page. search_documents results gain heading and page.

**Tests.** backend/tests/test_chunker.py, pure unit tests plus a temp-DB section; no network or models. Cases: (a) markdown with nested headings produces chunks whose heading path equals ['A','A.1'] and never crosses an H1 boundary; (b) small adjacent sibling sections under one parent merge, big ones do not; (c) a 5000-char paragraph splits with overlap and every piece <= max_chars; (d) a pipe table splits by rows with the header repeated; (e) build a DOCX in-test with python-docx (Heading 1, paragraph, 2x2 table) and assert extract_structured yields heading+table blocks and extract_text still returns plain text; (f) build a tiny PDF in-memory via pypdf PdfWriter blank pages and assert page blocks exist without crashing (text may be empty); (g) FTS on a term that appears only in a heading finds the chunk beneath it; (h) migration is idempotent on a DB created from the old schema; (i) reindex re-chunks an existing doc and keeps its id, and uploading identical bytes twice returns duplicate:true; (j) chunk_text fallback used when chunker raises (monkeypatch); (k) context excerpt header contains the section and page.

**Done when.** Uploading a markdown file with headings yields chunks with heading paths and a heading-only query retrieves the right chunk; DOCX tables survive into chunk text; POST /documents/reindex upgrades pre-existing documents without re-upload; duplicate upload is detected; existing tests pass; no new dependency; excerpts show section/page.

#### docs-3: Index the user's own Docs into the same retrieval and auto-inject them into chat context (M)

**Why.** build_context only injects uploaded documents; Docs-editor notes (docs/docs_fts) are whole-document FTS reachable only if the model calls doc_search, and are not chunked. Khoj-style personal-notes retrieval means the user's own writing should be retrievable in ordinary chat, scoped by project, with source labelled. Builds on docs-1/docs-2 so the same fusion and chunker serve both stores.

**Files.** `backend/personal_os/docs.py (add doc_chunks table to SCHEMA; hook Docs._reindex; add Docs.chunk_search)`, `backend/personal_os/retrieval.py (union search across files and docs; from docs-1)`, `backend/personal_os/context.py (label source; accept pre-computed hits)`, `backend/personal_os/tools.py (search_documents gains scope param, localized)`, `backend/personal_os/llm.py (DEFAULT_SETTINGS key)`, `backend/personal_os/app.py (small: pass docs into Retriever)`, `backend/tests/test_docs_retrieval.py (new)`

**Design.** Schema in docs.SCHEMA: doc_chunks(id TEXT PRIMARY KEY, doc_id TEXT NOT NULL REFERENCES docs(id) ON DELETE CASCADE, idx INTEGER NOT NULL, heading TEXT NOT NULL DEFAULT '', text TEXT NOT NULL) and VIRTUAL TABLE doc_chunks_fts USING fts5(text, chunk_id UNINDEXED, doc_id UNINDEXED, tokenize='porter unicode61'). Embeddings for doc chunks reuse docs-1's chunk_embeddings keyed by chunk_id with a nullable kind column OR a parallel doc_chunk_embeddings table (pick the parallel table to avoid FK clash with chunks).

Docs._reindex(c, doc_id, title, content) already runs on every write path (create, save, accept, restore, move); extend it to also delete and rebuild that doc's doc_chunks and doc_chunks_fts rows using chunker.chunk_blocks over markdown blocks (docs-2). To keep keystroke autosave cheap, only rebuild when content changed (compare hash stored in an in-memory dict or a docs.content_hash column) and debounce embedding: mark chunks unembedded and let the background embed task (docs-1 backfill) pick them up; never call the network inside the DB transaction. Assistant-proposed pending revisions are NOT indexed (they only land via accept, which already calls _reindex).

Docs.chunk_search(query, project_id, limit) -> same hit dict shape as Documents.search plus source='doc', doc_id, title; scope rule: project chat sees that project's docs plus personal (project_id NULL) docs, matching _scope_clause semantics used for files. retrieval.Retriever.search gains `sources=('files','docs')`, runs bm25 and vector lists for each store, fuses them in one RRF, and tags hits with source. Setting `useDocsInContext` (DEFAULT_SETTINGS, default True) gates inclusion in build_context; the per-chat `useDocuments` toggle still gates both. Excerpt header for docs: `### {title} (your doc) — {heading}`. used['chunks'] entries carry source and doc_id so the UI can open the right thing. tools.search_documents gains optional scope 'all'|'files'|'docs' (default 'all') and returns source and doc_id/document_id; description updated to say it now covers the user's own docs. doc_search is unchanged.

Backfill: on startup and in POST /documents/embed-backfill, rebuild doc_chunks for any doc with no rows (one-off, idempotent).

**Tests.** backend/tests/test_docs_retrieval.py with the stub embedder from docs-1, temp data dir. Cases: (a) creating a doc via the API populates doc_chunks and doc_chunks_fts; saving new content replaces them (old term no longer matches); (b) accepting a pending revision reindexes, a pending (unaccepted) revision does not; (c) delete doc and delete_folder(delete_docs=True) remove chunks; (d) project scoping: project A chat does not see project B docs but sees personal docs; (e) unified search returns both a file chunk and a doc chunk, tagged by source, fused in one ranking; (f) build_context includes a 'your doc' excerpt when useDocsInContext is true and omits it when false or when conv useDocuments is false; (g) search_documents scope='docs' returns only docs; scope='files' only files; (h) unchanged content save does not rebuild chunks (count calls via monkeypatch); (i) startup backfill creates chunks for a doc inserted with raw SQL; (j) existing doc_search behaviour unchanged.

**Done when.** A fact written only in a Docs-editor note is retrievable in a normal chat turn without the model calling doc_search, in the right project scope, labelled as the user's doc; edits and accepted revisions keep the index current; rejected or pending revisions never leak into the index; settings key persists via PUT /settings; keystroke autosave stays fast (no network in transaction); all existing docs tests pass.
