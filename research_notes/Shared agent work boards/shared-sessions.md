# Shared agent work: sessions, channels, and handoff

As of 2026-10-02. Scope is what shipping products actually share when more than one person works with the same agent or the same agent-produced artifact: the shared object, the private residue, and the permission boundary. "One person, many agents" is kept separate from "many people, one agent" inside each question.

A prior note already covered a TypeScript multiplayer harness. It is not treated as a product here.

## Chat projects: what is shared across people, and what stays private?

### Takeaway

Shipping chat products share a standing preamble (instructions, and usually files), then diverge on the transcript. ChatGPT shared projects put the chats themselves in the shared room and seal memory to that room. Claude shared projects share knowledge and instructions while leaving each person's chats private unless someone publishes a snapshot. Gemini Gems share the Gem definition and its uploaded files through Drive ACLs, and the help page does not say the chat transcript is shared. None of these docs describe a concurrent-editor lock. ChatGPT is the only one that states an explicit rule: a shared chat is branched, not edited by two people at once.

### Cited Findings

- ChatGPT project sharing is documented for Business, Enterprise, and Edu, and, as of an October 22, 2025 update still present on the help page, also for Free, Plus, Pro, and Go on web, iOS, and Android. Members see the project's chats, uploaded files, and custom instructions. The owner can create chats, change instructions, add files, invite and remove members, set permissions, rename, and delete. Edit access can update instructions, upload or remove files, and invite others, but cannot remove existing members. Chat access can see and use chats, files, and instructions, and cannot invite others. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- Once a ChatGPT project is shared, project-only memory turns on and cannot be reverted to default memory, including after collaborators are removed. Shared projects do not use any member's context, custom instructions, or memories from outside the project. Inside the project, chats can reference other conversations in that same project. Personal saved memories are not referenced in project-only mode. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- A chat moved into a ChatGPT shared project disappears from outside the project and inherits the project's instructions and files. Moving it back out, archiving it, or deleting it hides it from everyone else in the project, including the owner. Each chat shows which member started it. Branched chats stay in the project beside the original. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- OpenAI's own FAQ: "Chats in shared projects can be branched, not collaborated on synchronously." Branching does not change the original thread. The chat creator can make a branch private by moving it out of the project. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- Deleting a file in a ChatGPT shared project removes it for everyone. A same-name upload asks the uploader to add it anyway or skip that file. The help page does not describe a lock, a presence indicator, or a merge when two editors change instructions or the same file at the same time. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- Collaborator caps are plan-based: Pro 100 collaborators and 40 files; Plus and Go 10 collaborators and 25 files; Free 5 collaborators and 5 files. Business, Enterprise, and Edu workspace-link projects are capped at 100 people and 40 files. Workspace-link joiners start at chat access. "Anyone with a link" is an owner-only setting and lets any logged-in ChatGPT user join. Enterprise and Edu can disable the ability to view workspace members, which blocks sharing projects because the member picker is empty. The Compliance API can list shared users and isolate a project down to the owner. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- OpenAI trains on shared-project data only if every contributor and the owner has "Improve the model for everyone" on. Business, Enterprise, and Edu are not trained on by default. A single-chat share link from a personal project shows only that chat, frozen at share time, and does not include other chats, files, or instructions. A single-chat link from an already-shared project is not viewable until the recipient joins the project. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- The same ChatGPT help page still says project-only memory can only be chosen when creating a project, and that an older project cannot be switched later. A secondary write-up claims an August 14, 2026 release note added a settings toggle for unshared projects and that shared projects stay project-only permanently. This research did not fetch that release note. The help page, which presented itself as updated days before 2026-10-02, is the source used here. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt); secondary claim in [ChatGPT Projects: How They Work](https://felloai.com/chatgpt-projects/)
- ChatGPT Space is a different object from Projects. A shared page is an editable document. "When you collaborate, each person can use their own ChatGPT agent to work with the shared content." Sharing the page does not share private chats or ChatGPT Memory. If one person's agent writes personal context onto the page, everyone who can read the page can read that text, and their own Memory may retain it. Files uploaded into the page follow the page's permissions. A link to a file elsewhere does not grant access to that file; a summary copied onto the page does. Training follows the settings of the person whose agent touched the page, not the page owner's. — [ChatGPT Space: sharing, data, and controls](https://help.openai.com/en/articles/20001544-chatgpt-space-sharing-data-and-controls)
- Claude project sharing is Team and Enterprise, and admins can turn it off. Visibility is private (invite only) or public to the organization. Even on a public project, "your chats within that project will be private and inaccessible to other members of your organization unless you manually share them." Inviting someone shares the project and knowledge base; "your chats will remain private unless you choose to share them." Can view: see contents, knowledge, and instructions, and chat in the project, without editing. Can edit: change instructions and knowledge, update member settings, and contribute. Enterprise group sharing is in beta; access follows group membership, including people who join later, and is still limited to the project's organization. — [Manage project visibility and sharing](https://support.claude.com/en/articles/9519189-manage-project-visibility-and-sharing)
- A shared Claude chat is a snapshot of messages sent before the share, including artifacts. Messages sent after the share stay private until the sharer clicks Update. Unshare flips the chat back to Private and disables the link. — [Manage project visibility and sharing](https://support.claude.com/en/articles/9519189-manage-project-visibility-and-sharing)
- Claude's project help says context is not shared across chats in a project unless it is added to the project knowledge base. Instructions apply to every chat in the project. Each project has its own memory space, separate from non-project chats. Moving a chat out of a project takes it out of that project's memory summary. A project chat can be started with Memory off so it neither reads nor writes project memory. On Team and Enterprise, owners enable memory for the org and each member turns it on; "Owners can't view or edit a user's individual memories." The memory article does not say that one member's project memory summary is readable by, or injected into, another member's chats. — [How can I create and manage projects?](https://support.claude.com/en/articles/9519177-how-can-i-create-and-manage-projects); [Use Claude's chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- Cowork docs disagree with each other. The product docs say a Cowork project lives on the computer, is not synced to the cloud, and is not shareable, while a claude.ai project is shareable on Team and Enterprise. The help center says Cowork projects share the same way as Claude projects (Can view / Can edit) on Team and Enterprise, that new Cowork projects can be saved to the Claude account, and that projects created from a local folder stay on that computer. Local Cowork sessions do not use Claude memory; cloud Cowork shares memory with Chat. This research did not find a page that reconciles the two. — [Cowork projects guide](https://claude.com/docs/cowork/guide/projects); [Organize your tasks with projects in Claude Cowork](https://support.claude.com/en/articles/14116274-organize-your-tasks-with-projects-in-claude-cowork); [Use Claude's chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- A separate Claude projects rewrite, rolling out starting with Claude Code, defines a project as one conversation that fans out into parallel cloud threads. Every thread starts with that project's files, repositories, instructions, and memory. That is one person (or one account) with many threads on one project, not the Team/Enterprise invite model above. The sharing article, updated in the week before this research, still describes private chats plus shared knowledge. — [What are projects?](https://support.claude.com/en/articles/9517075-what-are-projects)
- A Gemini Gem share grants viewers and editors the instructions and uploaded files. Editors can change those, delete the Gem, and re-share it. Viewers can use the Gem and read instructions and files. NotebookLM notebooks cannot be a knowledge source on a shared Gem. If knowledge includes anything other than device uploads or Drive files, the Gem cannot be shared. Shared Gems are stored in a Drive folder, and Workspace sharing follows the org's Drive external-sharing settings. Admins can turn Gem sharing off; already-shared Gems remain accessible from Drive. Access can expire. Ownership can be transferred, after which the new owner can remove the previous owner. General access can be Private, the organization, anyone with the link, or Public (searchable without a Google sign-in; work and school accounts may not see Public or link-open). — [Share a Gem](https://support.google.com/gemini/answer/16504957); [Turn Gem sharing on or off](https://knowledge.workspace.google.com/admin/gemini/turn-gem-sharing-on-or-off); [Gems sharing launch note](https://workspaceupdates.googleblog.com/2025/09/gem-sharing-gemini-app-workspace.html)
- On September 30, 2026 Google said skills are replacing Gems. Sharing skills, Drive files, and Gemini Notebook sources on skills was described as arriving "in the coming weeks," so it was not documented as live that day. Gem removal is scheduled for November 2026 on personal accounts, March 2027 for Workspace business, enterprise, and nonprofit, and June 2027 for Workspace education, with automatic migration. As of 2026-10-02, Gems are still the documented shareable object. — [Let skills in Gemini tackle your most repetitive tasks](https://blog.google/products-and-platforms/products/gemini/automate-tasks-with-skills/)

### Inferences

- These are three different meanings of "shared." ChatGPT shared projects are many people in one context pile: instructions, files, and the transcripts, with personal memory walled off. Claude projects are many people using one preamble (instructions and knowledge) while each person keeps a private transcript unless they publish a snapshot. Gemini Gems are many people using one saved instruction-and-file object; the conversation each person has with it is not described as shared. ChatGPT Space is the inverse of a shared project: many people, each with their own agent, writing into one document.
- ChatGPT's synchronous-edit ban is only about the chat thread. Two editors can still change instructions and files; the only collision behavior documented is the same-filename upload prompt and the fact that a delete hits everyone.
- Claude's "owners cannot see a user's memories" plus "chats stay private" plus "cross-chat context only via the knowledge base" is the closest the docs come to a memory boundary. It is still not an explicit statement that project memory is per member inside a shared project.

### Gaps

- ChatGPT, Claude, and Gemini help pages are silent on a concurrent-editor limit or lock for instructions and files. ChatGPT is explicit only for the chat thread.
- Claude docs are silent on whether a shared project's memory summary is used when a different member chats. They do not say it is shared, and they do not say it is per member.
- Gemini's share article lists instructions and uploaded files as visible. It is silent on chat transcripts, personal memory, and whether two editors can edit a Gem at once.
- The Cowork "local and unshared" docs page and the Cowork "shares like Claude projects" help article were both live during this research and were not reconciled.
- The August 14, 2026 ChatGPT memory-toggle claim was not checked against OpenAI release notes.

## Channel and email agents: who can invoke them, and where the reply lands

### Takeaway

A channel agent is one agent whose reply is a message in a room other people can read. A DM agent is a per-person thread. Slack's platform leaves both the decision to answer an @mention and the decision of where to post up to the app. Teams' first-party Channel Agent and Copilot Studio's "add to a team" option are stricter: the reply is visible to the channel, invocation is limited to people the admin enabled, and knowledge that depends on the asker's own file permissions is either checked before a group reply or refused outside a 1:1. Discord and shared-mailbox email agents did not turn up a comparable first-party help article in this pass.

### Cited Findings

- Slack's agent developer guide treats the DM, including the split-view container, as the agent session. The app hears the user via `message.im`. `assistant:write` is what lets the app set status, suggested prompts, and thread titles. Calling `agents.sessions.setStatus` with `processing` on a `thread_ts` opens that thread. The guide says channel @mentions "can happen like they do today; whether you support this or not is up to you. You can engage with the user or ask them to use the container to converse with your app." So a channel mention is optional, and the reply location is the app's choice, not a platform rule that the answer must land in the channel. — [Developing an agent](https://docs.slack.dev/ai/developing-agents)
- Slack's `app_mentions:read` scope is "view messages that directly mention your Slack app in conversations that the app is in." `im:history` is the DM history scope. A third-party integration doc (not Slack's) separates a DM agent (`im:history`, `assistant:write`) from a channel agent (`app_mentions:read` plus channel history), and says that without history scopes the bot can use only the prompting message. That split matches Slack's scope list, but the "prompting message only" behavior is that vendor's, not a sentence in Slack's agent guide. — [Slack scopes](https://docs.slack.dev/reference/scopes/); [Bigmind Slack permissions](https://bigmind.ai/en-US/docs/collections/integrations/articles/slack/permissions)
- When a Slack agent app is open, `app_context_changed` tells it what that user is looking at (channel, DM, thread, canvas, or list). The same context is attached to `message.im`. That is per-viewer context for a DM agent, not a shared channel memory. — [Developing an agent](https://docs.slack.dev/ai/developing-agents)
- Cursor's cloud-agent entry points include Slack `@cursor`, a GitHub or Bitbucket `@cursor` comment, and Linear `@cursor`. A workspace admin has to install the Cursor Slack app. A separate admin toggle, "Display agent summary in external channels," controls whether file-diff images and code snippets from the agent appear in Slack or another connected channel. The run itself remains a cloud agent with its own URL. — [Cloud Agents](https://cursor.com/docs/cloud-agent); [Cloud Agents settings](https://cursor.com/docs/cloud-agent/settings)
- Microsoft's first-party Teams Channel Agent (public preview as of the Learn page) is one agent per channel. It takes the channel's name. It cannot be added to a second channel. Private channels are unsupported. External participants make it non-functional. In the channel, any licensed and admin-enabled user can ask it questions. People who are not enabled can see its presence and its messages and cannot interact with it. In a meeting or group chat where it was added, only licensed, enabled users who are also members of the source channel can ask. — [Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)
- A Teams Channel Agent's knowledge is channel messages, the channel's SharePoint files, channel meetings, standard meetings, and transcripts. It does not use files that were only linked, or files outside that SharePoint. In a group chat it does not absorb the chat into its knowledge; people can still ask questions, answered from the knowledge it already has. Meeting summaries sit for 24 hours for approve-or-reject and are added automatically if nobody acts. A summary then can be used for any channel member, including people who were not in the meeting and do not have the transcript. Removing the agent from the channel wipes that knowledge; recreating it starts empty. — [Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)
- Before a Teams Channel Agent answers from a file, it checks the asking user's access, sensitivity labels, and DLP. If it cannot confirm that everyone who would see the message can access the files, it asks the requester whether to share the response, and the requester can review it first. Questions asked outside the channel (group chats or meetings that may include non-members) are answered only after the requester confirms. The output shows a sensitivity label and does not inherit that label's controls. Microsoft notes that Channel Agents may gather context across Information Barriers. Status reports are Loop files in the channel's SharePoint, authored as the user who created the agent. — [Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)
- Copilot Studio's "add this agent to a team" option is the custom-agent version of the same pattern. Once the agent is on a team, members @mention it in channels and "all teammates see the responses." Turning the option on also gives the agent the channel, group-chat, or meeting history. Microsoft's instruction is to allow the whole organization to chat with the agent before enabling this, or members hit permission errors. Known limitation, stated as by design: in group chats and channels, these agents cannot use knowledge sources that require end-user authentication, such as SharePoint. Those sources work only in 1:1 chats. Group and meeting chats also do not support agents configured for manual authentication with Teams SSO. — [Connect and configure an agent for Teams](https://learn.microsoft.com/en-us/microsoft-copilot-studio/publication-add-bot-to-microsoft-teams)
- Copilot Studio separates "can chat with the agent" from "can author the agent." Collaborators with authoring rights can always chat. Chat permission can also be granted to a security group or the whole organization without authoring rights. — [Share agents with other users](https://learn.microsoft.com/en-us/microsoft-copilot-studio/admin-share-bots)

### Inferences

- The permission difference that matters is not "channel vs DM" as a label. It is whether the reply is a shared message, and whether the agent's knowledge is the room's history or the asker's private grants. Teams states both. Slack's platform can do either, and a given app has to choose.
- Teams Channel Agent is many people, one agent, one channel. Copilot Studio in a channel is the same shape, with a hard cut: user-authenticated knowledge stays in the 1:1. A Slack DM agent is one person, one agent thread, even if that person is looking at a shared channel while they type.
- Cursor-in-Slack is not a channel agent in the Teams sense. Slack is a trigger and, if the admin allows, a place to show a summary. The session and the credentials stay on the cloud agent.

### Gaps

- No first-party Discord document in this pass defined an agent that sits in a shared channel, who may invoke it, or how that differs from a DM. Discord was not researched past that absence.
- No OpenAI, Anthropic, Google, or Microsoft help article in this pass defined an email agent whose replies land in a shared mailbox versus a private mailbox. ChatGPT's project help says app links (Slack channels, Drive files and folders) are added from "your private project," and does not say whether those links work after the project is shared. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- Slack's agent guide does not say that a channel @mention must be answered in-thread, or that only certain members may mention the app. Those rules, if any, live in each app and in ordinary Slack channel permissions. This pass did not fetch a Slack help article for Slack's own first-party assistant in channels versus DMs.

## Coding-agent handoff: what the next person gets

### Takeaway

The thing another person can continue is almost always the branch and the pull request. The live VM, the creator's secrets, and the full run tape are a second object with their own ACL. GitHub shares Copilot cloud sessions with the repository by default and shares local sessions only as a view-only snapshot. Cursor shares the run read-only with teammates who already have the repo, and optionally lets them steer it while it still runs as the original creator. Devin's handoff and Jules both start a fresh cloud session; the documented bridge is a packaged prompt plus whatever git output the session later pushes, not the local agent's live context.

### Cited Findings

- Copilot cloud agent sessions are shared by default. They show up in the repository's Agents tab, "All sessions," for anyone with access to the repository. Local sessions (Copilot CLI, VS Code, JetBrains, or the Copilot app) are unshared by default. Sharing a local session gives repository collaborators view-only access to prompts, responses, and file changes. They cannot steer or modify it. Shared local sessions appear in All sessions and are not indexed for other users' session queries, including another user's `/chronicle`. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- A person's session list contains sessions they started and sessions where they prompted Copilot on another user's session. Opening a session shows the log: internal reasoning, tools used, token usage, and session length. Copilot runs in its own ephemeral development environment. Steering is a follow-up in the prompt box under the log; Copilot applies it after the current tool call. Steering spends AI credits and "is not available for third-party coding agents." Stopping a session ends the Actions run and keeps commits already pushed. Cloud sessions can be archived and cannot be deleted. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- Session search is narrower than the Agents tab. "You can only query sessions that you started." The same section says session data is private by default and that individual sessions can be shared view-only, which matches the local-session rule more than the cloud-session "shared by default" rule. Querying requires sync; an org can disable "Store local sessions in the Cloud," and a CLI can set `remoteExport` to false. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- Copilot cloud commits are authored by Copilot, with the person who started the task as co-author. Each commit message includes an `Agent-Logs-Url` trailer to the session logs. Commits are signed and show as Verified. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents); [Trace any Copilot coding agent commit to its session logs](https://github.blog/changelog/2026-03-20-trace-any-copilot-coding-agent-commit-to-its-session-logs/)
- On GitHub, handing work from Copilot Chat to a cloud session copies the chat's context into the new session. While it runs, chat shows status. Afterward, chat can answer from the session logs about what changed, what was validated, and why, and can start another session. That is one person moving context between two of their own surfaces, plus a PR others can open. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents); [Copilot Chat now sees your agent sessions](https://github.blog/changelog/2026-06-10-copilot-chat-now-sees-your-agent-sessions/)
- A Cursor cloud agent clones the repo, works on a separate branch, and pushes that branch for handoff. The user needs read-write on the repo. The shareable object for a teammate is the agent URL: conversation, code changes, and artifacts (screenshots, videos, logs). Visibility requires the same Cursor team and the viewer's own source-control account with access to that repository. Team membership alone is not enough. Viewing is read-only unless an admin enables team follow-ups. — [Cloud Agents](https://cursor.com/docs/cloud-agent)
- Team follow-ups have three settings: Disabled (only the creator steers), Service accounts only, and All (any teammate with visibility can follow up on any team agent). Follow-ups execute with the original creator's secrets and credentials. Cursor's own warning: a follow-up can tell the agent to read environment variables, print secrets, push credentials out, or use the creator's tokens, including a less-privileged teammate directing a more-privileged creator's agent. — [Cloud Agents settings](https://cursor.com/docs/cloud-agent/settings)
- Cursor secrets are workspace- or team-scoped and injected at start; a running agent does not pick up secrets added later. Runtime secrets are redacted from tool results, the chat transcript, commits, and commit messages. Build secrets stay in the image build and are not in the running agent. Environment-variable secrets are visible to the agent. User-level hooks in the local home directory are not available on the cloud VM. Snapshots can include `.env.local` if someone put that file in the snapshot; the docs say to use the Secrets tab instead. — [Cloud Agents](https://cursor.com/docs/cloud-agent); [Cloud Agent security and network](https://cursor.com/docs/cloud-agent/security-network)
- Cursor's diagnostic MCP is a second, tighter ACL on the same runs. A team admin can list and fetch transcripts for cloud-agent runs in repos and environments they already can access. A non-admin using that MCP sees only runs they started or own, even in a shared environment. Service-account runs are visible to all team admins, and service accounts need a team-level source-control connection rather than a personal one. — [Cloud Agent capabilities](https://cursor.com/docs/cloud-agent/capabilities); [Service accounts](https://cursor.com/docs/account/enterprise/service-accounts)
- A human can take the cloud agent's remote desktop to test the branch without checking it out, then release control so the agent continues. That is a handoff of the VM console between one human and the agent, not a second human joining the session. — [Cloud Agents](https://cursor.com/docs/cloud-agent)
- Devin handoff, from the Devin CLI `/handoff` or from another coding agent via the Devin Handoff plugin, creates a new cloud session in a fresh VM. The CLI "packages up the conversation context and current git branch." The plugin path sends repo and branch from git, `git diff HEAD` truncated at 100KB, and whatever extra context the calling agent includes (files examined, hypotheses, partial fixes). Local edits the user does not want sent have to be committed or stashed first, because the diff is included. The plugin returns a session URL. The docs do not say the local process, the local secret store, or the untruncated transcript are attached. — [Hand off to Devin Cloud](https://docs.devin.ai/work-with-devin/devin-handoff)
- Jules sessions are per API key. A session has a prompt, a source (a connected GitHub repo and starting branch, or a repoless environment), a state, a web URL, and outputs that can include a pull request or a git patch of the change set. Activities are an immutable event log the key holder can list. Plans can require explicit approval or be auto-approved. The API authenticates with `x-goog-api-key`. The docs say not to share the key, and "permission denied" means the caller cannot access the requested sessions or sources. They do not describe granting another Google account access to a session. — [Jules API quickstart](https://jules.google/docs/api/reference/); [Jules sessions resource](https://developers.google.com/jules/api/reference/rest/v1alpha/sessions); [Jules authentication](https://jules.google/docs/api/reference/authentication/); [Jules changelog, 2026-01-26](https://jules.google/docs/changelog/2026-01-26-4/)

### Inferences

- "Anyone with the repo can continue the work" means they can check out the branch or review the PR. It does not mean they inherited the agent's context window. GitHub is the outlier that also puts the cloud run tape in front of repository readers by default. Cursor puts the tape in front of teammates only after a team check and a repo check, and keeps steering off unless an admin opts in. Jules and Devin document the tape as belonging to the API key or the session URL, and document the PR or patch as the output.
- Cursor team follow-ups set to All are many people steering one agent that still acts as one person. That is a different boundary from "many people, each with their own agent, sharing a branch."
- Devin handoff and Jules are one person pointing a second agent at packaged context. Another human enters later through git, or through whatever ACL the session URL happens to have, which Devin's handoff page does not specify.
- GitHub's page says both "cloud sessions are shared by default" and, in the query section, "you can only query sessions that you started" and "session data is private by default." The consistent reading is that the repository Agents tab is the shared view, and the natural-language session index stays personal. The page does not say that in one sentence.

### Gaps

- GitHub does not state whether any repository collaborator can steer a cloud session, or only people who already prompted it. The list rule ("sessions you started, or that you prompted on someone else's session") shows that prompting another user's Copilot session is possible. It does not publish the ACL. Steering of third-party agents on GitHub is explicitly unavailable. Who may assign those agents is not in the pages fetched here.
- Devin's handoff page does not say who else in an org can open the session URL, whether they can send messages, or whether the cloud session uses the handoff initiator's connected accounts.
- Jules docs are silent on cross-user session visibility, concurrent messages into one session, and whether the web URL is restricted to the API key's owner.
- No official Claude Code on the web page in this pass described session visibility, whether a teammate can open a remote session, or what of the local context is absent from the cloud VM. The Claude projects rewrite (one conversation, many cloud threads) is an account-scoped fan-out, not a documented person-to-person handoff. — [What are projects?](https://support.claude.com/en/articles/9517075-what-are-projects)
- Cursor docs do not say the run tape is hidden from teammates. They say viewing the URL shows the conversation. They also say runtime-secret values are redacted in that transcript. They do not say ordinary file contents or tool output are hidden.

## Presence, locking, and "someone else is already on this"

### Takeaway

The products that show another worker on the same item show an agent's status on a ticket, or they refuse a second copy of a channel agent. They do not show two humans editing one agent transcript, and they do not lock a shared chat. ChatGPT forbids synchronous editing of a shared chat and tells people to branch. Cursor's remote desktop is a console lock between one human and the agent, released explicitly. Shared-mailbox products were not found, in this pass, to expose a "someone is replying" signal.

### Cited Findings

- Since March 26, 2026, assigning a coding agent (the changelog names Copilot, Claude, or Codex) to a GitHub issue shows that session under the assignee, with status queued, working, waiting for review, or completed. The same sessions can be shown on project table and board views. Clicking opens the session logs. This is described as generally available for repositories that have coding agents. — [Agent activity in GitHub Issues and Projects](https://github.blog/changelog/2026-03-26-agent-activity-in-github-issues-and-projects/)
- GitHub's session page adds a human steer and a stop control on a Copilot session, which is a way to interrupt an agent that is already working. It does not describe a lock that prevents a second person from steering the same session, or a banner that another human is in the prompt box. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- ChatGPT: shared-project chats are branched, not edited synchronously. Members can see who started a chat from the profile icon. There is no documented "X is in this chat" state. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)
- Teams allows one Channel Agent per channel, and that agent cannot be attached to another channel. Users who are not enabled for the feature still see the agent's presence and its messages. — [Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)
- Cursor: a teammate with access can open a running agent's URL and read the conversation while it runs. Follow-ups, if enabled, are additional prompts, not a lock. Remote desktop control is taken and then released back to the agent. The docs do not say a second teammate is blocked from taking that desktop, or that the UI shows who currently holds it. — [Cloud Agents](https://cursor.com/docs/cloud-agent)
- Jules session states include `QUEUED`, `PLANNING`, `AWAITING_PLAN_APPROVAL`, `AWAITING_USER_FEEDBACK`, `IN_PROGRESS`, `PAUSED`, `FAILED`, and `COMPLETED`. That is the agent's state for the API key holder, not a record of another human. — [Jules types](https://jules.google/docs/api/reference/types/)

### Inferences

- "Someone else is already on this" in these products means an agent is attached to an issue or a channel, and the status is visible. It does not mean a pessimistic lock on a shared transcript. ChatGPT's branch rule is the closest thing to a lock, and it is a product rule against co-editing, not a live presence indicator.
- GitHub's issue sidebar is the clearest cross-vendor presence surface found: several coding agents, one status line, on the work item rather than inside the agent's UI.

### Gaps

- No fetched page for ChatGPT, Claude, Gemini, Cursor, Devin, or Jules describes a live cursor, a typing indicator, or an edit lock when two humans open the same agent session.
- Cursor does not say what happens if two teammates send follow-ups at the same time, or if two people take the remote desktop.
- Teams "presence" in the Channel Agent doc is the agent's own presence in the roster (visible to people who cannot talk to it). It is not documented as presence of another human working the same task.
- A vendor article claims neither a Microsoft 365 shared mailbox nor Gmail delegation shows that a colleague is currently writing a reply, and that Microsoft warns of duplicated messages past 25 simultaneous users. This pass did not open the Microsoft or Google support page that would confirm either claim, so it is not used as a finding. — [How to avoid duplicate replies in a shared mailbox](https://www.trupeo.com/blog/avoid-duplicate-replies/)

## What breaks when a personal agent is pointed at shared work

### Takeaway

The documented failure is two actors treating one shared inbox as if it were private: the same message gets two replies, because delivery is at-least-once and because nothing in the mailbox assigns the thread to a single writer. Calendar writes fail the same way if the agent books from a stale read. Audit breaks when the side effect is attributed to the agent owner's grants rather than to the person who prompted, which Cursor documents for team follow-ups, and when a channel agent repeats file contents to people who could not open the file, which Teams tries to prevent with a per-asker check and a confirm-before-share step.

### Cited Findings

- A Nylas engineering recipe names three duplicate-reply causes for an agent on mail: webhook redelivery (at-least-once, so one `message.created` is processed twice), two workers racing the same event, and a shared inbox where two agents, or an agent and a human, both decide to answer. The recipe's boundary is one agent per inbox, plus dedup and a per-thread lock. It says shared access should stay read-only oversight rather than a second automated writer. This is a vendor how-to, not an incident report. — [Prevent duplicate replies](https://developer.nylas.com/docs/cookbook/agent-accounts/prevent-duplicate-replies/)
- The same vendor's calendar guidance says availability can change between the suggestion and the write, so the agent must re-check before booking, must not overwrite an existing event without approval, and should keep an idempotency record for webhook-triggered sends and bookings. A separate tutorial gives the agent its own calendar and mailbox instead of a human's shared ones, so an update is sent as that agent and replies thread back to it. — [Calendar conflict-resolution guidance](https://cli.nylas.com/ai-answers/calendar-conflict-resolution-agent.md); [Build a calendar conflict-resolution agent](https://dev.to/mqasimca/build-a-calendar-conflict-resolution-agent-with-nylas-2plc)
- Cursor team follow-ups are the concrete audit break for a shared agent: the follow-up is typed by teammate B and executed with teammate A's tokens, so downstream actions (the docs name environment variables, logs, external endpoints, and access tokens) are the creator's. The docs tell admins to treat the All setting like shared SSH keys. Service accounts are the documented alternative when the run should not be tied to a person who may leave; those runs are visible to team admins. — [Cloud Agents settings](https://cursor.com/docs/cloud-agent/settings); [Service accounts](https://cursor.com/docs/account/enterprise/service-accounts)
- GitHub's attribution for a Copilot cloud commit is Copilot as author and the human who started the task as co-author, with the session log linked from the commit. A later person's steer is not described as changing that co-author. — [Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- Teams Channel Agent will not use a file the asking user cannot access, and it asks before posting an answer to a room where other members might lack the file. It also warns that the answer does not inherit the source sensitivity label, and that knowledge collection may cross Information Barriers. A meeting summary, once accepted into the agent, is available to channel members who were not in the meeting. That is shared-work leakage by design of the knowledge base, with a confirm step rather than a lock. — [Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)
- Copilot Studio refuses end-user-authenticated sources such as SharePoint in the channel and the group chat, and allows them in the 1:1, specifically "to prevent unintended data exposure." A personal connector that works in DM does not automatically work, and is not supposed to work, once the same agent is in the shared room. — [Connect and configure an agent for Teams](https://learn.microsoft.com/en-us/microsoft-copilot-studio/publication-add-bot-to-microsoft-teams)
- ChatGPT shared projects will use a file or note a member adds in replies that other members can see. Personal memory stays outside. Space is the leak path in the other direction: an agent may write a private memory onto a shared page, after which readers see it and their own memory may store it, while the original chat stays private. — [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt); [ChatGPT Space: sharing, data, and controls](https://help.openai.com/en/articles/20001544-chatgpt-space-sharing-data-and-controls)
- Devin's handoff includes the uncommitted diff up to 100KB in the cloud prompt. The docs tell the user to stash or commit first if those local edits should not be sent. That is a personal working tree crossing into a cloud session another person might later open, with no further redaction described. — [Hand off to Devin Cloud](https://docs.devin.ai/work-with-devin/devin-handoff)

### Inferences

- Pointing a personal agent at a shared mailbox or calendar fails because the shared object has no single writer and the agent's trigger has no memory of the other actor. The fixes named in the vendor docs are isolation (the agent gets its own inbox or calendar), a lock around the thread, and a re-read before the write. None of the chat-product help pages fetched here describe those controls for Gmail, Outlook, or a family calendar.
- Two agents acting is a different break from two people sharing one agent. Two personal agents on one mailbox double-send. One Cursor agent with team follow-ups sends once, attributed to the wrong person. Teams' channel agent is the case they designed for: one agent, many askers, and the permission check is per asker at reply time.
- Audit of agent work, where it exists in these docs, sticks to the git commit (Copilot co-author plus log URL) or to the session creator (Cursor), not to every human who later prompted.

### Gaps

- No incident write-up in this pass named a specific shared-mailbox, shared-calendar, or shared-board failure with a date and a product. The Nylas pages describe the failure mode as an engineering pattern.
- No official doc in this pass said what a personal ChatGPT, Claude, or Gemini connector does when the connected mailbox or calendar is delegated or shared. Duplicate sends, double-booking, and audit for those products are undocumented here, not shown to be safe.
- Family or team boards (a shared task board with two people's local agents) were not covered by the help pages found. The nearest mechanism is GitHub project boards showing agent session status, which is visibility, not a lock against a second agent moving the same card. — [Agent activity in GitHub Issues and Projects](https://github.blog/changelog/2026-03-26-agent-activity-in-github-issues-and-projects/)
- Claude shared-project memory across members, Jules session ACLs, Discord channel agents, and Claude Code on the web session sharing remain undocumented in the sources fetched for this note.
