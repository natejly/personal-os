## Dashboards, canvas/spaces, artifacts, charts and interactive blocks

### Where we are

**Canvas / spaces (solid, mature).** `backend/personal_os/canvas.py` owns `canvases` (name, optional `project_id`, snap_mode/grid_size, zoom/pan, wallpaper, `locked`) and `canvas_windows` (kind, ref_id with no FK, geometry x/y/w/h/z, state normal|minimized|maximized|popped, restore/popout bounds, pinned, opacity, per-widget `config` JSON). Tables are created in `Canvases.__init__` with an `_ADDED_COLUMNS` ALTER shim, not in db.py `_migrate`. `set_layout` writes a whole drag in one tx; `delete_windows_for(kind, ref_id)` sweeps windows when a referent dies. `WIDGET_KINDS` (14 kinds: chat, todos, calendar, board, note, dashboard-widget, memory, graph, documents, recap, project, usage, activity, web) mirrors `src/shared/types.ts`. `presets.py` snapshots a canvas into `canvas_presets` (server-side snapshot, `REF_TABLES` skip windows whose referent is gone on instantiate). Frontend: `src/renderer/src/canvas/` (store, snapping, WindowFrame, Dock, Overview, SpacesBar, PresetsMenu, registry, 14 widgets). Weak spots: windows are only placed by the human or by presets; there is no agent-facing tool to open, arrange or populate a space (grep of tools.py for canvas/dashboard/widget returns nothing); presets cannot carry widget content, only refs.

**Dashboards (LLM-generated HTML per widget).** `dashboards.py`: `data_sources` (http|rss|internal, config JSON, server-held `secret`, last_status), `dashboards`, `widgets` (kind html|summary|markdown, prompt, source_ids, `code`, `output`, refresh_minutes, position, width 1-3, height). `generate_widget_code` prompts the model for one HTML doc that `fetch()`es `/sources/{id}/fetch`; app.py `render_widget` (~L3302) rewrites those URLs with a per-widget HMAC capability (`_widget_fetch_token`, expiring) and serves under `WIDGET_CSP` (`connect-src 'self'`). `_run_widget` regenerates code only on create/revise/`regenerate`; summary widgets re-run an LLM over source samples (24k char cap). Weak spots: every visual is bespoke model code (inconsistent style, no theming tokens, fragile: no lint or repair when the HTML throws or references remote assets, `sample` is truncated to 1800 chars so generated code guesses at schema); `refresh_minutes` is stored but a chart widget can't be refreshed without code that re-fetches itself; no widget-level data binding or transforms; no templating; grid is 3 columns by `width` only; `GET /widgets/{id}` does not exist (dashboardWidget.tsx fetches the whole dashboard).

**Artifacts (module exists, completely unwired).** `artifacts.py` is well designed: `artifacts` + `artifact_versions` (append-only, `restore` = new version, MAX_VERSIONS=50 pruning with monotonic numbers, source llm|user|restore), strict `RENDER_HEADERS` (CSP `default-src 'none'`, `connect-src 'none'`, `sandbox allow-scripts`, frame-ancestors the app only), `blocked_capabilities()` regex lint, `generate_artifact_code` / `revise_artifact_code` (whole-document rewrite, refuses above 120k chars). But a grep shows no `Artifacts(` instance, no routes, no tool, no WidgetKind and no panel in app.py/tools.py/renderer; only `src/renderer/src/artifacts/{bridge.ts,source.ts}` (the postMessage trust boundary, `resize`/`setTitle` verbs) and `tests/test_artifacts.py` exist. The README "Features" and docs/research.md A11 ("Artifacts side panel") are therefore not shipped for real. Revision is full-rewrite, which is slow, token-heavy and drifts.

**Charts / interactive / mermaid (good in chat, not reusable).** `ChartBlock.tsx` parses a ```chart JSON spec (bar/line/area/pie/scatter, mixed series, stacked, units, Chart.js-shape and key-value variants, MAX_ROWS 500) into Recharts with chart/table/source tabs. `InteractiveBlock.tsx` adds sliders/number/select/toggle controls and formula series via `lib/expr` (no eval; 12 controls, 8 series, 400 points). `MermaidBlock.tsx` lazy-loads mermaid. Weak spots: specs only live inside message text (cannot be pinned to a dashboard/space or bound to a data source); parse errors are shown to the user with no model repair loop; no transforms (group/bin/sort/top-N), no time axis, no brush/zoom; no JSON-schema for the spec.

### What the best open-source systems do

- **Vercel AI Chatbot artifacts** ([server.ts](https://github.com/vercel/ai-chatbot/blob/main/lib/artifacts/server.ts), [prompts.ts](https://raw.githubusercontent.com/vercel/ai-chatbot/main/lib/ai/prompts.ts)): artifacts are typed `DocumentHandler`s (text/code/sheet) with `onCreateDocument`/`onUpdateDocument`, content streamed as deltas through a `UIMessageStreamWriter`, persisted via `saveDocument` as versioned rows. The prompt gives the model three tools with a hard split: `createDocument`, `editDocument` (find-and-replace, for "fixing bugs, adding/removing lines, renaming variables") and `updateDocument` (full rewrite "only when most of the content needs to change or editDocument would require too many edits"). Rules: ONE tool call per response then stop, never echo artifact content in chat, do not edit in the same turn as create. We only have the full-rewrite path.
- **E2B Fragments** ([repo](https://github.com/e2b-dev/fragments)): the model emits a structured "fragment" object (template id, code/files, install command, port); `lib/templates.json` per template carries `lib` (allowed deps), `file` (entry), `instructions` (prompt text) and `port`; executed in an E2B microVM, previewed by port URL. Mechanism worth copying is the template registry: per-kind prompt + constraints in data, not code. (We already have microVM sandboxes elsewhere in the app, but artifacts stay inert HTML by owner choice.)
- **LibreChat artifacts** ([docs](https://www.librechat.ai/docs/features/artifacts)): artifacts are an agent tool with three instruction modes (normal, shadcn/ui, custom); renders React, HTML, SVG, Mermaid, Markdown in a side panel via Sandpack; fullscreen, export (SVG/PNG, file download with proper name), versioned iteration through follow-up messages. Self-hostable bundler for privacy.
- **Open WebUI**: renders HTML/SVG in sandboxed iframes with auto-height and a prompt-to-chat bridge (docs page 404'd in this session; treated as unverified detail, the iframe + message bridge pattern matches our `bridge.ts` design).
- **tldraw make-real** ([repo](https://github.com/tldraw/make-real), archived Feb 2026): sketch screenshot + text annotations + the previous generated HTML go to a vision model, which returns a single HTML doc, shown in an iframe; iteration is "draw on the preview and resubmit". Relevant lesson: send previous output as context so revisions are incremental. Source not readable via fetch, so mechanism details beyond that are unverified.
- **Glance** ([config docs](https://github.com/glanceapp/glance/blob/main/docs/configuration.md)): dashboards are pages > columns > typed widgets (RSS, weather, monitor, custom-api, iframe, html, group, split-column); each widget has a built-in cache with a TTL and the data fetch is separate from rendering; the `custom-api` widget binds a URL to a template, so users get a nice widget with zero code. That is the opposite of our "model writes JS per widget".
- **Vega-Lite** ([docs](https://vega.github.io/vega-lite/docs/)): a small JSON grammar: data + mark + encoding channels (x, y, color, size, tooltip, detail) + transforms (aggregate, bin, calculate, filter, regression, fold, timeUnit) + params/selections (point/interval, bound to inputs) + composition (layer, concat, facet, repeat); validated against a published JSON Schema. **Observable Plot** (page returned 429; treated as unverified) is the compact variant: marks with options and inferred scale types.
- **VegaChat** ([arXiv 2601.15385](https://arxiv.org/html/2601.15385v1)) and [Generating Statistical Charts with Validation-Driven LLM Workflows](https://arxiv.org/pdf/2605.00800): LLM-generated chart specs are validated against the schema plus heuristics (empty-but-valid charts, wrong datetime types); cheap fixes are applied algorithmically without a model call, remaining errors go back to the LLM with the validator's trace, bounded retries.
- **Google A2UI** ([repo](https://github.com/google/a2ui), [blog](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)): agents emit declarative JSON (a flat list of components with id references plus a data model); the client validates against a trusted component catalog and renders natively. Not executable code, streams progressively. Our ```chart/```interactive blocks are a narrow instance of this; the catalog idea generalises them to stat tiles, tables, lists.

### Build next

**artifacts-1** makes artifacts real on the backend: instantiate `Artifacts`, add CRUD/version/restore/render routes using `render_headers()`, add a `patch_artifact` engine (Vercel `editDocument` semantics: ordered exact search/replace pairs, atomic, fails loudly on zero or multiple matches) and three agent tools `create_artifact`, `edit_artifact`, `rewrite_artifact` with the one-tool-per-turn / no-echo prompt rules, plus a lint/repair pass on every saved version that reports `blocked_capabilities` back to the model once. All offline-testable with a stubbed `llm.complete`. **artifacts-2** is the thin UI half: an `artifact` WidgetKind (canvas.py, types.ts, registry.ts, presets REF_TABLES), an ArtifactWidget that frames the render URL and speaks `bridge.ts`, version history/restore, and an "open in space" action on chat results; verified by backend kind/preset tests and node tests for the renderer logic. **dashboards-1** adds a declarative `chart`/`stat`/`table` widget kind to dashboards, Glance custom-api style: the widget stores a spec plus a `source_id` and a small path/transform binding, refreshes by re-fetching the source on its `refresh_minutes` TTL with no model call, renders through the existing ChartBlock, and adds a one-shot validate-and-repair step (VegaChat style) for the model-written binding so a widget stops depending on bespoke generated JS.

### Specs

#### artifacts-1: Wire artifacts into the backend: routes, patch-edit engine, agent tools, lint-and-repair (M)

**Why.** artifacts.py is a finished, well-secured module with versions and strict CSP, but nothing instantiates it: no routes, no tool, no UI. Every leader (Vercel AI Chatbot, LibreChat, Open WebUI) makes artifacts a first-class agent tool. Vercel's createDocument/editDocument/updateDocument split (find-and-replace for small changes, rewrite only when most changes) is the proven way to cut cost and drift versus our whole-document revise. VegaChat-style validate-then-repair adds robustness.

**Files.** `backend/personal_os/artifact_patch.py (new)`, `backend/personal_os/artifact_routes.py (new APIRouter)`, `backend/personal_os/artifact_tools.py (new tool defs + handlers)`, `backend/personal_os/app.py (small: instantiate Artifacts, include_router, register tools)`, `backend/personal_os/tools.py (small: register the artifact tool group, default on, writes are local-only)`, `backend/personal_os/artifacts.py (add repair helper)`, `backend/tests/test_artifact_routes.py (new)`, `backend/tests/test_artifact_patch.py (new)`

**Design.** 1) artifact_patch.py: `apply_patch(code:str, edits:list[{search:str, replace:str}]) -> str`. Edits apply in order to the running text. Each `search` must occur exactly once (after exact match; if zero, try one whitespace-normalised match on line-trimmed text; if still zero or >1, raise PatchError(index, reason, nearby_snippet)). Atomic: no partial application. Cap 20 edits, total search+replace under 60k chars. Result goes through artifacts._check_code.
2) artifacts.py: add `async def repair_artifact_code(settings, model, code, issues:list[str]) -> str` that calls `revise_artifact_code` with an instruction built from `blocked_capabilities(code)` (e.g. 'Remove all network use, localStorage...'); max ONE repair round. Add `lint(code) -> {blocked:list[str], empty: bool}` where empty is true when stripped body text and script content are both under 20 chars.
3) artifact_routes.py (APIRouter, mounted unprefixed; reuses the app's auth middleware): GET /artifacts?project_id=&q=, POST /artifacts {title,prompt,code?,project_id?} (if no code and prompt, generate via generate_artifact_code then lint then at most one repair), GET /artifacts/{id}, PUT /artifacts/{id} (metadata), DELETE /artifacts/{id} (also `canvases.delete_windows_for('artifact', id)`), GET /artifacts/{id}/versions, GET /artifacts/{id}/versions/{n}, POST /artifacts/{id}/restore {version}, POST /artifacts/{id}/edit {edits:[...]} -> apply_patch -> save_version(source='llm', instruction='patch'), POST /artifacts/{id}/revise {instruction} (existing full-rewrite), POST /artifacts/{id}/code {code} (source='user'), GET /artifacts/{id}/render returning HTMLResponse(code or EMPTY_HTML, headers=render_headers()). NOTE app.py auth middleware exempts `/widgets/*/render` via PUBLIC_PATHS logic at ~L189: an iframe cannot send the token header, so add `/artifacts/{id}/render` exemption the same way but ONLY for GET of that exact shape; the CSP sandbox makes it inert. Responses on create/edit/revise include `lint`.
4) artifact_tools.py: tools `create_artifact(title, prompt)` (model-generated via generate_artifact_code), `edit_artifact(artifact_id, edits[])` (patch), `rewrite_artifact(artifact_id, instruction)`; local-only writes so not approval-gated, but each returns {id, version, lint}. Append a short prompt fragment (add to the system-prompt assembly near RENDER_HINT in app.py, one line call): 'Use create_artifact for a standalone tool/page. Prefer edit_artifact for small changes; rewrite_artifact only when most of it changes. One artifact tool per turn. Never paste the artifact HTML into chat.' Enforce one-artifact-tool-per-turn in the handler by returning an error on a second call within the same run id.
5) No schema migration: tables already exist via artifacts.SCHEMA. No new settings keys required; if a toggle is wanted use the existing per-tool-group `settings.tools` mechanism.

**Tests.** test_artifact_patch.py: exact single match applies; zero match raises PatchError with index; two matches raises; atomic (second edit bad leaves code unchanged); whitespace-normalised fallback; size caps. test_artifact_routes.py (TestClient style like backend/tests/test_presets.py, temp PERSONAL_OS_DATA_DIR): create with code, edit via patch makes version 2 with old version still fetchable, restore appends version 3, render returns the CSP header with `connect-src 'none'` and `sandbox allow-scripts`, render of an unknown id is 404, delete sweeps canvas windows of kind artifact, lint flags `fetch(` and empty body. Monkeypatch `llm.complete` with an async stub that returns canned HTML first with fetch() and then clean HTML, assert exactly one repair call happens and the saved version is the repaired one. Tool handler test: second artifact tool call in the same run is refused.

**Done when.** With the app running against stubbed models, POST /artifacts then POST /artifacts/{id}/edit with a search/replace pair yields version 2 containing the replacement; GET /artifacts/{id}/render in an iframe shows it under the strict CSP; the chat agent has create_artifact/edit_artifact/rewrite_artifact tools; all new tests and existing backend/tests/test_artifacts-equivalent tests pass offline; app.py diff is under ~40 lines.

#### artifacts-2: Artifact widget kind and panel: artifacts as windows in spaces (M)

**Why.** Once artifacts-1 exists, artifacts need a place to live. LibreChat and Open WebUI show them in a dedicated pane with fullscreen, versions and export; our advantage is the canvas, where an artifact can be a first-class window that persists in a space and in presets. bridge.ts (resize/setTitle trust boundary) was written for exactly this and has no consumer.

**Files.** `backend/personal_os/canvas.py (add 'artifact' to WIDGET_KINDS)`, `backend/personal_os/presets.py (REF_TABLES['artifact']='artifacts')`, `src/shared/types.ts (WidgetKind union, Artifact/ArtifactVersion types)`, `src/renderer/src/canvas/registry.ts (needsRef artifact entry)`, `src/renderer/src/canvas/widgets/artifact.tsx (new)`, `src/renderer/src/lib/api.ts (artifacts client)`, `src/renderer/src/canvas/AddWidgetMenu.tsx (add entry)`, `src/renderer/src/components/ToolEvents.tsx (render create_artifact result as an Open-in-space card)`, `backend/tests/test_artifact_widget.py (new)`, `src/renderer/src/artifacts/frame.test.ts (new, node:test)`

**Design.** Backend: add 'artifact' to WIDGET_KINDS and REF_TABLES (mirror of needsRef in registry.ts) so presets keep/skip artifact windows and `delete_windows_for('artifact', id)` runs on delete (already in artifacts-1). No migration, canvas_windows.kind is free text. Frontend: ArtifactWidget({window, live, onTitle}) renders `<iframe sandbox="allow-scripts" src={base}/artifacts/{ref_id}/render?v={version}>` only when `live` (same cost rule as dashboardWidget.tsx), listens for window 'message' events, requires `event.source === iframe.contentWindow`, passes `event.data` through `parseMessage` from artifacts/source.ts, and applies resize (clampHeight, only to auto-height mode) and setTitle (sanitizeTitle, via onTitle). Toolbar: version dropdown (GET /artifacts/{id}/versions, restore button -> POST restore), Revise input (POST /artifacts/{id}/revise), Download .html (fetch code, Blob), Copy source. Show `lint.blocked` as a dismissible warning strip ('this artifact uses network/storage, which is blocked'). In-frame shim: GET /artifacts/{id}/render must inject a tiny inline script posting `{source:ARTIFACT_SOURCE, v:ARTIFACT_PROTOCOL, type:'resize', height}` from a ResizeObserver; implement as `artifacts.inject_shim(code)` called by the render route (insert before </body>, CSP already allows inline script). Chat: when a create_artifact/edit_artifact tool result arrives, ToolEvents shows a card 'Artifact: <title> v<n> [Open in space]' which calls canvas add_window(kind 'artifact', ref_id). No new settings keys.

**Tests.** backend test_artifact_widget.py: add_window kind 'artifact' succeeds and unknown kinds still fail; preset round trip keeps an artifact window and, after deleting the artifact, instantiate skips it with skipped==1; delete artifact removes its windows; inject_shim adds exactly one shim, is idempotent, and the result still satisfies `blocked_capabilities` == [] (shim must not use banned APIs: use postMessage only). Node test frame.test.ts: message from a foreign source is ignored, resize clamped to [48,8000], setTitle control characters stripped. Run with the repo's existing renderer test command (see package.json test script, node:test).

**Done when.** From chat, asking for a small tool produces an Open-in-space card; clicking it opens an artifact window that renders under the strict CSP, auto-sizes via the shim, shows version history, restores an old version as a new version, and survives save-as-preset/instantiate. No network access from inside the frame.

#### dashboards-1: Declarative bound widgets (chart/stat/table) with TTL refresh and validate-and-repair (M)

**Why.** Glance's custom-api widget and A2UI's catalog show the better default: the model produces a small validated JSON spec bound to a data source, and the client renders it with trusted components. Today every dashboard widget is bespoke model JS (dashboards.py generate_widget_code), regenerated rather than refreshed, truncated to a 1800-char sample, and unlinted. VegaChat and validation-driven chart papers show a schema check plus one repair round plus algorithmic fixes removes most failures.

**Files.** `backend/personal_os/widget_spec.py (new: spec schema, binding, validation, repair)`, `backend/personal_os/dashboards.py (add 'chart','stat','table' to the documented kinds; new columns via additive ALTER)`, `backend/personal_os/app.py (small: in _run_widget branch for declarative kinds; route GET /widgets/{id}/data)`, `src/renderer/src/components/DashboardsView.tsx (kind picker + DeclarativeWidget)`, `src/renderer/src/canvas/widgets/dashboardWidget.tsx (render declarative kinds without iframe)`, `src/shared/types.ts (Widget.spec, Widget.data)`, `backend/tests/test_widget_spec.py (new)`

**Design.** Schema (additive, in Dashboards.__init__ after executescript, mirror canvas.py _ADDED_COLUMNS pattern): `widgets.spec TEXT NOT NULL DEFAULT '{}'` and `widgets.data TEXT NOT NULL DEFAULT 'null'` (cached bound rows) and `widgets.data_error TEXT NOT NULL DEFAULT ''`. Existing kind column accepts 'chart' | 'stat' | 'table' in addition to html|summary|markdown; update update_widget allowed-field set to include spec/data/data_error.
widget_spec.py:
- Spec JSON: `{kind, source_id, path:'$.items', select:{x:'name', y:['value']}, transforms:[{op:'sort',by:'value',dir:'desc'},{op:'limit',n:10},{op:'group',by:'cat',agg:{value:'sum'}},{op:'filter',field:'x',cmp:'>',value:0}], chart:{type:'bar|line|area|pie|scatter', stacked:false, unit:'', title:''}, stat:{field, agg:'last|sum|mean|count|min|max', label, unit, delta_field?}, table:{columns:[{key,label}]}}`.
- `resolve_path(data, path)` minimal dotted/`[*]` JSONPath (no eval, no external dep): `$`, `.key`, `[n]`, `[*]`; returns list[dict] (wrap scalars; dict-of-dicts becomes rows with `_key`). `apply_transforms(rows, transforms)` supports sort, limit (<=500), filter (== != > < >= <=, contains), group+agg (sum/mean/count/min/max). Pure functions.
- `validate_spec(spec, sample_rows) -> list[str]` problems: unknown op, path yields 0 rows, y field not numeric in >50% rows (try algorithmic coercion first: numeric strings, '$1,234', '12%', ISO dates left as category), x missing, too many series (>8), result empty. `autofix(spec, rows)` applies the cheap fixes (coerce, drop missing y fields, pick first string column as x, first numeric columns as y) and returns (spec, remaining_problems).
- `async def generate_spec(settings, model, prompt, source, sample_rows, kind) -> dict`: prompt includes the source's true row schema (field names + inferred types + 5 sample rows computed server-side, not an 1800-char blob), requests ONLY the JSON spec; then validate_spec -> autofix -> if problems remain, ONE repair call with the problem list; if still failing store spec and `data_error`. All llm calls go through llm.complete.
- `async def bind(spec, fetch_source_fn) -> {rows, error}`: fetches via Dashboards.fetch_source (reuses SSRF guard + secret injection), applies path+transforms, trims to 500 rows.
Routing: `_run_widget` gets a branch: kind in (chart,stat,table): if regenerate or no spec -> generate_spec; always bind and store `data`, `refreshed_at`. Refresh does NOT call the model unless regenerate=true. Add `GET /widgets/{wid}` and `GET /widgets/{wid}/data` returning cached data when `now - refreshed_at < refresh_minutes*60` else re-bind (TTL cache like Glance).
Frontend: DeclarativeWidget imports `Chart` and `DataTable` from ChartBlock.tsx (export a `specFromBound(widget)` that builds a ChartBlock `Spec` from rows+chart config, reusing parseSpec's numeric coercion) and a StatTile (big number + delta). Theme tokens (--chart-N) come for free, fixing style inconsistency. Revise box sends a natural-language change to POST /widgets/{id}/revise which for declarative kinds regenerates the spec only. No new settings keys; refresh_minutes already exists.

**Tests.** test_widget_spec.py offline plain script: resolve_path cases ($.items, $.a.b[*], dict-of-dicts, scalar), each transform (sort asc/desc, limit, group sum/mean, filter ops), validate_spec flags missing field / empty result / non-numeric y, autofix coerces '$1,234' and '12%' and picks default x/y, generate_spec with a stub llm.complete returning (a) a good spec, (b) a bad spec then a repaired one (assert exactly 2 calls) and (c) two bad specs (assert exactly 2 calls, data_error set), bind() with a fake fetch_source returning canned JSON, stat aggregation (last/sum/mean), TTL cache returns cached data within window and re-binds after (monkeypatch time). Dashboards schema test: opening a pre-existing DB without the new columns migrates in place and old html/summary widgets still load.

**Done when.** Creating a 'chart' widget from a prompt and an RSS or internal source produces a stored spec and cached rows with a single model call (two at most with repair); refreshing it makes zero model calls; the widget renders with the app's chart tokens in both the Dashboards view and as a canvas window; existing html/summary widgets are unaffected; all new tests pass offline with no network.
