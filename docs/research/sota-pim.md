## Google Calendar, Gmail, Tasks, todos, kanban boards and the outbox

### Where we are

**Google client (`backend/personal_os/google.py`, 1222 lines).** One `Google` class wraps Calendar v3, Gmail v1, Tasks v1, Drive, Docs and Sheets over a desktop-loopback OAuth flow. Reads go through a TTL cache (`cache.py`; TTLs in `google.TTL`: events 60s, Gmail list 60s, tasks 30s); writes invalidate by namespace and are read back and gated by `verify.py` (`_verify_event`, `_verify_sent`, `_verify_labels`, `_verify_task`), so an unverified write surfaces as an error rather than a success.
- Calendar has full CRUD, multi-calendar fan-out (`calendar_events` does one `events.list` per calendar, `singleEvents=True`, capped at 15 calendars), recurrence (RRULE passthrough), guests, Meet, reminders, colors, RSVP and `send_updates`.
- Gmail is `gmail_search` (list plus a batched metadata get), `gmail_get`, `gmail_draft`, `gmail_send`, `gmail_modify` (read, archive, star only) and `gmail_labels`.
- Weak spots, all confirmed by grep: there is no `syncToken`, `historyId`, `freebusy`, `threads.get` or `updatedMin` anywhere. Every view mount re-lists, Gmail has no thread model, and label/archive/snooze triage is manual in `MailView.tsx`.

**Todos (`todos.py`, `modules/todos.py`).** The `todos` table has id, project_id, title, notes, due (a date string), priority 1-3, done, source, `external_id`/`remote_updated`/`synced_at` (Tasks link), `calendar_event_id`/`calendar_link`/`calendar_id`/`calendar_sig` (mirror link) and completed_at. `todo_tombstones` and `todo_event_tombstones` carry deletions to Google. `Todos.list` sorts `done, due IS NULL, due, priority, created_at DESC`.
- The model has no recurrence, estimate, subtasks, dependencies, tags or start/scheduled date. `Todos.update` only accepts a fixed field set.
- The agent tools are `todo_list/add/update/delete`, with `todo_write` as the separate plan artifact. Migrations are the `PRAGMA table_info` plus `ALTER TABLE ADD COLUMN` loop in `Todos.__init__`.

**Google Tasks sync (`gtasks.py`).** `TasksSync._merge` is a full two-way pass every interval, poked on local edits. It calls `google.tasks_all` (a full list, deliberately uncached), applies tombstones first, then per-link compares `updated_at > synced_at` (local) against `remote.updated != remote_updated` (remote), with `_remote_wins` as tiebreak. It then creates unlinked items in each direction. It does not use `updatedMin`/`showDeleted`, so cost grows with list size. Google Tasks cannot hold recurrence, so none is mirrored.

**Todo-to-calendar mirror (`todocal.py`).** `TodoCalendarMirror` puts each due, open todo on a "Grain Todos" calendar. `_sig` records title, notes, due and the event's time of day, so a user dragging the event to a new time is adopted back into the todo (`_adopt`/`_update`). It is deliberately one-way for deletions: a hand-deleted event is re-created. Events are placed only where the todo's due date says; nothing chooses a time. There is no duration or estimate.

**Boards (`boards.py`).** The tables are `boards`, `board_columns` (with `wip_limit`), and `cards` (title, description, float `position`, due, priority, JSON labels). `move_card` uses midpoint float positions. The WIP limit is stored and editable but not enforced or displayed in any code path (`add_card`/`move_card` never read it). Cards are unrelated to todos: no sync, no cross-link, and cards do not appear in Today or the calendar.

**Outbox (`outbox.py`).** This is a 60-120s (default 90) hold-and-undo queue for Gmail sends. An atomic `UPDATE ... WHERE status='holding'` claim makes send and cancel race-free. Stale holds after a restart are expired rather than sent, a failed send is never retried (double-send risk), and the verify verdict is stored on the row. The agent cannot send now. It is solid and not a gap.

**UI.** `CalendarView/CalendarWeek/EventEditor.tsx` do the week grid and full editor. `MailView.tsx` has folder/label/date filters, debounced Gmail `q` search, star/archive, compose and reply. `TodosView.tsx` is a 116-line list. `BoardsView.tsx` is a plain kanban.

**docs/research.md status.** Its L7 (email triage, awaiting-reply detection), L9 (people memory), the `syncToken`/`history.list` recommendation, and G73 (arrival trigger) remain unbuilt here. G17 (outbox) and G38 (`todo_write`) have shipped.

### What the best open-source systems do

**Inbox Zero** ([github.com/elie222/inbox-zero](https://github.com/elie222/inbox-zero), [PR #3787](https://github.com/elie222/inbox-zero/pull/3787)).
- Rules are plain-English instructions with actions (label, archive, draft reply, forward). Reply Zero keeps a four-state thread status: TO_REPLY (the user owes a response), AWAITING_REPLY (the user sent the last message and is waiting), FYI (nothing was ever asked) and ACTIONED (the request is fulfilled).
- The status prompt scans every message for questions and requests and tracks who promised what. The user's rule text is the single definition of each status. When the user sent the last email, FYI is removed from the schema, so a thread that needs nothing cannot be mis-filed as FYI.
- Statuses are applied as Gmail labels so they can be filtered. In [PR #3795](https://github.com/elie222/inbox-zero/pull/3795) the assistant's own filing emails are ignored when deciding thread status.
- The README does not document how "ask first" works. I could not confirm approval-gate internals from fetched sources, so I am not citing them.

**Zero / Mail-0** ([github.com/Mail-0/Zero](https://github.com/Mail-0/Zero)): self-hostable Gmail alternative on Next.js, Drizzle and Postgres with an AI agent layer. The README gives no sync mechanism details, so it is only a UX reference.

**Taskwarrior urgency** ([taskwarrior.org/docs/urgency](https://taskwarrior.org/docs/urgency/)).
- Urgency is a sum of weighted terms: next tag 15, due 12, blocking 8, priority H/M/L 6/3.9/1.8, scheduled 5, active 4, age 2, annotations, tags and project 1 each, waiting -3, blocked -5.
- Tag and annotation terms are scaled 0.8/0.9/1.0 for one/two/three-plus items. Overdue counts more than merely approaching, but the docs omit the exact due ramp.
- Every user-visible "what next?" list is just a sort on this one number, and coefficients are user-tunable. It is deterministic, explainable and cheap.

**Vikunja** ([vikunja.io/docs](https://vikunja.io/docs/), [filters](https://vikunja.io/docs/filters/), `pkg/models/tasks.go`).
- Repeat is a duration with three modes. Default adds the interval to the due date, always advancing past now by arithmetic rather than looping. Monthly adds one calendar month. From-current-date uses `now + interval`.
- On completion the task re-opens with shifted dates, and reminders keep their relative offsets to the due date. A repeating task does not stay in the done bucket and returns to the default bucket.
- Relations include subtask, blocking and precedes. Filters are a query language (`done = false && priority >= 3`, date math `now+7d`, `now/d`), and saved filters are stored queries. Kanban buckets have limits.

**Super Productivity** ([github.com/super-productivity/super-productivity](https://github.com/super-productivity/super-productivity)): per-task time estimates and timeboxing, a schedule timeline that places tasks next to calendar events, subtasks, repeat tasks, and a plugin system. Its estimate-plus-timeline combination is what turns a to-do list into a day plan.

**FluidCalendar** ([blog.fluidcalendar.com](https://blog.fluidcalendar.com/fluidcalendar-open-source-intelligent-task-scheduling/)), the open Motion/Reclaim analogue.
- Pipeline: gather calendar events and free work-hour windows, cut them into candidate slots of task duration plus buffer, score each slot with fixed weights (due 40%, priority 25%, energy match 20%, preferred time 15%), and pick the best. It is explicitly deterministic with no ML.
- Tasks can be locked so they are not moved again. It is the template for a rules-based auto-scheduler we can test offline.

**Cal.com** ([github.com/calcom/cal.diy](https://github.com/calcom/cal.diy)): availability is working-hour schedules minus calendar busy times, with date overrides, buffers and minimum notice. The docs page I fetched did not detail the algorithm, so I take only the schedule-minus-busy shape from it.

**Google sync primitives.**
- Calendar: one full list returns `nextSyncToken` (only on the last page). Later calls pass `syncToken` and return only changes, including cancelled events, and the query params must stay identical. A 410 means wipe the cache and full-sync again ([guide](https://developers.google.com/workspace/calendar/api/guides/sync)).
- Gmail: store the `historyId`, then call `history.list(startHistoryId)` for added, deleted and label-changed message ids. History is kept about a week or more, and a 404 means do a full sync ([guide](https://developers.google.com/workspace/gmail/api/guides/sync)).

### Specs

#### todos-1: Recurring todos (Vikunja semantics) plus Taskwarrior urgency score (S)

**Why.** Todos have no recurrence (todos.py schema has no repeat field) and are ordered only by due/priority. Vikunja's tasks.go updateDone/addRepeatIntervalToTime gives repeat modes (default from due, from current date, monthly) that advance strictly past now by arithmetic, and Taskwarrior's urgency coefficients (due 12, blocking 8, priority H/M/L 6/3.9/1.8, age 2, active 4, waiting -3) give a deterministic explainable sort. Small, self-contained, verifiable offline.

**Files.** `backend/personal_os/todo_rules.py (new: pure repeat + urgency functions)`, `backend/personal_os/todos.py (schema column, update() hook, list sort)`, `backend/personal_os/modules/todos.py (TodoIn/TodoPatch fields, ?sort=urgency, tool args)`, `backend/personal_os/llm.py (no new settings key needed unless urgency weights are made tunable)`, `backend/tests/test_todo_rules.py (new)`, `src/renderer/src/components/TodosView.tsx (repeat picker, urgency sort toggle)`, `src/renderer/src/components/TodoItem.tsx (repeat badge)`

**Design.** Schema: in Todos.__init__ extend the existing ALTER loop with `repeat TEXT` (JSON or NULL) and `urgency_note` is NOT stored. repeat JSON = {"every": int>=1, "unit": "day"|"week"|"month"|"year", "mode": "from_due"|"from_completion"}. Validate in todo_rules.parse_repeat(raw)->dict|None (raise ValueError on bad unit/every<1; cap every at 366). Add 'repeat' to the allowed field set in Todos.update (accept dict, store json.dumps; None clears) and to Todos.create via an optional kwarg `repeat`.

todo_rules.py pure functions (no db, no clock reads other than an injected `today: date`):
- next_due(due: date|None, repeat: dict, completed_on: date) -> date. from_due: start from due (or completed_on if due is None) and add k intervals where k is the smallest integer >= 1 such that the result is strictly after completed_on, computed arithmetically for day/week (k = floor((completed_on - due)/step)+1, min 1) and by month index arithmetic for month/year (clamp day-of-month to month end, e.g. Jan 31 + 1 month = Feb 28/29). from_completion: completed_on + interval (month/year clamped the same way).
- urgency(todo: dict, today: date, blocked_count=0, blocking_count=0) -> float. Terms: due: 12 * ramp where ramp = 1.0 if overdue by >=7 days, else linear 0.2 + 0.8*(14 - days_until)/21 for -7<=days_until<=14 (i.e. ~1.0 at 7 days overdue, 0.2 at 14 days out), 0 beyond 14 days or when no due; priority: {1: 6.0, 2: 3.9, 3: 1.8}; age: 2.0 * min(1.0, age_days/365); notes non-empty: +1.0*0.8; project_id set: +1.0; done: return 0.0. Return round(x, 3). Expose DEFAULT_COEFFS dict so it is one place to tune.

Hook: in Todos.update, before the UPDATE, if 'done' in patch and patch['done'] truthy and the existing row has done==0 and a non-empty repeat, then after the UPDATE call self._spawn_next(row, completed_on=date.today()) which does a Todos.create with the same title, notes, project_id, priority, repeat, due=next_due(...), source='local' (NOT 'google', so Tasks sync creates a fresh remote task via the 'never synced' path), notify=False; then fire _changed() once if notify. The completed instance keeps its repeat so history is intact but the spawn is marked by clearing `repeat` on the completed row (UPDATE todos SET repeat=NULL WHERE id=?) so re-completing/un-completing it cannot spawn twice; because the Tasks pull path calls Todos.update(done=True, notify=False) this also fires when completion arrives from Google. Idempotency: un-completing then completing again does nothing since repeat is NULL on that row; document it in the docstring.

API: TodoIn/TodoPatch gain `repeat: dict | None` and `clear_repeat: bool` (mirrors clear_due). GET /todos gains `sort: str = 'due'`; sort=urgency computes todo_rules.urgency in Python over the filtered rows and sorts descending; each returned row gets an `urgency` float when sort=urgency. Tools: todo_add and todo_update gain `repeat_every: int`, `repeat_unit: str`, `repeat_mode: str`; todo_list gains `sort` ('due'|'urgency') and, in its row output, `urgency` and `repeat`. Add one example each to the ToolSpec examples lists (existing style). Settings: none; coefficients are module constants. UI: TodosView add-row gets a small 'Repeat' select (none/daily/weekly/monthly/yearly) writing repeat={every:1,unit,mode:'from_due'}; TodoItem shows a Repeat icon badge with a tooltip; a sort toggle 'Due | Urgency'.

Sync note: Google Tasks has no recurrence, so gtasks.py is untouched; the spawned next instance is just a new local todo and syncs as such. todocal.py mirrors by due date so the next instance gets its own event automatically.

**Tests.** backend/tests/test_todo_rules.py as a plain script (sys.path insert, tempfile Database, __main__ runner like test_todos.py), no network. Cases: next_due from_due daily when due is yesterday and completed today gives tomorrow-or-later strictly after completed_on; due 3 weeks ago with weekly repeat advances to the first Monday-aligned date after today (assert strictly > today and (result - due).days % 7 == 0); monthly Jan 31 -> Feb 28 and leap-year Feb 29; from_completion monthly; every=0 and unit='fortnight' raise ValueError. Todos integration: create todo with repeat, update(done=True) yields exactly one new open todo with the next due and same title/priority/project; completing again (after un-completing) yields no second spawn; completing a non-repeating todo spawns nothing; simulate the sync path with update(id,{'done':True}, notify=False) and assert it still spawns. urgency: overdue > due-tomorrow > due-in-30-days > no-due for equal priority; priority 1 beats priority 3 with equal dates; done == 0.0; ordering of a 5-item fixture is stable and exactly matches a hand-computed expected list. #### todos-2: Todo estimates and a deterministic time-block planner (proposals only) (M)

**Why.** The app owns both todos and the calendar but only mirrors a todo's due date as an untimed/fixed event (todocal.py has no duration or free-time search; calendar_events is only a list). FluidCalendar's open scheduler (due 40 / priority 25 / energy 20 / preferred time 15 weighted slot scoring over free work-hour windows with buffers) and Super Productivity's estimate plus timeline show the mechanism; Reclaim/Motion are the product reference. A pure function over busy intervals is fully testable offline, and keeping output as proposals preserves the ask-first rule for outside writes.

**Files.** `backend/personal_os/planner.py (new: pure slot search + scoring)`, `backend/personal_os/modules/planner.py (new Module: routes + schedule_suggest tool)`, `backend/personal_os/modules/__init__.py (append PlannerModule to build_modules)`, `backend/personal_os/todos.py (estimate_min column + allowed field)`, `backend/personal_os/modules/todos.py (estimate_min in TodoIn/TodoPatch and todo_add/todo_update tool args)`, `backend/personal_os/llm.py (DEFAULT_SETTINGS['planner'])`, `backend/tests/test_planner.py (new)`, `src/renderer/src/components/TodosView.tsx (estimate input, 'Plan my day' button + proposal list)`, `src/renderer/src/lib or api client file that defines api.google.* (add api.planner.suggest/apply)`

**Design.** Schema: Todos.__init__ ALTER loop gains `estimate_min INTEGER` (NULL = unknown, treated as 30 by the planner) and add 'estimate_min' to the allowed set in Todos.update; create() gains optional estimate_min kwarg.

Settings: add to llm.DEFAULT_SETTINGS (otherwise PUT /settings drops it): `"planner": {"workStart": "09:00", "workEnd": "17:30", "workDays": [1,2,3,4,5], "bufferMin": 10, "minBlockMin": 15, "maxBlockMin": 120, "slotStepMin": 15, "lookaheadDays": 7, "calendarName": "Grain Todos"}` (follow the googleTodoCalendar pattern: PlannerModule.config() merges stored with defaults and ignores unknown keys; a PUT /planner/config route validates ranges).

planner.py pure API (no Google, no db, no clock reads; `now` and tz-naive local datetimes injected):
- `Busy = tuple[datetime, datetime]`; `free_windows(busy: list[Busy], now: datetime, cfg) -> list[tuple[datetime, datetime]]`: for each day in lookahead that is in workDays, window = [workStart, workEnd] clipped to >= now; subtract busy intervals each padded by bufferMin on both sides; merge; drop windows shorter than minBlockMin.
- `busy_from_events(events: list[dict]) -> list[Busy]`: take rows as returned by Google.calendar_events (`start`, `end`, `all_day`, plus whatever the row exposes for transparency/RSVP; check _event_out), skip all-day events, skip events with transparency 'transparent' or the user's own RSVP 'declined', and skip events on the mirror calendar named cfg.calendarName so the planner does not block against its own earlier proposals' accepted events being re-planned (those are re-planned as locked, see below).
- `score_slot(todo, start, end, now, cfg) -> float` = 0.40*due_score + 0.25*priority_score + 0.20*energy_score + 0.15*time_pref_score, each in [0,1]. due_score: 1.0 if the slot ends before due (end-of-day of due date) and falls on the earliest such day, decaying by 0.15 per extra day of slack, 0.0 if the slot ends after the due date (such slots are also excluded as hard-infeasible unless the todo has no feasible slot, in which case return it as an `overdue_unschedulable` item). priority_score: {1:1.0, 2:0.6, 3:0.3}. energy_score: no energy field exists yet, so use title/notes-free heuristic: estimate_min>=60 prefers morning (start hour < 12 -> 1.0 else 0.4); shorter tasks prefer afternoon (inverse). time_pref_score: 1.0 for earlier-in-day start for priority 1, flat 0.5 otherwise. Keep all weights in a WEIGHTS dict.
- `plan(todos: list[dict], busy: list[Busy], now, cfg, locked: list[Block] = []) -> {'blocks': [Block...], 'unplaced': [{id, reason}]}`: sort todos by todo_rules.urgency desc if todos-1 exists else (due, priority); drop done or due-less-and-unestimated? (no: due-less todos with an estimate are placed best-effort); greedy: for each todo, duration = clamp(estimate_min or 30, minBlockMin, maxBlockMin); enumerate candidate starts on slotStepMin boundaries inside each free window that fit duration; pick the max-score candidate (ties earliest); subtract the chosen block plus buffer from the free windows and continue. Todos longer than maxBlockMin are split into ceil(est/maxBlockMin) blocks that are scored independently and tagged part i/n. Locked blocks (already accepted events) are treated as busy. Deterministic: same input gives identical output.
- Block = {todo_id, title, start, end, score, part:[i,n]} with ISO local strings.

PlannerModule (modules/planner.py, key='planner', label='Planner'): constructs from ModuleContext; shares the same Todos table via `Todos(ctx.db)` (a second Todos instance on the same db is how other modules coexist; or look up the todos module with modules.get). Routes: GET /planner/config, PUT /planner/config; POST /planner/suggest body {days?: int, project_id?: str} -> fetches events via `google.calendar_events(days, 'primary', 100, None, ['all'])` in a thread (asyncio.to_thread; GoogleNotConnected -> 409 with message), builds busy, loads open todos, returns plan(); POST /planner/apply body {blocks: [Block...]} -> for each block calls `google.calendar_create({'summary': f'Focus: {title}', 'start': start, 'end': end, 'description': 'Planned by Grain from todo <id>', 'transparency': 'opaque'}, calendar_id=<todocal target calendar or planner calendarName ensured via google.calendar_ensure>, send_updates='none')` and returns per-block verify verdicts (the existing verify gating in calendar_create applies; an unverified result is reported as failed, never ok). The apply route is the user's explicit approval; the agent tool never writes. Tool `schedule_suggest(days=5)` (group 'google', read-only, no 'external' danger tier) returns the proposal list text-ready (title, start, end, why) and the tool description tells the model to present it and let the user press Plan/Apply in the UI or explicitly confirm; it must not call calendar_create. Add `schedule_suggest` to the REFUSAL/alternative map in tools.py only if the maps there require every tool to have an entry (check the dict near line 89); keep tools.py edits to that single entry.

UI: TodosView gets an estimate input (minutes) on each item and a 'Plan my day' button opening an inline proposal list (checkboxes, per-block 'why' tooltip = score breakdown) with an 'Add selected to calendar' button that POSTs /planner/apply. Blocks the user unchecks are simply dropped.

**Tests.** backend/tests/test_planner.py, plain script, no network, no model. Pure-function cases with fixed `now` (e.g. Mon 2026-10-05 08:00) and a cfg fixture: free_windows subtracts a 10:00-11:00 meeting with 10-min buffers into [09:00-09:50] and [11:10-17:30]; windows before `now` are clipped; weekends skipped; windows under minBlockMin dropped; all-day, transparent and declined events are ignored by busy_from_events. plan(): a priority-1 todo due tomorrow with estimate 90 lands on the earliest feasible slot today or tomorrow before its due date end-of-day and never overlaps busy or buffer; two todos never overlap each other; a 200-minute todo with maxBlockMin 120 yields two blocks tagged part 1/2 and 2/2; a todo whose due date has no feasible slot appears in unplaced with reason 'no_slot_before_due'; determinism (call twice, assert equal); locked blocks are respected. Module tests with a stub google object (class with calendar_events returning canned rows, calendar_create recording calls and returning {'id':..., 'verified': True}) and a tempfile Database: POST /planner/suggest returns blocks and performs ZERO calendar_create calls; POST /planner/apply with two blocks makes exactly two create calls with the expected summary/start/end and surfaces a failed verify verdict as an error entry. Settings: PUT /settings keeps the `planner` key (assert it is in llm.DEFAULT_SETTINGS). Run with `backend/.venv/bin/python backend/tests/test_planner.py`.

**Done when.** With todos carrying estimate_min and a stubbed week of meetings, POST /planner/suggest returns non-overlapping, buffer-respecting blocks inside work hours and before each due date, deterministically; nothing is written to Google until POST /planner/apply is called by the UI; the schedule_suggest tool is read-only; the planner settings key survives PUT /settings; the new test passes and test_todocal.py, test_todos.py, test_google_datetime.py still pass.

#### mail-1: Reply tracker: needs-reply / awaiting-reply thread status with follow-up proposals (M)

**Why.** There is no thread model: google.py has no threads.get, MailView only lists messages, and nothing tells the user which sent emails are unanswered or which received ones need a reply (docs/research.md L7 is still open). Inbox Zero's Reply Zero keeps four statuses (TO_REPLY, AWAITING_REPLY, FYI, ACTIONED) per thread, scans all messages for questions/requests and who promised what, and skips FYI when the user sent last (PR #3787). A header-heuristic classifier with an optional stubbed LLM refinement delivers most of the value offline and stays read-only and proposal-only.

**Files.** `backend/personal_os/mailwatch.py (new: classifier + store)`, `backend/personal_os/modules/mailwatch.py (new Module: routes, tool, today())`, `backend/personal_os/modules/__init__.py (append MailWatchModule to build_modules)`, `backend/personal_os/google.py (add gmail_threads_recent + _gmail_thread_meta, nothing else)`, `backend/personal_os/llm.py (DEFAULT_SETTINGS['mailWatch'])`, `backend/tests/test_mailwatch.py (new)`, `src/renderer/src/components/MailView.tsx (status filter chips: Needs reply / Awaiting reply)`, `src/renderer/src/components/TodosView.tsx or Today card (optional: show suggested follow-ups; keep UI small)`

**Design.** google.py (only additive): `gmail_threads_recent(self, query: str = 'newer_than:14d -category:promotions -category:social -in:spam', max_threads: int = 40) -> list[dict]` cached under the existing 'gmail' namespace with a new TTL['gmail_threads']=120 key. Implementation: users().threads().list(userId='me', q=query, maxResults=...) then a batched users().threads().get(userId='me', id=tid, format='metadata', metadataHeaders=['From','To','Cc','Subject','Date','List-Unsubscribe','Auto-Submitted','Precedence']) like gmail_search does with new_batch_http_request; returns [{'thread_id', 'subject', 'messages': [{'id','from','to','date'(iso via _rfc2822_iso),'labels','snippet','auto': bool}]}] ordered oldest to newest, where auto=True when List-Unsubscribe, Precedence in (bulk, list, junk) or Auto-Submitted != 'no' is present. Add `_me()` helper that returns the connected address from the existing status()/profile settings the class already caches (read how status() gets the email; do not add a new API call per thread).

mailwatch.py pure classifier: `classify(thread: dict, me: str, now: datetime, cfg) -> {'status': 'to_reply'|'awaiting_reply'|'fyi'|'actioned', 'reason': str, 'age_days': float, 'last_from': str}` with deterministic rules in this order: (1) if last message is from me: status awaiting_reply only if the thread contains a question signal in my last message (a '?' in snippet, or request phrases from a small list: 'let me know', 'can you', 'could you', 'please confirm', 'when are you'), else actioned; (2) if last message is from someone else: if auto=True or sender local-part in (noreply, no-reply, donotreply, notifications, mailer-daemon) -> fyi('automated'); else if snippet has a question/request signal or the thread is directly addressed to me (me in To, not only Cc) and I have never replied in it -> to_reply; else fyi; (3) if I replied after the last question from them -> actioned. Mirror Inbox Zero's rule that when I sent last, fyi is not a possible outcome (assert in code and test). Optional LLM refinement: `refine(threads_with_status, llm_fn)` is only invoked when cfg['useLLM'] is true AND a callable is injected; it receives only subject, sender domain and snippet (no bodies) to keep data minimal, returns a status per thread from the same four values via a JSON schema, and any parse error or unknown value falls back to the heuristic result. The default is useLLM=false so nothing leaves the machine and tests never need a model. Reuse the app's existing llm.complete-style helper by injection only: the Module takes `llm_fn: Callable|None=None` and the app wiring (ModuleContext has no llm; leave None by default, document the hook).

Store: table `thread_status(thread_id TEXT PRIMARY KEY, subject TEXT, status TEXT, reason TEXT, last_msg_id TEXT, last_from TEXT, last_date TEXT, age_days REAL, dismissed INTEGER DEFAULT 0, followup_todo_id TEXT, updated_at REAL)` created with CREATE TABLE IF NOT EXISTS in MailWatch.__init__ (same style as todos.py SCHEMA). `refresh(threads)` upserts and, when the thread's last_msg_id changed since the stored row, resets dismissed=0 (new activity un-dismisses). Dismiss is per-thread via PUT.

Settings: llm.DEFAULT_SETTINGS['mailWatch'] = {'enabled': True, 'awaitingAfterDays': 3, 'needsReplyAfterHours': 24, 'useLLM': False, 'query': 'newer_than:14d -category:promotions -category:social', 'proposeFollowups': True}; MailWatchModule.config() merges and ignores unknown keys (googleTodoCalendar pattern).

Module: key='mailwatch'. Routes: GET /mail/watch?status=to_reply|awaiting_reply (reads the table, no Google call), POST /mail/watch/refresh (runs gmail_threads_recent in asyncio.to_thread, classifies, upserts; GoogleNotConnected -> 409), PUT /mail/watch/{thread_id} {dismissed: bool}, GET/PUT /mail/watch/config. today() returns {'mail_watch': {'to_reply': n, 'awaiting_reply_overdue': n}} from the table only (must not call Google, per Module.today contract). No background loop: refresh is on-demand from the UI and from the tool (no heartbeat per anti-goals; a later job can call the route). Tool `mail_followups(kind='awaiting_reply'|'to_reply', limit=10)` read-only, refreshes then lists rows with thread_id, subject, last_from, age_days, reason; wrap sender and subject strings as untrusted data the same way gmail_search results are (follow the convention used by the existing gmail_search tool in tools.py). Follow-up proposals: for awaiting_reply rows older than awaitingAfterDays with no followup_todo_id, `propose_followups()` returns suggested todo dicts {title: 'Follow up: <subject>', notes: link/thread id, due: today}; a POST /mail/watch/{thread_id}/followup creates the todo through Todos.create (a local in-app write) and stores followup_todo_id, so creation is explicit and idempotent. The module never labels, archives, drafts or sends.

UI: MailView adds two status chips (Needs reply n / Awaiting reply n) above the list that call GET /mail/watch and render rows with age; row actions: Open thread, Dismiss, Add follow-up todo.

**Tests.** backend/tests/test_mailwatch.py, plain script, no network, no model. Fixtures are hand-built thread dicts (the gmail_threads_recent output shape) and a fixed `now`, me='me@x.com'. classify: other-person last message with '?' and me in To -> to_reply; newsletter (auto=True) -> fyi/automated; noreply@ sender -> fyi; my last message with 'let me know' -> awaiting_reply with age computed; my last message 'Thanks!' -> actioned; invariant: when last_from == me the status is never 'fyi' (loop over a generated set of 30 variants); thread where I replied after their question -> actioned. Store: refresh upserts; a new last_msg_id resets dismissed; dismissed rows are excluded from GET filtered lists; app restart (new MailWatch on same tempdir Database) retains rows. Settings: awaitingAfterDays=3 gates propose_followups (2-day-old awaiting row excluded, 4-day included); POST followup creates exactly one todo and a second call is a no-op returning the same todo id; 'mailWatch' key present in llm.DEFAULT_SETTINGS. LLM refinement: with a stub llm_fn returning a valid status the result overrides the heuristic; stub returning garbage or raising falls back to the heuristic; useLLM=False never calls the stub (assert call count 0); the stub receives no body text (assert payload keys are only subject/domain/snippet). Module routes via a stub google object whose gmail_threads_recent returns the fixtures and whose other attributes raise AssertionError if touched (proves read-only: no modify/send/draft calls). today() makes zero google calls. Run with `backend/.venv/bin/python backend/tests/test_mailwatch.py`.
