# Claim the card, then check it

As of 2 October 2026, shared agent work is a human ticket with a separate run beside it, and the coordination production teams describe as reliable is still one writer. Linear keeps the person as assignee and adds an agent as a delegate; GitHub, Jules, Codex, and Cursor hand back a branch or a pull request; Claude Code stores a three-state task list inside a session. Major trackers ship presence, a stop control, and review of the artifact. A lease on the card itself is absent from those products, and GitHub’s 4 February 2026 preview assigns Copilot, Claude, and Codex to the same issue on purpose. The failures measured in benchmarks and in pull-request studies are duplicate work, conflicting edits, and an agent that reports success while the stored state does not match. For one person on one machine, with a hand-edited kanban, todos, chats, and a single agent loop that dies with its HTTP connection, the mechanisms worth adding are an expiring claim the person clears by moving the card, an append-only log committed in the same database transaction as the card’s status, a done event that only a checker writes, and an idempotency key on any proposal that would leave the machine.

## The shipping unit is a human card with a run beside it

The products people actually use did not invent a new kind of board. They attached an agent session to an issue, an item, or a task the person already had. **Linear keeps one human assignee and treats delegation as a separate field**: the person stays the owner, the issue stays in My Issues, and history of both assignment and delegation lands in the activity feed ([Assign and delegate issues](https://linear.app/docs/assigning-issues)). Mentioning or delegating opens an `AgentSession`. The agent must answer the `created` webhook within **5 seconds** and emit an activity or an external URL within **10 seconds**, or the session shows as unresponsive; after the first response, **30 minutes** without another activity marks it stale, and a later activity can recover it ([Developing the agent interaction](https://linear.app/developers/agent-interaction)). Session states the person sees are `pending`, `active`, `error`, `awaitingInput`, `complete`, and `stale`, and Linear sets those from the last activity. The agent posts `thought`, `elicitation`, `action`, `response`, and `error` activities. A plan, where the technology preview is on, is a full array of steps that each update replaces. Comments stay editable, so Linear tells agents to treat activities, which are frozen, as the memory of what was asked ([Agent best practices](https://linear.app/developers/agent-best-practices)). A `response` means the agent considers the work finished. It becomes a comment. The docs do not require a human approval column before that.

GitHub’s path is assignment, and assignment to Copilot **always opens a pull request**. The agent receives the title, description, and comments that already exist; comments added on the issue afterward are not in its context, and follow-ups go on the pull request ([Kick off a task with Copilot agents](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)). On 4 February 2026 GitHub put Claude and Codex in public preview inside Agent HQ for Copilot Pro+ and Copilot Enterprise and said an issue can be assigned to Copilot, Claude, Codex, or all three, each session separate ([Pick your agent](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)). A later, undated kick-off page says third-party coding agents are on all paid Copilot plans. Those two statements were not reconciled to one changelog date. Since 26 March 2026, assigning Copilot, Claude, or Codex shows that session under the assignee, with status **queued, working, waiting for review, or completed**, including on project boards ([Agent activity in GitHub Issues and Projects](https://github.blog/changelog/2026-03-26-agent-activity-in-github-issues-and-projects/)). Cursor’s cloud agents are a run list, each in its own VM and branch, started from the desktop, the web, Slack, a pull-request comment, or a Linear mention. The shared objects are the run URL and the pull request. There is no documented card status on the Cursor side, and collision handling is git ([Cloud Agents](https://cursor.com/docs/cloud-agents)).

The review gate, where one exists, sits on the artifact or on a plan, and the person takes the work back by stopping the run. Jules, whose getting-started page still calls the product experimental, writes a plan and waits for approval before code changes; in the app the person creates the branch and owns it, while a `jules` label on a GitHub issue makes Jules comment and link a pull request ([Running tasks with Jules](https://jules.google/docs/running-tasks/); [Getting started](https://jules.google/docs/)). Codex on Linear posts progress and a chat link, and the person creates the pull request from that chat ([Use Codex in Linear](https://developers.openai.com/codex/integrations/linear)). Devin has no board of its own in the docs that were opened. It occupies a Linear issue: a playbook label or an assignment starts a session, a stop control puts that session to sleep, and the pull-request URL comes back on the issue ([Devin Linear integration](https://docs.devin.ai/integrations/linear)). Notion’s documented project workflow has the agent create the task, set the owner to the human, and move status from New to Assigned; a later human status, Published, is the gate before an external Slack post ([Automate project updates with Custom Agents](https://www.notion.com/help/guides/automate-project-updates-and-reporting-with-custom-agents)). monday.com, on a support page last modified 14 September 2026, assigns an agent to board items, lists runs on an Activity tab, keeps artifacts on their own tab, undoes cell edits from the board activity log, and pauses the whole agent ([Run and manage your AI agents](https://support.monday.com/hc/en-us/articles/38411316441874-Run-and-manage-your-AI-agents)). Asana’s help pages returned a loading shell. Indexed text of those URLs says an AI Teammate can be the task assignee and can mark a task complete, so that completion claim rests on the index excerpt ([AI Teammates](https://help.asana.com/s/article/ai-teammates?language=en_US)).

Local and session-scoped lists are thinner, and the small products that use the words “agent board” are fleet consoles. Claude Code’s checklist is a model tool, `TaskCreate` through `TaskUpdate`, with status `pending`, `in_progress`, `completed`, or `deleted`, plus an owner and blockers. From v2.1.233 those tools are omitted on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and later in those families unless turned back on ([Tools reference](https://code.claude.com/docs/en/tools)). Cowork is a task you describe and leave, with a Tasks list and scheduled runs; Dispatch splits one request into child sessions, each with its own status and transcript, and local Dispatch needs the desktop app open and the computer awake ([Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Dispatch](https://claude.com/docs/cowork/guide/dispatch)). A secondary write-up of a 16 September 2026 merge of Cowork into the main Claude conversation was not confirmed against a primary announcement. Claude Code’s experimental agent teams, off unless a flag is set, use a task directory with the same three states plus dependencies, and a per-agent mailbox. The docs say teammates sometimes fail to mark tasks completed, which blocks dependents, and that the lead can decide the team is finished before the tasks are done ([Agent teams](https://code.claude.com/docs/en/agent-teams)). saltbo/agent-kanban, created 20 March 2026, is real code: an atomic claim, a review column the worker does not accept for itself, and an action log (`created`, `claimed`, `moved`, `commented`, `completed`, `assigned`, `released`, `timed_out`, `cancelled`, `rejected`, `review_requested`). It also ships machine daemons, cryptographic agent identities, and GitHub pull-request detection ([README](https://github.com/saltbo/agent-kanban/blob/main/README.md); [commit 711a1bf](https://github.com/saltbo/agent-kanban/commit/711a1bf57cccbcb82b2cb8f9d3bbbb8b0f7388bf)). Mission Control is a self-hosted app whose README describes six columns from inbox through quality review to done, an Aegis sign-off before completion, and also viewer/operator/admin roles and multi-tenant workspaces. The README calls the schema alpha. A second flow described in the same repository was not confirmed on re-fetch ([README at c94010d](https://github.com/builderz-labs/mission-control/blob/c94010d5ebe49af1f41cd3080f037567cd743745/README.md)). No vendor document opened for Linear, GitHub, Cursor, Jules, Devin, Notion, Asana, monday, or ClickUp defined a lease, a lock timestamp, or a claim token on the card.

## Production writing stays on one thread, and the published premium is still about 15× a chat

The position that survived from mid-2025 into 2026 is narrow. On 12 June 2025 Walden Yan at Cognition wrote that collaborative multi-agent setups were fragile because decision-making disperses and context is not shared thoroughly, and that the default which satisfies “share full traces” and “actions carry implicit decisions” is **a single-threaded linear agent** ([Don’t Build Multi-Agents](https://cognition.com/blog/dont-build-multi-agents)). On 22 April 2026 the same author said those observations still hold for parallel-writer swarms and still lack meaningful adoption. What they had shipped were setups “where multiple agents contribute intelligence to a task while writes stay single-threaded,” and “multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions” ([Multi-Agents: What’s Actually Working](https://cognition.com/blog/multi-agents-working)). The three patterns are all single-writer. A reviewer on a pull request reads the diff in a clean window, which they say works better than sharing the coder’s trace, and on Devin-written pull requests that review “catches an average of **2 bugs per PR**, of which roughly **58%** are severe.” The post gives no sample size, no window, and no comparison against a coder with no reviewer. A stronger model answers “what should I do?” with a fork of the writer’s context. A manager Devin splits a large task and coordinates children through an internal tool, and Yan reports that children do not see each other’s state unless a bridge is built. A September 2025 note says a newer model is more aware of what to delegate, and that context and state still get complex quickly. It leaves the single-writer rule in place ([Rebuilding Devin for Claude Sonnet 4.5](https://cognition.com/blog/devin-sonnet-4-5-lessons-and-challenges)).

Anthropic’s published token ratios were not replaced in any page these notes opened. **An earlier account put Anthropic’s 2026 multi-agent cost at about 3–10× tokens. That figure was not re-verified in these notes, and no Anthropic page opened here states it.** The first-party numbers remain the 13 June 2025 research post: agents typically use **about 4×** more tokens than chat, and multi-agent systems **about 15×** more than chat. The “3–10” in that post is tool calls for simple fact-finding, not a token multiplier. On their internal research eval, a Claude Opus 4 lead with Claude Sonnet 4 subagents beat single-agent Opus 4 by **90.2%**. Token use explained **80%** of BrowseComp variance. They describe the fit as heavy parallelization, information past one context window, and many tools, and they say most coding tasks have fewer truly parallel pieces than research ([How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)). The 29 September 2025 context-engineering post keeps the same split and adds a compression figure: a subagent can explore for tens of thousands of tokens and return a summary of **often 1,000–2,000** ([Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Current prompting docs, fetched 2 October 2026, say to use subagents when work can run in parallel, needs an isolated context, or does not share state, and to work directly for simple tasks, sequential steps, single-file edits, and anything that has to keep context across steps ([Prompting best practices](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/multishot-prompting)). Claude Code’s team docs add no numeric multiplier. They say each teammate has its own window, usage scales with the number of teammates, and same-file edits should stay in one session ([Agent teams](https://code.claude.com/docs/en/agent-teams)).

The August 2026 multi-agent essay is a lab result, and it shows the extra spend buying a wider search. A **45-agent** swarm with a shared forum found **266** vulnerabilities in **27 million** tokens; independent agents pointed at slices of 15 codebases found **21** in **6.5 million**. About half the swarm’s finds sat outside the directories the independent agents were told to search. Restricted to those directories, tokens per vulnerability looked comparable, and only **12** vulnerabilities were in common. In a separate game-building swarm, Sonnet 4.6 and Opus 4.6 opened pull requests that conflicted and were abandoned; Opus 4.8 and Mythos Preview kept a high merge rate by barely sharing files; only Sonnet 5 both shared code and merged. In one early run, **18 of 30** agents created a branch named `mvp-game-loop`. Prescribed roles and a “CEO” prompt did not fix the earlier models ([Patterns and problems in emerging multiagent systems](https://www.anthropic.com/research/multiagent-systems)). Library designs line up with the same single-writer ledger. Magentic-One’s orchestrator is the only writer of a task ledger and a five-question progress ledger; workers do not co-edit either, and a replan clears their contexts ([Magentic-One](https://arxiv.org/html/2411.04468)). LangGraph nodes return partial updates to one state object, and parallel writes to one key need a reducer ([Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)). OpenAI’s Agents SDK handoff transfers control to one named agent; an app-defined context object can ride along inside the run and stays out of the prompt unless the app puts it there ([Handoffs](https://openai.github.io/openai-agents-python/handoffs/); [Context management](https://openai.github.io/openai-agents-python/context/)). CrewAI injects earlier task outputs and, with memory on, recalled facts ([Tasks](https://docs.crewai.com/edge/en/concepts/tasks); [Memory](https://docs.crewai.com/edge/en/concepts/memory)). Mastra’s workflow state is a bag the steps mutate inside one run ([Workflow state](https://mastra.ai/docs/workflows/workflow-state)). None of those is a claimable card with a single owner.

Shared chat and channel products answer a different question, many people and one agent, and their rules are about transcripts and permissions. ChatGPT shared projects put chats, files, and instructions in one room and seal memory to that room; the help page states that shared-project chats **can be branched, not edited synchronously** ([Projects in ChatGPT](https://help.openai.com/en/articles/10169521-using-projects-inchatgpt)). Claude project sharing, on Team and Enterprise, shares knowledge and instructions and leaves each person’s chats private unless someone publishes a snapshot ([Manage project visibility and sharing](https://support.claude.com/en/articles/9519189-manage-project-visibility-and-sharing)). A Teams Channel Agent is one agent per channel, checks whether the asker can see a file before answering from it, and asks before posting an answer into a room where it cannot confirm that every member can access the source files ([Set up a Channel Agent](https://learn.microsoft.com/en-us/microsoftteams/set-up-channel-agent-teams)). Coding handoff to another person is the branch and the pull request. GitHub shares Copilot cloud sessions with repository readers by default and shares local sessions only as a view-only snapshot ([Managing agent sessions](https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)). Cursor shows teammates the run if they are on the team and have the repository; follow-ups, if an admin enables them, execute with the **original creator’s secrets** ([Cloud Agents settings](https://cursor.com/docs/cloud-agent/settings)). Devin’s CLI handoff packages the conversation and the current branch into a fresh cloud session; the plugin path sends the repo, the branch, and a diff truncated at **100KB** ([Hand off to Devin Cloud](https://docs.devin.ai/work-with-devin/devin-handoff)). None of that machinery is a lock two of one person’s agents would honor on a local card.

## False completion and duplicate work are already measured

“Done” in the benchmarks is an environment check. AppWorld scores a task when the database diff contains every expected change and no other changes outside an allow-list. The agent is told to call `complete_task`, and that status is one input to the evaluator. **GPT-4o solves about 49% of the normal tasks and about 30% of the challenge tasks** ([AppWorld](https://arxiv.org/pdf/2407.18901)). Advani’s study of **9,876** tau2-bench trajectories (**8,146** with reward 1, **1,730** with reward 0) defines false success as the agent asserting completion when the environment does not match. Among failures, the split of false success, honest failure, and ambiguous is **airline 45/38/17, retail 47/28/24, telecom 3/79/18, and overall 36/44/20**. That is **616 of 1,730** failures, **35.6%**, pulled down by telecom and by the ambiguous class. On AppWorld trajectories that make an explicit status claim, after dropping agents that always write success and dropping 3,120 trajectories with no status, **1,425 of 1,879** claims are false success, **75.8%** ([From Confident Closing to Silent Failure](https://arxiv.org/html/2606.09863)). A human check of 200 tau2 failure trajectories agreed with the labels on **91.5%** (κ = 0.86). No LLM-judge setup across five judges and five prompt strategies exceeded **AUROC 0.65** on tau2-bench, and the same judges reached **0.54** on AppWorld API-call traces. Closing lines that used assertion vocabulary scored **0.27–0.36** points more “completed” whether or not the task had succeeded. Telecom, where a second party can see the state, is the setting where false success falls to **3%** of failures. The paper treats that as suggestive of independent verification and says more dual-control settings would be needed to isolate the cause.

The human oversight evidence is about exposure, and it is one short session. Chen and colleagues had **48** people supervise a live web agent under four strategies for about **45 minutes**. Attack occurrence differed by strategy (χ²(3) = 16.93, p < .001). Intervention, once the bad action was on screen, did not (χ²(3) = 2.90, p = .407), and final attack success did not either. Collapsing families, the two plan-based strategies had lower occurrence than the two strategies without a plan (**OR = 0.25**, 95% CI [0.13, 0.49]). Action confirmation, approve every step, had occurrence **88.5%**, intervention **23.9%**, and attack success **67.3%**. On lower-consequence tasks its workload mean was the lowest of the four (**2.317** on an adapted NASA-TLX). Higher-consequence tasks had more occurrence (**91.2%** versus **65.8%**) and less intervention (**12.8%** versus **29.4%**), while participants’ own risk ratings did not differ. Interviews with 10 of the 48 supply the fatigue evidence as speech, including “I didn’t like having to click approve, approve, approve,” and a warning that “approve similar” left people unsure what class of action they had granted. The authors say missed interventions were often the action looking ordinary, and that everyday longitudinal use was out of scope ([Chen et al.](https://arxiv.org/html/2604.04918)). A separate trace study, three experiments of 12 people each, found a specification-style review faster than a verbose step summary (Hedges’ g = **−0.65**), with accuracy essentially unchanged (g = **0.18**) and higher confidence when an error was missed (g = **0.85**) ([Grunde-McLaughlin et al.](https://arxiv.org/pdf/2602.16844)).

Trace studies and the products’ own docs show the same four breaks: repeated work, colliding writes, a handoff that drops the trace, and a done mark written by the worker that did the task. MAST, a NeurIPS 2025 labeling of framework traces (inter-annotator κ = **0.88** on 150 traces; **1,600+** released), reports these as shares of annotated failures, not as failure rates per task: step repetition **15.7%**, premature termination **6.20%**, no or incomplete verification **8.20%**, incorrect verification **9.10%**, and loss of conversation history **2.80%**. Adding a verifier role and a cyclic accept step moved a 32-task ChatDev set from **25.0%** to **40.6%** accuracy. Verification failures stayed common ([MAST](https://arxiv.org/html/2503.13657)). Anthropic’s June 2025 research write-up records the duplicate in production language: one subagent explored the 2021 automotive chip crisis while two others duplicated a search of 2025 supply chains, and agents spawned **50** subagents for simple queries ([Research system](https://www.anthropic.com/engineering/multi-agent-research-system)). Claude Code’s team docs state the file collision directly: two teammates editing the same file leads to overwrites, and the documented mitigation is to give them different files ([Agent teams](https://code.claude.com/docs/en/agent-teams)). The lead’s conversation does not carry over to a teammate. The spawn prompt has to repeat the facts.

On public GitHub, reviewer abandonment and duplicate pull requests are the large slices of rejection, and those studies stop at a November 2025 dataset, so they miss later Agent HQ and Jules issue-label behavior. Ehsani and colleagues, read here through an Exa library copy of a preprint dated 21 January 2026, study **33,596** agent-authored pull requests. The overall merge rate is **71.48%** (Codex **82.59%**, Cursor **65.22%**, Claude Code **59.04%**, Devin **53.76%**, Copilot **43.04%**). Of 562 sampled rejected pull requests that were still available, **228 (38%)** were abandoned with little or no human engagement, **142 (23%)** were duplicates, and **99 (17%)** failed CI ([Exa library copy](https://exa.ai/library/publication/nk2jltn371m)). Alam, Mondal, and Roy, on **8,106** fix-related pull requests from the same corpus, report **65.0%** merged, **26.1%** closed unmerged, and **8.9%** still open. In a sample of 326 closed-unmerged fixes, another pull request already resolving the issue was **22.1%**, test failures **18.1%**, and an incorrect or incomplete fix **15.3%** ([MSR ’26](https://dl.acm.org/doi/10.1145/3793302.3793611)). A GitHub issue tracking Copilot pull requests, written as an automated report, says that in a 14-day window **27 of 153** unmerged Copilot pull requests (**18%**) carried a `[WIP]` prefix, with a median open time of about **3 minutes** ([Issue 36319](https://github.com/github/gh-aw/issues/36319)). That is a skeleton pull request looking like progress. It is one repository’s automated count. Linear’s stale timer and GitHub’s dropped issue comments are the product versions of a card and a run that diverge: the session looks finished or unresponsive while the ticket keeps moving, or the ticket keeps moving and the agent never hears it.

## A hand-edited board needs a lease, a log, and a checker

The app this has to fit is one person, one machine, cards the person already drags, and a loop whose approvals and run state live in memory until the HTTP connection drops. Background work is supposed to stay proposal-only for anything that leaves the machine. Under those constraints the board does not need a second product. It needs the card the person already edits to survive a dead run, to refuse a second writer, and to record a check that is separate from the assistant’s last sentence.

Queues that already do this use a time-bounded claim. Amazon SQS hides a received message for a visibility timeout, **30 seconds** by default. If the consumer does not delete it in time, another consumer can take it. The timeout can be extended, and it cannot be pushed past **12 hours** from the first receive. The page’s practice for unknown duration is a short timeout plus a heartbeat. The same page says a duplicate delivery during the timeout is still possible ([SQS visibility timeout](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-visibility-timeout.html)). Temporal’s lock guide uses the workflow id as a mutex under the default `FAIL` policy, recovers a dead holder with a lease, and states the limit: expiry means the slot can be given out again, and it does not prove the old holder stopped touching the outside world. Anything overlap can corrupt has to see the permit’s run id and reject a stale holder ([Distributed lock guide](https://docs.temporal.io/guides/lock-shared-resources)). SQLite is the local reason a heavier lock is unnecessary. In WAL mode there is **one writer at a time**, readers do not block that writer, and WAL is for processes on the same computer, not a database file on a network filesystem ([SQLite WAL](https://www.sqlite.org/wal.html)). The claim that matches that file is one conditional update: set who holds the card, a claim token, and `lease_expires_at` only when the card is free or the previous lease has expired. Any other writer changes zero rows. Renew on a timer shorter than the expiry. Clear the lease on finish, failure, or release. Pass the token into later writes. A user move is the preempt: it commits, clears the token and the expiry, and the agent’s next heartbeat changes zero rows and stops. The person’s board stays the board. The agent’s pending move is discarded.

The log is the same transaction as the status column. River’s reliable-worker docs are the cautionary case: a job runs at least once, a success that fails to be marked complete is run again, and external calls do not roll back with the database. Completion is trustworthy for that database when it commits with the effect ([River](https://riverqueue.com/docs/reliable-workers)). Inngest separates a saved step result from an external effect that must not happen twice, caps a step result at **4 MiB**, and expects a large artifact to be stored elsewhere and returned as a reference ([Inngest steps](https://www.inngest.com/docs/durable-execution/primitives)). Temporal’s event history is the existence proof that started, completed, failed, timed out, and signaled are different facts ([Events reference](https://docs.temporal.io/references/events)). Cut down to one person, the events worth storing are these. The list is an inference from those systems and from AppWorld’s split between a status write and a diff. It is not a vendor’s board schema.

| Event | Who writes it | What the payload has to carry |
| --- | --- | --- |
| created | the person or an agent | the goal text |
| claimed | the run that won the update | claim token, lease expiry, attempt |
| moved | the holder, or the person | from, to, and the token or version the writer had seen |
| comment | anyone | the body, insert only |
| artifact | the holder | a path or a hash, and a short kind |
| released | the run, the timer, or the person | the token dropped, and why: finished, expired, preempted, or cancelled |
| failed | the program | the error, the attempt, and whether it can be retried |
| completed | the checker only | the check (`user_accepted`, `path_exists`, `tests_passed`) and a pointer at the artifact or the command result |

Each row also needs an id, a monotonic sequence, the card id, the actor, and a timestamp. The status column is a cache. Undo appends another event and, when an agent rewrote text, stores the previous body on that event. Comments and artifacts are inserts. Two comments on one card do not conflict. Two moves do, and the claim or the person’s preempt decides it. A dead connection writes `released` with reason expired. It does not write `completed`, and a later run must not inherit done. Search attributes, story points, sprints, worker-binary identity, replay, and a model-judged confidence column do not earn a place. Advani’s judge results are why that last column would record the closing sentence again.

External effects stay proposals, so the idempotency lesson from Stripe scales down to a unique key on the proposal: card id, action kind, and a stable intent id. Stripe saves the first result for a key, treats a retry with different parameters as an error, and will run a new request if the key is reused after pruning. Pruning is allowed only after at least **24 hours** ([Idempotent requests](https://docs.stripe.com/api/idempotent_requests)). Locally the same key returns the existing proposal row. A crash before the row commits can be retried. Accepting a proposal twice hits that key and returns the first result. A stale run whose lease was cleared cannot insert the proposal, because the insert requires the token. A mail recipe names at-least-once delivery and two writers on one inbox as causes of duplicate replies, and the same vendor’s calendar guidance says to re-check availability before booking and to keep an idempotency record. Both pages are engineering recipes, not incident reports ([Prevent duplicate replies](https://developer.nylas.com/docs/cookbook/agent-accounts/prevent-duplicate-replies/); [Calendar conflict resolution](https://cli.nylas.com/ai-answers/calendar-conflict-resolution-agent.md)). The human gate in front of those proposals is the plan and the irreversible step, persisted because the in-memory approval dies with the connection. Chen’s result supports gating the plan: plan structure cut how often the bad action appeared (OR 0.25), and the choice of strategy did not change how often people stopped it once it was on screen (p = .407). The grant has to name the class of action. A vague “approve similar” is the boundary people in that study could not interpret. A second model reading the transcript is a weak checker next to the person and the file. A clean-context comment on the artifact, the pattern Cognition describes, is a comment. It is a second claim on the card only if someone mistakenly treats it as one. One writer holds the artifact. A breadth-first read can return a short summary into that writer’s thread. It does not get a column, a mailbox, or a turn editing the same note.

## Conclusion

What shipped through 2026 is visibility and isolation. You can see an agent on an issue, open its session, and take a branch. The card itself stayed a human object with a status, and the products that run coding agents still tell you to keep writes on one thread. The leftover problem is ownership while a process can die, and a personal app is in a better position than those products because the person is already the second party who can see the file and move the card. Telecom’s drop in false success is only a hint, and Advani says so, but the hint points at a checker with its own view of state. A local kanban already has that checker. The lease exists so a vanished run cannot freeze the card in the person’s hand, and the completion event exists so the assistant’s last sentence stays a comment until a check is stored. Shared transcripts, channel agents, and follow-ups that act with someone else’s credentials are answers to leakage between people. Two of one person’s runs, or one run and the person’s hand, on a single card are the collision this machine can actually have.
