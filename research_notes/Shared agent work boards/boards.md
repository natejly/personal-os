# Shared agent work boards

Research date: 2026-10-02. Scope is product surfaces where a person and one or more agents share a board, kanban, issue, or task list as the unit of work. Chat sidebars with no shared card are out of scope except where a vendor documents them as distinct from the board agent.

Direct fetches that failed or only partially rendered are called out. Comparison blogs are not used as product facts.

## Which products assign an agent to a card, issue, or column, and what is shipping versus announced?

### Takeaway

By 2026-10-02 the shipping pattern is an existing issue or board item plus a separate agent run, not a new kind of board. Linear keeps a human assignee and adds a delegate. GitHub, Asana, and monday.com put the agent on the assignee or item. Cursor, Jules, Codex-in-Linear, and Claude Code/Cowork track a run, plan, or checklist beside the ticket. Devin does not ship its own board; it occupies Linear (and claims Jira and GitHub). Height was not verified. Products that literally say “agent board” or “mission control” are small self-hosted or hosted tools, not the team trackers above.

### Cited Findings

#### Linear — shipping

- An issue has one human assignee. Delegating to an agent is a separate act: the human stays the owner and the agent works on their behalf. The assignment menu can set “No agent.” The agent must be a member of the issue’s team. Delegated issues still appear in the human’s My Issues view. History of assignment and delegation is in the issue Activity feed. Triage rules (Business and Enterprise) can set an assignee and delegate an agent in the same rule. — [Assign and delegate issues](https://linear.app/docs/assigning-issues); [Agents in Linear](https://linear.app/docs/agents-in-linear)
- Assigning an app with the `app:assignable` scope sets `delegate`, not `assignee`. Mention or delegation creates an `AgentSession`. The agent must answer the `created` webhook within 5 seconds and emit an activity or external URL within 10 seconds or the session is shown as unresponsive. — [Getting started (agents)](https://linear.app/developers/agents); [Developing the agent interaction](https://linear.app/developers/agent-interaction)
- A separate, non-delegation path opens the issue in an external coding tool (Cursor, Claude Code, or Codex are named in settings) via “Work on issue.” That launches a tool with issue data and an optional prompt. It is not the delegate field. — [Assign and delegate issues](https://linear.app/docs/assigning-issues)

#### GitHub issues and Copilot cloud agent — shipping; multi-agent assignment in public preview as of 2026-02-04

- Assigning an issue to Copilot always creates a pull request. Copilot is chosen from the issue’s Assignees list. Optional fields at assignment: an extra prompt, target repository, base branch, a custom or third-party agent, and a model. Copilot is given the issue title, description, and comments that already exist. Comments added after assignment are not seen; follow-ups go on the pull request. Prompt-started tasks (Agents tab, `github.com/copilot/agents`, or `/task`) work on a branch by default and do not open a pull request unless the prompt asks for one. — [Kick off a task with Copilot agents](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task); [About GitHub Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)
- The issues REST and GraphQL APIs can assign Copilot (`copilot-swe-agent` in the REST example) with an `agentAssignment` / `agent_assignment` payload: target repo, base branch, custom instructions. — [Using Copilot cloud agent via the API](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api)
- On 2026-02-04 GitHub wrote that Claude by Anthropic and OpenAI Codex were in public preview inside Agent HQ for Copilot Pro+ and Copilot Enterprise, startable from github.com, GitHub Mobile, and VS Code 1.109+. The same post says you can assign an issue to Copilot, Claude, Codex, or all three, and that agents submit draft pull requests. It also says Google, Cognition, and xAI agents were being worked on and were not in that release. Access to Claude and Codex was described as expanding to more Copilot plans later. — [Pick your agent: Use Claude and Codex on Agent HQ](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- The undated kick-off doc crawled for this research says third-party coding agents are available for all paid Copilot plans and that the assignment UI has an agent dropdown. That is broader than the 2026-02-04 Pro+/Enterprise preview. The two pages were not reconciled to a changelog date. — [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task); [Agent HQ post, 2026-02-04](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)

#### Cursor cloud agents — shipping, and it is a run list, not a kanban

- Cloud Agents were formerly called Background Agents. Each run is an isolated VM. Entry points that are shipping in the docs: Cursor desktop (Cloud in the agent dropdown), `cursor.com/agents`, the iOS app, Slack `@cursor`, a `@cursor` comment on a GitHub issue or PR or a Bitbucket PR, `@cursor` on a Linear issue, and an API. The agent pushes a branch and can open a pull request. The dashboard shows which environment and Build the run used. — [Cloud Agents](https://cursor.com/docs/cloud-agents)
- There is no documented issue status, assignee, or column on the Cursor side. The shared objects are the agent URL (conversation, diff, artifacts) and the pull request. Teammates on the same Cursor team can open a run only if they also have repository access. Viewing is read-only unless an admin enables team follow-ups. A paid Cursor plan is required. One person can run agents without a team; sharing is the team-shaped part. — [Cloud Agents](https://cursor.com/docs/cloud-agents)

#### Claude Code task list and Cowork / Dispatch — shipping, and neither is a shared kanban

- Claude Code’s checklist is a model tool, not a board a person columns. As of Claude Code v2.1.142 the tools are `TaskCreate`, `TaskGet`, `TaskList`, and `TaskUpdate`. `TaskUpdate` can set `status` (`pending`, `in_progress`, `completed`, or `deleted`), `owner`, and blockers (`addBlocks`, `addBlockedBy`). `TodoWrite` is the older session checklist and is off unless `CLAUDE_CODE_ENABLE_TASKS=0`. From v2.1.233 those task tools are omitted on Opus 4.8, Sonnet 5, Fable 5, Mythos 5, and later in those families unless opted in (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` or an allow-list). The CLI command `/tasks` lists background work in the current session, including finished subagents. It is not the TaskCreate list. — [Tools reference](https://code.claude.com/docs/en/tools); [Todo tracking (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/todo-tracking); [Commands](https://code.claude.com/docs/en/commands)
- Cowork, documented on Anthropic’s help center, is a task you describe and then leave. Sessions can run in the cloud. There is a Tasks list; deleting a task removes it from history immediately and from backend storage within 30 days. `/schedule` and a Scheduled sidebar manage recurring tasks. Projects hold files, links, instructions, and memory. — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)
- Dispatch, documented at claude.com, is a long-running Cowork agent that splits one request into child tasks. Each child appears under the Dispatch group in the sidebar with its own status and transcript. Coding children run in Claude Code against a workspace; other children run in Cowork inside a project. Follow-up is a message in that child session. Local Dispatch needs the desktop app open and the computer awake. — [Run tasks in the background with Dispatch](https://claude.com/docs/cowork/guide/dispatch); [Assign tasks from anywhere in Claude Cowork](https://support.claude.com/en/articles/13947068-assign-tasks-from-anywhere-in-claude-cowork)
- A secondary write-up says that on 2026-09-16 Anthropic began merging Cowork into the main Claude conversation and that Cowork tasks then sit in Recents with chats. That page is not an Anthropic doc. The help center articles above still describe a Cowork mode, a Tasks list, and Dispatch. Treat the merge as unverified against a primary announcement. — [Claude Cowork Merging Into Claude (secondary)](https://www.aiagentslibrary.com/blog/claude-cowork-merging-into-claude/); contradicted in structure by [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)

#### Devin — shipping on other companies’ tickets, no Devin board found

- Current Devin docs: connect Linear at app.devin.ai, pick teams, then start a session by assigning the ticket, adding a synced playbook label (`!plan`, `!implement`, `!triage`, `!review` are the examples; `!plan` is the default for new connections), or mentioning Devin in a comment. Automation triggers fire on the edge of a team, label, or status match, not on tickets that already match. Devin then uses Linear’s agent session: activity feed, plan synced into Linear’s plan UI, follow-up messages, a stop control that puts Devin to sleep, the PR URL, and a link back to the Devin session. Linking a personal Linear user attributes the session. Enterprise can map Linear teams to Devin organizations. — [Devin Linear integration](https://docs.devin.ai/integrations/linear)
- Linear’s own integration page describes an older comment-shaped loop (summary, plan, confidence marks, then a link out to draft a PR). It does not describe agent-session plan sync or the stop control. Prefer the Devin docs for the current mechanism. — [Devin integration on Linear](https://linear.app/integrations/devin)
- Devin’s backlog guide says you can assign tickets to Devin on Jira as well as Linear, and that a GitHub Actions workflow plus a `devin` label can open a session from a GitHub issue. Those are Devin’s docs, not Atlassian’s or a fetched GitHub App doc. — [Clear engineering backlogs](https://cognitionai.mintlify.app/use-cases/examples/clear-engineering-backlogs)

#### OpenAI Codex on Linear — shipping on paid plans

- Assigning an issue to Codex, or mentioning `@Codex`, creates a Codex cloud chat. Codex posts progress on the issue and, when finished, a summary plus a link to the chat so the person can create a pull request. Repo choice: Linear suggests a repository, Codex picks a matching environment, and if that is ambiguous it uses the most recently used environment. The chat runs on the default branch of the first repo in that environment’s repo map. Triage rules can delegate to Codex; those runs use the issue creator’s account. Enterprise needs an admin to enable Codex cloud chats and the Linear connector. Local Codex can also attach Linear through MCP (`codex mcp add linear --url https://mcp.linear.app/mcp`), which is read access for a local agent, not a board. — [Use Codex in Linear](https://developers.openai.com/codex/integrations/linear)

#### Google Jules — shipping; the docs still call it experimental

- In the Jules app a task is a repo, a branch, a prompt, and optional images (PNG/JPEG, 5MB, only at creation). Jules writes a plan and the person approves it before code changes. While it runs there is an activity feed, per-file mini diffs, mid-task chat, and pause. Pause stops work until the next instruction; the task can also be deleted. On finish Jules shows files changed, runtime, and line counts. The person clicks Create branch. The documented ownership split: the person is the branch owner, Jules is the commit author, and the person opens the pull request from that branch. — [Running tasks with Jules](https://jules.google/docs/running-tasks/); [Getting started](https://jules.google/docs/)
- Since the 2025-06-26 changelog, adding the label `jules` (case insensitive) on a GitHub issue starts a task if the Jules GitHub app can see the repo. Jules comments on the issue and, when finished, links a pull request. That issue path’s handoff (Jules links a PR) is not the same sentence as the in-app path (the person creates the branch). — [Jules now listens to GitHub issues (2025-06-26)](https://jules.google/docs/changelog/2025-06-26/); [Running tasks](https://jules.google/docs/running-tasks/)
- The public marketing page lists concurrency caps by plan: 15 tasks/day and 3 concurrent (Gemini 2.5 Pro), 100/day and 15 concurrent, 300/day and 60 concurrent (Gemini 3 Pro). Those numbers are not in the running-tasks doc. The Jules GitHub Action README still describes the model as Gemini 3 Pro. — [Jules homepage](https://jules.google/); [jules-action README](https://github.com/google-labs-code/jules-action/blob/main/README.md)
- Getting started still says Jules is experimental. No 2026 changelog was fetched that retires that word. — [Getting started](https://jules.google/docs/)

#### Notion Custom Agents — shipping, and the agent usually files the card for a person

- Custom Agents read pages and databases, run on schedules and workspace events (comment added, page added, property updated, page removed, meeting note finished), and can create or update records, post to Slack, and hand part of a run to another Custom Agent. They can be @mentioned on pages, database properties, and comments. They are installed as their own identity with their own page access, not as “Notion AI acting as you.” — [Custom Agents](https://www.notion.com/help/custom-agents); [Sharing and permissions](https://www.notion.com/help/custom-agents-sharing-and-permissions)
- The project-updates guide’s concrete card write is: the agent creates a task in a project database, sets the owner to the human, and moves status from New to Assigned. The agent is the writer, not the assignee, in that documented workflow. A later status change to Published is the human’s review gate before a Slack post. — [Automate project updates with Custom Agents](https://www.notion.com/help/guides/automate-project-updates-and-reporting-with-custom-agents)
- Database property fill (Basic Autofill vs Custom Agent Autofill) can set summary, tags, and status on a row. That is a column writer, not an assignee taking the card. — [Notion AI autofill](https://www.notion.com/en-gb/help/autofill)

#### monday.com — shipping on the monday AI platform; not yet every monday product

### Inferences

- Mechanisms that assume a team: Linear team membership for the agent, triage rules, and Inbox subscriptions; GitHub org agent controls and multi-assignee comparison; Asana’s shared teammate and “designed for teams” wording in the indexed help text; monday sharing, org agent directory, and admin governance; Notion agents whose access can exceed the triggering user’s; Devin org connections and enterprise team mapping; Cursor team follow-ups.
- Mechanisms that work for one person plus their agents: a Linear workspace where that person is the assignee and an agent is the delegate; a personal GitHub repo with Copilot (or, on an eligible plan, Claude/Codex) assigned to issues; Cursor cloud agents on a paid individual plan; a Jules account bound to that person’s GitHub; Codex cloud chats from that person’s Linear issues; Claude Code’s task list and Cowork/Dispatch, which are that person’s sessions, not a multi-human board; a monday board where one member assigns items to an agent they own.
- A local app that already has a single-user kanban, todos, chats, and one agent loop does not need org governance, shared memory across colleagues, or multi-assignee comparison. The pieces that transfer are: a durable card, a separate run record, a human owner distinct from the agent, a review gate before “done,” and a way to stop the run. The pieces that do not transfer cleanly are team Inbox fan-out, “assign all three agents,” and agents that see other people’s private rows.

## What does the card store in practice?

### Takeaway

The durable card is still a human issue or board item: title, body, status, comments, and usually one assignee. Agent-specific state lives beside it: Linear’s session and plan, GitHub’s session and pull request, Cursor’s run and artifacts, Jules’s plan and branch, monday’s run log. Acceptance criteria are whatever the person wrote in the description. A lease/lock field was not found on the major products.

### Cited Findings

- Linear issue fields used by the agent prompt include identifier, title, description, team, labels, parent issue, and project, plus comment threads and workspace/team guidance. Session states, visible to the user, are `pending`, `active`, `error`, `awaitingInput`, `complete`, and `stale`. Linear sets those from the last activity; the agent does not set the session state itself. Activities are `thought`, `elicitation`, `action` (with optional result), `response`, and `error`, plus a user-authored `prompt`. A technology-preview plan is a full array of `{content, status}` with status `pending`, `inProgress`, `completed`, or `canceled`; updates replace the whole plan. `externalUrls` on the session can point at the vendor dashboard and at a GitHub pull request. — [Agent interaction](https://linear.app/developers/agent-interaction)
- Linear’s recommended status write: if a human delegated the issue and it is not already started, completed, or canceled, move it to the first workflow state of type `started`. If an automation delegated it, leave it in triage for a human to assign. When implementation starts and no delegate is set, the agent should set itself as delegate. Completion is a `response` activity, which also becomes a comment. User input that must be answered is an `elicitation`. — [Agent best practices](https://linear.app/developers/agent-best-practices)
- GitHub issue assignment payload, as documented: title, description, existing comments, optional extra prompt, target repo, base branch, agent identity, model. The artifact is a branch and, for issue assignment, a pull request. Session logs are the run history. There is no documented acceptance-criteria field beyond the issue body and the optional prompt. — [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)
- Cursor run contents documented: conversation, code changes, screenshots, videos, logs, environment and Build identity, remote desktop. Handoff artifact is a branch and pull request. No card schema. — [Cloud Agents](https://cursor.com/docs/cloud-agents)
- Jules in-app task: repo, branch, prompt, images, approved plan, activity feed, diffs, summary (files, runtime, line counts), then a branch whose owner is the human. Issue-label task: the GitHub issue plus a Jules comment and a PR link. — [Running tasks](https://jules.google/docs/running-tasks/)
- Devin-on-Linear adds, on the Linear session: commands, files edited, progress, the plan checklist, PR URL, session URL, playbook link. The Linear issue itself is unchanged in schema. — [Devin Linear](https://docs.devin.ai/integrations/linear)
- Codex-on-Linear stores progress in issue Activity and a cloud chat link. The pull request is created by the person from that chat, not described as automatic. — [Use Codex in Linear](https://developers.openai.com/codex/integrations/linear)
- Claude Code task record, from the SDK docs: `subject`, `description`, optional `activeForm`, optional `metadata`, `status`, `owner`, dependency links. IDs are returned by the tool result, not chosen in the input. This list is not documented as containing comments, pull requests, or acceptance criteria. — [Todo tracking](https://code.claude.com/docs/en/agent-sdk/todo-tracking)
- Cowork/Dispatch child: sidebar status, transcript, steps, and files produced. No column schema was documented. — [Dispatch](https://claude.com/docs/cowork/guide/dispatch)
- Notion database row, in the documented example: a task page, an owner (the human), and a status (New, then Assigned; reports use Published). The agent’s own run is a Custom Agent chat, not a property that was named in the guide. — [Project updates guide](https://www.notion.com/help/guides/automate-project-updates-and-reporting-with-custom-agents)
- Asana, from indexed help and the API: the task assignee can be the agent; the agent reads title, description, and context; it can write comments, subtasks, name, description, due date, and completion. Early-access API only guarantees the assignee GID. — [Forum changelog](https://forum.asana.com/t/upcoming-ai-teammates-and-agent-api-support/1142767); [Triggering AI Teammates](https://help.asana.com/s/article/triggering-ai-teammates?language=en_US)
- monday item: assigning the agent to the item is the trigger. Run history is the agent Activity tab (status, date, apps, credits), not fields on the item that were named. Artifacts are agent-level. Undo is the board activity log. — [Run and manage your AI agents](https://support.monday.com/hc/en-us/articles/38411316441874-Run-and-manage-your-AI-agents)
- `agent-kanban.io`’s described ticket: description, comments, history, assignee, status, priority. Claim is “set assignee and move to in_progress.” This is that site’s description, not an API spec that was fetched. — [Agent Kanban](https://agent-kanban.io/)

### Inferences

- “Acceptance criteria” is not a separate object in these products. It is the issue body, a Jules prompt, a Linear guidance rule, or an Asana teammate instruction.
- Run history is almost never the card’s status column. Linear comes closest by mirroring work into `started` and by showing session state on the issue. monday and Cursor keep run history on the agent or the run.
- For a single-user app, the useful split is the one Linear made: the card keeps a human owner and a status, and the run keeps thoughts, tool calls, a plan, and links to artifacts. Putting the agent in the only assignee slot (Asana, GitHub, monday items) makes “who is responsible” and “who is executing” the same field.

### Gaps

- No vendor doc fetched here defined a lease, lock timestamp, or claim token on Linear, GitHub, Cursor, Jules, Devin, Notion, Asana, monday, or ClickUp.
- Whether GitHub’s issue status (open/closed) is changed by Copilot when the PR opens was not stated in the kick-off doc.
- ClickUp’s stored task fields when a Super Agent is involved were not in the help article.

## How does the human review or take the work back?

### Takeaway

Review is a pull request for the coding agents, a comment or elicitation when the agent is blocked, and an activity-log undo on monday. Taking the work back is “remove the delegate,” “stop,” “pause,” or “take the remote desktop,” not moving a card to an approval column. Asana is the outlier that documents the agent marking the task complete itself.

### Cited Findings

- GitHub: issue assignment ends with Copilot requesting review on the pull request it opened. Later instructions are pull-request comments, including `@Copilot`, `@Claude`, or `@Codex`. Prompt-started sessions let the person read the diff and open the pull request themselves. Agent HQ’s stated review path is the same draft-PR and comment workflow as a teammate, plus logs. — [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task); [Agent HQ, 2026-02-04](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- Linear: `awaitingInput` is the session state for waiting on the user. An `elicitation` activity asks for clarification and is also written as a comment. The human stays the assignee, so the issue remains in My Issues. Removing the agent is “No agent.” Unassignment fires `issueUnassignedFromYou` for the app user. A `response` means the agent considers the work finished; it does not by itself document a required human approval column. — [Agent interaction](https://linear.app/developers/agent-interaction); [Best practices](https://linear.app/developers/agent-best-practices); [Assign and delegate issues](https://linear.app/docs/assigning-issues)
- Devin: follow-up messages in the Linear agent thread, and a stop control that puts Devin to sleep on that task. The PR URL is attached for review. — [Devin Linear](https://docs.devin.ai/integrations/linear)
- Codex on Linear: the person reviews the chat and creates the pull request. The doc says to review answers and diffs because the model can be wrong. If the environment is wrong, the person replies in the thread with the repo to use. — [Use Codex in Linear](https://developers.openai.com/codex/integrations/linear)
- Cursor: review is the pull request plus screenshots, video, and logs. The person can take the agent’s remote desktop, test, and hand control back. Teammates cannot steer the run unless team follow-ups are enabled. `@cursor autofix off` on a PR disables autofix for that PR. — [Cloud Agents](https://cursor.com/docs/cloud-agents); [Cloud Agents help](https://cursor.com/help/ai-features/cloud-agents)
- Jules: the in-app gate is plan approval before code, then chat or pause at any time, then the person creates the branch and opens the PR. The issue-label path reviews the linked PR after Jules comments. — [Running tasks](https://jules.google/docs/running-tasks/)
- Notion’s documented review gate is a status the human sets (Published) before the agent posts externally. The agent can also be told to file tasks already assigned to the human. — [Project updates guide](https://www.notion.com/help/guides/automate-project-updates-and-reporting-with-custom-agents)
- Asana, indexed text: review is a reply on the task; the quick-start says review the draft, reply with edits, or approve, and the teammate iterates and marks relevant subtasks complete. The teammate itself is allowed to mark a task complete. Some writes (assigning someone who lacks access, deleting a task the teammate did not create) wait for approval. — [Triggering AI Teammates](https://help.asana.com/s/article/triggering-ai-teammates?language=en_US); [Access control](https://help.asana.com/s/article/understanding-access-control-for-ai-teammates?language=en_US)
- monday: undo from the board activity log; pause the whole agent; bell plus What Went Wrong on a failed run; memory rules can require an ask before an action such as sending email. There is no documented “needs you” column. — [Run and manage your AI agents](https://support.monday.com/hc/en-us/articles/38411316441874-Run-and-manage-your-AI-agents)
- ClickUp help: approval is requested for critical decisions. No column name was given. — [What are Super Agents?](https://help.clickup.com/hc/en-us/articles/31010910371991-What-are-Super-Agents)
- Cowork: the person reviews the approach, then lets the task run, and can delete the task. Dispatch review is opening the child transcript and sending a follow-up. — [Get started with Claude Cowork](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork); [Dispatch](https://claude.com/docs/cowork/guide/dispatch)
- The small agent-kanban descriptions are the only ones that name an In Review column and say the worker cannot accept its own review. That was not confirmed in a fetched API reference. — [agent-kanban.dev](https://agent-kanban.dev/); [agent-kanban.io](https://agent-kanban.io/)

### Inferences

- “Needs you” already exists under other names: Linear `elicitation` / `awaitingInput`, Jules pause and plan approval, monday’s failed-run panel, Cursor’s read-only teammate view. A personal app can show that as a card state without copying a team inbox.
- Coding handoff that matches a single user is the pull request or the branch, because the card status and the artifact can diverge. Codex’s “here is the chat, you open the PR” keeps completion with the human. Copilot’s “assignment always opens a PR” does not.
- Asana’s “agent may mark the task complete” is the failure mode a personal kanban has to decide explicitly: either the agent cannot move the card to done, or done requires an artifact link.

### Gaps

- No fetched page documented a dedicated approval column in Linear, GitHub, Cursor, Jules, Devin, Notion, ClickUp, or monday.
- How a person reclaims a GitHub issue after Copilot, Claude, and Codex are all assigned was not documented beyond ordinary assignee edits and PR review.
- Cowork’s exact status labels in the sidebar were not listed.

## How do multiple agents avoid editing the same card?

### Takeaway

The major products mostly do not prevent it. Linear allows one human assignee and talks about the delegate in the singular, but a mention can open another session. GitHub’s 2026-02-04 post tells you to assign Copilot, Claude, and Codex to the same issue on purpose. Account-level concurrency caps (Jules) and per-run VMs (Cursor) isolate execution, not the card. The only explicit claim/lock language found was on the small agent-kanban sites.

### Cited Findings

- Linear: “Issues in Linear are assigned to a single person at a time.” The delegate UI is singular: change the agent, or “No agent.” Nothing fetched says the API rejects a second delegate or a second `AgentSession` on the same issue. Sessions are also created when the agent is mentioned, and an agent may call `agentSessionCreateOnIssue` itself. Comments are called out as unsafe to treat as the source of truth because they are editable; activities are frozen snapshots. That is a consistency rule for one agent’s memory, not a lock against a second agent. — [Assign and delegate issues](https://linear.app/docs/assigning-issues); [Agent interaction](https://linear.app/developers/agent-interaction); [Best practices](https://linear.app/developers/agent-best-practices)
- GitHub, 2026-02-04: “Assign an issue to Copilot, Claude, Codex, or all three to compare results.” Parallel agents are the feature. Each session is separate and consumes one premium request. — [Agent HQ](https://github.blog/news-insights/company-news/pick-your-agent-use-claude-and-codex-on-agent-hq/)
- Cursor: “You can run as many agents as you want in parallel,” each in its own VM and branch. Collision handling is git, not a card lock. Two `@cursor` comments can start two runs. — [Cloud Agents](https://cursor.com/docs/cloud-agents)
- Jules marketing page: concurrent-task caps of 3, 15, or 60 depending on plan. That limits how many Jules tasks an account runs, not who else may label the same issue. The label `jules` has no documented “already running” check. — [Jules homepage](https://jules.google/); [Running tasks](https://jules.google/docs/running-tasks/)
- Devin triggers use edge detection so the same ticket does not re-fire while it still matches. Assign, label, and mention are three separate ways to start a session; the docs do not say they exclude each other. Stop sleeps “the current task.” — [Devin Linear](https://docs.devin.ai/integrations/linear)
- Asana’s task `assignee` is one GID, user or agent. That is a single-assignee field. Nothing fetched says a second agent is blocked from commenting or creating subtasks if it is mentioned. — [Forum changelog](https://forum.asana.com/t/upcoming-ai-teammates-and-agent-api-support/1142767)
- monday: several agents can be stages of one AI workflow. Pause is per agent, not per item. No item-level mutex was documented. Restricted columns are an edit permission, not a claim. — [Run and manage your AI agents](https://support.monday.com/hc/en-us/articles/38411316441874-Run-and-manage-your-AI-agents); [AI Agents FAQ](https://support.monday.com/hc/en-us/articles/33347027353746-AI-Agents-on-monday-com)
- Notion: a Custom Agent can hand work to other Custom Agents in one run. Database edits are last-write on the row. No claim API was documented. A permissions hazard runs the other direction: the agent answers with its own access, so it may reveal rows the person who triggered it cannot see. — [Custom Agents](https://www.notion.com/help/custom-agents); [Sharing and permissions](https://www.notion.com/help/custom-agents-sharing-and-permissions)
- Claude Code `TaskUpdate` has an `owner` field. The docs do not describe a compare-and-swap claim or what happens if two sessions set `owner`. A community guide (not Anthropic) says a shared `CLAUDE_CODE_TASK_LIST_ID` coordinates sessions via files under `~/.claude/tasks/`. That guide is not treated as the product’s locking spec. — [Todo tracking](https://code.claude.com/docs/en/agent-sdk/todo-tracking); community only: [task-management.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/e110346d/guide/workflows/task-management.md)
- `agent-kanban.io` says the agent sets itself as assignee and moves to in progress so two agents do not take the same ticket. The GitHub READMEs say claims are atomic via D1 batch operations, workers who are idle 2 hours are marked offline, and the assigned agent cannot complete its own review submission. Those are the projects’ own descriptions. — [agent-kanban.io](https://agent-kanban.io/); [saltbo/agent-kanban](https://github.com/saltbo/agent-kanban)

### Inferences

- Single-assignee (Linear’s human, Asana’s one GID, monday’s item assignment) is the practical mutex, and only if the product refuses a second writer. GitHub deliberately does not.
- For one person and several of their own agents, a claim is still useful: two local runs can open two branches for one card. Cursor’s answer is “branches are cheap.” A personal kanban that wants one artifact per card needs an explicit claim the shipping team tools do not provide.
- Linear’s 30-minute stale session is a liveness timeout, not a lock. A second agent is not blocked by it.

### Gaps

- No Linear schema quote was fetched that says `delegate` is a single ID rather than a list. The UI copy is singular; the field cardinality was not confirmed in GraphQL.
- GitHub’s behavior when Copilot is already assigned and a second agent is added (extra PR vs shared branch) was not documented in the pages read.
- Jules’s server behavior when the `jules` label is applied twice was not documented.

## What fails in practice?

### Takeaway

The sourced failures are not “the model was dumb” in the abstract. They are: the ticket and the artifact diverge, humans never review, a second agent or a second PR does the same work, and short-lived placeholder pull requests look like progress. Linear also documents sessions going stale and comments drifting. Notification noise is described directly for monday run failures and for Linear’s assignee Inbox; broader “agent spam” complaints were not pinned to a reliable 2025–2026 user report in this pass.

### Cited Findings

- GitHub’s own kick-off doc: Copilot does not see issue comments added after assignment. Follow-up on the issue is silently dropped from the agent’s context. — [Kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task)
- Linear: if the agent does not emit an activity within 10 seconds of `created`, the session is shown as unresponsive. After the first response, 30 minutes without another activity marks the session stale. Stale is recoverable by a later activity. Comments can change after the run, so an agent that re-reads comments can pick up a different instruction than the one it was given. — [Agent interaction](https://linear.app/developers/agent-interaction); [Best practices](https://linear.app/developers/agent-best-practices)
- Linear subscribers: the assignee is auto-subscribed and Inbox receives updates on assigned issues, including ones delegated to an agent. That is the notification path. The docs do not say it is too noisy. — [Assign and delegate issues](https://linear.app/docs/assigning-issues)
- monday: a failed or partial run notifies with a bell even if the person is not looking at the agent. The failure panel is part of the product, which implies runs fail in ways a status column would hide. Undo exists because the agent writes board cells directly. — [Run and manage your AI agents](https://support.monday.com/hc/en-us/articles/38411316441874-Run-and-manage-your-AI-agents)
- Jules Action README: issue-triggered workflows can be started by anyone who can open an issue. It tells readers to allow-list who may trigger Jules. — [jules-action README](https://github.com/google-labs-code/jules-action/blob/main/README.md)
- Notion: a Custom Agent uses its own access, not the triggering user’s, and can surface rows that person cannot open. — [Sharing and permissions](https://www.notion.com/help/custom-agents-sharing-and-permissions)
- Asana, indexed: the teammate can mark tasks complete, and it will not reveal objects the triggering user cannot already see. Completion without a named artifact is allowed by that capability table. — [AI Teammates](https://help.asana.com/s/article/ai-teammates?language=en_US); [Access control](https://help.asana.com/s/article/understanding-access-control-for-ai-teammates?language=en_US)
- github/gh-aw issue 36319, titled as a Copilot optimization: in a 14-day window, 27 of 153 Copilot pull requests closed without merge (18%) had a `[WIP]` prefix, median open time about 3 minutes, one open for 28 seconds. The issue’s claim is that the agent opens a skeleton pull request and then closes it without a working implementation. A linked mention is dated 2026-06-03. This is an issue in a GitHub repository, written in the voice of an automated report, not an independent postmortem. — [Issue 36319](https://github.com/github/gh-aw/issues/36319)
- Ehsani, Pathak, Rawal, Al Mujahid, Imran, and Chatterjee, arXiv preprint dated 2026-01-21 as indexed by Exa (the arXiv abstract page was not opened separately). They study the AIDev-pop set: 33,596 agent-authored pull requests (Codex 21,799; Copilot 4,970; Devin 4,827; Cursor 1,541; Claude Code 459). Overall merge rate 71.48%. By agent: Codex 82.59%, Cursor 65.22%, Claude Code 59.04%, Devin 53.76%, Copilot 43.04%. Of 600 sampled rejected PRs, 38 were gone; of the remaining 562, reviewer abandonment with little or no human engagement was 228 (38%), duplicate PRs 142 (23%), CI/test failure 99 (17%). Documentation, CI, and build tasks merged more often (84%, 79%, 74% across agents) than performance (55%) and fixes (64%). Each extra failed CI check was associated with about 15% lower odds of merge. — [Exa library copy of the preprint](https://exa.ai/library/publication/nk2jltn371m)
- Alam, Mondal, and Roy, MSR 2026, published 2026-07-31, DOI 10.1145/3793302.3793611. The proceedings page body was readable in fetch; the experimental AI summary on that page was paywalled. On 8,106 fix-related PRs from the same AIDev-pop dataset (released November 2025, per the paper): merged 65.0% (5,267), closed unmerged 26.1% (2,113), still open 8.9% (726). Agent merge rates on fixes: Codex 81.6% (3,539/4,338), Cursor 68.4% (281/411), Claude Code 57.4% (66/115), Devin 42.9% (536/1,249), Copilot 42.4% (845/1,993). Copilot also had 21.8% of its fix PRs still open (435). Of 326 sampled closed-unmerged PRs, the top causes were resolved by another PR 22.1% (72), test failures 18.1% (59), incorrect or incomplete fix 15.3% (50), inactivity auto-close 9.2% (30). In that sample, 27 of Devin’s 50 closed-unmerged PRs (54%) were inactivity closures, and 50 of Codex’s 91 (54.9%) were test failures. The paper’s dataset is older than 2026-10-02; the publication date is 2026-07-31. — [MSR ’26 proceedings](https://dl.acm.org/doi/10.1145/3793302.3793611)

### Inferences

- “Agent marked done without the artifact” shows up in three places that are not the same bug: Asana allows the teammate to complete the task; Copilot issue assignment always opens a PR, including the short-lived `[WIP]` ones in gh-aw; Codex on Linear finishes in a chat and leaves the PR to the human, so the issue can look updated before any branch exists.
- Duplicate work is the coordination failure the studies measure (another PR already fixed it; 23% duplicates in the Ehsani rejection sample). It matches the absence of a card lock and GitHub’s compare-three-agents feature.
- Stale work is a session timeout in Linear (30 minutes), an inactivity close in the MSR sample (especially Devin), and a still-open PR pile (Copilot fixes, 21.8% open in that dataset). A personal board will accumulate the same cards unless “done” requires a linked artifact and abandoned runs are marked stale on a timer.
- The studies are about pull requests on public GitHub, not about Asana, monday, Notion, or Cowork task lists. They should not be read as failure rates for those boards.

### Gaps

- No 2025–2026 user postmortem was fetched that described notification fatigue in Linear, GitHub, or Cursor in the user’s own words. The Inbox and bell behavior above is vendor documentation, not a complaint.
- The Ehsani preprint was read through an Exa library page, not arxiv.org. Figures in that copy are messy; the counts cited are the ones stated in prose.
- AIDEV-pop’s November 2025 cutoff means both studies miss later Agent HQ and Jules issue-label behavior.
- No sourced failure report was found for Notion agents double-filing tasks, ClickUp Super Agents, Height, or Cowork task lists.
